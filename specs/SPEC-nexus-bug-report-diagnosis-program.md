# Bug reports become ranked hypotheses with evidence — khala grounds, a code-reading agent reads, the owner rules

## 0. 한 줄

사용자 제보(주로 채팅 스크린샷)를 받으면 khala 가 근거를 모으고, 코드를 읽는 에이전트가 가설을
세워 **근거·확인할 런타임 증거·기권을 값으로** 내고, 어느 값이 정본인지는 **사람이 판정해 claim 에
남긴다**. 자동 수정·자동 조치는 범위 밖이다(사용자 확정, 2026-09-23). 목표의 이름은 「원인을 찾아
알려주는 에이전트」가 아니라 **「어디를 봐야 하고, 어떤 근거가 있으며, 무엇이 부족한지를 사람이
도구를 열기 전에 정리해 두는 에이전트」**다. 현장 조사가 확인한 도달 수준이 정확히 거기까지이고
([research/2026-09-23](../research/2026-09-23-bug-diagnosis-agents-field-data.md)), 그 모양은 khala 가
이미 가진 골격(그라운딩 · 인용 없으면 침묵 · 판정은 사람)과 같다. 그래서 이 문서는 새 제품이 아니라
**있는 골격 위의 다섯 조각**을 정한다.

## 1. 무엇이 이것을 촉발했나

2026-09-23 에 카카오톡 오픈채팅으로 온 제보 스크린샷 하나 — 닉네임 13글자를 넣었는데 카운터는
`13/16` 이고 「필수 입력」 오류가 뜬다. 원인은 프론트 두 겹이었다. 입력창 상한 16 과 검증 스키마
12 가 한 폼에 같이 살고, `requiredString` 래퍼가 안쪽 실패를 전부 「필수 입력」 문구로 뭉친다.
그리고 표면 간 차이가 있었다. 앱 안 편집 화면(정본, 12)과 온보딩 화면 둘(데스크톱·모바일, 16).
사용자가 던진 질문은 넷이었고 순서대로 답이 나왔다.

1. *khala 가 현상·원인 분석을 하게 개선할 수 있나* → 코드 0줄 드라이런으로 어디까지 가는지 측정.
2. *어느 수준까지 되나, 판 벌리기 전에 견적* → 실제 버그 61건 분류 + 프로브 10건 + 코드 읽는 에이전트 4건.
3. *시키지 않아도 표면 간 차이를 스스로 발견하는 모양이 되나* → 무힌트 실험 2/2.
4. *결국 정본 문제로 회귀하는 것 아닌가* → 맞다. 회귀가 아픈 것은 판정이 필요해서가 아니라
   같은 판정을 매번 다시 하기 때문이다 → 판정을 claim 에 기록(#553, 라이브 확인 3/3, A27 닫음 #554).

## 3. 결정 (사용자 확정 2026-09-23)

1. GitHub 이슈·포스트모템·KNOWN_ISSUES 를 코퍼스에 넣는다.
2. 프론트 리포를 읽기 범위에 넣는다.
3. 라벨 셋부터 시작한다.
4. 자동 수정·자동 조치는 처음부터 범위 밖이다.
5. 실행 시간대 규칙은 두지 않는다 — 이 서비스를 호출하는 사람이 없다(실행 배치에 관한 판단이지 수요 자료가 아니다).
6. 구현은 이 문서가 승인된 뒤에 시작한다. 게이트는 **되돌리기 비싼 조각**(저장되는 내용 · 설정·의존성 · 요청 계약)에만 걸고, 탐색·측정 조각(라벨 셋 · 에이전트 스킬)은 승인 없이 진행한다.

**발동 신호(ADR-0002 가 첫 기록물에 적으라고 한 항목).** 관측된 제보는 2026-09-23 의 1건이고 유입률은
측정된 적이 없다. 이 프로그램을 여는 근거는 수요 계수가 아니라 소유자의 결정이며, 그 결정은 「이 제품의
개발자가 자기 제보를 자기 도구로 진단한다」는 갈래 1 의 재개 조건(2026-08-30) 위에 서 있다. 그래서 §6 의
측정 단계는 실제 제보가 아니라 **라벨 셋**을 1차 재료로 삼고, 실제 제보는 있는 만큼만 더한다.

지키는 원칙은 리포의 것 그대로다: **System decides, LLM narrates** · 인용 없으면 침묵 · 기권은 값 ·
정본은 사람이 정하고 기계는 기억한다(#553) · 읽기 전용 자격증명.

## 4. 설계 — 다섯 조각

### 4.1 U0 라벨 셋과 채점기 (게이트 없음 — 측정 도구)

**왜 먼저인가.** 현장 자료가 한목소리로 「진짜 비용은 루프가 아니라 채점」이라 말하고, 오늘 프로브에서
정확했던 3건이 전부 원인이 코퍼스에 있던 경우였다. 채점기 없이 다른 조각을 넣으면 효과를 측정할 수 없다.

- 위치: `nexus/tests/eval/bug-diagnosis/` — `labels.yaml` · `README.md`(채점 규칙, 결과를 읽기 전에 고정)
  · 러너 `scripts/bug_diagnosis_probe.py`.
- 라벨 한 건: 제보 원문(**증상만**, 원인 힌트 금지) · 출처(이슈 번호 또는 `kakao-2026-09-23`) ·
  `corpus.tenant`(**필수** — `resolve_tenant` 규칙, 기본값 없음) · 기대값: 층(C1~C4) · 부품(파일·컴포넌트
  이름 목록, 하나라도 짚으면 방향 정답) · 원인 가족(한 문장) · 정본 판정이 있으면 claim id 와
  **`claim_concepts_present`**(제보 원문에 그 claim 의 개념이 전부 나오는가) · 대조군(NC) 표시 ·
  **`cause_in_corpus`**(원인이 어느 코퍼스에든 문서화돼 있는가).
- 채점 다섯: R1 방향 · R2 헛소리(인용 근거 밖 기제를 단정형으로) · R3 기권 정직(근거 없을 때 그렇다고) ·
  R4 다음 열 곳(관련 문서 절·코드 위치) · R5 판정 존중(claim 판정이 있으면 되묻지 않고 판정값으로 답).
  **R5 는 `claim_concepts_present` 가 참인 라벨에서만 채점한다** — claim 매칭은 개념 전부 일치 규칙이고
  형태소로 넓히지 않으므로(2026-09-03 결정), 어휘가 어긋나 안 붙은 경우는 「매칭 미부착」으로 따로 세지
  시스템 실패로 세지 않는다. **3회 다수결**(답변 품질 하니스 규칙 — 1회차 수는 적지 않는다). 채점 정본
  함수는 `scripts/ko_eval_answer_quality.py` 의 것을 쓰고 새로 쓰지 않는다(2026-08-26 교훈).
- 재료와 목표 수: 셈이 둘이라 갈라 적는다. 「원인이 코퍼스에 있는 것」은 61 중 3 이고, 「이슈 기록(본문·댓글·
  연결 PR)에 확정 원인이 적힌 것」은 아직 세지 않았다. **U0 의 첫 일은 그 수 N 을 세는 것**이고 라벨 목표는
  `min(20, N)` 이다. 20 은 상한이지 약속이 아니다. Cleric 의 200 중 12 는 포스트모템 수율이라 여기 그대로
  옮기지 않되, N 이 한 자릿수면 그 사실을 §7 의 판정에 그대로 싣는다. 층별 목표(C1 6 · C2 8 · C3 4 · NC 2)는
  N 이 허락하는 만큼만 채우고, **원인이 어느 코퍼스에도 없는 라벨을 8건 이상** 넣는다(알려진 원인의 회수만
  측정하지 않기 위해). 기대값은 소유자가 서명한다.
- 라벨 저술 검사: `label_authoring_check.py` 의 정신 — 요구가 gold(이슈 기록)에서 성립하고 대조군에서
  불성립 — 을 이 라벨 형식에 맞춰 한 번 더 쓴다. 판정 대상을 편하려고 줄이지 않는다(규칙 5).
- 기준선: 같은 라벨을 **khala 답변 경로만으로** 3회 돌린 값을 먼저 적는다. U2 의 목표는 이 기준선에 대한
  상대값이다(§7).

### 4.2 U1 이슈·포스트모템·KNOWN_ISSUES 적재 (게이트 — 저장되는 내용)

**왜.** 61건 중 원인이 코퍼스에 있는 것이 3건이고, 원인이 적힌 이슈 기록에는 적재 경로가 없다
(`ingest/sources` 는 notion·ops_map 뿐). 알려진 버그의 재발·형제 진단이 오늘 P2·P7 처럼 답해지려면
그 기록이 코퍼스에 있어야 한다. 국내 A1Mobilsoft 는 과거 유사 사례가 답의 36% 를 냈다.

- **테넌트는 새로 만든다: `issues`.** 이유 둘. ① 닫힌 이슈는 「그때 그 말」이라 `design_docs` 에 섞이면 설계
  별칭 소비자가 옵트아웃하지 않는 한 옛 증상을 근거로 받는다(ADR-0006 의 버전 공존 실패 모드). ② 테넌트
  격리는 SQL 의 정책 필터라 기존 소비자의 후보 집합이 바이트 단위로 안 바뀐다. 읽는 신원은 dev 신원의
  `read_tenants` 에 `issues` 를 더하는 것으로 정하고(선언 없이는 기동하지 않는 자물쇠 그대로), 슬랙 별칭은
  소유자가 원할 때만 연다. `picasso`·`narrator`·`design_docs`·`default` 는 건드리지 않는다.
- 임포터 `nexus/nexus/ingest/sources/github_issues.py`: `gh issue list --json`(본문) 과 `gh issue view --json
  comments`(댓글) 의 JSON 파일을 받아 **이슈 하나 = 문서 하나**를 만든다. 댓글은 넣는다 — 원인은 흔히 논의 끝
  댓글과 연결 PR 에서 확정되기 때문이고, 연결 PR 은 제목과 번호만 싣는다. 문서는 `## 본문` 과 `## 논의` 두 절.
- **문서 식별자**: `canonical_uri = "{tenant}:{filename}"` 이 basename 이라(ADR-0006 Slice 1 의 알려진 한계)
  리포가 둘이고 번호가 겹치면(376 이 양쪽에 있다) 한쪽이 다른 쪽을 말없이 덮어쓴다. 파일명 규칙은
  `issue-<repo>-<number>.md` 로 고정하고, 적재 검사는 「내보낸 이슈 수 = 적재된 문서 수」를 센다.
- frontmatter: `doc_type: issue` · repo · number · state · labels · created · closed · url ·
  `origin_updated_at`(이슈 `updatedAt`). **결정론**: 같은 입력은 바이트 단위로 같은 출력(ops_map 규칙 — 생성
  시각을 넣지 않는다). 종류는 코드 변경 없이 frontmatter 로 정해진다(`ingest/classifier.py` 가 frontmatter
  `doc_type` 을 우선한다). 그래서 소비자는 `exclude_doc_types: [issue]` 로도 뺄 수 있다(#521 기제).
- 신선도: 닫힌 이슈는 `labels` 에 `closed` 를 실어 답변의 낡음 표시가 붙게 하고, 답변 프롬프트 규칙 6·7 이
  범위와 상충을 밝히게 한다. 같은 버그가 다시 열려 새 이슈가 되면 새 문서가 옛 문서를 **supersede** 한다
  (기존 `nexus_supersede` 프리미티브). 재적재는 수동이다(`gh` 내보내기 → 컨테이너 안 `nexus ingest`);
  주기화는 열어 둔다(§8).
- 포스트모템 3편은 로컬 폴더의 사본에 `doc_type: postmortem` frontmatter 를 붙여 같은 테넌트에 적재한다
  (원본 불변). KNOWN_ISSUES 는 이미 `design_docs` 에 있으므로 그대로 둔다.
- 사람 식별자: 이메일 등은 PII 게이트가 격리한다. GitHub 핸들은 문서에 남을 수 있으나 **답변 산문에는
  싣지 않는다**(AGENT-01 규칙). 공개 리포에 커밋되는 것은 임포터 코드뿐이고 이슈 본문은 코퍼스 DB 에만 있다.
- 적재 뒤 **코퍼스 경계 시각**을 기록한다(SOP-03 관행).

### 4.3 U2 에이전트 루프 (게이트 없음 — khala 코드 변경 0)

**왜.** 버그의 70%(C2·C3)는 코드를 읽어야 원인에 닿고, khala 의 답변 경로는 설계상 코드를 읽지 않는다.
코드 읽는 에이전트는 오늘 4건 중 3건에서 이슈 기록과 같은 방향을 냈고 2/2 에서 시키지 않은 차이를 찾았다.
그러나 1건은 이슈 기록과 반대였고 표본은 n=4·n=2 다 — 그래서 산출물은 「확정」이 아니라 **검증 가능한
가설과 확인할 증거 목록**이고, 목표는 §7 에서 기준선 대비 상대값으로 잡는다.

- 형태: 리포 안 Claude Code 프로젝트 스킬 `.claude/skills/diagnose-report/SKILL.md`. khala 는 그라운딩 팩을
  주는 쪽이고 읽기는 에이전트가 한다.
- 순서: ① khala `/search`(또는 MCP `nexus_search`) 로 `default`·`design_docs`·`issues` 를 조회 — 알려진
  이슈·정책. 판정이 붙은 claim 은 에이전트가 필드 이름을 짚은 뒤 `archon_claim_value` 로 따로 조회한다
  (제보 문구에 개념이 없어도 판정에 닿는 길) ② 가설 목록 ③ 코드 읽기(읽기 전용, 마운트된 두 리포)
  ④ 출력 계약 ⑤ 사람이 읽고 판정 → 어긋남은 claim 에 기록(U3 와 연결).
- 출력 계약(전부 값으로): 증상(제보를 읽은 대로) · 가설[근거 file:line, 판정 `확정|유력|기각|미확인`,
  **반대 근거**] · 결론과 확신도 · 그 밖에 발견한 것 · **확인할 런타임 증거 목록** · **체크아웃 시점 vs
  제보 시점** · **정본 판정이 필요한 어긋남 목록** · 기권(근거 없음은 정상 출력).
- 금지: 쓰기 권한 · 자동 수정·PR · `/search/answer` 호출(브리지 점유). 비용 90~110k 토큰/건(구독), 4~7분.
- 측정: U0 라벨을 3회 돌려 R1~R5, 기준선(khala 답변 경로만)과 나란히.

### 4.4 U3 프론트 리포 읽기 범위 + TS 값 해석 + 짝 대조 규칙 (게이트 — 설정·의존성)

**왜.** 오늘의 제보는 프론트에 살았고 khala 는 그 리포를 못 봤다. 표면 간·값 어긋남 부류(버그의 10~15%)는
추론이 아니라 대조로 잡히고, 현장의 정합성 검출은 전부 비교 방식이다.

- 마운트: `CODE_SRC_WEB_PATH` → `/code-src-web:ro`. `code_source.repo_path` 는 **별칭이 붙은 목록**이 된다
  (`- {alias: platform, path: /code-src}` · `- {alias: web, path: /code-src-web}`; 문자열이면 별칭 `platform` 의
  한 원소 목록으로 읽는다 — 하위 호환).
- `CodeValueResolver` 의 리포 해결 규칙: `value_source` 는 `<alias>:<기존 표기>` 로 리포를 **명시**한다.
  별칭이 없으면 첫 리포(`platform`)만 본다 — 오늘의 claim 10건은 바이트 그대로 유효하다. 별칭이 있으면 그
  리포만 본다. **리포를 넘나드는 첫 매치는 없다** — 한정자 없는 이름이 여러 곳에 있을 때 답하지 않는 기존
  규칙을 리포 축에도 적용한다. 드리프트 해시는 명시된 리포의 심볼에만 묶인다.
- 새 값 모양 셋 — JSX 속성 `maxLength={N}` · zod `.max(N)`/`.min(N)`(스키마 파일이 한정자) · i18n 키 값
  (`ko.json` 경로:키). **리터럴 정수만 값으로 인정한다.** 변수 참조·조건식·스프레드·재수출·동적 스키마는
  `found=False` 에 이유 「리터럴 아님」으로 기권하고, 값 종류는 `value_ref_kind: code_literal_ts` 로 따로 표기해
  소비자가 Java 어노테이션 값과 가를 수 있게 한다. 1차는 정규식 + 파일 한정자로 하고 AST 그래머는 열어
  둔다(의존성을 늘리지 않는다). 비리터럴 모양마다 픽스처 검사를 둔다.
- 짝 대조(결정론, LLM 0): 같은 필드 이름의 모든 입력창 상한 = 그 필드 스키마 상한. 어법은 표로 관리한다
  (`name='x'` 과 `register('x')` 둘 다). 다르면 **판정 후보** 행(필드 · 표면 · 값들 · 파일:줄)을 낸다.
  「같은 훅을 쓰는 소비자끼리 일치」 규칙은 함께 틀린 사본을 통과시켰으므로 쓰지 않는다. **소유 컴포넌트는
  소유자 결정이다**(§9 I-020): 권고는 Observer — ADR-0004 가 플랫폼 정합성·계약 린트를 Probe/Observer 쪽
  접지로 두었고 그 코드가 TS 다. khala 에 남는 것은 claim 판정과 `ruling_conflict` 뿐이다.
- 판정은 claim 에 남고(`ruled_value`), 이후 어긋남은 `ruling_conflict` 가 지킨다. 어느 쪽이 정본인지는
  규칙이 정하지 않는다 — 스키마 값을 **후보**로 낼 뿐이다.
- 심볼 인덱스와 앵커 스캔은 1차에서 백엔드 리포에 한정한다(앵커 표에 리포 식별자가 없다 — §8).

### 4.5 U4 스크린샷 입구 (게이트 — 요청 계약 · ADR-0010 여섯 홉)

**왜.** 제보는 스크린샷으로 온다. 판독기는 이미 6초에 되지만 어느 표면도 이미지를 받지 않는다. 이것은
능력이 아니라 편의다 — 스크린샷은 증상만 주고(92.65%), 화면 판독 정확도는 76%(영문)라 읽은 값은 근거가 아니다.
ADR-0010 이 적재 시점 추출에 건 조건을 **질문 시점에도 전부** 건다.

- 요청: `AnswerRequest.attachments: [{media_type, data_b64}]`(1장 · 2MB 상한), CLI `--image`. 모르는 칸 422
  계약은 그대로이고 선택 칸 추가는 계약 문서를 갱신한다(#552).
- 판독기: `ingest/vision.read_image` 를 질문 시점에 부른다. 브리지의 `/v1/vision` 경로는 **도구·파일시스템
  없이** 돈다 — `build_vision_argv` 가 `_DOORS_CLOSED` 를 그대로 물리고 이미지는 stdin 의 base64 로만 들어간다
  (`nexus/tools/claude_llm_bridge.py`). ADR-0010 §6 의 「판독기는 도구도 파일시스템도 없다」는 이미 코드로
  성립하고, 이 SPEC 은 그것을 요구 조건으로 명시한다. 판독기 신원은 적재 경로와 같은 `{model}/{prompt_sha}`.
- **스캐너가 먼저다**(ADR-0010 §6). 판독 텍스트는 근거 꾸러미에 들어가기 전에 `ingest/scanner.py` 의 PII
  판정을 **적재 문서와 같은 조건으로** 통과한다. 걸리면 그 첨부는 격리된다 — 텍스트는 버리고 응답에
  `attachment_status: quarantined` 를 싣는다. 카카오톡 오픈채팅 스크린샷은 정확히 사람 식별자가 픽셀에
  있는 부류다(오늘 판독에 채팅 이름 둘이 그대로 옮겨졌다).
- **등급이 여섯 홉을 다 지난다**(ADR-0010 §4). 판독 조각은 꾸러미의 `SearchHit` 과 같은 모양으로 들어가고
  `provenance_tier=machine_read` · `doc_title="첨부 스크린샷"` · `source_uri="attachment:sha256:<앞16>"` 을
  갖는다. 그래서 (1) 청킹 — 조각 하나, 저자 텍스트와 섞이지 않음 (2) `SearchHit` (3) 프롬프트 — 기존
  `[그림에서 기계가 읽음]` 표기 (4) 인용 — `[출처: 첨부 스크린샷]` 이 검증기의 제목 대조를 통과 (5) API
  응답 — `evidence_snippets` 의 `provenance_tier` (6) MCP — `_tier_mark` 가 붙는다. 홉마다 검사 하나.
- **기록은 남되 그림은 안 남는다**(ADR-0010 §3.1 의 동반 필드). `search_log` 행에 판독기 신원과 이미지
  sha256 을 남기고 응답에도 `attachment: {sha256, reader}` 를 싣는다. 이미지 바이트와 판독 텍스트는 저장하지
  않는다 — 회수 수단은 「요청자가 자기 원본을 다시 읽힌다」이고, 응답의 sha 가 그 원본을 짚는다.
- **보존 경로 전체 제외.** 첨부가 있는 요청은 질의 보존(`search/query_retention.py`)과 슬랙 피드백 제안
  저장(`slack/feedback.py` 의 `answer_text`)을 **둘 다 건너뛴다** — 판독 텍스트는 답변 산문과 인용으로
  재생산되므로 텍스트만 막는 것으로는 닫히지 않는다. 검사는 그 두 표를 센다.
- 프롬프트 규칙 한 줄: 「스크린샷에서 읽은 값은 근거가 아니라 질문의 일부다 — 값은 코퍼스·코드에서 다시 확인」.
- 브리지 점유와 실패 모드: 판독은 브리지의 동시 한도(1)를 6~11초 쓴다. 브리지가 503 이나 시간 초과를 내면
  요청은 **첨부 없이 계속 진행**하고 응답에 `attachment_status: reader_busy | reader_timeout` 을 싣는다 —
  부분 답변이 아니라 「첨부 없는 답변」이며, 그 사실이 값으로 나간다.
- Slack `files` 는 열어 둔다(§8). 첨부 없는 요청의 프롬프트는 바이트 동일.

### 4.6 설명 층(picasso-narrator) 영향

배선으로 확인했다. `narrator-events` 는 읽기 전용에 `read_tenants: [picasso]` 이고 최근 7일 답변 486건이
전부 `picasso` 범위다. claim 12건은 `default` 라 `picasso` 질의에 0건 붙고 프롬프트는 바이트 동일(검사 있음).
`picasso` 문서의 코드 앵커는 0건. 유일한 공유 자원은 키리스 브리지(동시 한도 1, 5초 대기 뒤 503)다 — U2 는
브리지를 안 쓰고, U0 채점과 U4 판독은 쓴다. 사용자 결정으로 시간대 규칙은 두지 않으며, U4 의 실패 모드는
§4.5 에 값으로 정해 두었다. §7 의 전체 조건은 U0 채점 실행과 U4 라이브 뒤에 각각 한 번씩 측정한다.

## 5. 하지 않는 것

- 자동 수정·자동 조치. 현장에도 되돌릴 수 있는 동작 말고는 사례가 없고, 파괴 사고는 전부 과다 권한에서 났다.
- 기계의 정본 판정. 모델은 문서 편을 든다(−21~43pp). 정본은 사람이 claim 에 남긴다.
- 런타임 증거(로그·DB)로 원인 확정. 저장소가 없다. 읽기 전용 DB 계정(OPEN H14)이 열리면 그때 따로 SPEC.
- 카카오톡 직접 입구. 사람이 옮긴다(Slack·CLI·MCP).
- `picasso`·`narrator` 테넌트와 설명 층 계약의 변경.
- LLM 이 스크린샷 둘을 보고 표면 간 차이를 판정하는 것(검증된 사례 0).
- claim 매칭을 형태소로 넓히는 것(2026-09-03 결정 유지).

## 7. 완료 조건 — 결과를 보기 전에 고정한다

- **U0**: 라벨 가능 이슈 수 N 을 세어 README 에 적는다. 라벨 `min(20, N)` 건(대조군 2 · 원인이 어느 코퍼스에도
  없는 것 ≥ 8 · 기대값 소유자 서명). 채점 규칙이 README 에 먼저 앉는다. 러너가 3회 다수결로 돌고, **기준선**
  (khala 답변 경로만)의 R1~R5 가 기록된다.
- **U1**: 내보낸 이슈 수 = 적재된 문서 수(덮어쓰기 0) · 포스트모템 3 적재 · **`default`·`design_docs`·`picasso`
  청크 수 불변**(검사) · 프로브 10건 재실행(3회): 근거 없는 단정 0 유지 · 정확 ≥ 5(오늘 3; P2 형 재발 진단이
  늘어야 한다) · 기권-정답 3 유지 · 설계 별칭 회귀: 정책 15문항 기준선 14/15 유지.
- **U2**: 라벨 3회 — R2 헛소리 0 · **R1 방향 ≥ 기준선 + 3**(절대값도 같이 적되 게이트는 상대값) · NC 전부
  기권 · 원인이 코퍼스에 없는 8건 중 R1 ≥ 3 · 출력 계약 칸 전부 채움 · 브리지 호출 0(브리지 기록 파일로 확인).
- **측정 단계**: 재료는 라벨 셋이고 실제 제보는 있는 만큼 더한다. 통과 = U2 조건 충족. 달력 상한 4주. 실제
  제보가 4주에 5건 미만이면 「유입률 미측정」으로 적고 라벨 결과만으로 다음 조각의 착수를 판정한다 — 연장하지
  않는다.
- **U3**: 닉네임 사례에서 규칙이 온보딩 두 표면의 16 ≠ 12 를 후보로 내고 앱 안 편집 12 는 내지 않는다 ·
  후보 행 전부를 소유자가 판정하고(예상 10건 미만, 실제 수를 적는다) 판정이 claim 에 기록된다 — 「오탐 0」
  은 요구하지 않는다, 판정된 행 수와 「의도된 차이」 판정 수를 적는다 · 비리터럴 모양 픽스처 전부 기권 ·
  `platform` 별칭 없는 기존 claim 10건 값 불변 · claim 판정 뒤 `ruling_conflict` 참.
- **U4**: 카카오 스크린샷 → 텍스트 제보와 같은 가설 (a) · 홉 여섯 각각의 검사 초록(청킹·SearchHit·프롬프트·
  인용 검증·API·MCP) · PII 픽스처 첨부가 격리되고 `attachment_status: quarantined` 로 나온다 · 첨부 요청이
  `query_retention` 과 피드백 제안 표에 0행 · `search_log` 에 판독기 신원과 sha256 이 남는다 · 브리지 503
  픽스처에서 첨부 없는 답변과 `reader_busy` 가 나온다 · 첨부 없는 요청의 프롬프트 바이트 동일.
- **전체**: 설명 층 `picasso` 범위의 검색 결과·지연 불변(`search_log` 대조) — U0 채점 실행 뒤와 U4 라이브
  뒤에 각각 측정. 조건이 안 서면 다음 조각으로 가지 않는다.

## 8. 열어 둔 것

- 읽기 전용 DB 계정(H14) — 「런타임 증거로 확정」 단계의 전제.
- 이슈 주기 동기화(수동 → 주기).
- 심볼 인덱스·앵커 스캔의 다중 리포(앵커 표의 리포 식별자).
- 코드 값 절의 인용 이름 — 오늘 답이 그 절을 「출처」로 인용해 검증기가 2건을 미검증으로 셌다.
- Slack `files` 입구.
- claim 판정의 편집 표면(지금은 YAML 손편집).
- 「근거 없음」의 값 — `abstained` 는 히트 0건에만 참이고 `weak_evidence` 는 검색 적합도다. U2 출력 계약이
  대신 값을 내지만 khala 답변 경로 자체는 여전히 산문으로만 기권한다.
- 판독기 잡음 바닥(질문 시점 판독기 신원의 `reader_variation`) — 저장하지 않으므로 1차에서 요구하지 않는다.
