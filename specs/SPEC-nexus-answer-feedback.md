# Answer feedback: a 👎 is a lead, not a rate

## 0. 게이트 — 디렉터가 채운다

ADR-0008 §3 항목 3: 게이트는 **디렉터가 발화를 선언하고 그 방향의 첫 SPEC 에 기록하는 것**이지
SPEC 이 스스로 논증해 만들어내는 것이 아니다.

> **선언**: 답변 피드백 게이트를 발화한다.
>
> - **발화한 게이트**: 슬랙 파일럿이 돌고 있고 팀원이 실제로 묻는다. 두 평가셋(Pack A·B)은
>   **둘 다 천장에 닿았고**, 오른 점수는 전부 계측기 몫이었다 — 새로 잴 것이 생기려면
>   실사용에서 신호가 들어와야 한다. 지금 시스템은 **자기 답이 틀렸다는 것을 알 방법이 없다.**
> - **선언자·날짜**: LivingLikeKrillin · 2026-08-14 (세션 지시로 발화)
> - **범위**: 이 SPEC 의 U1~U2 만. 만족률 발표·자동 경보·자유 텍스트 수집은 **비목표**(§2).

**이 방향의 첫 SPEC 인가.** [[SPEC-nexus-query-text-retention]] 은 **입력**(사람이 무엇을
물었나)을, [[SPEC-nexus-answer-quality-ruler]] 는 **저술된 라벨로 채점하는 자**를 다룬다.
사람이 답을 보고 내리는 **판정**을 받는 표면은 지금까지 없었다 — 그 방향의 첫 SPEC 이 이것이다.
서명자가 이 구분을 인정하지 않으면 이 SPEC 은 기록 위치부터 틀린 것이므로 그때는 반려가 맞다.

### 0.1 ADR-0008 §5 — 재독 트리거이지 승인 관문이 아니다

앞선 SPEC 들은 여기에 "판정: backstop 은 발화하지 않는다" 를 서명과 함께 적었다. **그 형식은
ADR 에 없다.** ADR-0008 §5 원문은 이렇다(2026-08-14 대조):

> **Backstop.** No periodic ADR review process exists in this repository … **this ADR is
> re-read at the start of any work that would materially expand Nexus's retrieval stack** —
> a new retrieval channel, a second index backend, a tokenizer or embedding-model change,
> or connector work beyond the existing two sources.

**재독 트리거**이지 owner 가 내리는 승인 단계가 아니다. 리뷰 패킷에 ADR 본문이 없으면 이
단정을 검증할 수 없으므로 인용을 본문에 박아 둔다 — 이 단정이 틀리면 승인 절차 하나가 근거
없이 사라지는 것이라 서명 전에 대조가 필요하다.
SPEC 이 ADR 에 없는 관문을 만들어 스스로를 그 앞에 세우지 않는다.

사실만 적는다: 이 SPEC 은 새 검색 채널·두 번째 인덱스 백엔드·토크나이저/임베딩 변경·커넥터
작업을 하지 않으므로 **재독 트리거에 해당하지 않는다.**

그리고 §0 의 *"바뀌는 것은 블록 하나뿐"* 은 부정확하므로 실제 추가 표면을 전부 적는다:

1. 답변마다 DB 쓰기 한 번(클릭이 없어도)
2. 답변 메시지에 `actions` 블록 추가
3. **새 인바운드 경로** — `block_actions` 인터랙션 핸들러
4. ephemeral 메시지 발송
5. **새 아웃바운드 경로** — 👎 시 운영자에게 DM(§3.7)
6. 슬랙 앱 설정의 **Interactivity 토글** + 스코프 `im:write` → **앱 재설치** 필요

## 1. 무엇이 이것을 불렀나

### 1.1 자를 더 손봐도 얻을 것이 없다

- Pack A 34~35 → 38~40, Pack B 39~40. **오른 점수 전부가 계측기 몫**이었다(검색·생성 무변경).
- 3런 지속실패 4건 중 시스템 결함 **0**.
- 서술 U2 측정에서 `three_sentences` 가 양팔 0/30 이었는데, 원인은 시스템이 아니라 **자**였다.

라벨은 문서를 보고 저술된다. 답을 보고 낸 문제는 코퍼스가 반드시 답을 갖는다 — 그 천장을
낮추는 유일한 재료가 사람이 실제로 던진 질문이고([[SPEC-nexus-query-text-retention]]),
그 질문에 대한 **판정**은 지금 어디에도 없다.

### 1.2 실사용 오답은 이미 있었고, 우연히 발견됐다

2026-08-13, 팀원이 *"너가 근거로 사용 중인 corpus 범위는 어떻게 돼?"* 라고 물었고 봇은 그 턴의
근거 패킷 5건을 **범위**라고 답했다. 실제 범위는 108건이었고 시스템은 그 수를 알고 있었다.

**그 오답이 발견된 경로는 사람이 우연히 눈치챈 것뿐이다.** 시스템에는 흔적이 없다.

### 1.3 비율은 영원히 안 나온다 — 그것을 설계 전제로 삼는다

팀은 5명 규모다. 자원 응답률까지 감안하면 한 달에 표 열 개 남짓이다. 그 수로 "만족률 73%" 를
계산하는 것은 **잡음에 이름을 붙이는 짓**이고, 이 리포가 반복한 실패다(`search_log` 의
`n_snippets>0 AND n_citations=0` 을 게이트로 굳히지 말라고 적어 둔 것과 같은 이유).

그래서 피드백을 **지표가 아니라 결함 신고 채널**로 설계한다. 👎 한 건은 통계가 아니라 단서다.

## 2. 비목표

- **만족률을 발표하지 않는다.** 비율 산출은 §5.2 의 최소 N 을 넘기 전까지 금지.
- **문턱 기반 경보를 만들지 않는다.** "X% 미만이면 경보" 는 재본 적 없는 숫자다. §3.7 의
  운영자 DM 은 **건당 라우팅**이지 집계 문턱이 아니다 — 초안은 이것을 "자동 경보 없음" 으로
  뭉뚱그려 §3.7 과 정면으로 읽혔다.
- **자유 텍스트를 수집하지 않는다** (§8). PII 표면이고 스캐너·격리 경로가 없다.
- **투표자를 식별하지 않는다** — *기록으로는*. 이 표에는 신원 컬럼도, 신원에서 파생된 값도
  **없다**(§3.4). 다만 안 B(§3.5)를 채택했으므로 **운영자는 스레드를 열어 질문자를 추정할 수
  있다.** 투표자 ≠ 질문자이므로 추정이지 기록이 아니고, 5명 팀에서 그 구분이 얇다는 것도
  사실이다 — 숨기지 않고 §7 에 적는다.
- **검색·답변 생성을 바꾸지 않는다.**

## 3. 설계

### 3.1 답변 블록에 버튼 둘, 👎면 사유 넷

봇은 이미 Block Kit blocks 로 답하고 Socket Mode 로 붙어 있다. `actions` 블록 하나와
`block_actions` 핸들러 하나면 된다 — 슬랙 앱 설정의 **Interactivity 토글**만 켜면 되고,
Socket Mode 라 공인 URL 이 필요 없다.

👎 는 **고정된 사유 넷**을 되묻는다:

| 사유 코드 | 사용자에게 보이는 말 | 무엇을 가리키나 |
|---|---|---|
| `wrong_evidence` | 근거가 틀렸다 | 인용은 붙었는데 내용이 아니다 |
| `not_my_question` | 내 질문이 아니다 | 재작성·라우팅이 딴 데로 갔다 |
| `ignored_format` | 형식을 무시했다 | 서술 U2 가 고쳤다고 주장하는 바로 그것 |
| `not_found` | 못 찾았다 | 커버리지·등급·색인 문제 |

**한 비트로 네 가지 질문을 읽지 않기 위한 것이다.** 사유 넷은 각각 **다른 수리**를 가리킨다.
이 taxonomy 는 [[adept-core-question-generation-grading]] 의 오답 분류와 같은 모양이다.

### 3.1.1 상태기계 — 애매하면 분자 정의가 흔들린다

1. 👍/👎 클릭 → **즉시** 투표 행을 쓴다. 👎 는 `verdict='down', reason=NULL`.
2. 👎 직후 **ephemeral** 메시지로 사유 넷을 되묻는다. 원 답변 메시지는 고치지 않는다 —
   채널의 다른 사람에게 남의 투표가 보이면 그것 자체가 신원 노출이다.
3. 사유를 고르면 그 투표 행의 `reason` 을 UPDATE 한다. **어느 행인지는 `answer_key` 로
   찾을 수 없다** — 한 답변에 여러 사람이 투표하므로 후보가 여럿이고, 잘못 고르면 남의 투표에
   내 사유가 적힌다. 사유는 이 기능의 **유일한 산출물**이므로 그 오배정은 신호를 통째로
   오염시킨다. 그래서 1 에서 만든 **투표 행 `id` 를 사유 버튼의 `value` 에 실어** 되돌려받고,
   UPDATE 는 그 `id` 로 한다. **가드 셋**: 그 행이 `verdict='down'` 이고, `reason IS NULL`
   이고, `voted_at` 이 1시간 안이어야 한다. 셋 다 없으면 오래된 ephemeral 을 다시 눌러
   **이 기능의 유일한 산출물이 조용히 덮어써진다** — 그것은 5 의 append-only 입장과도 어긋난다.
   **가드가 걸리면 조용히 무시하지 않는다**: 사용자에게 ephemeral 로 "이미 사유가 기록됐거나
   시간이 지났습니다" 를 보이고 `reason_rejected` 를 센다. 조용한 무시는 이 리포가 반복
   지적한 "초록인데 동작 안 함" 을 사용자 쪽에서 재생산한다.
4. **고르지 않고 이탈하면 `reason=NULL`** 인 채로 남고, 그것은 "사유 미상 부정" 이지 무효표가
   아니다 — 분자에 들어간다.
5. **번복은 없다.** 다시 누르면 새 투표 행이 append 된다(§3.3). 집계는 행을 그대로 센다.

### 3.2 답변에는 **불투명한 난수 키**가 붙는다

투표는 "이 답변" 에 붙어야 하는데 붙일 손잡이가 없다. `search_log.id` 는 fire-and-forget 이라
봇에게 돌아오지 않고, `retention_key` 는 질의 **텍스트**의 키다.

그래서 답변마다 `answer_key` 를 발급해 버튼 `value` 에 싣는다.

- **128비트 CSPRNG** (`secrets.token_urlsafe(16)`). 열거·위조를 막는 보안 파라미터다.
- 질의·답변·신원 어느 것에서도 파생되지 않는다.
- **발급 후 30일이 지나면 투표를 받지 않는다.** 오래된 스레드의 버튼이 영원히 살아 있으면
  그 값은 만료 없는 자격증명이 된다.
- **가시성은 슬랙에서 상속된다** — 버튼은 그 사람이 이미 볼 수 있는 메시지 위에 있다.
  Nexus 가 별도로 등급을 재검사하지 않는다(재검사할 신원이 없다, §3.4).

> 이것은 [[SPEC-nexus-multi-turn-narration]] §3.2 재개조건 (a) 가 요구하는 "직전 답변의
> 서버측 신원" 과 같은 프리미티브다. **여기서는 그 용도로 쓰지 않는다** — 서술 본체는
> (b)~(d) 도 필요하다. 재사용될 수 있다는 사실만 적어 둔다.

### 3.3 표 둘, 분모와 분자

**투표 수만 세면 침묵을 중립으로 오해한다.** 자원 응답은 화난 사람과 감동한 사람이 누르고
나머지는 안 누른다. 그래서 제안(분모)과 투표(분자)를 각각 행으로 남긴다.

```
answer_offered(tenant, answer_key, offered_at, notice_version, synthesized,
               channel_id, message_ts)          -- 안 B (§3.5)
    PRIMARY KEY (tenant, answer_key)

answer_vote(id, tenant, answer_key, verdict, reason, voted_at)
    FOREIGN KEY (tenant, answer_key) → answer_offered
    id      TEXT  -- **CSPRNG. serial 금지** (아래)
    verdict TEXT  CHECK (verdict IN ('up','down'))
    reason  TEXT  CHECK (reason IS NULL OR reason IN
                        ('wrong_evidence','not_my_question','ignored_format','not_found'))
                  CHECK (verdict = 'down' OR reason IS NULL)
```

**`id` 는 `answer_key` 와 같은 이유로 CSPRNG 다.** `bigserial` 이면 사유 버튼의 `value` 가
**열거 가능한 값**이 되고, §3.1.1 (3)의 가드 셋(`verdict='down'`·`reason IS NULL`·1시간 이내)은
**남의 최근 👎 행에서도 전부 참**이므로 조작된 페이로드가 타인의 투표에 사유를 적을 수 있다.
`answer_key` 에 적용한 논거(§3.2)가 같은 이유로 `id` 에도 걸린다.

**사유 값 집합은 스키마가 강제한다.** CHECK 제약이 없으면 이 기능의 유일한 산출물이 자유 텍스트
컬럼이 되고, 그것은 §2 의 "자유 텍스트 미수집" 과 마찰한다.

**텍스트 컬럼이 하나도 없다.** 질의도 답변도 담지 않는다 — `channel_id`·`message_ts` 는
슬랙 메시지를 가리키는 포인터이지 내용의 사본이 아니다. 그 스레드가 지워지면 우리 쪽에도
아무것도 안 남는다(§7).

- 분모 = `COUNT(answer_offered)`, 분자 = `COUNT(answer_vote)`.
- **투표는 행 추가다.** 한 답변에 여러 사람이 투표할 수 있고(슬랙 채널의 답변은 여러 명이
  본다), 두 번째 투표가 첫 투표를 덮어쓰지 않는다. 초안은 `answer_key` 단독 PK 에 UPDATE
  였는데, 그러면 **분모는 남고 분자가 조용히 유실된다** — 편향을 보이게 하겠다는 §7 과
  정반대 방향이다.
- `verdict IS NULL` 인 상태는 없다. 투표가 없으면 `answer_vote` 에 행이 없을 뿐이고,
  **"무응답" 은 "중립" 이 아니다.** 어떤 집계도 둘을 합치지 않는다.
- **제안 행이 없는데 투표가 오면** 그 자리에서 `synthesized=true` 인 제안 행을 만들어 넣고
  `orphan_votes` 카운터를 올린다. 제안 쓰기는 best-effort 인데(I6) 투표를 FK 로 막으면,
  **시스템이 불안정할 때 정확히 그때의 투표만 통째로 사라진다.**
- **`synthesized` 행은 분모에서 뺀다.** 그 행의 `offered_at` 은 발급 시각이 아니라 투표 시각
  이고 `notice_version` 도 모른다 — 제안이 아니었던 것을 제안으로 세면 분모가 부풀고,
  §3.2 의 30일 만료도 그 행에서는 잴 기준이 없다. §5.2·§5.3 의 분모는
  `WHERE NOT synthesized` 다. 이 행들은 **따로** 센다.
- **`synthesized` 행에 딸린 투표는 유효표로 세되, 고지를 가리킬 수 없음을 기록한다.**
  §3.6 이 "가리킬 수 없는 동의는 동의가 아니다" 를 근거로 삼았으므로 이것은 **예외**다.
  근거: 그 사용자는 실제로 버튼과 고지 문구를 보고 눌렀다(그래야 클릭이 온다) — 모르는 것은
  *어느 버전*이었나뿐이고, 그 불확실성은 표에 `notice_version=NULL` 로 남는다. 고지를 못 봤을
  가능성이 아니라 **우리 기록이 유실된 것**이므로 투표를 버리는 것이 더 나쁘다.
- **orphan 경로는 I10(결속)도 함께 우회한다.** 제안 행이 없으면 대조할
  `(channel_id, message_ts)` 가 없기 때문이다. **신뢰 경계를 분명히 한다**: `block_actions`
  는 Socket Mode 로 **슬랙이 인증한** 인터랙션이므로 공격자는 임의의 인터넷 호출자가 아니라
  **키를 손에 넣은 워크스페이스 구성원**이다. 그 모델에서 orphan 수용은 받아들일 만하고,
  투표를 버리는 쪽이 더 나쁘다. 대신 `orphan_votes` 를 **원인별로** 센다
  (`offer_write_failed` · `race` · `unknown_key`) — 한 칸에 뭉치면 "수가 크면 조사" 라는
  처방이 발화해도 무엇을 볼지 모른다.
- **orphan 투표에는 만료를 적용할 수 없다.** `offered_at` 이 발급 시각이 아니므로 §3.2 의
  30일을 잴 기준이 없다 — 즉 이 경로는 I7 을 우회한다. 그래서 orphan 투표는 `synthesized`
  로 표시되고 **분모에서 빠지는 것과 같은 이유로 만료 판정에서도 제외**되며, 그 수
  (`orphan_votes`)가 비정상적으로 크면 그 자체가 조사 대상이다. 이 구멍을 숨기지 않는다.

### 3.4 투표자는 **어디에도** 남지 않는다

초안은 `voter_hash = sha256(answer_key ‖ \0 ‖ slack_user_id)` 로 답변 안 중복투표를 막으려
했다. **그 익명성은 거짓이다**: `answer_key` 는 버튼 value 와 DB 양쪽에 평문으로 있고 팀은
5명이다. DB 를 읽는 사람이 후보 user_id 다섯 개를 해시해 보면 투표자가 특정되고, 행마다 같은
대입을 반복하면 사람별 이력까지 복원된다. 소금은 **오프라인 대입을 막지 못한다.**

그래서 **신원에서 파생된 값을 아예 두지 않는다.** 대가는 명확하다:

- 같은 사람이 두 번 눌러도 못 막는다.
- 한 사람이 모든 표를 던져도 못 본다 → §5.3 에서 그 규칙을 **삭제**했다. 발화될 수 없는
  조건은 규칙이 아니다.

**약속보다 구조가 강하다**는 [[SPEC-nexus-query-text-retention]] 의 판단을 그대로 따른다.

⚠ **안 B 채택으로 이 절의 주장은 무조건적이지 않다.** 여기서 지우는 것은 **투표자**이고,
`channel_id`·`message_ts` 는 **질문 스레드**를 가리킨다. 운영자는 그 둘을 이어 "이 답에 👎가
있었고 이 스레드다" 까지 간다 — 그리고 5명 팀에서 질문자와 투표자는 대개 같은 사람이다.
**투표자를 기록하지 않는다는 것과 투표자를 알 수 없다는 것은 다르다.** 전자만 참이다.

### 3.5 ⚠ **서명자가 골라야 하는 갈림길** — 익명이냐, 조사 가능하냐

세 라운드의 비평이 같은 자리로 수렴했다. **5명짜리 슬랙에서 이 둘을 동시에 가질 수 없다.**

버려진 시도 둘이 그 증거다:

- **`retention_key` + 👎 시 답변 본문 저장** — `search_query_text` 가 질문을 평문으로 담고
  `a2a_audit.query_sha256` 이 소금 없는 `sha256(query)` 이므로, 평문에서 해시를 재계산하면
  principal 로 이어지는 **결정적 경로**가 성립한다(§7). 손잡이를 하나 더 다는 꼴이다.
- **👎 시 답변 메시지에 표시 리액션** — 봇은 `thread_ts` 로 **채널 스레드**에 답한다
  (`nexus/nexus/slack/bot.py`). 깃발이 공개로 꽂히면 5명 팀에서 그 스레드의 질문자가 사실상
  지목된다. §3.4·I1·I4 가 DB·로그에서 지운 연결을 **슬랙 UI 가 공개로 복원한다.**

남은 것은 값 판단이고, 그것은 SPEC 이 아니라 **서명자의 몫**이다.

#### 안 A — 익명 우선 (**기각**)

DB 에 **수와 사유 코드만**. 채널·메시지·질의·답변 어느 것도 저장하지 않는다.

- 얻는 것: 어떤 종류의 실패가 얼마나 나는지. §3.1 표의 네 갈래 분포.
- **잃는 것: 개별 신고를 따라갈 수 없다.** "형식을 무시했다 3건" 은 알아도 *어느 답변*인지
  모른다. §5.1 의 "👎 1건 = 조사 대상 1건" 은 **성립하지 않으며**, 그 문장을 안 A 에서는
  "사유 분포가 쌓이면 그 방향을 본다" 로 읽어야 한다.
- `answer_key` 는 순수 무기명 자격증명이 된다 — 값을 가진 누구든 30일 안에 반복 투표할 수
  있고 사후 구분이 불가능하다(§7).

#### 안 B — 조사 가능 우선 (**채택**)

`answer_offered` 에 `channel_id` + `message_ts` 를 담는다. 👎 가 오면 **운영자에게만 DM** 으로
퍼머링크를 보낸다(공개 리액션 아님).

- 얻는 것: 신고가 실제로 따라갈 수 있는 단서가 된다. 그리고 투표가 **그 메시지에 결속**되므로
  유출된 `answer_key` 의 재사용을 막는다(§7 의 무기명 자격증명 문제도 같이 해소).
- **잃는 것: 운영자는 스레드를 열 수 있고, 따라서 질문자를 추정할 수 있다.** 투표자 ≠ 질문자
  이므로 투표자가 기록되는 것은 아니지만, 5명 팀에서 그 구분은 얇다.
- 완화할 수 없는 것을 완화하는 척하지 않는다: 운영자는 이미 그 채널을 읽을 수 있으므로
  **새로 열리는 것은 "이 답이 나빴다" 라는 사실이지 접근 권한이 아니다.**

> **결정: 안 B.** 디렉터(LivingLikeKrillin) · 2026-08-14.
>
> 근거로 채택한 것: 운영자는 이미 그 채널을 읽을 수 있으므로 **새로 열리는 것은 접근 권한이
> 아니라 "이 답이 나빴다" 는 사실 하나**다. 그리고 안 A 는 §5.1 의 대전제를 스스로 무너뜨린다
> — 따라갈 수 없는 신고는 신고가 아니고, 그렇다면 이 SPEC 이 존재할 이유가 얇아진다.
>
> 이 결정이 아래를 바꾼다: §2 의 비목표 표현, §3.3 스키마(+`channel_id`·`message_ts`),
> §3.4 의 무조건적 익명 주장, §4 의 결속 불변식(I10), §5.3 셋째 행의 반증가능성, §7 의 한계.
> **전부 이 문서에 반영돼 있다** — 결정만 적고 본문을 안 고치면 그 결정은 기록이 아니다.

### 3.6 고지는 저장한다

`query_retention` 은 *"가리킬 수 없는 동의는 동의가 아니다"* 라며 `notice_shown` 이 비면 쓰기를
거부한다. 버튼 옆 한 줄이 여기서의 고지지만 **슬랙 메시지는 편집·삭제된다.** 그래서 그때 보여준
문구의 식별자(`notice_version`, 예: `fb-notice-v1`)를 제안 행에 함께 남긴다 — 문구 자체는
코드 상수이고, 나중에 "그때 무엇을 보여줬나" 에 답할 수 있다.

정확히 말한다: **누르지 않아도 제안 행은 남는다.** 신원도 텍스트도 없는 한 줄이지만 남는다.
초안의 *"누르지 않으면 아무것도 안 남는다"* 는 거짓이었다.

### 3.7 👎는 운영자에게 **DM 으로** 간다 — 공개 표시는 하지 않는다

버려진 안(공개 리액션)이 실패한 이유가 그대로 설계 제약이다: **채널에 보이는 표시는 5명 팀에서
질문자를 지목한다.** 그래서 라우팅은 사설이다.

- 대상은 설정값 하나(`NEXUS_FEEDBACK_OPERATOR`, 슬랙 user id). **비어 있으면 DM 을 보내지
  않고 표 기록만 한다** — 설정 누락이 답변 경로를 죽이지 않는다(I6).
- DM 내용: 사유 코드 + **퍼머링크**(`chat.getPermalink(channel_id, message_ts)`). 질문·답변
  본문은 싣지 않는다 — 링크가 있으면 본문을 복사할 이유가 없고, 복사하는 순간 §3.5 가 거절한
  텍스트 저장이 DM 이라는 다른 경로로 되살아난다.
- 선행조건: `chat:write`(이미 있음) + DM 을 열기 위한 `im:write`. **`reactions:write` 는
  이제 필요 없다** — 공개 표시를 안 하기 때문이다.

**결속의 부수 효과.** `answer_key` 가 `(channel_id, message_ts)` 에 묶이므로 유출된 키를
**다른 메시지에서** 재사용하는 경로가 닫힌다. **그러나 원 메시지 값을 통째로 얻은 제3자**
(메시지 전달·워크스페이스 익스포트)의 투표는 막지 못한다 — 결속은 값의 이동을 막지 않는다.
"무기명 자격증명 문제가 해소된다" 고 단정하지 않는다(§7).

## 4. 불변식

- **I1 — 표에 신원이 없다.** 스키마에 principal·user_id·그 파생 해시 컬럼이 부재.
  검사: 컬럼 목록 단언.
- **I2 — `answer_key` 는 CSPRNG 이고 무엇에서도 파생되지 않는다.** "두 번 부르면 다르다" 는
  검사가 **아니다** — 카운터도, 타임스탬프도, `sha256(질의‖nonce)` 도 그 검사를 통과한다.
  엔트로피는 유한 표본으로 단언할 수 없다. 검사는 **소스 수준**이다: 발급 함수가
  `secrets.token_urlsafe` 를 부른다는 것 **그리고** 그 값이 DB 의 `answer_key` 컬럼에 그대로
  앉는다는 것을 — **경로를 실제로 실행해서** 확인한다. 소스 문자열 검사만 두면 이 리포가 이미
  기록한 거짓 초록 유형("사본이 정본 그물 밖", "등록이 `__main__` 가드 뒤")이 된다.
  (초안은 "그 호출에 질의·답변·신원이 인자로 안 들어감" 을 단언하라고 했는데,
  `token_urlsafe(nbytes)` 는 그런 인자를 받을 수조차 없어 **공허한 단언**이었다.)
- **I3 — `answer_key` 는 다른 어떤 표에도 적히지 않는다.** 특히 principal 을 가진 표
  (`a2a_audit`)와 **동거하지 않는다.** 검사: 스키마 전수 조회로 이 이름의 컬럼이 두 표
  (`answer_offered`·`answer_vote`)에만 있음을 단언. [[SPEC-nexus-query-text-retention]] 이
  `retention_key` 에 건 교차표 검사와 같은 모양이다.
- **I4 — 슬랙 사용자 id 는 어디에도 기록되지 않는다.** 스키마만 깨끗한 것으로는 부족하다:
  `block_actions` 페이로드는 `answer_key` 와 `slack_user_id` 를 **같은 객체**에 담아 오므로,
  핸들러의 로그 한 줄이면 §3.4 가 스키마에서 지운 투표자↔답변 연결이 로그에 복원된다.
  검사: 피드백 핸들러의 로그 호출에 사용자 id 필드가 없음을 단언하고, 페이로드를 통째로
  찍는 로깅을 금지한다.
- **I5 — 투표는 INSERT 다.** 검사: 한 `answer_key` 에 두 번 투표하면 행이 둘이다.
- **I6 — 피드백 실패가 답변을 죽이지 않는다.** 제안 쓰기는 best-effort. 검사: 저장이 예외를
  던져도 봇이 답을 보낸다. 그리고 제안 행이 없을 때 투표가 **버려지지 않는다**(§3.3).
- **I7 — 만료된 키는 투표를 못 받는다.** 검사: `offered_at` 이 30일보다 오래된 키로 투표하면
  거절된다. §3.2 가 "만료 없는 자격증명" 을 피하겠다고 했으므로 그 거절이 실제로 있어야 한다.
- **I12 — 포인터 행은 90일 뒤 지워진다.** 안 B 채택으로 `answer_offered` 가
  `channel_id`·`message_ts` 를 담고, §3.4·§7 이 그것을 **질문자 추정 경로**로 인정했다.
  "저장하는 것이 수와 사유 코드뿐이라 만료가 필요 없다" 는 **안 A 시절 문장**이고 지금은
  거짓이다. 만료 후에는 포인터 두 칸을 NULL 로 지우고 **수와 사유 코드는 남긴다** — 집계는
  살고 추정 경로는 죽는다. 검사: 91일 된 행의 `channel_id` 가 NULL 이고 그 행의 투표는
  여전히 세어진다.
- **I8 — 블록 예산.** 추가 블록을 붙인 뒤에도 메시지가 **세 상한을 전부** 지킨다: 메시지당
  블록 50개, `actions` 블록당 요소 25개, 텍스트 객체당 3000자. **어느 상한에 먼저 걸리는지는
  선언하지 않고 잰다** — `formatter.py` 의 블록 수는 근거 건수에 따라 변하므로 그것은 측정
  대상이지 주장할 것이 아니다. 검사: **`top_k` 상한(기본 10)만큼의 근거**를 가진 답변에
  버튼을 붙여 세 값을 전부 단언한다 — "최대 개수" 를 이름으로 고정하지 않으면 검사가
  임의 표본이 된다.
  (이 리포는 3000자 상한으로 첫 실사용 질문이 `invalid_blocks` 로 죽은 전례가 있다.)
- **I9 — 검색·답변 생성 무변경.** 검사는 구체적으로: 고정 요청 하나에 대해 `hybrid_search`
  와 `generate_answer` 가 받은 **kwargs 딕셔너리**를 이 SPEC 이전 커밋의 값과 비교한다
  (`tests/test_narration_user_query.py` 의 spy 방식 그대로). "무엇에 대해 같은지" 를 정하지
  않으면 검사가 아니라 문장이다.
- **I10 — 투표는 결속된 메시지에서만 받는다** (안 B). `block_actions` 페이로드의
  `(channel, message.ts)` 가 `answer_offered` 의 값과 다르면 거절한다. 검사: 같은
  `answer_key` 를 다른 채널·다른 메시지에서 보내면 거절되고 표에 행이 안 생긴다.
  **이것이 없으면 `answer_key` 는 30일짜리 무기명 자격증명이다** — 워크스페이스 익스포트나
  메시지 전달로 값이 새면 누구든 임의 횟수로 투표할 수 있고, 검사할 신원이 없으므로 사후
  구분도 안 된다.
- **I11 — 운영자 DM 에 본문이 없다.** 검사: DM 페이로드에 질의·답변 문자열이 없고
  퍼머링크와 사유 코드만 있다. 텍스트를 저장하지 않겠다는 결정이 다른 경로로 새면 안 된다.

## 5. 사전 등록한 규칙

### 5.1 무엇을 하면 행동하는가

- **👎 1건 = 조사 대상 1건.** 비율을 기다리지 않는다.
- **사유 코드가 어느 팀의 어느 수리를 가리키는지는 §3.1 의 표가 전부다.** 그 이상은 적지
  않는다 — 초안은 `ignored_format` 에 대해 "답변을 `format_compliance.check` 로 재채점하라" 는
  절차를 규정했는데, 둘 다 틀렸다:
  - **범위 밖이다.** 그것은 이 SPEC 의 유닛이 아니라 **다른 SPEC(서술 U2)의 주장에 대한
    반증 프로토콜**이고, 구현·검증 항목이 여기 없으므로 규정만 남는다.
  - **그리고 그 절차는 신고를 자동 확증한다.** `check(kind, answer, prior="")` 는 `prior` 에
    기본값이 있고, `shorter` 를 그 기본값으로 부르면 `shorter_than(answer, "")` 가 **항상
    False** 를 낸다(2026-08-14 실행 확인). 조사 절차가 "위반" 을 스스로 만들어낸다.

  조사는 사람이 스레드를 읽는 것이고, 그 사람이 무엇을 쓸지는 이 SPEC 이 규정하지 않는다.

### 5.2 비율을 말해도 되는 시점

**투표 30건 이상 그리고 제안 100건 이상**을 넘기기 전까지 어떤 비율도 산출·발표하지 않는다.
그 전의 수는 `n/N` 원시값으로만 보고한다.

통계적 검정력이 아니라 **자기구속**이다: 이 리포는 5회 표본으로 잡음 폭을 과소평가한 전례가
있고(5회 0.021 vs 10회 0.061), 작은 N 을 비율로 말하는 순간 그것이 근거로 굳는다.

### 5.3 이 기능 자체를 언제 기각하는가

**평가일은 달력으로 못 박는다: U2 머지 + 90일.** 그날 아래 두 수를 보고 셋 중 하나를 고른다.
"제안이 30건 쌓이면" 같은 **조건부 평가일은 규칙이 아니다** — 제안이 안 쌓이면 영원히 발화하지
않고, 기능은 기본값으로 살아남는다. §5.3 이 막겠다는 "조용한 방치" 가 정확히 그것이다.

- **소유자**: 디렉터(LivingLikeKrillin). **시작일**: U2 머지일. **평가일**: +90일.
- **판정 질의** (§6 이 뷰를 안 만들므로 이 두 줄이 관측 수단 전부다):
  ```sql
  SELECT count(*) FROM answer_offered WHERE tenant = $1 AND NOT synthesized;
  SELECT count(DISTINCT v.answer_key) FROM answer_vote v
    JOIN answer_offered o USING (tenant, answer_key)
   WHERE v.tenant = $1 AND NOT o.synthesized;   -- 분모와 **같은 모집단**
  ```
  분자에서도 `synthesized` 를 빼는 이유: 초안은 분모만 걸러서 **분모에 존재하지도 않는
  답변만으로 하한이 충족될 수** 있었다. §5.3 은 관측 수단이 이 두 줄뿐이라고 못 박았으므로
  이 불일치를 메울 다른 뷰가 없다.
  **투표는 행 수가 아니라 서로 다른 답변 수로 센다.** §3.1.1 (5)가 재클릭마다 행을 쌓으므로
  행으로 세면 **한 사람의 망설임 한 번이 문턱을 넘긴다.** 서로 다른 답변을 셀 수 있는 것은
  안 B 의 메시지 결속 덕분이다(안 A 였다면 이 줄을 못 썼다).

| 90일 뒤 관측 | 처분 |
|---|---|
| 제안 30건 미만 | **파일럿이 안 돈 것**이다. 이 기능이 아니라 파일럿을 본다. 평가일을 +90일 미룬다 — **1회만**. 두 번째 평가일에도 30건 미만이면 **버튼을 뗀다** |
| 제안 30건 이상 · 표를 받은 답변 **3개 미만** | **표면이 안 먹었다.** 버튼을 떼거나 자리를 옮긴다 |
| 제안 30건 이상 · 표를 받은 답변 3개 이상 | 유지. 비율은 여전히 §5.2 를 넘기기 전엔 말하지 않는다 |

여전히 **한 사람이 서로 다른 답변 셋에 눌렀는지** 팀 셋이 눌렀는지는 구분하지 못한다(§3.4 는
투표자를 기록하지 않는다). 구분하려면 투표자를 기록해야 하고 그 대가는 §3.5 에서 거절했다.
**"셋 미만" 이라는 하한만 반증 가능하다는 것을 그대로 적는다.**

§1.3 의 추정(월 10표)대로면 §5.2 의 투표 문턱 30건은 **약 3개월**이고, 제안 100건은 자원
응답률에 달렸다 — 응답률 10%면 제안이 월 100건이라 한 달, 응답률 50%면 다섯 달이다.
**둘 중 늦은 쪽이 실제 시점이고 지금은 그 값을 모른다.** 초안은 여기에 "10개월" 이라고
적었는데 그 수는 어느 전제와도 맞지 않았다. 아는 것만 적는다: 비율은 두 문턱을 **둘 다**
넘긴 뒤에야 말하고, 그 사이의 중간 상태는 위 표가 덮는다.

초안의 둘째 규칙("투표가 한 사람에게서만 오면")은 **삭제했다** — §3.4 가 그것을 구조적으로
관측 불가능하게 만들었고, 발화될 수 없는 조건은 규칙이 아니다.

## 6. 유닛

| 유닛 | 내용 | 위험 |
|---|---|---|
| U1 | 마이그레이션(표 둘) + `answer_key` 발급·**30일 만료 거절** + 제안 기록 + 투표 저장 + **메시지 결속 검증**(I10) | 낮음 — 표면 없음 |
| U2 | 슬랙 버튼·사유 ephemeral + `block_actions` 핸들러 + **운영자 DM 라우팅**(§3.7) | 낮음 — 실패해도 답변은 나감(I6) |

**뷰·집계·대시보드는 유닛이 없다.** §5.2 를 넘기기 전에는 읽을 것이 없고, §5.3 은 COUNT 두
줄로 판정한다. **행 만료 유닛도 없다** — 저장하는 것이 수와 사유 코드뿐이라 만료시킬 텍스트가
없다(I7). 만료가 걸리는 것은 `answer_key` 의 투표 수용이고 그것은 U1 안이다.

## 7. 한계

- **자원 응답 편향은 설계로 못 없앤다.** 분모를 남기는 것은 편향을 없애는 게 아니라
  **보이게** 하는 것이다.
- **타임스탬프 근접은 남는다.** `answer_offered.offered_at` 과 `a2a_audit` 의 시각이 가까우면
  "이 시각의 질의가 👎를 받았다" 정도는 추정된다. 시각을 뭉개는 완화는 **하지 않는다** —
  하루 답변이 몇 건뿐이라 시간 단위로 뭉개도 상관성이 남고, 그건 보호가 아니라 연극이다.
  실질 보호는 §3.4·§3.5 로 **이 표에 신원도 텍스트도 없다**는 것이다.
- ⚠ **이 SPEC 밖의 결함: 보존된 질문에서 principal 이 역산된다.** `search_query_text` 는
  질문을 평문으로 담고 `a2a_audit.query_sha256` 은 소금 없는 `sha256(query)` 이므로,
  평문 → 해시 재계산 → principal 로 이어지는 **결정적 경로**가 이미 배포돼 있다.
  [[SPEC-nexus-query-text-retention]] 이 `retention_key` 에 건 소금은 키 동등 조인만 막고
  이 재계산은 못 막는다 — 그 SPEC 이 주장한 *"조인할 대상이 없는 것이 약속보다 강하다"* 는
  **자기가 저장한 평문에 대해서는 성립하지 않는다.**
  2026-08-14 라이브 확인: 실제 재식별 **0/1** 이지만 그것은 설계가 막아서가 아니라
  **표면이 아직 안 겹쳐서**다(보존 허용목록은 `slack-bot`, `a2a_audit` 에는 테스트
  principal 둘뿐). A2A principal 이 허용목록에 들어가거나 같은 질문이 양쪽에 생기는 순간
  이어진다. **이 SPEC 은 그 구멍을 고치지 않는다 — 가리키지 않을 뿐이다**(§3.5).
  별도 수리가 필요하고, 그것은 이 SPEC 의 유닛이 아니다.
- **사유 넷은 사용자의 어휘가 아니라 우리의 어휘다.** 넷 중 어디에도 안 맞는 실패는 아무거나
  눌리거나 안 눌린다. 그 오차는 이 설계 안에서 관측되지 않는다.
- **"근거가 틀렸다" 는 사용자가 옳다는 뜻이 아니다.** 신고는 단서이지 판정이 아니다.
- **같은 사람의 반복 투표를 못 막는다** (§3.4 의 대가). 메시지 결속(I10)이 막는 것은 **다른
  메시지에서의 재사용**이지 같은 메시지에서의 재클릭이 아니다.
- **운영자는 질문자를 추정할 수 있다** (안 B 의 대가, §3.4·§2). 새로 열리는 것은 접근 권한이
  아니라 "이 답이 나빴다" 는 사실이지만, 5명 팀에서 질문자와 투표자는 대개 같은 사람이다.
  **이것은 완화되지 않는다** — 완화하는 척하지 않고 적어 둔다.
- **원 메시지 값을 통째로 얻은 제3자는 투표할 수 있다.** 메시지 전달·워크스페이스 익스포트로
  `answer_key` 와 `(channel_id, message_ts)` 는 **함께** 샌다. I10 의 결속은 값의 이동을 막지
  않는다. 막으려면 투표자 신원을 검사해야 하고 그 대가는 §3.5 에서 거절했다.
- **아티팩트의 수명은 슬랙이 정한다.** 우리는 포인터만 갖고 있으므로 무료 플랜의 90일 이력이
  지나거나 메시지가 지워지면 퍼머링크는 죽은 링크가 된다. 그때 그 신고는 사유 코드로만 남는다.

## 8. 미해결

- **자유 텍스트.** 가장 정보량이 많지만 PII 표면이다. 스캐너·격리 경로 설계가 필요.
- **테넌트 매핑을 두 번째 조직까지 미룰 수 없는 부분이 있다.** U1 마이그레이션이 지금 값을
  넣어야 하므로, **봇 설정의 `NEXUS_TENANT` 를 그대로 쓴다**(오늘 단일값). 그리고 §5.3 의
  판정 질의 두 줄에 **`WHERE tenant = $1` 을 반드시 붙인다** — 두 번째 워크스페이스가 붙는
  순간 분모·분자가 테넌트를 넘어 합산되면 기각 판정이 오염된다. 워크스페이스·채널 → 테넌트
  매핑 자체는 [[khala-tenant-clearance-vocabulary-limit]] 과 같은 트리거로 미룬다.
- ~~**보존 질문 → principal 역산 결함**(§7)의 수리~~ → [[SPEC-nexus-audit-query-hash]] 로
  분리됐다. ⚠ 여기 적었던 후보(*"테넌트로 소금 치는 것"*)는 **틀렸다** — 테넌트는 비밀이
  아니므로 평문을 가진 사람이 그 값을 그대로 다시 계산한다. 그 SPEC §1.4 가 철회한다.
- **90일 뒤 슬랙 아티팩트가 사라지는 것**을 받아들일지. 표시된 스레드만 따로 보존하는 것은
  결국 텍스트 저장이라 §3.5 의 결정을 되돌리는 일이다 — 되돌리려면 새 결정이 필요하다.
- **운영자가 여럿이 되면** `NEXUS_FEEDBACK_OPERATOR` 단일값으로는 부족하다. 지금은 한 명이다.
- **`shorter_than(answer, "") == False` 를 고정하는 검사가 없다** (§5.1 이 초안 규칙을 지운
  근거). 그 기본값이 바뀌면 삭제 근거가 조용히 무효가 되고 문서엔 결론만 남는다 —
  **U1 에서 그 반례 검사를 `tests/test_format_compliance.py` 에 함께 넣는다.**
- **Langfuse.** [[khala-llmops-assessment]] 가 Scores API 로 품질 신호를 주입하기로 정해 뒀다.
  이 표를 거기 태울지는 이 SPEC 이 정하지 않는다 — **전송은 조직 밖으로 나가는 일**이라
  별도 결정이다.
