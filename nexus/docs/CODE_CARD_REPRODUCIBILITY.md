# 코드 카드 재현성 — 같은 코드에 같은 카드를 쓰는가

`SPEC-nexus-code-semantic-cards` §3.3 · §6.1 의 측정 기록.

**이 측정이 왜 먼저인가.** 카드 방향 전체가 하나의 비싼 가정 위에 서 있다 — *모델이 코드를
업무 언어로 충실하고 **반복 가능하게** 서술할 수 있다*. 그 가정이 틀리면 아래 어떤 것도 설계할
값어치가 없다: 카드를 임베딩해 문서와 매칭하면, 재는 것이 코퍼스의 성질이 아니라 **생성기의
잡음**이 된다.

이 리포는 같은 실수를 이미 한 번 했다. 배포 스크린샷 판독기가 같은 그림에 **84.7% 다른 글**을
내는 것을 SPEC 을 네 개 쓴 뒤에 발견했고, 그때까지 쌓은 근거 32건이 전부 잡음이었다
(`SPEC-nexus-vision-reproducibility`). 그래서 순서를 뒤집었다: **잡음 폭을 먼저 재고**,
숫자가 나온 뒤에 매칭을 설계한다.

## 계측기

`scripts/card_reproducibility.py`. 출하될 생성자를 그대로 부른다 (§3.3) — 프롬프트·홉 수·모델이
카드에 실리는 `generator_id` 와 같아야 하고, 다르면 무엇의 재현성인지 말할 수 없다.

| | |
|---|---|
| 지표 | 같은 심볼 여러 실행의 `domain_terms` **Jaccard**, 쌍 평균 (`index/cards.py:term_agreement`) |
| 정규화 | 소문자·공백만. **동의어 병합 없음** — 재려는 것이 그 흔들림이다 |
| 표본 | 카드 후보 중 **파일당 하나**씩 흩어 고른다(닮은 심볼만 재면 생성기가 실제보다 안정적으로 보인다) |
| 백엔드 | 선언 없이는 돌지 않는다(`NEXUS_LLM_PROVIDER`). dev 측정은 keyless 브리지 — **지출 0** |
| 트리 | 더러운 체크아웃은 거부. 스캔 커밋을 함께 찍는다 |

## 사전등록 판정 규칙

**데이터를 보기 전에 적는다.** 이 리포는 재본 적 없는 수로 문턱을 만든 적이 있고(ADR-0008 §5(b)),
반대로 결과를 보고 판정 기준을 옮긴 적도 있다.

1. **1차 판정** = 심볼 ≥10개 · 실행 ≥5회의 **평균 일치도** 대 SPEC §6.1 문턱 **0.70**.
2. 평균과 함께 **최저·최고·심볼별 값**을 낸다. 평균만 보면 "대체로 되는데 어떤 종류에서
   전혀 안 되는" 모양을 놓친다.
3. **문턱은 결과를 보고 바꾸지 않는다.** 0.70 은 잠정값이고 검색 결과에서 유도된 값이 아니다 —
   매칭 층이 코퍼스가 아니라 생성기 잡음을 재지 않게 두는 바닥이다. 부적절하다고 판단되면
   그 판단은 **다음 SPEC 개정**에서 근거와 함께 하고, 이 측정의 판정은 그대로 남긴다.
4. **범위(최저~최고)로 전칭 주장을 하지 않는다.** 실행 5회의 범위는 10회보다 좁게 나온다 —
   range 는 편향된 추정량이다(멀티턴 측정에서 5회 0.021 vs 10회 0.061 을 실제로 봤다).
5. 규칙 재검사(`check_card`)에 걸려 버려진 카드 수를 함께 낸다. **버려진 것을 빼고 잰 일치도는
   생성기가 아니라 필터의 성질이다.**

## 결과 (2026-08-17)

생성자 `claude-sonnet-4-6·cards-v1·hops2`, 대상 저장소 = Java 1,292 파일(미파싱 0),
스캔 커밋 고정. 백엔드는 keyless 브리지 — **호출 180건, API 지출 $0.**

| 실험군 | 모집단 | 심볼 | **평균** | 최저~최고 | 문턱 넘은 심볼 | 버려진 카드 |
|---|---|---:|---:|---|---:|---:|
| **A** (1차·사전등록) | 파일당 첫 후보 | 12 | **0.303** | 0.117~0.800 | 1 | 10/60 |
| **B** (대조) | 씨앗 고정 무작위 | 11 | **0.227** | 0.017~0.518 | 0 | 8/60 |
| **C** (대조) | 무작위 · 테스트 제외 · 본문 ≥15줄 | 11 | **0.263** | 0.080~0.733 | 1 | 5/60 |

**판정: 미달.** 사전등록 규칙대로 1차(A)의 **0.303 vs 문턱 0.70** 이 판정이고, 대조군 둘이
같은 자리를 다시 짚는다. 심볼 34개 중 문턱을 넘은 것은 **2개**다.

### 세 실험군이 필요했던 이유

A 는 파일은 흩었지만 경로 정렬을 그대로 따라가서 알파벳 앞쪽 한 패키지의 요청·응답 DTO 만
뽑혔다. 그 표본으로는 낮은 수가 **생성기의 성질인지 그 묶음의 성질인지** 구별할 수 없다.
B 는 무작위로 흩었더니 12개 중 **10개가 테스트 코드**였다 — `setUp` 을 업무 용어로 서술하라는
요구에는 안정된 답이 있을 수 없고(0.017·0.062), 그건 생성기가 아니라 **모집단의 결함**이다.
C 가 테스트를 빼고 실제 도메인 코드만 남겼다. **세 모집단에서 값이 움직이지 않았다.**

### 값이 어디서 낮은가 — 방향에 불리한 쪽이다

| 심볼 종류 (C 실험군) | 본문 | 일치도 |
|---|---:|---:|
| 응답 DTO (데이터 모양) | 35줄 | 0.733 |
| 결과 record | 25줄 | 0.556 |
| 공통 엔티티 상위 클래스 | 26줄 | 0.427 |
| 필터 (횡단 관심사) | 64줄 | 0.267 |
| 조회 서비스 (실제 도메인 행동) | 219줄 | **0.093** |
| 리포지터리 인터페이스 | 83줄 | **0.115** |
| 인프라 설정 클래스 | 35줄 | **0.080** |

안정된 것은 **데이터 모양을 가진 작은 타입**이고, 흔들리는 것은 **행동을 가진 코드**다.
이 방향이 카드를 원하는 이유가 정확히 후자다 — 정책·설계 문서가 말하는 것은 필드 목록이
아니라 행동이다. 그래서 이 결과는 표본을 고쳐서 나아질 성질이 아니다.

### 계측기 쪽에서 같이 나온 결함 셋

1. **모집단에 테스트 코드가 있다.** `scan_repo` + `is_card_candidate` 는 테스트를 걸러내지
   않는다. 하니스에 `--exclude-tests` 를 뒀지만, 이건 **후보 규칙(§3.1)** 이 져야 할 몫이다.
2. **span 이 너무 좁다.** `code_terms 가 span 에 없음` 으로 버려진 카드들은 모델이 감싼
   클래스 이름을 코드 용어로 낸 경우다. 규칙은 옳고(카드는 span 에 근거해야 한다) 준 것이
   메서드 본문뿐인 것이 문제다. 한 심볼은 이 사유로 5회 전부 버려져 측정에서 빠졌다.
3. **검증 애노테이션이 식별자 규칙에 걸린다.** `@Size`·`@Getter`·`@NotBlank` 는 DTO 에서
   정당한 코드 용어인데 맨 식별자만 허용해 거부된다.

`is_card_candidate` 가 `class`·`interface`·`record`·`enum` 을 **길이 무관하게** 후보로 잡는
것도 같은 계열이다 — 본문 5줄짜리 부트스트랩 클래스가 A 실험군의 첫 심볼이었고 일치도 0.117 이었다.

## 이 측정이 닫는 것과 남기는 것

- **닫는다:** 카드를 임베딩해 문서와 맞추는 단위는 이 생성자·이 프롬프트(`cards-v1`)로
  **진행하지 않는다.** 매칭 층을 얹으면 재는 것이 코퍼스가 아니라 생성기 잡음이 된다.
  SPEC §6.1 게이트는 **세 모집단에서 미달**이다.
- **남긴다:** 이 수는 `domain_terms` **문자열**의 안정성이다. 같은 뜻을 다른 낱말로 쓴 경우도
  불일치로 센다(정규화는 소문자·공백뿐 — 의도된 설계다). 카드의 산문(`subject`·`behavior`)이
  더 안정적인지는 **재지 않았다.** 그것을 재려면 다른 지표가 필요하고, 지표를 바꾸는 것은
  이 문서가 아니라 SPEC 개정의 몫이다.
- **다음에 무엇을 하든 재측정이 조건이다.** 프롬프트를 고치거나 모델을 바꾸거나 후보 규칙을
  좁히면, 그것은 새 생성자다 — `generator_id` 가 바뀌므로 이 표는 그 생성자에 대해 아무것도
  보증하지 않는다.
