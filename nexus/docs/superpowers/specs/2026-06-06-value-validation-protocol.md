# 가치 검증 프로토콜 — "이 도구가 쓸모 있는가"

> 작성일: 2026-06-06
> 대상: 도메인 불변식·값 거버넌스 (#17) MVP 값조회 쐐기
> 성격: 사전 등록(pre-registered)·반증 가능·교란 통제. 빌드 후 *이걸로* go/no-go.

---

## 0. 왜 이 문서가 따로 필요한가

리서치 결론: 이 부류 시스템의 진짜 실패는 **기술이 아니라 "기획자가 실제로 쓰고 믿느냐(#4)"**이고, 그건 **설계로 답이 안 나오고 경험으로만** 갈린다. 그래서 "쓸모"를 *증명/반증*하는 절차를 코드와 분리해 사전에 못 박는다. **합격선을 사후에 바꾸지 않는다(post-hoc 합리화 금지).**

---

## 1. 검증할 가설 (경쟁 가설로)

- **H1 (우리 베팅):** 잠재 수요는 있고, 막던 건 UX였다. 비엔지니어가 자연어로 묻고 코드앵커 답을 받으면, 낡은 Notion보다 이걸 1차 신뢰원으로 쓴다.
- **H2 (귀무/회의):** 기획자는 *사실*보다 *해석·책임*을 원해서 그냥 엔지니어에게 묻는 걸 선호한다. 도구가 답을 줘도 1차로 안 쓴다.

이 테스트는 **H1을 H2에 대해 검증**한다. (둘 다 "지금까지 좋은 UX가 없었다"와 양립하므로, 단순 사용성 호평으로는 안 갈림 — 아래 교란통제 참조.)

---

## 2. 사전 등록 합격선 (스펙 §11과 동일, 변경 금지)

| 지표 | 합격 기준 |
|---|---|
| **채택률** | 기획자 **≥3명 × 실제 질문 ≥10건**에서, 도구 답을 **≥80%** 1차 신뢰원으로 채택 |
| **stale 적발** | 기간 중 **≥1건**, 코드와 어긋난 기존 문서(Notion 등)를 도구가 드러냄 |
| **정확성 전제** | 채택된 답의 **코드 대조 정확도 100%** (틀린 답을 채택시키면 무효 — 신뢰성=캘리브레이션 위반) |

→ **3개 모두 충족 = GO** (boolean 불변식·요구·전처리 단계로 확장).
→ 채택률 미달 = **H1 기각** → 범위 축소/중단 재검토.
→ 정확성 깨짐 = 즉시 중단(가치 이전에 신뢰 붕괴).

---

## 3. 셋업

1. **시드 데이터** (실제 pfplay):
   - 핵심 개념 8~10개를 Khala entity로 + 코드앵커 (준회원, 파티룸, 플레이리스트, 재생곡, DJ큐, 크루, 게스트, 정회원...).
   - value-bearing claim 5~10개를 **실제 코드 상수**로 (준회원 플레이리스트 한도, 재생곡 제한시간 등 — 날조 금지).
2. **참가자:** 실제 pfplay 서비스 기획자 **2~3명**. (도구를 만든 사람 제외 — 자기검증 편향 차단.)
3. **비교 기준선:** 각 기획자의 *현재* 방법(Notion 검색 / 엔지니어에게 질문)을 같은 질문에 병행.

---

## 4. 질문 소싱 — 날조 금지

- **실제 질문만** 쓴다. 출처: 최근 기획·운영 회의록, Slack 로그에서 "이거 지금 어떻게 돼 있죠?"류 질문 수집. 또는 실제 기획 세션 중 라이브로 발생한 질문.
- 도구가 답하기 좋은 질문만 고르지 않는다 → **§6 miss율로 커버리지 편향을 정직하게 측정.**

---

## 5. 측정 프로토콜 (질문당)

각 질문에 대해 기록:

| 항목 | 측정 |
|---|---|
| a. 도구가 답했나 | yes / no(miss) |
| b. 답이 코드와 맞나 | 검증자(엔지니어)가 코드 대조 → correct / wrong |
| c. **1차 신뢰원으로 채택했나** | 기획자가 "이 답을 믿고 의사결정에 쓰겠다" → adopt / reject |
| d. 현재 방법 대비 시간 | 도구 vs Notion/엔지니어 (초 단위 대략) |
| e. stale 적발 | 도구 답 ≠ 기존 Notion 문서 → 기존이 낡았던 사례인가 |
| f. (reject 시) 이유 | "왜 엔지니어에게 물을 건가" 자유응답 ← **H2 직격 신호** |

---

## 6. 교란 통제 (이게 없으면 거짓 GO)

| 교란 | 위험 | 통제 |
|---|---|---|
| **신규성 편향** | 새로워서 잠깐 쓰는 것 | **2주 지속 사용** 후 채택률 재측정. day-1 호평만으로 GO 금지 |
| **커버리지 편향** | 시드된 개념 질문만 잘됨 | **miss율 별도 보고**. miss가 높으면 "쓸모"의 분모가 작다는 뜻 — 정직 표기 |
| **H2 위장** | "좋아요"라 하지만 실제론 엔지니어에게 또 물음 | c는 *말*이 아니라 *행동*(실제 의사결정에 썼나)으로. f로 교차확인 |
| **관찰자 효과** | 만든 사람 앞이라 후하게 답함 | 가능하면 비관여 관찰자/자기기록 로그. 익명 피드백 1회 |
| **정확성 착시** | 그럴듯하지만 틀린 답을 채택 | b를 c의 *전제*로. wrong을 adopt하면 그 건은 실패로 집계 |

---

## 7. 산출 & 결정

- **결과 리포트:** 채택률 %, miss율 %, stale 적발 건수, 정확도, reject 이유 분류(특히 H2형).
- **결정 게이트:**
  - 3 합격선 충족 → GO. 다음 단계(boolean 불변식 검증 → 기획문서 전처리).
  - 채택률만 미달 → reject 이유 분석. UX 문제면 1회 개선 후 재시도, H2형이면 기각.
  - 정확도 깨짐 → 중단(신뢰성 결함 우선 해결).

---

## 8. 정직한 타당성 위협 (결과 해석 시 명시)

- 표본 2~3명은 통계가 아니라 **신호**다. GO는 "확실"이 아니라 "다음 단계 베팅 정당화".
- 단일 조직(pfplay)·단일 도메인 → 일반화 주장 금지.
- 2주는 "지속"의 하한선이지 장기 유지(shelfware 여부)를 증명하진 못함 → 확장 단계에서 재관찰.
- miss율이 높으면 채택률 80%가 "작은 분모 위의 80%"일 수 있음 — 분모(커버 가능 질문 비율)를 함께 보고.

---

## 부록 — 이 프로토콜이 빌드 계획과 맺는 관계

구현 계획(writing-plans 산출)의 **마지막 마일스톤 = 이 프로토콜 실행**이다. 즉:
`코드 소스 추출기 → value-bearing claim rtype → MVP 값조회(Khala MCP/Web) → ★ 본 프로토콜 실행 → go/no-go`.
GO 전에는 boolean 불변식·전처리 단계에 착수하지 않는다(YAGNI + 리스크 선소거).
