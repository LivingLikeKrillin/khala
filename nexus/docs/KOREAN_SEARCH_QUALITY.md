## 1. 왜 필요했나

`tests/test_search_recall.py` 는 **자체 회귀 가드로는 유효하지만 토크나이저 비교기로는 설계상
불가능**했다. 이유가 둘이고, 둘 다 이번 작업 내내 반복해서 발목을 잡았다.

1. **기대 어휘를 못박았다.** 질의마다 "이 어휘가 매칭을 지탱한다"를 적었는데, 그 어휘는 mecab 의

   불가능하다. 무엇을 해도 만점이 나온다.

→ 새 자의 제1규칙: **판정은 "정답 문서를 찾았나" 이고, "토큰 X 가 있나" 여서는 안 된다.**

### 2.1 코퍼스 팩 (Pack A)

`kubernetes/website` 한국어 문서 265건, 커밋 `b035ea80` 으로 핀, CC BY 4.0.
`nexus/tests/eval/ko/corpus/` 에 커밋되어 있다.

**Notion 미러를 기각한 이유는 기술이 아니라 공개성이다** — 리포가 public이라 조직 내부 문서를
재배포하게 된다. 대신 같은 종류(한국어 기술 문서, 외래어 조밀)의 공개 대역을 쓴다.

정규화 규칙은 **측정해서 정했다.** 2,872개 숏코드 중 `text="…"` 를 가진 것이 464개, 그중 387개가
한글이다. 초안대로 "숏코드 태그를 지운다" 였으면 `{{< glossary_tooltip text="파드" … >}}` 가
통째로 사라져 **외래어 층이 재려던 어휘 자체가 없어졌다.**

```bash
cd nexus
python -m scripts.ko_eval_pack build    # 업스트림에서 다시 만든다 (네트워크)
python -m scripts.ko_eval_pack verify   # 커밋된 팩 ↔ 매니페스트 (오프라인)
python -m scripts.ko_eval_pack check    # 선택 규칙을 업스트림 트리에 재적용해 대조
```

`check` 가 있는 이유: 매니페스트만 자기검증하면 **첫 실행이 낸 것이 곧 표준**이 된다. 규칙과 팩이
어긋나면 규칙이 이긴다.

### 2.2 라벨 45건

`nexus/tests/eval/ko/labels.yaml` — 답변가능 40건(5층 × 8) + 답변불가 5건.

| 층 | 재는 것 |
|---|---|
| `loanword` | 외래어 표기 변이 (`파드`↔`Pod`, `앱아머`↔`AppArmor`) |
| `compound` | 복합명사 분해 (`퍼시스턴트볼륨클레임`) |
| `particle` | 조사 결합 |
| `mixed` | 한영 혼용 (`노드에 taint 를…`) |
| `spacing` | 띄어쓰기 변이 (`스테이트풀 셋`↔`스테이트풀셋`) |

**게이트가 곧 자의 신뢰성이다** (`scripts/ko_eval_labels.py`):

- `token|lexeme|morpheme|term|expected_word` 를 담은 키는 **어느 깊이에서도 못 들어온다.** 옛
  스위트를 비교 불가로 만든 결함을 관례가 아니라 **표현 불가능성**으로 막았다.
- gold 는 팩 상대 경로 전체여야 한다(접두사 금지). 예전에 8자 접두사가 두 페이지에 걸려 정답
  1위를 '회귀'로 기록한 적이 있다.
- 질의가 정답 문서의 **전체 제목**(6자 이상)을 품으면 실패한다. 짧은 제목(`노드`·`파드`)은
  검사하지 않는다 — 그러면 외래어·복합명사 층이 쓸 어휘가 없어진다.
- `authored_by: agent` 인데 `reviewed_by` 가 비면 실패한다. 검토 기록 없는 "사람이 봤다"는
  이름만 지키는 금지다.
- 층별 **정확히 8건**.

라벨 리비전은 gold 가 늘 때마다 올라가고(현재 2), **바닥값은 리비전을 인용**한다 — 라벨이
바뀌었는데 바닥값이 그대로면 테스트가 막는다.

### 2.3 하니스

`scripts/ko_eval_harness.py`. 다리는 청크를 돌려주므로 **문서로 접은 뒤 문서 10개** 안에서
잰다(청크 10개 창이 아니다 — 한 문서가 청크를 여러 개 올리면 두 읽기가 크게 갈린다).

- 지표: `Recall@10` · `MRR@10` · 미스, **다리별**(keyword / vector / fused)로 낸다. 토크나이저는
  키워드 다리 말고는 못 건드리므로, 융합 숫자로 읽은 토크나이저 판정은 희석된 판정이다.
- 융합은 **프로덕션 `_rrf_fusion` 을 그대로 부른다.** 평가용으로 다시 구현하면 fused 숫자가
  사용자가 겪는 것과 다른 뜻이 된다 — AST 테스트가 호출이 사라지면 실패한다.
- 분모는 **답변가능 40건**. 답변불가 5건은 어떤 집계에도 안 들어간다(Nexus 에 기권 기제가 없어
  잴 것이 없다; 멀티턴 작업의 첫 재료로 남겨둔 것).

### 2.4 판정 규칙 (숫자가 나오기 **전에** 고정)

1. 질의별 승패 = 키워드(또는 벡터) 다리 `Recall@10`, **동점이면 MRR 로 깬다.** 265문서에서
   Recall 은 대부분 동점이라, 동점을 버리면 분해가 옮기는 정보를 통째로 버린다.
2. 양측 정확 이항검정(부호검정), α = 0.05.
3. **불일치쌍 6개 미만이면 p 값을 내지 않는다.** 6–0 이라야 p≈0.031 이므로 그 아래에서는 검정이
   애초에 결론을 낼 수 없다. 그 상태를 "차이 없음"이라 적는 것이 지표가 자기 둔감함을 세탁하는
   방법이다 — 우리는 **"검정력 부족"** 이라고 쓴다.
4. 층별 수치는 **서술용**이다. 8건짜리 층은 아무것도 결정하지 못한다.
5. 결론 못 내면 **현직 유지** — 측정 안 된 이득에 교체 비용을 내지 않는다.

## 3. 굵직한 이슈들

### 3.1 같은 질의·같은 코퍼스인데 결과가 달랐다 (수정 완료)

**내용.** 바닥값을 박으려는데 같은 팩을 다시 적재할 때마다 `Recall@10` 이 0.700~0.775, 미스가
9~12 로 흔들렸다. tsvector 전체 md5 는 동일했다.

**증거.**

- `md5(string_agg(tsvector_ko::text, '|' ORDER BY source_uri, chunk_index))` 가 적재본 간 일치 →
  색인 내용은 같다.
- 같은 적재본에 같은 질의를 반복하면 항상 같은 결과 → 질의는 결정적이다.
- **적재를 다시 하면** 달라진다 → 물리적 행 순서가 축이다.
- `ts_rank_cd` 동점이 빽빽하다: 상위 25행에 서로 다른 점수가 13~16종뿐.

**원인.** `_bm25_search` 의 `ORDER BY rank_score DESC` 에 전순서 키가 없다. 동점 안 순서가 힙
순서를 따라가고, 그게 `LIMIT 20` 경계와 문서 접기(top-10)를 흔든다.

**적용** (`SPEC-nexus-deterministic-retrieval-order`, 12이슈 전량 수용 후 승인):

```sql
ORDER BY rank_score DESC, c.rid ASC     -- 키워드 다리
ORDER BY distance ASC,   c.rid ASC      -- 벡터 다리
```
```python
sorted(scores.values(), key=lambda x: (-x["score"], x["rid"]))   # _rrf_fusion
```

융합에 키를 **명시**한 이유: 안정 정렬에 기대면 융합 순서가 입력 구성 순서에 좌우되고,
`heapq.nlargest` 나 병렬 병합으로 리팩터하는 순간 비결정성이 조용히 돌아온다.

**검증** (`tests/test_search_determinism_db.py`):

- **같은 테넌트에 3회 재적재** 후 결과 순서가 바이트 단위로 같아야 한다. 테넌트를 바꾸면 rid 가
  테넌트를 품고 있어 순서가 **정당하게** 달라진다 — 이 테스트의 첫 버전이 그래서 틀렸고, 게이트
  비평이 코드 전에 잡았다.
- 사용자가 보는 층(`hybrid_search` 결과)에서도 확인한다 — 다리만 봐서는 접기 단계가 안 덮인다.
- 구조 검사: 각 `ORDER BY` 가 기본키로 끝난다. 경험적 비교는 우연히 통과할 수 있지만 이건 못 한다.

**남은 것.** 벡터 다리는 `idx_chunk_vector` 가 **ivfflat(ANN)** 이라 동점 정렬은 결정적이 됐어도
**후보 집합**은 보장되지 않는다. SPEC 이 이를 명시하고, 테스트는 실패 시 "정렬 키가 깨졌다"가
아니라 "후보 집합이 흔들렸다"로 읽히도록 메시지를 붙였다.

### 3.2 긴 청크가 벡터 검색에서 조용히 사라진다 (기록·유예)

**내용.** Ollama 의 `nomic-embed-text` 는 창(2,048토큰)을 넘는 입력을 **거부**한다
(`HTTP 500 · the input length exceeds the context length`). `PARAMETER num_ctx 8192` 로 파생 모델을
만들어도 올라가지 않는다.

이 팩에서 **1,906청크 중 10건(0.5%)** 이 걸렸다 — 가장 짧은 거부 청크가 3,324자, 가장 긴 것이 8,163자다.

> **정정.** 처음엔 232건(12.2%)이라고 적었다. `"가"*n` 이분탐색으로 얻은 문자 한계(≈2,042자)를
> 실제 청크 길이 분포에 그대로 적용한 추정이었는데, 순수 한글은 글자당 약 1토큰이고 실제 한국어
> 기술 문서는 라틴 식별자·공백·마크다운 덕에 훨씬 적게 든다. **20배 틀렸고, 팔을 실제로 돌려서야
> 알았다.** 게이트 비평(I-016)이 "토큰 수치는 문자 측정에서 유도된 추론"이라고 경고했는데도 그
> 추론으로 모집단을 셌다. 지금 숫자는 추정이 아니라 실행 결과다.

**프로덕션에서 무슨 일이 일어나나.** `providers/embedding.py` 가 3회 재시도 후 예외 →
`index/embed.py` 가 삼키고 `False` 반환 → 그 청크는 `embedding = NULL` 로 남는다. **벡터 다리에서
영구히 안 보이고, 아무 데도 집계되지 않는다.** `index/embed_health.py` 는 세대 혼재는 보지만
미임베딩 비율은 보지 않는다.

**평가에서의 적용.** 거부를 중단 사유로 두면 그 팔이 아예 측정 불가가 되고, 무엇보다
**프로덕션이 겪지 않는 상태**를 재게 된다. 그래서:

- 거부를 **행으로 남긴다**(`status='refused'` + 백엔드 메시지 원문), 임베딩과 합쳐 팩의 청크 수와
  맞아야 한다. 둘 중 어느 쪽도 아닌 청크는 커버리지가 아니라 **설명되지 않는 구멍**이라 중단.
- 거부된 청크는 **없는 것으로 채점**한다 — 프로덕션의 NULL 과 같은 상태.
- **커버리지를 판정보다 위에 적는다.** 이 팩에선 격차가 작지만(99.5% vs 100%), 그건 코퍼스 길이
  분포의 성질이지 상수가 아니다 — 작아서 안 적는 게 아니라, 작은지 큰지를 보이려고 적는다.
- **조용한 절단은 여전히 중단 사유다.** sentence-transformers 는 `max_seq_length` 에서 말없이
  자르므로, KURE 팔은 인코딩 전에 자기 토크나이저로 길이를 센다. Ollama 는 반대로 거부하므로
  "자르지 않았다"가 관측으로 확인된다.

**범위 제한.** 0.5%는 **Pack A 형태의 코퍼스에 대한 수치**다. Notion 문서는 길이 분포가 달라
그대로 옮겨지지 않는다. 옮겨지는 것은 비율이 아니라 **실패가 조용하다**는 사실이다.

**유예와 트리거.** 소유자 LivingLikeKrillin. 트리거 = **청킹 설정·프로덕션 임베딩 모델·
`embed_health.py` 중 하나가 처음 바뀔 때.** 각각 커밋을 남기므로 기억이 아니라 로그에서 확인된다.

### 3.3 토크나이저 판정 — mecab-ko 유지는 이제 측정된 판단이다

**방법.** nori 를 **토크나이저로만** 썼다: OpenSearch `_analyze` 로 토큰만 받아 우리
`tokens_to_tsquery` · 우리 tsvector · 우리 `ts_rank_cd` 에 넣는다. 그러면 ADR-0008 §2.6 이 기록한
교란 둘이 사라진다.

- **엔진 교란** — 예전 탐색은 OpenSearch `match`+BM25 대 Postgres `to_tsquery`+`ts_rank_cd` 였다.
- **품사 필터 교란** — mecab 팔만 `_INCLUDE_POS` 로 걸러지면 그 차이를 "분해 차이"라 부르게 된다.
  `explain: true` 로 품사를 받아 **같은 allow-list 를 우리 코드에서** 적용한다.

두 팔은 **같은 테넌트를 순서대로** 쓴다 — rid 가 테넌트를 품으므로 테넌트가 다르면 동점 정렬
키까지 달라져 토크나이저와 무관한 차이가 승패에 섞인다.

**결과** (라벨 rev2, 리포트 `tests/eval/reports/2026-08-03-mecab-vs-nori.md`)

| 다리 | Recall@10 | MRR@10 | 미스 |
|---|---:|---:|---:|
| keyword/mecab-ko | 0.783 | 0.565 | 4 |
| keyword/nori-mixed | 0.850 | 0.578 | 3 |

nori 7승 2패 31무, 불일치쌍 9(검정력 조건 충족), **p = 0.180 → 이 표본에서 측정 가능한 차이 없음
→ mecab-ko 유지.**

**해석의 한계.** ADR-0008 §5(b) 는 **닫히지 않는다.** (b)는 "khala 자신의 코퍼스"를 요구하는데
Pack A 는 같은 종류의 공개 대역이다. 리포트 머리말이 그 문장을 달고 있다.

### 3.4 한국어에서 nomic 벡터 다리는 사실상 실패한다 (측정 완료)

`nexus/CLAUDE.md` 9번은 "영어 전용 embedding model 사용 금지 → multilingual 필수"인데
`config.yaml` 은 `nomic-embed-text`(영어 중심 v1)를 쓴다. 둘은 **양쪽 다 존재한 이래로 서로
어긋나** 있었고, 잴 자가 없어서 아무도 결판내지 못했다.

`SPEC-nexus-korean-embedding-comparison` 이 그 측정이다(4라운드 60이슈 전량 수용 후 승인).

**결과** (Pack A · 라벨 rev2 · 리포트 `tests/eval/reports/2026-08-04-nomic-vs-kure.md`)

| 팔 | 커버리지 | vector Recall@10 | fused | keyword(동일) |
|---|---|---:|---:|---:|
| nomic-embed-text | 1,896/1,906 (99.5%) | **≥0.402** | ≥0.777 | 0.771 |
| KURE-v1 | 1,906/1,906 (100%) | **≥0.975** | ≥0.988 | 0.771 |

확증 분석(비교가능 부분집합 36/40 질의, 벡터 다리): **27승 1패 8무, 불일치쌍 28, p≈0 → KURE-v1
우세.** 규칙(CLAUDE.md 9번) 쪽이 맞았다.

**읽는 법이 셋 있다.**

- **융합 0.777은 벡터가 기여해서가 아니다.** 키워드 다리가 0.771이다 — 현재 프로덕션의
  "하이브리드"는 한국어에서 사실상 BM25다.
- **모든 수치는 하한이다.** 풀 판정을 보류해서 미판정 문서가 비관련으로 세어진다. 여기 있던
  *"그 페널티는 새 문서를 더 많이 건져 올린 팔이 더 많이 받으므로 결론 방향에는 보수적이다"* 는
  **2026-08-05 에 삭제됐다** — 도움이 되는 항만 세고 해치는 항을 안 셌기 때문이다. 미판정 문서를
  관련으로 올리면 분모는 두 팔 모두 오르고 분자는 그 문서를 건진 팔만 오른다. 그래서 어떤 판정은
  마진을 넓히고, 어떤 판정은 줄이며, **어떤 판정은 뒤집는다.** 그 자리에 계산된 두 숫자를 안심도
  반증도 주장하지 않고 나란히 둔다 (`SPEC-nexus-ko-eval-pool-sensitivity`):
  - **최악값** — 비교가능 부분집합의 **746쌍 중 10쌍**이 특정 패턴으로 관련이면 확증 판정이 깨진다
    (flip·tie·removal 전수 탐색 + DP; 도달 가능한 패배 `W22 L10 p=0.0501`, `W23 L11 p=0.0576`).
  - **기저율** — 무작위 30쌍 표본(시드 `20260805`) 판정 결과 **관련 0건**. 점추정 **0쌍**,
    95% CI `[0, 86]`. 이견이 기록된 1건(#15)을 관련으로 세는 **안전 읽기**에서는 점추정 25쌍,
    CI `[0.6, 128]`. **양쪽 다 임계 10 을 걸치므로** 사전등록 규칙의 답은 **"n=30 에서 미해결"**
    이고, 아래 정정은 그 답을 바꾸지 않는다.
  - **캘리브레이션이 판정 하나를 뒤집었다** (2026-08-06). §4.1 은 각 질의의 기존 gold 를
    대조군으로 섞으라고 요구하는데 **표본을 판정할 때 그 대조군을 안 돌렸다.** 뒤늦게 돌린 결과:
    원 판정은 **관련성 기준을 글로 남긴 적이 없고**(자 설계 SPEC 은 "풀 문서를 읽어서 판정한다"는
    절차만 적는다) 따라서 대조는 문장이 아니라 **행동**으로만 가능한데, rev2 gold 는 how-to 질의에
    대해 **개념 문서가 아니라 task 문서**를 고른다(q021→`access-api-from-pod.md`,
    q030→`configure-liveness-readiness-startup-probes.md`). 그 기준이 #15 기각을 **정당화**하고
    #4 수용을 **무효화**한다 — 후보였던 개념 문서는 41줄에 설정형 매치 1건, gold 는 46건이다.
  - **두 수는 비교 가능한 양이 아니다.** 10 은 *특정 적대적 패턴*의 쌍이고 25 는 풀에 흩어진 관련
    쌍의 추정치이며, 흩어진 관련 판정은 KURE 쪽 마진을 넓히기도 한다. **"마진이 불완전 판정의
    산물일 수 있다"는 추론은 따라 나오지 않는다** — 그러려면 추정 비율로 관련 쌍을 뿌려 판정 분포를
    계산해야 하고, 그건 하지 않았다. 지금 말할 수 있는 것은 **유예가 무해함이 입증되지 않았다**
    뿐이다.
- **이 결과는 교체를 허가하지 않는다.** 평가용 벡터 다리는 정확 스캔이라 프로덕션(ivfflat)을
  예측하지 못하고, 교체는 차원까지 바꾼다(768→1024). 이 숫자가 허가하는 것은 **교체 SPEC 을
  쓰는 것**이고, 그 SPEC 은 자기 ANN 측정을 져야 한다.

**설계에서 신경 쓴 것** — 정확 스캔(ANN 흔들림 배제) · 두 팔이 같은 문자열을 보게(`input_sha256`
공용 / `payload_sha256` 팔별) · 커버리지를 판정보다 먼저 · **비교가능 부분집합**(창에 걸린 gold
문서가 있는 질의를 빼서 창 크기를 모델 품질로 착각하지 않게) · 판정 규칙과 부분집합 정의는
**팔이 한 청크도 임베딩하기 전에** 승인본에 박혀 있었다(사후에 고른 게 아니다).

**풀 판정은 보류했다.** 후보 821건을 판정하면 절대치가 오르지만 방향은 안 바뀌고, 그 비용은
사람의 검토 821건이다. 익명 덤프(`tests/eval/ko/pool-blind.json`)를 커밋해 두고, **라벨 리비전이
2를 넘는 순간 미판정 풀이 남아 있으면 테스트가 실패**하도록 트리거를 걸었다 — 기억이 아니라
스위트가 지킨다.

### 3.5 KURE 우세는 ivfflat 을 통과한다 — 그런데 처음엔 반대로 나왔다

교체 SPEC 은 앞선 비교가 갚지 못한 빚을 명시적으로 졌다: 평가의 벡터 다리는 **정확 스캔**이었고,
"프로덕션(ivfflat)을 예측하지 못한다" 고 문서에 적혀 있었다. 그 빚을 갚은 결과.

| 팔 | fused 정확 스캔 | fused ANN | 델타 |
|---|---:|---:|---:|
| nomic-embed-text | 0.777 | 0.777 | +0.000 |
| **KURE-v1** | 0.988 | **0.988** | **−0.000** |

팔 대 팔(ANN 경로): KURE **Recall@10 0.988 · MRR 0.941 · 미스 0/40** 대 nomic 0.777 · 0.536 ·
미스 5. **ANN 이 먹는 리콜은 0** 이고, 그건 기제가 예측한 그대로다 — `lists=1` 이면 리스트가
하나뿐이라 사실상 전수 스캔이다.

#### 그런데 첫 실행은 "KURE 가 0.988 → 0.650 으로 무너진다" 고 보고했다

그 실행이 읽은 `chunks.embedding_1024` 는 KURE 벡터가 아니라 **DB 테스트 스위트가 써 넣은 상수
벡터**(`[0.01]*1024`)였다. `reembed()` 의 큐에 테넌트 필터가 없어서, 테스트가 자기 테넌트를
재임베딩할 때마다 같은 DB 의 평가 코퍼스 1,906건까지 덮어썼다(1,906개 중 서로 다른 값이 53종뿐).

**어떻게 잡았나.** 후속 작업(인덱스 튜닝)에 들어가기 전에 전제를 확인한 것이 전부다: `lists=1`
이면 전수 스캔인데 **그런 인덱스가 리콜을 3분의 1이나 먹는다는 것이 기제와 앞뒤가 맞지 않았다.**
청크 본문을 다시 임베딩해 대조하니 평가 저장소와는 거리 0.0000, `chunks` 와는 1.026 이었다.

**진짜 결함은 범위였다.** 재임베딩은 마이그레이션 도구라 전 테넌트를 도는 것이 정상 사용이지만
**범위를 좁힐 수단이 없었다.** `_disposable_test_db` 가 지키는 것과 같은 경계다 — 파괴 범위가
선언되지 않으면 언젠가 넘친다. 수정: `--tenant` 를 재임베딩·집계·컷오버 판정·CLI 에 추가, 테스트를
자기 테넌트로 묶고, **범위 유출 자체를 잡는 테스트** 둘과 **정렬 검사**를 넣고, 가짜 임베딩
서비스를 상수에서 **텍스트 의존**으로 바꿨다(상수를 돌려주는 가짜는 정렬 어긋남을 원리적으로
통과시킨다 — 그래서 통과시켰다).

정정 절차가 그대로 다음 사람의 체크리스트다: **재고 나서 결론 내기 전에 두 저장소의 벡터가 같은지
먼저 확인한다.** 이번엔 1,906쌍 평균 거리 3e-8 을 확인하고 시작했다.

#### 컷오버는 배포별 운영 행위다

네 조건(§4.5)이 측정 테넌트에서 모두 섰지만 **리포지토리 기본값은 `embedding` 그대로 둔다.**
기본값을 바꾸면 아직 재임베딩하지 않은 설치가 빈 컬럼을 읽어 벡터 다리가 죽는다. 배포마다:

**절차의 정본은 `docs/TEAM_DOGFOOD_DEPLOY.md` §6.1 이다.** 여기 처음 적었던
"config.yaml 의 `search.embedding_column` 한 줄" 은 **틀렸다**: 그 값만 바꾸면 질의 벡터는
nomic 768 차원 그대로라 `different vector dimensions` 로 검색이 죽고, 그것도 재임베딩이 끝나 행이
차는 순간에 죽는다. 세대는 **모델·컬럼·백엔드 셋**이고, 배포는 그 셋을 `.env` 에서 함께 움직인다
(`SPEC-nexus-embedding-cutover-seam`).

```bash
docker compose --profile embed up -d nexus-embed                 # 사이드카 (리비전은 커밋으로 핀)
nexus reembed run --column embedding_1024 --model KURE-v1 --backend sidecar --all-tenants
nexus reembed create-index --column embedding_1024               # 다 채운 뒤 행 수로 lists 산정
nexus reembed run --column embedding_1024 --model KURE-v1 --backend sidecar --all-tenants  # 2차: 0이어야
nexus reembed status --column embedding_1024 --all-tenants       # 조건은 테넌트마다 선다
# 통과하면 배포 .env 의 NEXUS_EMBEDDING_MODEL / _COLUMN / _BACKEND 를 함께 전환 후 재기동
```

롤백은 그 세 줄을 되돌리는 것이다 — 옛 컬럼과 인덱스는 손대지 않는다. 다만 **flip 이후 적재된
청크는 옛 컬럼이 비어 있다**(이중 쓰기를 하지 않기로 한 대가). 그 수는
`nexus reembed status --column embedding --all-tenants` 가 보고하고, 같은 도구를 반대로 겨눠 메운다.

#### 실제로 했다 (2026-08-05, 도그푸딩 배포)

재임베딩 167/167 · 실패 0 · waived 0 → `create-index` (행 167 → `lists=1`) → 2차 패스 0건(창 안에
적재된 것 없음) → 조건 4개 충족 → `.env` 세 줄 전환 → 재기동. `/status` 가 KURE-v1 ·
`embedding_1024` · sidecar 와 핀 리비전 `d14c8a94…` 를 보고하고, 커버리지는 두 컬럼 모두 167/167.

**지연**(사전등록 규칙 `p95(after) ≤ 1.5× p95(before)` 이고 `≤ 1500 ms`):
`/search` p95 **133 → 188 ms (×1.41)** — 통과, 그러나 한도의 94% 다. 증가분의 거의 전부가 질의
임베딩(p50 74 → 128 ms)이고, 이 사이드카는 CPU 단일 프로세스라 **동시 질의는 큐를 만든다** —
재측정 트리거는 코퍼스 크기가 아니라 동시성이다. 전문: `tests/eval/reports/2026-08-05-cutover-latency.md`.

**컷오버가 스스로 잡은 것 하나.** 전환 직후 앱이 **부팅을 거부**했다 — `config.yaml` 이 아직
nomic 의 지시문(`search_document: `)을 들고 있었는데 KURE 의 카드에는 지시문이 없다. 차원과 같은
부류(모델의 사실이 설정에 하드코딩됨)라 같은 처분을 했다: 지시문 키를 배포 설정에서 뺐다. 가드가
없었으면 **다른 모델의 형식을 씌운 벡터로 조용히 검색했을 것이다.**

## 4. 되풀이된 실수와, 그래서 생긴 규칙

이번 작업에서 **같은 함정을 두 번 이상 밟았다.** 규칙으로 적어 두는 이유다.

| 함정 | 어디서 밟았나 | 규칙 |
|---|---|---|
| **코퍼스가 조회 창보다 작다** | 옛 리콜 스위트(5문서/창20), 그리고 **내가 새로 쓴 벡터 다리 fixture(5문서/창10)** — 음성 대조군이 실패해서 알았다 | fixture 든 코퍼스든 **창보다 훨씬 크게**. 42문서로 넓히니 정상 작동 |
| **기대값을 토크나이저 출력에서 유도** | 옛 스위트의 기대 어휘 | 판정은 문서 단위. 어휘 칸은 **스키마에서 표현 불가능**하게 |
| **자명한 대조군** | "같은 모델 두 번 = 같은 결과"는 결정성만 증명 | 대조군은 **실패할 수 있어야** 한다 — 벡터를 섞으면 무너지는가 |
| **첫 실행이 곧 표준** | 바닥값·매니페스트 | 독립 하한 + 규칙 재유도(`check`) |
| **커버리지를 재현율 아래에 묻기** | §3.2 | 커버리지를 **판정보다 먼저** 읽는다 |
| **파괴 범위 미선언** | §3.5 — 재임베딩 큐에 테넌트 필터가 없어 테스트가 평가 코퍼스를 덮어씀 | 파괴적 도구는 범위를 **인자로** 받는다. "전부"는 기본값이 아니라 선택이어야 한다 |
| **상수를 돌려주는 가짜** | 재임베딩 테스트의 가짜 임베딩 서비스 | 가짜는 **입력에 의존**해야 한다. 상수는 정렬 어긋남을 원리적으로 통과시킨다 |
| **말이 안 되는 숫자를 그대로 보고** | 첫 ANN 결론 — `lists=1` 은 전수 스캔인데 리콜이 0.338 빠졌다 | 결과가 기제와 모순되면 **먼저 계측기를 의심**한다. 이 세션에서 두 번 다 계측기가 틀렸다 |
| **프록시로 모집단을 추정** | §3.2 — 퇴화한 탐침(`"가"*n`)의 문자 한계를 실제 분포에 적용해 232건이라 적었다. 실제는 10건 | 모집단 수치는 **돌려서** 얻는다. 경계 측정은 경계까지만 말한다 |
| **풀에 없던 설정을 그 gold 로 채점** | KURE·nori 추가 시 | 새 설정은 **재풀링**. 라벨에 `pooled_over` 로 무엇에 유효한지 적는다 |
| **스키마 갱신의 침묵** | `CREATE TABLE IF NOT EXISTS` 가 예전 모양을 그대로 두고, 임베딩 10분 뒤 INSERT 에서 죽음 | `ensure_table` 이 컬럼을 검사해 **시작 전에** 실패 |
| **판정자가 가설을 들고 판정** | 풀 판정 | 후보에서 팔 정보 제거·셔플(시드 기록), 익명 덤프를 판정 **전에** 커밋 |

한 줄로: **자가 자기 무효를 스스로 알아채게 만들어라.** 이번에 잡은 두 프로덕션 결함은 둘 다
"측정하려다 측정 도구가 이상해서" 나왔다.

### 6.2 승인본 §5.3 의 기본값을 왜 뒤집었나 (2026-08-05)

승인본은 `clean_db` 가 `chunks` 와 함께 `ko_eval_embeddings` 도 TRUNCATE 하라고 적었다. 구현은
**반대로** 한다: 기본은 보존, 파괴는 `NEXUS_TRUNCATE_KO_EVAL_STORE=1`. 승인 이후에 알게 된 사실 둘이
셈을 뒤집었다.

1. **고아 상태는 이미 잡히고 있었다.** `verify_arm` 이 "살아 있는 청크가 없는 행"을 잡고 `cmd_run`
   이 거기서 멈춘다 — 승인본 §5 는 공식 경로에 구멍이 있는 것처럼 읽히게 썼지만, 2026-08-05 의
   `Recall@10 = 0.000` 은 그 검사를 우회한 임시 스크립트가 낸 것이었다. 남은 노출은 그런 우회
   경로였고, 그건 이제 `collapse_to_documents` 가 `OrphanedStoreError` 로 직접 막는다.
2. **지우는 비용이 시간 단위다.** 저장소는 두 팔 × 1,906 청크이고 KURE 팔은 CPU
   sentence-transformers 다. 그리고 **2026-08-05 에 이 픽스처를 검증하다가 정확히 그렇게 날렸다** —
   DO 블록이 도는지 보려고 실 DB 에 직접 실행했고 3,812 행이 사라졌다. 설계 판단이 실증이 됐다.

그래서 truncate 기본이 사는 것은 "우회 스크립트 보호" 하나인데 그 대가가 시간짜리 데이터의 조용한
소멸이고, 그 보호는 (1)+하니스 가드로 파괴 없이 얻어진다. 고아가 된 저장소는
`ko_eval_embed_compare restore-chunks` 가 rid 집합과 `input_sha256` 을 함께 대조해 복구한다.

**이것은 승인본과의 이탈이므로 후속 레코드를 진다** (§6 표). 여기 적는 것은 근거의 보존이지 처분이
아니다.

### 6.1 Pack B 의 트리거를 왜 바꿨나 (2026-08-05)

옛 트리거는 **"(b)를 실제로 인용해 무언가를 결정할 때"** 였다. 그건 ADR-0009 가 자기 표에서
*"deliberately not 'the next backstop event', since that is the thing nothing can detect"* 라며
피한 바로 그 형태 — **아무것도 감지하지 못하는 트리거**다. 그리고 더 나쁜 사실이 측정으로 드러났다.

**지금 만들면 실패한다.** 라이브 테넌트는 활성 문서 **20건**(청크 167). 하니스는 청크를 문서로 접어
**상위 10문서** 안에서 채점하므로, 무작위 랭커의 `Recall@10` 바닥값은 `W/N` 이다:

| 코퍼스 N | 바닥값 (W=10) | 측정 가능 구간 |
|---:|---:|---|
| **20 (현재)** | **0.500** | [0.50, 1.00] — 매 질의가 코퍼스의 절반을 돌려준다 |
| 100 | 0.100 | [0.10, 1.00] |
| 265 (Pack A) | 0.038 | [0.04, 1.00] |

Pack A 에서 nomic 0.402 대 KURE 0.975 라는 격차가 잡히고 불일치쌍 28개가 나온 것은 바닥이
0.038 이라 **아래로 벌어질 자리가 있었기** 때문이다. N=20 이면 두 팔이 0.5 위에 붙어 대부분
무승부가 되고, 불일치쌍 6 미만 → 판정 규칙이 **"검정력 부족"** 을 돌려준다. ADR-0009 는
*"If the comparison is underpowered … the obligation **stays open**"* 라고 명시했으므로, 그 결과는
의무를 **갚지 못한다.** 라벨 노동만 태우고 제자리다.

**그래서 새 트리거는 `활성 문서 ≥ 100`** — 바닥값을 Pack A 와 같은 자릿수(≤0.10)로 유지하는 최소치다.
`select count(*) from documents where status='active'` 로 **세어서 확인**되므로 기억이 아니라 숫자가
지킨다. §1 의 옛 리콜 스위트가 폐기된 이유(코퍼스 5문서 < 창 20)와 §4 의 재발 함정
("fixture 든 코퍼스든 창보다 훨씬 크게")이 같은 결함이고, 이번이 세 번째다.

**두 조건은 함께 서야 한다.** 크기는 자가 **작동할 수 있는지**를, 수요는 만들 **가치가 있는지**를
정한다. 크기만 차면 만들 이유가 없고, 수요만 있고 크기가 모자라면 만들어도 "검정력 부족"이 나온다.

**이 트리거 변경이 의무를 미루는 것은 아니다.** ADR-0008 §5(b) 도, ADR-0009 의 재검토 의무도
문구 그대로다. 바뀐 것은 **자를 언제 만드는가** 뿐이고, 근거는 "지금 만든 자는 (b)를 닫을 수 없다"는
측정이다. 그리고 코퍼스 크기는 팀이 통제한다 — Notion 소스가 1개 걸려 있고, 실적재를 넓히면
차오른다. 막힌 것은 외부 사건이 아니다.

**ADR-0009 쪽 사본은 고칠 수 없다.** 그 표의 Pack B 행은 수락·스탬프된 불변 기록이라 여기서
편집하지 않았다. 한쪽만 보는 독자에게 옛 트리거가 그대로 보이는 문제는 후속 레코드나
`adr/README.md` 포인터가 필요하며, 그 처리는 소유자 몫이다
(`SPEC-nexus-ko-eval-pool-sensitivity` §1.2 의 네 번째 질문과 같은 갭이다).

> **이 트리거는 불충분했다. §6.2 를 보라.** 위 표는 그대로 옳지만, 세는 대상이 하나 모자랐다.

### 6.2 트리거가 통과했는데 여전히 못 쟀다 — 두 번째 조건 (2026-08-07)

§6.1 의 트리거(`활성 문서 ≥ 100`)가 **충족됐다.** 정책 문서 적재로 코퍼스가 20 → **116문서**가
됐고 바닥값은 `10/116 = 0.086` 으로 목표(≤0.10) 아래다. 그래서 라벨을 쓰러 갔다가, 문서를 훑는
첫 질의에서 걸렸다:

| 본문 길이 | 문서 수 |
|---|---:|
| < 200자 | **57** |
| 200 – 800자 | 40 |
| 800자 – 3k | 4 |
| 3k 이상 | 15 |

**gold 가 될 수 있는 문서가 19건이다.** 나머지 97건은 개정 이력 행이고, 200–800자 구간을 실제로
열어 보니 길이의 대부분이 URL 이었다(`- **Epic**: … - **날짜**: … - **바로가기**: https://…`).

§6.1 이 센 것은 **창 경쟁**이었다. 그건 지금도 맞다 — 짧은 문서도 상위 10문서 자리를 두고 겨루므로
바닥값 계산에는 116건이 다 들어간다. 놓친 것은 **라벨 가능성**이다. 답변가능 40건을 19개 문서에
걸면 층별 8건을 서로 다른 문서에서 뽑을 수 없고, 두 팔이 같은 소수 문서를 두고 겨뤄 무승부가
쌓인다. 불일치쌍 6 미만 → **"검정력 부족"**, 그리고 그 결과는 §6.1 이 스스로 적었듯 ADR-0008
§5(b) 를 **갚지 못한다.**

**그래서 트리거는 두 조건이다:**

| # | 조건 | 재는 것 | 현재 |
|---|---|---|---|
| 1 | 활성 문서 ≥ 100 | 창 경쟁 — 바닥값 `W/N` ≤ 0.10 | 116 ✅ |
| 2 | **본문 800자 이상 문서 ≥ 60** | gold 후보 — 40개 질의를 서로 다른 문서에 | **19 ❌** |

800자는 실측으로 정했다(위 표의 200–800 구간이 전부 이력 행). 60은 답변가능 40건 + 층을 억지로
채우지 않을 50% 여유다. Pack A 는 265문서에 40라벨(6.6:1)이었다.

**같은 결함의 네 번째다.** §1 의 옛 리콜 스위트(코퍼스 5 < 창 20), §4 의 fixture 함정, §6.1 의
N=20 — 그리고 이번. 앞의 셋은 "코퍼스가 창보다 작다" 였고 이번은 "코퍼스는 큰데 **셀 수 있는 것만
셌다**" 다. 문서 수는 구하기 쉬운 숫자였고, 실질 문서 수는 한 번 더 물어야 나오는 숫자였다.

**이번엔 숫자가 지킨다.** `scripts/ko_eval_packb.py status` 가 두 조건을 따로 찍고 미달이면
종료코드 1 을 낸다. 매니페스트가 문서마다 `body_chars` 를 남기므로
`tests/test_ko_eval_packb.py::test_enough_documents_can_actually_carry_a_query` 가 **DB 없이**
검사한다. 지금 이 테스트는 **실패한다** — 그것이 맞는 상태다.

**막힌 것은 여전히 외부 사건이 아니다.** 정책 문서 트리에 공유되지 않은 블록이
하나 있고, 그 아래 본문이 있을 수 있다. 그 밖에도 팀 문서 루트를 더 걸 수 있다.

> **위 조건 [2]의 근거는 같은 날 반증됐다. §6.3 을 보라.** 관찰(19건)은 사실이지만, 거기서
> 끌어낸 결론("무승부가 쌓인다")이 틀렸다.

### 6.3 재보지 않은 문턱을 재서 걷어냈다 (2026-08-07, 같은 날)

§6.2 는 문턱 하나를 새로 박았다 — **"본문 800자 이상 문서 ≥ 60"**. 60 이라는 수의 근거는 측정이
아니라 추론이었다:

> gold 후보가 19건뿐이면 두 팔이 **같은 소수 문서**를 두고 겨뤄 무승부가 쌓이고, 불일치쌍 6 미만
> → "검정력 부족".

그럴듯했고, 그 추론 하나로 라벨 45건을 세웠다. 그런데 **그 추론은 라벨 없이 잴 수 있는
것이었다.** 판정에는 정답이 필요하지만 "두 팔이 다른 문서를 돌려주는가" 에는 필요 없고, 그것이
불일치쌍의 **필요조건**이다:

```
상위 10문서가 같다  →  두 팔의 Recall·MRR 이 같다  →  무승부  →  불일치쌍 0
```

같은 엔진·같은 스코러·같은 품사 정책으로 nori 를 토크나이저로만 끼운 뒤(§4.4 와 같은 배선),
탐침 질의 30건(Pack B 라벨과 같은 다섯 층 형태)으로 잰 결과:

| 잰 것 | 값 |
|---|---:|
| 순위표가 갈리는 질의 | **12 / 30** |
| ↳ 처음 갈리는 자리 **1–3위** | **8** |
| ↳ 4–6위 | 1 |
| ↳ 7–10위 | 3 |
| 1위가 다른 질의 | 0 / 30 |
| 상위 10문서 집합이 다른 질의 | 9 / 30 |
| 평균 자카드 유사도 | 0.937 |
| **상위10에 한 번이라도 뜬 서로 다른 문서** | **48 / 116** |

**추론의 핵심이 틀렸다.** "같은 소수 문서를 두고 겨룬다" 고 했는데 48개 문서가 상위10에 뜬다.
그리고 8건은 **2~3위에서** 갈린다 — gold 가 그 자리에 있으면 MRR 이 뒤집히고, 창 밖으로 밀리면
Recall 이 뒤집힌다. 승패가 생길 자리가 있다.

**그래서 문턱을 옮겼다.** 조건 [2] 는 이제 **측정한 양**이다:

| # | 조건 | 재는 것 | 현재 |
|---|---|---|---|
| 1 | 활성 문서 ≥ 100 | 창 경쟁 — 바닥값 `W/N` ≤ 0.10 | 116 ✅ |
| 2 | **탐침에서 상위 3위 안 갈림 ≥ 6** | 승패가 생길 자리 | **8 ✅** |

6 은 판정 규칙의 `MIN_DISCORDANT` 와 같은 수다(테스트가 강제). 필요조건이 최소 요구치에 이미
못 미치면 판정은 확실히 검정력 부족이기 때문이다. 실질 문서 수(19)는 계속 **보고**하되 문턱에서는
뺐다 — 코퍼스가 무엇으로 차 있는지는 게이트와 무관하게 알아야 한다.

**보장이 아니다.** 순위가 갈려도 두 팔이 gold 를 둘 다 잡으면 자리에 무관하게 무승부다.
"검정력 부족" 은 여전히 나올 수 있고, 그러면 ADR-0009 대로 의무가 **열린 채 남는다.** 이 게이트가
주는 것은 보장이 아니라 **라벨 노동의 기대값이 양수라는 근거**다.

**같은 실수를 처방에서 반복했다.** §6.2 는 "문서 수는 구하기 쉬운 숫자였고, 실질 문서 수는 한 번
더 물어야 나오는 숫자였다" 로 끝난다. 그러고는 실질 문서 수를 세는 문턱을 박았는데, 검정력을
예고하는 양은 **또 한 번 더 물어야 나오는** 것이었다 — 순위가 갈리는 자리. 세 번째로 같은 형태다.
기계: `scripts/ko_eval_packb_disagreement.py` (질의와 결과는 `tests/eval/local/`, 커밋 안 함).

### 6.4 Pack B 판정 (2026-08-07)

트리거 두 조건이 다 서고, 라벨 45건(층별 8 + 답변불가 5)이 저술·검토·서명된 뒤 돌렸다.
**질의·gold·리포트는 커밋하지 않는다** — 다른 조직의 문서를 가리키고 이 리포는 public 이다
(§4.1). 여기에는 숫자와 그 한계만 적는다.

```
Pack B (문서 116 · 청크 289, 매니페스트 검증 통과) · 라벨 revision 1 · 답변가능 40

mecab-ko : Recall@10 0.975 · MRR@10 0.711 · 미스 1
nori     : Recall@10 0.975 · MRR@10 0.714 · 미스 1

승패(nori 기준) 4승 2패 34무 → 불일치쌍 6 · p = 0.688
판정: 이 표본 크기에서 측정 가능한 차이 없음 — 현직(mecab-ko) 유지
```

**"검정력 부족"이 아니다.** 불일치쌍이 정확히 `MIN_DISCORDANT` 인 6이라 검정이 p값을 냈다.
그리고 **Pack A 의 결론이 독립적으로 재현됐다** — Pack A 는 p=0.180, 여기는 p=0.688, 둘 다
mecab 유지. 서로 다른 코퍼스(공개 k8s 문서 265건 vs 팀 문서 116건)에서 같은 방향이다.

**자의 약점을 판정보다 위에 적는다.**

- **Recall 이 천장에 붙었다**(0.975, 미스 1/40). 라벨을 문서 쪽에서 저술하면 질의가 쉬워진다 —
  답이 있는 것을 알고 묻기 때문이다. 그래서 40건 중 34건이 무승부가 됐고 불일치쌍은 **간신히 6**
  이었다. 하나만 적었어도 p값 없이 "검정력 부족" 이 나왔을 것이다.
- **층별 Recall 차가 다섯 층 모두 정확히 0.0** 이다. 승패는 전부 MRR 동점처리에서 갈렸다. 층별
  수치가 서술조차 못 하는 상태이므로, 이 실행에서 층은 아무것도 말하지 않는다.
- §6.3 이 잰 "승패가 생길 자리"(상위 3위 안 갈림 8건)는 **필요조건이었고 충분조건이 아니었다.**
  실제로 두 팔이 gold 를 둘 다 잡은 경우가 많아 무승부가 됐다. 게이트는 통과시켰지만 그 게이트가
  약속한 것은 딱 여기까지다.

**§6.3 에서 한 진단은 방향만 맞았다.** 아침에 "무승부가 쌓인다" 고 했고 원인을 "gold 후보가
19건뿐" 이라고 짚었다. 무승부가 쌓인 것은 맞다(34/40). 그런데 원인은 코퍼스가 아니라 **질의가
쉬워서**다 — 상위10에는 48개 문서가 뜬다(§6.3). 걱정은 맞고 진단은 틀렸다.

**ADR-0008 §5(b) — 처분: 불발화 (소유자, 2026-08-07).**

조건은 *"한국어 평가셋이 khala 의 진짜 코퍼스에서 토크나이저를 비교할 수 있고, 그 결과가 mecab-ko
를 편들지 않을 것"* 이다. 평가셋은 존재하고, 결과는 nori 를 편들지 않으며, mecab 이 남은 것은
**판정 규칙 5번**(결론 못 내면 현직 유지)이지 측정된 mecab 우위가 아니다. 그럼에도 발화하지
않는다 — 조건이 요구하는 것은 *mecab 을 편들지 않는 결과* 인데 나온 것은 **차이 없음**이고, 차이
없음은 현직을 흔들 근거가 아니다.

**이 처분은 결과에 대한 것이지 조건에 대한 것이 아니다.** §5(b) 는 살아 있다 — 더 나은 자, 또는
더 크거나 어려운 Pack B 라면 mecab 을 편들지 않는 결과가 나올 수 있다. 정해진 것은 *2026-08-07 의
이 실행이 그 결과는 아니다* 라는 것뿐이다.

**그리고 다음 발화를 감지할 기제는 여전히 없다.** §5 의 어떤 백스톱이 울리는지 아무것도 보고
있지 않다는 문제는 `governance/open-items.yaml` 의 `adr-0008-backstop-detector` 가 **열린 채로**
계속 진다(설계 두 건이 기판에서 실패한 기록은 `SPEC-nexus-retrieval-backstop-detector` §2).

**ADR-0008 본문은 고치지 않는다** — 수락·스탬프된 불변 기록이다. 처분은 여기와 장부에 후속
기록으로 남는다(`packb-result-disposition`, closed).

기계: `scripts/ko_eval_packb_run.py`. 두 관문(매니페스트 검증 · 라벨 게이트)을 **측정 전에**
통과해야 결과로 친다 — 관문이 뒤에 있으면 숫자를 보고 자를 고치게 된다.

## 8. 답변 품질 — 처음 재봤더니 부러진 것은 답변이 아니었다 (2026-08-08)

§0 부터 §7 까지는 전부 **검색**을 잰다. 답변은 한 번도 안 쟀다 — 있던 것은 결정론적 가드
셋(인용 사후검증·숫자 근거검증·근거 신선도)뿐이고, 셋 다 답변이 근거를 **벗어났는지**를 보지 답이
**맞는지**를 보지 않는다.

### 8.1 자

`scripts/ko_eval_answer_quality.py` — **LLM 심판 없이** 세 가지를 코드가 판정한다.

| | 방법 | 실패의 뜻 |
|---|---|---|
| `grounded` | 인용이 1개 이상이고 전부 근거 packet 안 | 출처를 지어냈다 |
| `cites_gold` | 그중 하나가 정답 문서 | 엉뚱한 문서로 답했다 |
| `has_facts` | `must_contain` 의 사실이 답변에 있다 | **검색은 맞았는데 답이 틀렸다** |

답이 좋은지를 LLM 에게 물으면 그 모델의 취향을 재게 되고, 그 취향은 우리 라벨보다 검증이 덜 된
것이다. **인용 0개는 grounded 가 아니다** — 미검증 수만 세면 0이라, 아무것도 인용 안 하는 것이
가장 쉬운 만점이 된다.

`must_contain` 은 **모든 항목 × 각 항목은 표기 후보 중 하나**(`[["100"], ["곡","트랙"]]`). 후보를
안 주면 답변의 *표현* 을 재게 된다. 정규화는 공백만 접고 **소문자화는 안 한다** — `NexusResponse`
는 `nexusresponse` 가 아니다.

**백엔드는 claude-code 브리지**(`claude -p`, 툴 전면 차단). 유료 키가 필요 없고, 무엇보다 그
프로세스는 라벨도 `must_contain` 도 못 본다. 에이전트가 답을 직접 쓰면 시험지를 본 사람이 답안을
쓰는 것이라 측정이 성립하지 않는다.

### 8.2 결과 — 22/40 → 40/40, 그중 모델 교체로 얻은 것은 0

| 단계 | 셋 다 | 무엇을 고쳤나 |
|---|---:|---|
| 첫 측정 | 22/40 | — |
| 인용 정규화 | 31/40 | 활자 따옴표 `‘락’` 가 진짜 출처를 가짜로 만들었다 |
| 인용 파싱 + 라벨 2건 | 36/40 | 제목의 `[파티룸]` 이 인용을 통째로 깼다 |
| 이미지 URL 제거 + 재적재 | 36/40 | 청크 18,839→3,794자, 임베딩 288→289/289 |
| **스니펫/근거 분리** | **39/40** | 300자 상한이 표를 잘라 프롬프트에 보냈다 |
| 3회 다수결 | **40/40** | 재현되는 실패 0건 |

**17건이 회복됐고 전부 파이프라인 또는 자의 결함이었다.** 그래서 상위 모델 비교(§8.4)가 아무것도
못 가린 것이다 — 두 팔이 같은 벽에 부딪히고 있었다.

### 8.3 검색 지표로는 원리적으로 안 보이던 구간

세 질의가 매 회차 실패하며 모델이 같은 말을 했다: *"표가 중간에 잘려 있어 그 행이 제공되지
않았습니다."* 청킹 문제로 읽고 재적재까지 했지만 안 풀렸다. 실측:

```
청크         846자 — 대기열 잠금·재입장 불가가 한 청크에 함께 있다
검색         그 청크를 1위·4위·1위로 뽑았다 (융합 문서 Recall@10 = 1.000)
근거 packet  max_snippet_chars = 300      ← 여기
```

**`Recall@10 = 1.000` 은 정답 문서가 창 안에 있다는 뜻이지, 답이 든 문장이 프롬프트에 갔다는 뜻이
아니다.** `_truncate_snippet` 이 사람 화면용으로 300자에서 자르는데 같은 값이 프롬프트에도 물려
있었다. 역할 계층은 표 앞부분이라 살아남고 묻는 행은 잘려 나갔다.

**모델의 보고가 정확한 관찰이었고, 그것을 자기 가설의 확증으로 읽은 것이 진단 실패의 원인이다.**

고치는 데 새 숫자는 필요 없었다 — 그 300은 **두 소비자 중 한쪽에만** 틀린 값이었다. `snippet`(사람)
과 `chunk_text`(프롬프트)를 가르니 API 응답은 한 글자도 안 바뀐 채 해결됐다.

### 8.4 상위 모델 비교 — 가릴 수 없었다

판정 규칙은 `scripts/ko_eval_answer_verdict.py` 에 **어떤 팔도 돌리기 전에** 고정했다. 검색과 달리
답변은 결정론이 아니기 때문이다.

```
sonnet-4-6  회차별 [34, 31, 32]  다수결 34/40
opus-5      회차별 [33, 30, 33]  다수결 32/40
잡음 폭 ±3 · 차이 -2 → 구별되지 않는다. 현직 유지
```

**규칙 2(잡음 폭)가 규칙 3(검정)보다 먼저 걸려 p 값을 아예 안 냈다.** 숫자를 먼저 봤다면 "Opus 가
2건 낮지만 유의하지 않다" 고 쓰고 싶었을 텐데, 그건 검정을 돌릴 자격이 없는 상태였다.

**잡음 폭 자체가 흔들린다** — 다른 3회 묶음에서 ±1, ±3, ±2 가 나왔다. 3회로는 폭을 못 고정한다.
모델을 다시 가리려면 회차를 늘려야 하고, 그것도 **재보기 전에는 주장이 아니다.**

### 8.5 남은 것

- 라벨 40건은 문서 쪽에서 저술해 **쉽다.** 40/40 은 "완벽" 이 아니라 "이 난이도에서는 안 틀린다".
- 답변불가 5건은 여전히 어떤 집계에도 안 들어간다. 기권은 이제 기계가 읽을 수 있지만(`abstained`)
  **한 번도 발화하지 않는다**(0/5) — `abstention-never-fires`.
- 이 실행의 백엔드(claude-code 브리지)는 배포(`claude-sonnet-4-6` API)와 경로가 다르다. 프롬프트·
  근거·채점은 같지만 `has_facts` 에는 모델 성질이 섞인다.

기계: `ko_eval_answer_run.py`(관문 2개 → 실행 → 누적) · `ko_eval_answer_quality.py`(채점) ·
`ko_eval_answer_verdict.py`(판정). 질의·gold·답변 본문은 `tests/eval/local/` 에만 — 다른 조직의
문서다.
