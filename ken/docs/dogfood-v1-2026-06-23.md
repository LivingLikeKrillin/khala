# ken v1 dogfood — 2026-06-23 (keyless, agent-driven)

First keyless self-run of the v1 cognitive-debt loop. There is **no
`ANTHROPIC_API_KEY` and no API call**: I (the Claude Code agent) am the cognition.
ken owns only the deterministic substrate — the question store, the append-only
attempt ledger, and the pure derivations (schedule / coverage / weakness). I read
the artifact, *I* wrote the questions, *I* graded the answers, and I fed the
verdicts in by hand through the primitives:

```
save-questions  →  due  →  record-attempt (×2)  →  coverage
```

The `review` command (the keyed, LLM-self-driving path) was deliberately **not**
used — this run proves the loop closes with the agent as the only intelligence.

## Commands (run from the repo root)

The v1 CLI is exposed as a module with a `__main__`. Manifest paths are relative
to the **repo root**, so the loop runs from there (not from `ken/`), pointing
`--manifest` at `ken/ken.manifest.yaml` and isolating the stores under `ken/`:

```bash
export PYTHONPATH=ken/src PYTHONUTF8=1 PYTHONIOENCODING=utf-8
AID=ad4940ce2f44
HASH=sha256:fa40aeb0998e8079d91bf7fd2ed071fbb5cf7152c7a4d546549af74e4901b933
QSTORE=ken/dogfood.questions.json
LEDGER=ken/dogfood.attempts.jsonl

# --help works first
python -m ken.cli --help

# 1) I generate the questions, feed them on stdin (one per line)
printf '%s\n' \
  '...q1...' '...q2...' '...q3...' \
  | python -m ken.cli save-questions "$AID" --hash "$HASH" \
      --manifest ken/ken.manifest.yaml --questions "$QSTORE"

# 2) confirm the 3 now show as due
python -m ken.cli due --as kr --manifest ken/ken.manifest.yaml \
  --questions "$QSTORE" --ledger "$LEDGER"

# 3) record TWO attempts — one PASS, one FAIL on a different question
python -m ken.cli record-attempt --as kr --artifact "$AID" \
  --question 1021cc6f8391 --passed --score 0.9 \
  --manifest ken/ken.manifest.yaml --questions "$QSTORE" --ledger "$LEDGER"
python -m ken.cli record-attempt --as kr --artifact "$AID" \
  --question 156f815198de --failed --score 0.3 \
  --manifest ken/ken.manifest.yaml --questions "$QSTORE" --ledger "$LEDGER"

# 4) coverage — still an orphan; failed question in the weakness map
python -m ken.cli coverage --as kr --manifest ken/ken.manifest.yaml \
  --questions "$QSTORE" --ledger "$LEDGER"
```

(The `dogfood.*` stores are scratch — deleted after the run, not checked in.)

## Friction notes (for v2)

1. **cwd vs. manifest paths.** The manifest stores repo-root-relative paths
   (`nexus/nexus/search/signals.py`), so the CLI only resolves them when run from
   the repo root — but the package isn't installed, so it needs `PYTHONPATH=ken/src`
   and an explicit `--manifest ken/ken.manifest.yaml`. The "`cd ken && python -m
   ken.cli`" form fails (`ModuleNotFoundError` + unresolvable paths). v2 should
   either pin paths relative to the manifest's own location or ship an installed
   `ken` entrypoint so cwd stops mattering.

2. **The hash is needed before `save-questions`, but no command just prints it.**
   I had to import `registry.load_manifest` to read `content_hash`. `due` only
   emits `needs-questions <id>` without the hash, so there's a chicken-and-egg:
   to save questions I must already know the hash that `save-questions` will then
   re-check. A `ken hash <artifact_id>` (or printing the expected hash in the
   `needs-questions` line) would close that gap.

3. **No per-artifact coverage view / question listing.** To get question ids I
   parsed `due` output; to confirm the weakness I read the global `coverage`. For
   a single-artifact review session a `ken status <artifact_id>` (its questions,
   each one's pass/fail/never state, and whether it's vouched) would be the
   natural unit — the current commands are all manifest-wide.
