# 조각은 분야마다 있고 조립한 곳은 없다

2026년 9월 25일까지 공개된 기록을 여섯 갈래(엔터프라이즈 아키텍처와 조직 문서 정책·데이터 거버넌스·요구사항 추적성과 문서 방법론·카탈로그와 지식관리 제품·LLM/RAG 연구·국내)로 나눠 훑은 결론은, **이 구상을 통째로 — 서비스→기능→세부 지도, 세부마다 사람이 고른 정본 포인터, 결정자와 시점, 기계 검증, 「정본 아직 없음」 허용, 그 밑의 전문·임베딩 검색 — 주창하거나 구현한 사례는 국내외 어디에도 없다**는 것이다. 그러나 여섯 속성 하나하나에는 이름 붙은 선례가 있다. 데이터 거버넌스는 요소 단위의 사람 지정을 "authoritative data source/set"(미 국방부·연방 데이터 전략)이라 부르고, 속성 단위 판정을 MDM 의 "survivorship", 열 단위 정본 URL 을 데이터 계약 표준 ODCS 의 `authoritativeDefinitions` 라 부른다. 요구사항 추적성은 낡은 포인터를 "suspect link", 부모 없는 항목을 "orphan item" 이나 `derived` 라 부르며, Doorstop 은 링크마다 대상의 fingerprint 를 저장해 대상이 바뀌면 자동으로 suspect 로 떨어뜨리고 사람이 `clear` 해야 다시 믿는다. 문서 방법론에는 Google 의 "designate canonical documentation" 과 `freshness: { owner, reviewed }`, Martraire 의 Living Documentation(reconciliation mechanism·living curation)이 있고, Wikidata 는 문장 하나마다 사람이 preferred/normal/deprecated rank 를 매기고 "reason for rank" 를 적으며 normal 이 「판단 없음」이다. 가장 가까운 결합은 DoD ADS(요소·스튜어드·범위와 목적·카탈로그), ODCS(형식 있는 포인터), Wikidata(항목별 사람 판정과 중립 기본값), Doorstop/ReqToCode(기계 검증 포인터), Chromium `flag-metadata.json`(항목별 소유자·만료·생성된 검사)인데 각각 두세 속성이 빠진다. 무슨 일이 있었나를 보면 채택 증거는 얇고 프로그램 수준에서는 대체로 부정적이다 — BCBS 239 는 10년 뒤 31개 은행 중 **2곳**만 완전 준수(2019년엔 0곳), 추적성 실무자의 **80%** 가 비용을 첫째 장애물로 꼽고, 산업 추적 행렬은 suspect link 로 가득 차며, 데이터 카탈로그는 "owner 가 여섯 달 전에 퇴사한" 채 "digital graveyard" 가 되고, Google 의 옛 위키는 폐기 시점에 문서 **약 90%** 가 몇 달간 조회도 수정도 없었으며, Guru 는 2026년 1월 검증 기본값을 「1개월」에서 「만료 없음」으로 바꿨고, Microsoft Viva Topics(2025-02)와 SpecFlow+ LivingDoc(2025)은 사라졌다. 살아남은 등록부(Airbnb Minerva 12,000 metrics·Uber uMetric 10K+ metrics·Lyft Amundsen·Rippling·Chromium flags)는 예외 없이 **매일 실행 경로 안**에 있었고 **이름 붙은 희소한 판정 역할**이 계층으로 위임했다. 검색 위에 권위 신호를 얹은 효과는 측정돼 있으나(오라클 라벨로 **+25~32 EM**, 결정론적 신선도 규칙으로 **+10.8pp**, 4 KB 손으로 쓴 semantic layer 로 **+17~23pp**) 전부 문서·출처 단위의 기계 라벨이지 사람의 항목별 포인터가 아니며, 「잘못된 버전에서 답한 비율」을 측정한 곳은 하나도 없다. 국내에는 이 구상을 주창한 글도 구현도 없고, 가장 가까운 것은 LINE Words(사람이 쓰는 용어 정본), 우아한형제들 물어보새의 「검증된 데이터 마트」, 2026년 9월에 몰린 개인 프로젝트 셋의 `file:line` 인용 검사, 그리고 출처 **종류**에 권위 순서를 매긴 개인 블로그 — 바로 이 구상이 거부하는 방식 — 이며, 「정본」이라는 낱말 자체는 국내 법률·기록관리에서 다른 뜻으로 쓰인다.

## 통째로 부르는 이름은 없고, 분야 다섯이 조각마다 다른 이름을 쓴다

이 구상의 「정본」에 가장 가까운 정식 용어는 데이터 거버넌스에 있다. 미 국방부 DoDI 8320.07 은 authoritative data source 를 "a recognized or official data production source with a designated mission statement, source, or product that publishes reliable and accurate data for subsequent use by customers" 로 정의하고, CDAO 의 「Authoritative Data Set 지정 지침」은 ADS 를 "one or more data elements that a data producer, working with their Data Steward, has identified as authoritative for a specific scope and purpose" 라고 적으며 지정은 Data Steward 가 하고 "DoD's federated data catalog" 에 기록하게 한다 — 다만 두 PDF 모두 이번 조사에서 403 으로 열리지 않아 **검색 요약만 확인한 문장**이다 ([DoDI 8320.07](https://www.esd.whs.mil/portals/54/documents/dd/issuances/dodi/832007p.pdf); [CDAO ADS 지침](https://www.ai.mil/Portals/137/Documents/Resources%20Page/Guidance%20on%20Designating%20Authoritative%20Data%20Sets.pdf)). 미 연방 데이터 전략의 「Data Governance Playbook」(2020-07)은 본문을 열었고, 거버넌스 조직이 "designate authoritative data systems for common elements" 해야 한다며 점검 항목으로 "Consult with agency stakeholders to determine which data system should be the authoritative source for each priority common data element" 를 두어 **요소 단위의 사람 결정**을 명시한다 ([Federal Data Strategy playbook, p.12](https://resources.data.gov/assets/documents/fds-data-governance-playbook.pdf)). DAMA/MDM 어휘는 시스템 단위와 레코드 단위를 가른다. system of record 는 데이터가 생성·유지되는 권위 시스템, system of reference 는 정확·완전·최신 데이터를 담을 것으로 기대되는 권위 시스템, golden record 는 그 안의 올바른 레코드 하나이고, 어느 값이 살아남느냐를 정하는 속성 단위 규칙이 survivorship 이다 — Profisee 는 "'trust the ERP for all customer data' can quickly lead to problems. Instead, build logic based on each attribute needed for a record" 라고 쓴다 ([Nwaneri, 2019-02-12](https://medium.com/all-things-data/system-of-record-system-of-reference-golden-records-and-other-confusing-terms-in-master-data-23a87064bc05); [Profisee, 2025-10-23](https://profisee.com/blog/mdm-survivorship/) [vendor]). ECB 의 2024년 리스크 데이터 집계 가이드는 "critical data element" 마다 "data owner" 를 두고 속성 수준의 lineage 를 요구하되, "golden source" 나 "authoritative source" 라는 말은 한 번도 쓰지 않는다(본문 텍스트 추출 0건) ([ECB, 2024-05, p.9–10](https://www.bankingsupervision.europa.eu/ecb/pub/pdf/ssm.supervisory_guides240503_riskreporting.en.pdf)). 카탈로그와 BI 제품은 자산 단위 배지 어휘 — Alation 의 Trust Flags(Endorsement/Warning/Deprecation), Atlan 의 Verified/Draft/Deprecated/No certificate, Microsoft Fabric 의 Promoted/Certified/Master data, Tableau 의 Certified — 를 쓰고, 데이터 계약 표준 ODCS(Linux Foundation Bitol, v3.0.0 은 2024-10-05 승인)는 계약·테이블·열 수준에 `authoritativeDefinitions` 라는 `{type, url}` 목록을 두어 "URL to the authority" 를 가리키게 한다 ([ODCS v3.0.2](https://bitol-io.github.io/open-data-contract-standard/v3.0.2/)). 지표 등록부는 스스로를 "a single source of truth for each metric definition"(Airbnb Minerva)·"the single source of truth for business metrics"(Uber uMetric)라 부른다 ([Airbnb, 2020-11-24](https://medium.com/airbnb-engineering/data-quality-at-airbnb-870d03080469); [Uber, 2021-01-12](https://www.uber.com/blog/umetric/)).

엔터프라이즈 아키텍처는 권위를 데이터 엔티티와 그것을 마스터하는 애플리케이션 단위로 둔다. TOGAF 9.1 의 Data Dissemination Diagram 은 "application ownership of the master reference for data" 를 보여 줄 수 있다고 하고 ([TOGAF artifacts, QualiWare 미러](https://coe.qualiware.com/resources/togaf/togaf-artifacts/)), LeanIX·Ardoq 의 business capability map 문서에는 「capability 별 system of record」 필드가 없으며, 2025년 LeanIX 커뮤니티 답변은 어느 fact sheet 가 관계를 마스터하느냐를 모델 기능이 아니라 프로세스 결정으로 돌린다 ([LeanIX community, 2025-04-17](https://community.leanix.net/sap-leanix-onboarding-64/which-fact-sheet-masters-data-1191)). GitLab 은 이 구상이 기대는 구분을 문장으로 적은 유일한 조직이다: "while it is possible to have a system of record that is also a single source of truth, simply just being a system of record doesn't directly imply it is the single source of truth" ([GitLab handbook usage](https://gitlab.com/gitlab-com/content-sites/handbook/-/raw/main/content/handbook/about/handbook-usage.md)). 즉 지도는 **포인터의** SSOT 이고 가리켜진 문서·코드는 **값의** system of record 라는 이 구상의 분리를, GitLab 은 이름만 갖고 있다. GitLab 의 정본 단위는 페이지이고 소유자는 code owner(Maintainers)이며 "the handbook is not what we hope to do… It is what we do right now" 이지만, 답이 없으면 "immediately make a merge request to add it" 하라고 해 「미결」 상태를 「지금 써라」로 접는다 ([GitLab communication](https://handbook.gitlab.com/handbook/communication/)).

요구사항 추적성(requirements traceability)은 식별자로 산출물을 잇는 가장 오래된 실천이다. Gotel & Finkelstein(1994)의 정의 "the ability to describe and follow the life of a requirement, in both a forwards and backwards direction" 이 지금도 표준과 벤더 문서에 그대로 인용되고, 같은 논문은 실무자들이 가장 유용하다고 답한 pre-RS 정보가 "(a) the ultimate source of a requirement; and (b) those involved in the activities which led to its inclusion and refinement" 이며 "The common approach, listing contributors to information in document fields, was felt insufficient" 이라고 적는다 — 「누가 정했나」가 1994년에 이미 통계적으로 유의한 요구였다는 뜻이다 ([Gotel & Finkelstein, 1994](https://discovery.ucl.ac.uk/749/1/2.2_rtprob.pdf)). 도구 어휘는 낡은 포인터의 이름을 이미 갖고 있다: IBM DOORS 의 "suspect links"("Linked objects are marked as having suspect links if the object that they are linked to has changed"), Jama Connect 의 "Orphan Item"·"Missing Downstream"·"Causing suspect", Doorstop 의 "unreviewed changes" 와 `derived`, OpenFastTrace 의 "not ok (transitive)", Sphinx-Needs 의 `allow_dead_links`, DO-178C 의 "trace data"(§11.21) ([IBM DOORS 9.7.2](https://www.ibm.com/docs/en/engineering-lifecycle-management-suite/doors/9.7.2?topic=data-suspect-links-changed-objects); [Jama Connect](https://help.jamasoftware.com/ah/en/manage-content/coverage-and-traceability/relationships/relationship-status-indicator.html); [Doorstop](https://raw.githubusercontent.com/doorstop-dev/doorstop/develop/docs/reference/item.md); [OpenFastTrace](https://openfasttrace.itsallcode.org/user_guide/reference/input_format_support.html)). 소프트웨어 제품 라인의 feature model(FODA, SEI 1990)은 「서비스→기능」 계층의 형식적 조상이지만 목적이 가변성이고 기능↔자산 매핑은 presence condition 이지 정본 포인터가 아니며, 2024년 MODELS 논문은 여전히 기능과 요구사항의 경계가 "ambiguous" 하다고 쓴다 ([Wikipedia: Feature model](https://en.wikipedia.org/wiki/Feature_model); [Chiang et al., MODELS 2024](https://dl.acm.org/doi/10.1145/3652620.3688349)).

문서 방법론 쪽의 이름은 Google 과 Martraire 에게 있다. 『Software Engineering at Google』 10장은 "Documents without owners become stale" 이라 하고, 소유자가 다른 문서들이 충돌하면 "designate canonical documentation: determine the primary source and consolidate other associated documents into that primary source (or deprecate the duplicates)" 하라며, `freshness: { owner: 'username' reviewed: '2019-02-27' }` 블록을 기계가 읽어 예컨대 석 달 안 건드린 문서의 소유자에게 메일을 보낸다고 적는다 ([SWE at Google, ch.10](https://abseil.io/resources/swe-book/html/ch10.html)). Cyrille Martraire 의 『Living Documentation』(2019)은 목차만으로도 이 구상의 어휘 대부분을 미리 갖고 있다 — "Identifying Authoritative Knowledge", "Single-Source Publishing", "Setting Up a Reconciliation Mechanism (aka Verification Mechanism)", "Running Consistency Tests", "Living Curation", "Decision Logs", "Linked Knowledge", "Documentation Bankruptcy" — 다만 본문은 이번에 열지 못했다(O'Reilly 403) ([InformIT 목차](https://www.informit.com/store/living-documentation-continuous-knowledge-sharing-by-design-9780134689326); [InfoQ Q&A, 2019-09-22](https://www.infoq.com/articles/book-review-living-documentation/)). 소유권 파일 계열(GitHub CODEOWNERS, Kubernetes OWNERS, Chromium OWNERS)은 경로를 리뷰어에 잇고, Backstage 는 `spec.owner` 를 필수로 두되 `metadata.links` 는 "not intended to drive any additional functionality within Backstage" 라고 명시한다 ([GitHub docs](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners); [Backstage descriptor format](https://backstage.io/docs/features/software-catalog/descriptor-format/)). Python PEP 1 은 정본이 생애주기에 따라 옮겨 간다는 규칙을 명문화한 드문 텍스트다: Final 이 되면 "a PEP is considered a historical document rather than a living specification" 이고 "Formal documentation of the expected behavior should be maintained elsewhere" 다 ([PEP 1](https://peps.python.org/pep-0001/)). 같은 축의 양극이 2025년에 나란히 나왔는데, GitHub spec-kit 은 "Code was truth" 를 뒤집어 "Specifications don't serve code—code serves specifications" 라 하고, Adam Ard 는 "If your ADR is accurate after three sprints, you're ignoring what the code is trying to tell you" 라며 코드를 정본으로 둔다 ([spec-kit](https://github.com/github/spec-kit/blob/main/spec-driven.md); [Ard, 2025-07-25](https://rethinkingsoftware.substack.com/p/good-docs-describe-bad-docs-prescribe)). 이 구상의 「세부마다 사람이 정한다」는 두 규칙을 동시에 쥐는 방법인데 — 이 한도의 정본은 코드 상수, 저 규칙의 정본은 정책 문서 절 — 그렇게 쓰자고 한 저자는 PM·엔지니어링 문헌 어디에서도 찾지 못했다.

지식관리 제품은 이 층을 "Verification" 이라 부른다: Guru 의 Verifier·Verification Interval·Verified/Unverified/none 세 상태와 Trust Score, Glean·Notion·Slab·Tettra·Confluence 의 verified 배지와 만료 ([Guru help](https://help.getguru.com/docs/what-is-verifcation); [Notion help](https://www.notion.com/help/wikis-and-verified-pages)). Wikidata 는 문장(statement) 단위의 사람 판정 어휘를 갖는다 — preferred/normal/deprecated rank, "References merely state where a data value comes from; ranks indicate what data value is considered the most correct", 그리고 "reason for preferred rank (P7452)"·"reason for deprecated rank (P2241)" 한정자 ([Wikidata Help:Ranking](https://www.wikidata.org/wiki/Help:Ranking)). 코딩 에이전트 생태계는 2025년에 같은 규칙을 다른 말로 재발명했다: HumanLayer 의 "Prefer pointers to copies… include `file:line` references to point Claude to the authoritative context", Cursor 의 "Reference files instead of copying their contents—this keeps rules short and prevents them from becoming stale as code changes", Anthropic 의 "link to docs instead" 와 `@path/to/import` ([HumanLayer, 2025-11-25](https://www.humanlayer.dev/blog/writing-a-good-claude-md); [Cursor docs](https://cursor.com/docs/context/rules); [Claude Code best practices](https://code.claude.com/docs/en/best-practices)). 그리고 「지도는 가리키되 담지 않는다」는 원칙 자체는 오래됐다 — Davenport & Prusak(1998)의 knowledge map 은 "points to knowledge but does not contain it"(검색 요약만 확인, 본문 미열람)이고, Wegner(1985)의 transactive memory 는 구성원이 "what information is available for retrieval" 의 metamemory 를 나눠 갖는 것이다 ([Working Knowledge, Google Books](https://books.google.com/books/about/Working_Knowledge.html?id=-4-7vmCVG5cC); [Wikipedia: Transactive memory](https://en.wikipedia.org/wiki/Transactive_memory)). 이 구상에 굳이 이름을 붙이자면 조사 노트가 제안한 합성이 가장 정직하다: **element-level authoritative-source designation(연방·DoD 의 뜻) + typed `authoritativeDefinitions` 식 포인터(ODCS) + trust-flag provenance(Alation: 누가·언제·왜) + contract-style verification(dbt/DataHub)** — 조각마다 선례가 있고, 결합에는 없다.

| Living Documentation | authoritative knowledge, reconciliation mechanism, living curation, decision log | 코드에 붙은 지식 조각 | 생성(single-source publishing) | decision log | consistency tests | documentation bankruptcy |
| 대기업 문서 정책 | canonical documentation, freshness {owner, reviewed}, DRI, code owner | 문서·페이지 | 문서 자체 | 소유자·검토일 | 메일 알림 | 없음(없으면 지금 써라) |
| 지식관리 제품 | Verification, Verifier, verification interval, Trust Score, "Verified only" | 카드·페이지 | 문서 자체 | 검증자·시점·만료 | 없음(달력 알림) | none / unverified |

## 가장 가까운 선례 여덟은 이렇게 만들어졌고, 각각 두세 속성이 빠진다

**미 국방부 ADS 와 연방 playbook** 은 「항목별로 사람이 정본을 정하고 카탈로그에 적는다」는 뼈대를 정부 표준으로 갖춘 유일한 사례다. 지정은 "a mission decision, which will be officially designated by Data Stewards" 이고 지정마다 "(1) quality, (2) scope, and (3) purpose" 를 적으며, 같은 데이터 요소가 어떤 범위에서는 권위이고 다른 범위에서는 아닐 수 있다 — "for a specific scope and purpose" 가 이 구상의 「세부마다, 용도마다」에 가장 가까운 공식 문구다(전부 검색 요약만 확인) ([CDAO ADS 지침](https://www.ai.mil/Portals/137/Documents/Resources%20Page/Guidance%20on%20Designating%20Authoritative%20Data%20Sets.pdf)). 빠진 것은 단위(데이터셋이지 기능 세부가 아니다)와 포인터의 대상(시스템이지 문서 절이나 코드 심볼이 아니다), 그리고 확인 가능한 텍스트 안에서는 「아직 지정 안 됨」 상태다. **ODCS `authoritativeDefinitions`** 는 포인터의 형식을 갖춘 유일한 표준이다: 열 하나가 `businessDefinition` URL 과 `transformationImplementation` URL 과 `implementation` URL 을 **동시에** 가질 수 있고, `logicalType` 과 `physicalType` 이 갈라져 있으며, `quality` 규칙은 별도 블록이다 ([ODCS v3.0.2](https://bitol-io.github.io/open-data-contract-standard/v3.0.2/)). 이것은 한 세부(예: 검증 상한)가 정책 문서 절·검증기·스키마 제약이라는 세 층에 각각 정본을 갖는 상황을 「값 셋」이 아니라 「형식 있는 포인터 셋」으로 적는 직접적 선례다. 빠진 것은 포인터에 결정자·시점이 없고(`team` 의 `dateIn`/`dateOut` 은 사람 이력이지 결정 기록이 아니다), 포인터를 검증하는 기제가 없다는 점이다.

**Wikidata 의 rank** 는 이 구상의 데이터 구조에 가장 닮은 기존 모델이다. 문장마다 사람이 preferred(합의된 최신 값)·normal(기본값, "provides no judgement or evaluation of a value's accuracy and currency and therefore should be considered neutral")·deprecated(오류 또는 낡은 지식)를 매기고, 옛 값은 deprecated 가 아니라 start/end time 한정자로 남기며, 판정 이유를 P7452/P2241 로 적는다 ([Wikidata Help:Ranking](https://www.wikidata.org/wiki/Help:Ranking)). 「항목별 사람 판정 + 출처 포인터 + 이유 + 중립 기본값」이 다 있고, 빠진 것은 검색 층(LLM 이 없다)과 포인터 검증(reference 는 인용이지 기계가 확인하는 링크가 아니다)이다. **Doorstop·OpenFastTrace·ReqToCode** 는 「기계 검증 가능한 포인터」의 세 가지 구현이다. Doorstop 은 항목을 YAML 파일로 두고 `links` 에 부모 UID 와 "the fingerprint of the parent when it last reviewed" 를 저장해 부모가 바뀌면 suspect 로 떨어뜨리고, 항목 자체의 `reviewed` 해시로 "unreviewed changes" 를 잡으며, 외부 파일 `references` 에 SHA256 을 달고, 부모가 없어야 정상인 항목은 `derived` 로 표시해 「링크 없음」을 오류가 아니라 상태로 만든다 ([Doorstop item](https://raw.githubusercontent.com/doorstop-dev/doorstop/develop/docs/reference/item.md); [Doorstop validation](https://raw.githubusercontent.com/doorstop-dev/doorstop/develop/docs/cli/validation.md)). OpenFastTrace 는 ID 자체에 revision 을 넣어(`req~name~2`) 옛 revision 을 가리키는 커버리지를 드러내고, ReqToCode(2026-03)는 요구사항을 언어 네이티브 코드 요소 "Traceable" 로 생성해 "A broken trace is a broken build" 를 컴파일러가 보장하되 "no quantitative evaluation" 이라고 스스로 적는다 ([OpenFastTrace](https://openfasttrace.itsallcode.org/user_guide/reference/console_tracing_report.html); [ReqToCode, arXiv 2603.13999](https://arxiv.org/html/2603.13999)). 셋 다 단위가 요구사항이고 권위 방향이 명세→설계→코드→테스트로 **산출물 층에 고정**돼 있어, 「이 세부의 정본은 코드이고 저 세부의 정본은 문서」라는 항목별 선택이 없다.

**Chromium flag ownership** 은 엔지니어링 쪽에서 「항목·소유자·만료·기계 검사」를 다 갖춘 드문 지도다. `chrome://flags` 의 모든 항목은 `//chrome/browser/flag-metadata.json` 에 소유자를 적어야 하고, 만료는 milestone 으로 정하며("at least one milestone after you expect your feature to have launched to stable"), 만료된 플래그 목록은 `generate_expired_list.py` 가 생성하고, 만료 안 하는 플래그는 "the flags team requires a comment in the json file as to the rationale" 다 ([Chromium flag_ownership.md](https://chromium.googlesource.com/chromium/src/+/main/docs/flag_ownership.md)). 빠진 것은 포인터의 대상이 문서가 아니라 이메일 주소라는 점과, 「미결」 상태가 없다는 점(소유자 없는 플래그는 규칙 위반)이다. **LaunchDarkly Code references** 는 플래그 키 문자열을 코드에서 스캔해 파일·행을 잇고 참조가 모두 사라지면 "extinction event" 를 기록하며 maintainer 와 stale 판정(생성 30일 이상·7일 inactive)을 갖는다 — 값이 코드에 리터럴로 있어야만 성립하는 검증이다 ([LaunchDarkly](https://launchdarkly.com/docs/home/flags/code-references); [Flag health](https://launchdarkly.com/docs/home/releases/flag-health)). **Zally** 는 「규칙 ↔ 정본 문서 절」의 가장 깔끔한 사례로, API 린터의 규칙 id 가 곧 가이드라인의 앵커(`#116`)라 위반마다 정본 절 링크가 붙는다 — 소유자·만료는 없고 가이드라인 문서가 소유자다 ([Zally rule-development](https://github.com/zalando/zally/blob/main/documentation/rule-development.md)). **Swimm** 은 문서 안의 코드 스니펫·"Smart Tokens"·경로를 커밋마다 대조해 "Up to date / Out of sync / Outdated" 세 상태를 내고 판단이 안 서면 "we leave a task for someone on your team to reselect the snippet" 하는데, 단위가 문서이지 사실이 아니다 ([Swimm Auto-sync, 2021-12-30](https://swimm.io/blog/how-does-swimm-s-auto-sync-feature-work/); [Swimm, 2022-06-28](https://swimm.io/blog/swimm-native-integrations)).

「누가 언제 정했나」를 결정 단위로 기록하는 곳은 셋뿐이다. Alation 의 Trust Check Flag 객체는 `flag_type`·`flag_reason`·`ts_created`·`user`·`subject` 를 갖고 Warning/Deprecation 에는 이유가 **필수**이며 열·쿼리 수준까지 내려간다 ([Alation Flags API](https://developer.alation.com/dev/reference/flags-api); [Alation Trust Flags](https://docs.alation.com/en/latest/welcome/BestPractices/UseTrustFlagstoProceedwithConfidence.html) [vendor]); Snowflake Cortex Analyst 의 Verified Query Repository 는 `verified_by`·`verified_at` 을 갖되 둘 다 선택 항목이고 저장하는 것은 포인터가 아니라 SQL 사본이다 ([Snowflake VQR](https://docs.snowflake.com/en/user-guide/views-semantic/verified-query-repository) [vendor]); Wikidata 는 위와 같다. Atlan·Databricks·Fabric 은 인증자와 시점이 기록되는지 문서에 적지 않는다. 「정본 아직 없음」을 **결정의 한 갈래**로 적은 곳은 Uber 가 유일하다 — uMetric 의 Verification Committee 가 답해야 할 질문에 "In the case where none of the data sources is qualified, what actions should be taken and who are the owners?" 가 들어 있다 ([Uber, 2021-01-12](https://www.uber.com/blog/umetric/)). 나머지는 부정형(배지 없음·unverified·deprecated·Draft)이거나 요청 큐(Glean 검증 요청·Tettra Page requests·Slite 실패 질의 패널)다.

이 구상이 AI 코딩 시대에 재발명되고 있다는 신호도 둘 있다. `ngocquang/source-of-truth`(MIT, 약 60 커밋)는 "The catalog is the source of truth for 'what exists, why it exists, and what rules apply'. The code is the source of truth for 'how it works'" 라 선언하고 기능별 `specs/spec-<feature>.md` 와 날짜 붙은 `decisions/` 를 두며, 동기는 "Stop your AI from silently deleting features it doesn't know exist" 다 ([ngocquang/source-of-truth](https://github.com/ngocquang/source-of-truth)). `datarelay-labs` PR #54(2026-09-20)는 `docs/architecture/source-of-truth-index.md` 를 "the canonical authority map" 으로 세우고 일곱 권위 층을 정하며 사본을 걷어내고 파일명·버전 불일치를 "integrity findings" 로 적는다 — 저장소 이름이 fetch 결과와 URL 에서 달라 정체는 불확실하다 ([datarelay-labs PR #54](https://github.com/datarelay-labs/gdc-platform/pull/54)). 둘 다 이 구상이 더하는 두 속성 — 명시적 「정본 아직 없음」과 포인터의 기계 검증 — 이 없고, 소유자·시점 필드도 없다. 정리하면 이렇다.

## 무슨 일이 있었나: 살아남은 등록부는 실행 경로 안에 있었고, 죽인 것은 기술이 아니라 유지 비용이었다

프로그램 수준의 독립 증거는 얇고 대체로 부정적이다. 은행 규제 BCBS 239 는 「리스크 데이터 유형마다 단일 권위 출처를 지향하라」는 원칙을 2013년에 내고 2016년부터 G-SIB 에 적용했는데, BIS 의 2023-11 평가는 "additional work is required at all banks" 라 했고 Deloitte 의 요약은 **31개 은행 중 완전 준수 2곳, 2019년엔 0곳**이라 적으며, ECB 는 2024년 가이드에서 자기 표본의 "none" 이 완전히 따랐고 "the observed progress stalled on some of the key deficiencies, such as the effectiveness of governance arrangements" 라고 썼다 ([BIS press, 2023-11-28](https://www.bis.org/press/p231128.htm); [Deloitte, 2024-02-23](https://www.deloitte.com/us/en/services/audit/blogs/accounting-finance/bis-assessment-bcbs-239-principle-compliance.html) [컨설팅 요약]; [ECB, 2024-05, p.2](https://www.bankingsupervision.europa.eu/ecb/pub/pdf/ssm.supervisory_guides240503_riskreporting.en.pdf)). Gartner 의 「2027년까지 D&A 거버넌스 이니셔티브의 80% 가 실패한다」는 측정이 아니라 예측이고, 2026-03 조사(n=223)는 실패 원인으로 문화적 저항 60% 대 예산 40% 를 든다 ([Gartner, 2024-02-28](https://www.gartner.com/en/newsroom/press-releases/2024-02-28-gartner-predicts-80-percent-of-data-and-analytics-governance-initiatives-will-fail-by-2027-due-to-a-lack-of-a-real-or-manufactured-crisis-); [Gartner, 2026-09-21](https://www.gartner.com/en/newsroom/press-releases/2026-09-21-gartner-predicts-60-percent-of-organizations-that-ignore-data-governance-culture-challenges-will-fail-to-govern-ai-successfully-by-2027)). 추적성 쪽은 자기 분야의 진단이 더 솔직하다. ICSE FOSE 2014 는 "traceability is often conducted in an ad-hoc, after-the-fact manner", 링크는 산출물이 바뀔 때 갱신되지 않아 "it is not uncommon to see an industrial trace matrix populated with a high percentage of suspect links" 라 했고, 연구 노력의 44% 가 링크 **생성**, 15% 만 **유지**에 갔다고 센다 ([Cleland-Huang et al., FOSE 2014](http://selab.netlab.uky.edu/homepage/publications/2014-ICSE-FOSE.pdf)). 2023년 실무자 조사(n=55, 13개국)는 **80% 가 비용을 첫째 장애물**로 꼽고 63% 가 "clear roles/responsibilities" 를 요구했으며 ([Ruiz et al., 2023](https://link.springer.com/article/10.1007/s00766-023-00408-9)), Apache 프로젝트 여섯 곳의 실측은 커밋의 약 48% 가 이슈에 링크되지 않았음을 보였다(초록의 "60% linked" 와 본문의 "48% unlinked" 는 분모가 다르다) ([Rath et al., ICSE 2018](https://arxiv.org/pdf/1804.02433)). 포인터 자체의 부패율도 측정돼 있다: GitHub 23,110개 저장소의 커밋 링크 1,820만 건 중 **70% 가 decay** 를 겪었고 ([Xiao et al., 2023](https://arxiv.org/abs/2305.16591)), 3,000개 이상 프로젝트의 대부분이 이력 어느 시점엔 코드에서 사라진 식별자를 문서에 남기고 있었다 ([Tan et al., 2022](https://arxiv.org/abs/2212.01479)). 반대편 증거도 하나 있다 — 71명 통제 실험에서 추적성이 있으면 과제를 평균 24% 빨리, 정답을 50% 더 냈다는 Mäder & Egyed 의 수치인데, 이번 조사는 초록을 못 열어 **검색 요약과 벤더 블로그 재인용**으로만 확인했다 ([Springer](https://link.springer.com/article/10.1007/s10664-014-9314-z)).

문서와 카탈로그의 부패는 수치보다 1인칭 기록이 많다. Google 이 GooWiki 를 폐기할 때 "around 90% of the documents had no views or updates in the previous few months" 였고 ([SWE at Google, ch.10](https://abseil.io/resources/swe-book/html/ch10.html)), Grudin & Poole 의 WikiSym 2010 연구는 번성하는 기업 위키가 "a minority of the thousands" 라 했으며 ([Microsoft Research](https://www.microsoft.com/en-us/research/publication/wikis-at-work-success-factors-and-challenges-for-sustainability-of-enterprise-wikis/)), 2025년 Will Kelly 는 "92 wiki pages all tagged 'source of truth' that contradicted each other" 를 사례로 들며 "Most wiki pages are false not because they're wrong, but because they're frozen" 이라고 썼다 ([Kelly, 2025-08-20](https://willkelly.medium.com/your-wiki-is-gaslighting-you-39826f074e62)). 데이터 카탈로그 쪽에서 10개 조직 이상을 코치했다는 Österlin 은 "Month 3–6: … 70% are staging tables, test data, or deprecated assets… Year 2+: Digital graveyard" 라는 수명을 그리고, "if the 'owner' of the customer table is someone who left the company six months ago… the governance model is fiction", 숨은 비용은 "Data Stewardship Program (2–5 FTEs)" 와 "Ongoing Maintenance (15–25% of initial effort annually)" 라고 적는다 — 이 글은 Microsoft Purview 를 홍보하는 글이기도 하다 ([Österlin, 2025-08-26](https://medium.com/@marcoOesterlin/the-hard-truth-about-data-catalogs-why-microsoft-purview-unified-catalog-can-be-your-strategic-62372a052c94) [practitioner·vendor 겸]). Backstage 는 같은 부패를 기제 수준에서 인정한다: 프로젝트 FAQ 가 "Owners of catalog-info files will constantly be surprised by their files 'breaking' in ingestion, maybe a very long time after they were initially created" 이라 쓰고 ([Backstage FAQ](https://backstage.io/docs/features/software-catalog/faq/)), 한 SRE 는 "no team owns the catalog itself… Eventually the catalog falls into disrepair, and a new initiative is launched to 'fix the catalog'" 이라 적었으며 ([Chronicles of a SRE, 2026-07-25](https://chroniclesofasre.substack.com/p/service-catalogs-and-backstage-why)), 컨설턴트 출신 벤더는 "The catalog has stopped being an authoritative graph and started being documentation that was *supposed to be* authoritative" 라고 진단했다 ([Riftmap, 2026-05-07](https://riftmap.dev/blog/the-catalog-maintenance-trap/) [vendor]). 널리 퍼진 「Backstage 사내 채택률 10%」는 경쟁 벤더 글과 포럼에만 있고 1차 출처가 없으며, 독립 조사(DX, n=180)가 측정한 것은 포털 프로그램의 상태(72% 개발 중·28% 유지 모드)이지 카탈로그의 신뢰가 아니다 ([bex.co, 2026-07-12](https://bex.co/blog/2026/07/12/backstage-adoption-gap-plugin-upgrade-tax) [경쟁 벤더]; [DX, 2025-03-19](https://newsletter.getdx.com/p/backstage-and-the-developer-portal-market)).

제품의 방향 전환은 유지 비용의 간접 증거다. Guru 의 Verification 은 2015년 출시 때 "The default setting is 1 month" 였는데 2026년 1월 이후 만든 카드의 기본값은 "Does not expire" 이고, 같은 페이지는 "Automated verification eliminates 80% or more of manual review work" 라고 쓴다 — 예정된 사람 재검증을 고객이 지속하지 못했다는 추론이 가능하지만 벤더가 그렇게 말한 것은 아니다 ([Guru, 2015 출시글](https://www.getguru.com/blog/introducing-verification); [Guru help, 2026-09-16 갱신](https://help.getguru.com/docs/verifying-and-unverifying-cards) [vendor]). Microsoft 는 사람이 큐레이션하던 층을 걷어냈다: Viva Topics 는 2025-02-22 에 은퇴했고 "Topic pages that were generated entirely by AI… will no longer be available", Microsoft Search 의 관리자 큐레이션 Q&A 는 2025-03-31 에 사라졌으며 후속은 "your SharePoint pages are already indexed and will be used in responding to users' questions" 다 ([Microsoft Learn: Topics](https://learn.microsoft.com/en-us/microsoft-365/topics/changes-coming-to-topics?view=o365-worldwide); [Microsoft Learn: Search 은퇴](https://learn.microsoft.com/en-us/microsoftsearch/retirement-microsoft-search-bing)). 실행 가능한 명세를 정본으로 삼는 BDD 쪽은 Adzic 의 2020년 조사(응답 514)가 낸 수치가 남는다 — 예시를 쓰는 팀 중 **약 3분의 1은 자동화하지 않고**, 명세의 1차 정본이 "text files in version control" 인 곳은 **12%**, 작업 추적 도구인 곳은 57% 였으며, Seb Rose 는 "I see far more people using G/W/T for test automation than to support BDD/SbE" 라고 했다 ([Adzic, 2020-03-17](https://gojko.net/2020/03/17/sbe-10-years.html)). 대표 도구 SpecFlow+ LivingDoc 은 2025년 1월 사용자들이 "They pulled the plug on Specflow" 라고 보고했고, 오픈소스 후속 Reqnroll 의 리포팅은 2025년 8월에야 나왔다 ([Reqnroll discussion #196](https://github.com/orgs/reqnroll/discussions/196)). 포인터 기반 권위의 감사 사례는 하나가 있고 실패였다: 미 GAO 는 OMB 가 웹 페이지 하나를 "the authoritative source for data definition standards" 로 지정하고도 변경 절차가 없어 2018년 6월 요소 정의를 문서화된 절차 없이 바꿨다고 지적했고, 권고는 2024년 3월 현재 "Open" 이다 — 포인터가 가리키는 **대상의 변경 통제**가 없으면 포인터는 성립하지 않는다 ([GAO-19-284](https://www.gao.gov/products/gao-19-284)).

살아남은 등록부는 공통점이 뚜렷하다. Airbnb 는 2019년 사내 조사에서 "data scientists were finding it increasingly difficult to… identify which data sources met the high quality bar" 라는 결과가 나오자 Midas 인증을 만들었고, 모든 모델에 데이터 엔지니어링·데이터 사이언스 소유자를 요구하며 "Data Architects or Metrics Architects" 로 지정된 희소한 검토자가 Spec·Data·Code·Minerva 네 단계 리뷰를 하고, Dataportal 은 Minerva 지표를 검색 결과 맨 위에 올린다; 규모는 **지표 12,000개·차원 4,000개·생산자 200명 이상**인데 인증 소요 시간과 커버리지 비율은 어디에도 없다 ([Airbnb, 2020-11-24](https://medium.com/airbnb-engineering/data-quality-at-airbnb-870d03080469); [Airbnb Minerva, 2021-04-30](https://medium.com/airbnb-engineering/how-airbnb-achieved-metric-consistency-at-scale-f23cc53dea70)). Uber uMetric 은 **30개 팀 이상·지표 10K 이상**을 Verification Committee 로 다루다 위원회 대역폭이 모자라 tiering 으로 "Delegate more responsibilities and grant more permissions to metric authors" 했다 ([Uber, 2021-01-12](https://www.uber.com/blog/umetric/)). Lyft Amundsen 은 "time to discover an artifact to be 5% of the pre-Amundsen baseline", Spotify Lexikon 은 데이터 사이언티스트 사용률 75%→**95%** 를 보고하는데 둘 다 검색·발견 도구이지 인증 도구가 아니다 ([Lyft, 2019-04-02](https://eng.lyft.com/amundsen-lyfts-data-discovery-metadata-engine-62d27254fbb9); [Spotify, 2020-02-27](https://engineering.atspotify.com/2020/2/how-we-improved-data-discovery-for-data-scientists-at-spotify)). Rippling 은 엔지니어 700명 규모에서 `service_catalog.yaml` 한 파일에 서비스마다 Slack 채널 ID·Opsgenie 팀·경로 접두사를 적고 거기서 CODEOWNERS 를 **생성**하며 "Include the programmatic IDs instead of display names as the source of truth" 라는 규칙을 세웠고, 4주 이전 뒤 온콜을 "within 30 seconds" 에 찾게 됐다 ([Rippling, 2024-03-22](https://www.rippling.com/blog/code-ownership-at-rippling)). Meta 는 2026년 4월 데이터 파이프라인 저장소 세 곳 4,100개 파일에 대해 각 25–35줄짜리 context file 59개를 AI 에이전트 50개 이상으로 생성하고 critic 세 바퀴로 점수를 3.65→4.20 으로 올렸으며 "all referenced file paths were verified with zero hallucinations", 이후 "Every few weeks, automated jobs periodically validate file paths… and auto-fix stale references" 한다; 효과는 도구 호출·토큰 약 40% 감소와 복잡한 워크플로우 안내 2일→30분인데 전부 자기 보고다 ([Meta Engineering, 2026-04-06](https://engineering.fb.com/2026/04/06/developer-tools/how-meta-used-ai-to-map-tribal-knowledge-in-large-scale-data-pipelines/) [practitioner]). 이 넷과 Chromium flags 의 공통점은 등록부가 **매일 실행 경로 안**(대시보드가 그것을 읽고, 온콜 라우팅이 그것을 읽고, 빌드가 그것을 읽는다)에 있었고, 판정이 **이름 붙은 희소한 역할**에 있으면서 계층으로 위임됐다는 것이다. Atlan 의 Sankar 가 semantic layer 의 실패 원인으로 든 "The semantic layer wasn't something analysts touched every day" 는 그 역이다 ([Sankar, 2026-02-03](https://contextandchaos.substack.com/p/semantic-layers-failed-context-graphs) [vendor 계열 논평]).

## 검색 위에 권위를 얹은 효과는 측정돼 있으나, 전부 문서 단위의 기계 라벨이다

LLM 이 검색 결과의 충돌을 스스로 풀지 못한다는 것은 여러 편이 같은 방향으로 보여 준다. ClashEval(1,200문항 이상·6개 도메인·6개 모델)은 모델이 교란된 검색 내용을 받으면 **자기의 맞는 사전 지식을 60% 넘게 뒤집는다**고 했고, 토큰 확률을 백분위로 보정하면 GPT-4o 정확도가 61.5%→75.4%(+13.9pp), GPT-3.5 +16.2pp, Llama-3 +14.9pp 오르며 문맥 편향(맞는 사전 지식을 틀린 문맥으로 덮는 비율)은 약 30% 에서 10–11% 로 준다 ([ClashEval, arXiv 2404.10198](https://arxiv.org/html/2404.10198v3)). Wan 등은 모델이 "the relevance of a website to the query" 에 크게 기대고 "stylistic features that humans find important such as whether a text contains scientific references or is written with a neutral tone" 은 대체로 무시한다고 했고 ([Wan et al., ACL 2024](https://arxiv.org/abs/2402.11782)), Jin 등은 "RALMs follow the principle of majority rule" 과 확증 편향을 보고했다 ([Jin et al., 2024](https://arxiv.org/abs/2402.14409)). 즉 신호가 없으면 모델은 관련도·빈도·일관성·자기 확신으로 판정하며, 이것이 이 구상의 지도가 끊으려는 바로 그 경로다. 권위 신호를 **문서 단위로** 주면 효과는 크다: CrAM 은 문서 신뢰도로 attention head 를 조정해 Llama2-13B 의 TriviaQA EM 을 28.00→59.90(**+31.9**), Qwen1.5-7B 를 +25.5 올렸는데 그 라벨은 "manually assigned as 10 for high-credibility documents and 1 for low-credibility ones" 인 오라클 설정이거나 gpt-3.5 가 매긴 점수다 ([CrAM, AAAI 2025](https://arxiv.org/html/2406.11497)); CAG 는 프롬프트에 High/Medium/Low credibility 를 붙여 2WikiMHQA 60.4 대 50.4, 낡은 문서가 섞인 EvolvingTempQA 82.9 대 57.0 을 냈고 라벨은 검색 관련도×시의성×시나리오별 출처 등급의 산식이다 ([CAG, EMNLP 2024](https://arxiv.org/abs/2404.06809)); RA-RAG 는 사람 라벨 없이 출처 간 교차 확인의 가중 다수결로 NQ 0.745(vanilla 0.612)를 냈다 ([RA-RAG, EMNLP 2025](https://arxiv.org/abs/2410.22954)). 가장 구조적으로 닮은 것은 「신선도 판정을 LLM 에서 떼어 결정론적 규칙에 준」 논문이다 — BM25 로 찾고 LLM 이 후보 사실을 뽑되 승자는 `max(serial)` 이 정하게 하자 "prior-override" 와 "serial-comparison drift" 두 실패가 사라지고 **+10.8pp(67.2→78.0), 262K 문맥에서 +21pp** 가 났으며, 다만 LongMemEval 에서는 26/45 대 29/45 로 유의하지 않았고(McNemar p=0.45) v1 과 v2 의 단일 홉 수치가 조금 다르다 ([arXiv 2606.01435 v1](https://arxiv.org/html/2606.01435v1); [v2](https://arxiv.org/abs/2606.01435)). 이 구상은 그 규칙을 「가장 큰 serial 이 이긴다」에서 「사람이 지정한 포인터가 이긴다」로 일반화한 것이고, 그 일반화를 사람 라벨로 측정한 논문은 2023–2026년 사이에 하나도 찾지 못했다.

제품 쪽 기제는 넷으로 갈린다. 하드 필터는 Guru 뿐이다 — Knowledge Agent 를 "only verified sources, verified and neutral sources, or all sources" 로 제한할 수 있고 "Verified only" 면 미검증 외부 출처는 검색조차 안 한다 ([Guru help](https://help.getguru.com/docs/what-is-verifcation) [vendor]). 순위 가중은 Tableau("Certified data sources rank higher in search results"), Alation("Endorsement boosts an object's search rank… Deprecation penalizes an object's rank", 가중치 조정 가능), Power BI/Fabric(endorsed 항목 "given priority in searches"), Airbnb Dataportal 이다 ([Tableau](https://help.tableau.com/current/server/en-us/datasource_certified.htm); [Alation search](https://docs.alation.com/en/latest/welcome/CatalogBasics/FullPageSearch.html); [Fabric endorsement](https://learn.microsoft.com/en-us/fabric/governance/endorsement-overview) [모두 vendor]). Notion 은 가이드에서 "When a document is verified, it will be prioritized in search results and Q&A responses" 라 하지만 자사 Q&A 설명서는 권위 신호로 최근 수정과 조회수만 들고 verification 을 언급하지 않아 **자기모순**이다 ([Notion guide](https://www.notion.com/help/guides/verify-knowledge-your-teammates-can-trust-with-page-verification); [Notion Q&A 설명](https://www.notion.com/help/guides/understanding-how-q-and-a-finds-answers-can-help-you-get-better-results)). 경고 표시는 Fabric Copilot 이다 — 시맨틱 모델 저자가 "approved for Copilot" 을 켜지 않으면 "warnings that the answer quality could be low" 가 붙되 답은 볼 수 있다, 즉 「정본 아닌 출처로 답하되 그렇다고 말한다」는 자세다 ([Power BI Copilot](https://learn.microsoft.com/en-us/power-bi/explore-reports/copilot-chat-with-data-standalone) [vendor]). 답 사본의 우선은 지원 봇과 text-to-SQL 에 있다: Intercom Fin 의 Custom Answers 는 스태프 게시글대로 "will trigger *first* if they match the customer's question (before any AI answers…)" 이고(도움말 페이지는 401 이라 검색 요약만 확인) ([Intercom community, 2024-04-23](https://community.intercom.com/ask-the-intercom-team-about-fin-54/how-to-decide-between-snippets-and-custom-answers-7060)), Databricks Genie 는 편집 권한자가 넣은 예시 SQL 의 원문이 그대로 쓰이면 "verified answer" 를 붙이고, 13문항 벤치마크에서 컨텍스트를 더할수록 0%→54%→77%→100% 가 됐다(벤더 자기 측정) ([Databricks docs](https://docs.databricks.com/aws/en/genie-agents/tune-quality); [Databricks blog, 2026-02-06](https://www.databricks.com/blog/how-build-production-ready-genie-spaces-and-build-trust-along-way)). 어느 벤더도 「검증 유무에 따른 답변 품질 차이」를 발표하지 않았고, 인용은 예외 없이 **문서**를 인용하지 「누가 언제 이 값을 정했나」를 사실에 붙이지 않는다.

semantic layer 벤치마크는 「정의를 준다 대 안 준다」의 효과를 가장 깨끗하게 분리한다. dbt Labs 의 2026년 재측정(11문항×20회, 벤더)은 모델링된 프로젝트에서 text-to-SQL 90.0% 대 Semantic Layer **98.2%**(claude-sonnet-4-6), 84.1% 대 **100%**(gpt-5.3-codex)를 냈고, 실패 양상이 "plausible but incorrect answer" 대 "an error message. It never returns invalid data" 로 갈린다고 적었다 — 사본은 조용히 틀리고 간접 참조는 시끄럽게 깨진다는, 이 구상과 같은 논거다 ([dbt, 2026-04-07](https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026) [vendor]). Cube 의 짝지은 벤치마크(100문항, 벤더 VP 저술 arXiv)는 스키마만 줄 때 45.5–50.5% 에서 "a 4 KB hand-authored markdown document" 하나를 더하면 67.7–68.7%, **+17~23pp**, McNemar p≤0.0015 였고 비용은 "an afternoon of an analyst's time" 이었다 ([Cube, arXiv 2604.25149](https://arxiv.org/abs/2604.25149); [Cube blog, 2026-04-28](https://cube.dev/blog/why-semantic-layers-make-llm-analytics-reliable-a-paired-benchmark-across-three-frontier-models) [vendor 계열]). Snowflake 는 시맨틱 모델 유무로 평균 57%→78% 를 보고한다 ([Snowflake, 2025-03-31](https://www.snowflake.com/en/blog/engineering/agentic-semantic-model-text-to-sql/) [vendor]). 이 층들은 전부 정의를 **사본**으로 갖고(지표 식·필터·동의어·검증된 SQL), 그것을 왜 그렇게 정했는지 외부 문서 절이나 코드 심볼을 가리키는 곳은 없다.

코딩 에이전트의 「큐레이션된 지도」는 이 구상의 소비자 쪽 증거를 준다. AGENTS.md 는 "over 60k open-source projects" 가 쓰지만 ([agents.md](https://agents.md/)), ETH 그룹의 통제 실험은 context file 이 "does not generally improve task success rates, while increasing inference cost by over 20% on average" 이고 "repository overviews… are not helpful" 인 반면 "Instructions in the context files are well followed" 라고 했으며 ([Gloaguen et al., arXiv 2602.11988](https://arxiv.org/abs/2602.11988)), 다른 연구(10개 저장소·PR 124건)는 성공률은 비슷한데 중앙값 실행 시간 −28.64%·출력 토큰 −16.58% 를 냈다 ([Lulla et al., arXiv 2601.20404](https://arxiv.org/abs/2601.20404)). 둘은 다른 것을 측정한 것이고, Meta 의 −40% 도구 호출은 뒤쪽과 맞는다. 함의는 두 가지다 — 지도는 **설명이 아니라 판정(규칙·결정)** 을 실어야 에이전트가 따르고, 지도는 **소비자가 먼저 읽도록 배선돼야** 효과가 난다. 후자의 반례가 llms.txt 다: 30만 도메인 중 10.13% 가 채택했지만 인용 예측 모델에서 이 변수를 빼면 정확도가 오히려 올랐고, 약 900개 도메인의 서버 로그에서 AI 연구소의 요청은 "0 verified" 였으며, Google 의 John Mueller 는 "none of the AI services have said they're using LLMs.TXT" 라고 했다 ([Digital Applied, 2026-08-07](https://www.digitalapplied.com/blog/llms-txt-in-practice-adoption-evidence-2026); [PPC Land, 2025-07](https://ppc.land/llms-txt-adoption-stalls-as-major-ai-platforms-ignore-proposed-standard/)). 사내 어시스턴트라면 그 배선은 개발자 손에 있다 — 이것이 이 구상이 llms.txt 와 다른 출발점이다.

## 국내에는 주창한 글도 구현도 없고, 「정본」이라는 낱말부터 뜻이 다르다

국내 테크 블로그·컨퍼런스·벤더 문서·학술 자료를 한국어로 검색해 본문을 연 범위에서, **이 구상을 그대로 주창하거나 구현한 국내 사례는 없다.** 사내 RAG 를 만든 1인칭 기록은 여럿인데 권위의 처리가 전부 **적재·수집 쪽**이다. 토스 프론트엔드 챕터의 「박씨」는 기존 문서를 근거로 답하며 출처를 주고, 「실록봇」이 메신저의 문제 해결 대화를 감지해 문서 저장소에 PR 을 올리지만 문서 순위·낡은 문서·소유자·정본 상태는 기사에 없다 ([toss.tech, 2024-11-15](https://toss.tech/article/31643)). 우아한형제들의 교육 운영 RAG 는 "업데이트 시 기존 데이터를 전체 삭제 후 재적재하는 방식" 을 택했고 ([우아한형제들, 2026-03-10](https://techblog.woowahan.com/25900/)), 카카오페이증권 「춘시리」는 Confluence 를 매시간 스캔해 변경분만 반영하며 낡은 정보는 **사용자가 「학습 기능」으로 직접 정정**한다 ([카카오페이증권, 2025-01-24](https://tech.kakaopay.com/post/choonsiri/)). 가장 닮은 것은 우아한형제들 「물어보새」다 — Text-to-SQL 이 "검증된 데이터 마트" 와 카탈로그의 테이블 메타데이터를 쓰고 "데이터 거버넌스를 관리하는 조직이 있어… 비즈니스 용어를 잘 관리하고 있었습니다" 라며 「비즈니스 용어집」을 표준 정의의 출처로 삼는데, 권위 단위가 테이블·용어이고 문서 절·코드 심볼로 가는 링크나 결정자·시점은 없다 ([우아한형제들, 2024-07-12](https://techblog.woowahan.com/18144/)). LINE 의 「LINE Words」는 크라우드소싱 대신 "테크니컬 라이터가 주도해 작성" 하고 관련 부서 검토를 거친 용어 정본을 사내 위키 안에서 찾아 주는 Chrome 확장으로 배포한, 국내에서 확인된 유일한 「사람이 쓰는 정본 사전」이다 ([LINE Engineering, 2022-05-27](https://engineering.linecorp.com/ko/blog/glossary-project-line-words-open/)). 삼성SDS 는 레거시 약 40개 시스템·월 API 약 100만 건·업무 문서 14,000건 이상을 "문서 표준화 체계" 로 정비해 RAG 에 썼다고 하되 최신 문서·공식 문서 지정·소유자 검증은 적지 않았고, 해외 페이지의 「RAG 로 정확도 최대 98%」는 검색 요약에서만 보였다 ([삼성SDS, 2025-10-24](https://www.samsungsds.com/kr/insights/samsung-sds-ai-journey.html) [vendor]). kt cloud 가 "공식 문서를 우선 보여주거나" 하도록 메타데이터를 쓰라고 한 것은 구현이 아니라 설계 권고다 ([kt cloud, 2025-08-22](https://tech.ktcloud.com/entry/2025-08-ktcloud-ai-rag-%EC%8B%9C%EC%8A%A4%ED%85%9C%EA%B5%AC%EC%A1%B0-%EC%9D%B4%ED%95%B4) [vendor]). 국내 엔터프라이즈 AI 검색 제품(올거나이즈 Alli·포티투마루 RAG42·LG CNS)의 문서와 보도에서 공통으로 확인되는 것은 「답변에 출처를 붙인다」까지이고, 「검증된 문서만 쓴다」「사람이 승인한 문서에 가중치」는 어느 제품 문서에서도 확인하지 못했으며, RAG42 의 "20% 이상의 환각 해소" 는 분모와 측정법이 없는 회사 발표다 ([Alli 가이드](https://docs.allganize.ai/allganize-alli-works); [벤처스퀘어, 2023-09-22](https://www.venturesquare.net/897093) [벤더 주장 인용]).

국내 MDM 어휘에서 「정본」에 해당하는 것은 낱말이 아니라 구조다. SK하이닉스는 마스터 데이터를 「기준 정보」로 정의하고 "핵심(Core) 시스템을 정의해 데이터를 관리해야 한다" 며 "데이터 오너십" 과 소유 부서의 "데이터 검증" 을 요구하고 ([SK하이닉스 뉴스룸, 2021-01-15](https://news.skhynix.co.kr/why-is-master-data-important-again-now/)), 삼성SDS 는 "기준정보 전담 조직" 을, 컴퓨터월드는 "하나의 기준(single view of truth)" 을 쓴다 — 확인한 본문 어디에도 「정본」「골든 레코드」「원천 시스템」은 없고, 「골든 레코드」는 검색하면 보이저호의 그것이 먼저 나온다 ([삼성SDS, 2018-11-15](https://www.samsungsds.com/kr/insights/master-data-management-2.html); [컴퓨터월드, 2015-04-30](https://www.comworld.co.kr/news/articleView.html?idxno=48750)). 이 구상의 「항목별 사람 결정」에 국내 실무자가 바로 알아들을 이웃 개념은 「기준정보 담당 조직」과 「검증된 데이터 마트」다. 「정본」이라는 낱말은 국내에서 두 가지 다른 뜻을 이미 갖고 있다. 법률에서 정본은 "원본 그 자체이거나 원본을 그대로 베껴서 작성한 것으로 그 서류에 단순한 증명력을 넘어서는 법적인 효력이 부여되는 서류" 이고 ([김준기 칼럼, 2008-10-22](https://www.kurotimes.com/news/articleView.html?idxno=6791)), 기록관리학의 「진본성」은 "기록의 생산이 종료된 이후 발생하는 조작, 변조 등을 방지함으로써 보장 가능한 품질", 「신뢰성」은 "생산단계에서의 완전성과 통제의 정도" 로, 국가기록원은 "원본성이 아니라 진본성을 보존하는 것이 전자기록 관리의 핵심" 이라 한다 ([이젬마·오경묵, 2020](https://www.kci.go.kr/kciportal/landing/article.kci?arti_id=ART002615998); [국가기록원](https://www.archives.go.kr/next/newmanager/electronicProperty.do)). 셋 다 「이 기록이 손대지 않은 그것인가」를 다루지 「여러 값 중 어느 것이 맞는가」를 다루지 않으므로, 이 구상의 「정본」(항목별로 사람이 지정한 권위 출처)을 국내 독자에게 쓸 때는 첫 등장에서 이 차이를 못 박아야 하고, 「기계 검증 가능한 포인터」는 기록관리의 「출처확인(provenance)」과 이름이 겹치니 갈라 써야 한다.

이 구상의 「기계 검증 가능한 포인터」 부분만은 국내 개인 개발자 사이에서 AI 코딩 도구의 부산물로 자생하고 있다. 2026년 9월 한 달에 개인 프로젝트 셋이 같은 문제를 같은 방법으로 풀었다: `perArdua/arch-prac` PR #19(09-14 머지)는 문서의 `file:line` 인용이 의도한 코드를 가리키는지 보는 `citation_audit` 과 여러 문서의 같은 수치가 일치하는지 보는 `consistency_audit` 을 넣고 일부러 틀린 값을 심어 검사기가 잡는지 확인했으며 동기는 "AI가 쓴 문서와 코드를 믿으려고 만듦" 이다 ([arch-prac PR #19](https://github.com/perArdua/arch-prac/pull/19)); `UncleSamsun/syncdoc` #10(09-10)은 문서 규약과 검증 규칙을 따로 두고 파일 경로·앵커·중복 스펙 ID 를 검사하되 코드 블록은 건너뛴다 ([syncdoc #10](https://github.com/UncleSamsun/syncdoc/issues/10)); `EinSofINTEREST/IssueTracker` #565(09-22)는 실패의 1인칭 기록이다 — `harness-check.sh` 가 "문서가 낡으면 다음 세션의 AI 가 잘못된 전제를 받는다" 는 이유로 문서↔코드 정합을 검사하는데, 머지 뒤 **검사 7개가 전부 통과하고도 드리프트 6건이 남았고**, 원인은 스캔 범위(`.cursor/rules/`·`docs/architecture/` 제외), 코드펜스 제거("아키텍처 문서의 디렉토리 트리가 바로 그 코드펜스 안"), 트리 표기 미인식 셋이었다 ([IssueTracker #565](https://github.com/EinSofINTEREST/IssueTracker/issues/565)). 셋 다 「문서→코드」 방향의 유효성 검사이고 기능 지도·결정자·「정본 없음」은 없지만, #565 는 이 구상이 마주칠 유지 부담을 미리 보여 준다 — 검사기의 범위 밖과 표기 형식에서 드리프트가 새고, 통과 표시가 곧 정합을 뜻하지 않는다. 「문서 절 포인터」에 가장 가까운 국내 구현은 사내 취업규칙 RAG `geonhoa3/company-policy-rag` 다: 글자 수가 아니라 `제N조` 경계로 나눠 `article_no` 메타데이터를 붙이고 답에 `(제12조)` 처럼 조항을 인용하며 최고 유사도 0.5 미만이면 경고 배너를 띄우지만, 포인터가 **검색 결과에 붙는 것**이지 지도가 항목별로 **미리 지정**하는 것이 아니고 "개정 이력 미지원" 이다 ([company-policy-rag](https://github.com/geonhoa3/company-policy-rag)). 마지막으로, 국내에서 권위를 가장 명시적으로 다룬 글은 이 구상이 거부하는 방식을 택한다 — 한 개인 블로그(Cerebras 공개 글의 해설, 필자가 2차 요약에 의존했다고 밝힘)는 "코드가 최종 권위, 그다음 인시던트 기록, 그다음 위키, 그다음 Slack" 이라는 **출처 종류별** 순서를 두고 "시간 감쇠는 신선도 문제의 해법이 아니라 완화책", "주기적인 재조정(reconciliation)이 필요합니다", 평가셋에 기권 사례 10~20% 를 제안한다 ([youngju.dev, 2026-07-31](https://labhub.hopto.org/blog/2026-07-31-enterprise-knowledge-base-with-llm) [individual]). 국내에서 이미 지불된 비용은 「용어 사전을 사람이 쓴다」(LINE Words)와 「포인터를 기계로 검사한다」(개인 프로젝트 셋)이고, 지불되지 않은 비용은 「항목별로 정본을 정하고 결정자를 적는 일」이다. 이 국내 조사는 검색 예산이 도중에 소진돼 네이버·당근·쿠팡·NHN·야놀자·컬리·뱅크샐러드의 사내 문서 RAG 글, 데이터 카탈로그 오너·스튜어드 국내 도입기, 검증된 문서만 쓰는 승인 워크플로우 등 아홉 개 검색을 실행하지 못했고 DEVIEW·if(kakao)·SLASH 의 발표 원문은 하나도 열지 못했으므로, 위의 「없다」는 「이번 조사에서 안 나왔다」로 읽어야 한다.

## 결론

이 조사가 바꾸는 것은 신규성 주장의 자리다. 「값을 복사하지 않고 정본을 가리킨다」는 1998년 knowledge map 과 1999년 DRY("single, unambiguous, authoritative representation")와 2025년 코딩 에이전트 지침에 있고, 「소유자와 시점」은 Google freshness 와 Guru 에 있으며, 「기계가 확인하는 포인터」는 Doorstop·Swimm·LaunchDarkly·Meta 에 있다. 선례가 없는 것은 세 가지의 결합 — **세부 단위의 사람 판정 + 형식 있는 포인터 + 명시적 「정본 아직 없음」** — 을 검색 층 위에 얹는 것이고, 그 효과를 사람 라벨로 측정한 논문도 제품도 없다. 그러니 이 구상은 「검증된 방법」이 아니라 「측정되지 않은 결합」으로 소개하는 것이 사실과 맞고, 측정할 지표도 스스로 정해야 한다 — 기존 시스템이 하나도 측정하지 않는 「잘못된 버전·낡은 출처에서 답한 비율」이 그것이다. 이 구상에 유리한 두 사실은, ETH 실험이 에이전트가 잘 따르는 유일한 내용이 개요가 아니라 지시·결정임을 보였다는 것과, 신선도 판정을 모델 밖의 규칙으로 빼기만 해도 10~21pp 가 났다는 것이다.

증거가 예고하는 실패는 링크 부패가 아니라 **결정 부패**다. 포인터 검사는 죽은 링크를 잡지만, Backstage 의 소유자 필드가 퇴사자를 가리키고 GAO 의 「권위 페이지」가 절차 없이 바뀌고 IssueTracker 의 검사 7개가 통과한 채 드리프트 6건이 남는 동안 검사는 초록이다. 그래서 설계에 필요한 것은 Doorstop 의 방식(대상의 fingerprint 를 포인터에 저장하고, 대상이 바뀌면 판정을 suspect 로 떨어뜨리며, 사람이 다시 판정해야 초록으로 돌아온다)과 ODCS 의 방식(한 세부가 정책 절·검증기·스키마 제약 세 층에 각각 형식 있는 포인터를 갖고, dbt 처럼 어느 층이 「강제」이고 어느 층이 「메타데이터뿐」인지 적는다)이고, 조직에 필요한 것은 살아남은 등록부 넷이 공유한 두 조건 — 어시스턴트가 답하기 전에 **반드시 지도를 먼저 읽는 실행 경로**, 그리고 판정을 내리는 **이름 붙은 희소한 역할**이 Uber 처럼 계층으로 위임하는 것 — 이다. 1인 개발자에게는 첫째 조건이 공짜에 가깝고(llms.txt 와 달리 소비자 배선이 자기 손에 있다) 둘째 조건이 곧 자기 자신이므로, 진짜 비용은 Uber 위원회가 답해야 했던 그 질문에 세부마다 답하는 시간이다 — 이것의 정본은 어디이고, 아직 없다면 누가 정할 것인가.
