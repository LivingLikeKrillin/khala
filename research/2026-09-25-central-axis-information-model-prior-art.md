# 완전한 축은 드리프트했고, 작은 축만 살아남았다

있었다 — 여섯 갈래에서 스무 개가 넘는 이름으로. 통합 아키텍처의 Canonical Data Model(2003), 의료의 HL7 RIM, 통신·전력·정부의 SID·CIM·NIEM 같은 reference model, 소프트웨어 설계의 domain model 과 ubiquitous language, 모델 주도의 MDA PIM, 시스템 공학의 MBSE 와 미 국방부의 authoritative source of truth, 학계의 Single Underlying Model, 온톨로지와 지식 그래프(Palantir Ontology·FIBO·Bosch), API 계약과 2025–26년의 spec-driven development, Kubernetes 의 `spec`/`status` 와 GitOps, 그리고 국내의 공공데이터 공통표준용어까지, 「한 곳에 정의하고 나머지가 거기 매달린다」는 구상은 분야마다 세워졌다. 2026년 9월 25일까지 공개된 기록을 여섯 갈래(reference model·DDD 계열·모델 주도/시스템 공학·온톨로지/지식 그래프·계약/명세·기대 상태와 조정)로 훑은 결론은 둘이다. 첫째, **조직·제품의 개념·규칙·관계를 한 모델에 넣고 문서·코드·데이터를 거기서 파생시킨 단일 조직 사례는 국내외 어디에도 없고**, 거기에 가장 가까이 간 것들 — 모든 v3 메시지를 하나의 추상 모델에서 derive 하게 한 RIM, 전사 데이터 모델(EDM), 학계의 SUM — 은 예외 없이 **모델 자체가 드리프트하는 것**으로 끝났다. RIM 은 14년 뒤 알려진 구현 22개를 남기고 훗날 FHIR 를 이끈 당사자에게서 "HL7 v3 has failed" 라는 판정을 받았고, MDA 는 Fowler 에게 "Night of the Living Case Tools" 였으며, Vitruvius 는 SUM 을 버리고 기존 모델들을 규칙으로 잇는 *virtual* SUM 으로 물러섰다. 둘째, **살아남은 축은 다섯 조건을 공유한다** — 구속하는 부분이 작고 경험적으로 골라졌으며(FHIR 의 80% 규칙, data mesh 의 polysemes, 국내 공통표준용어), 그 부분은 교환 경계에서 기계가 검사하고(CGMES 적합성 시험, schema registry, Zalando 의 linter), 나머지 참조 층은 "a guide, not an absolute" 로 강등돼 있고, 구매자나 규제자가 비준수를 비싸게 만들며, 공개 변경 절차로 버전이 관리된다. 어긋남을 다룬 다섯 방식(모델에서 생성 · 모델이 곧 코드 · 조정 루프 · 검증 · 기록하고 수용)은 결국 한 선으로 갈린다 — 상태를 기계가 관찰하고 되돌릴 수 있는 쪽(Kubernetes 필드, 설정 파일, 와이어 스키마)만 자동으로 수렴하고, 그렇지 않은 쪽(오토스케일러가 고친 replicas, 데이터베이스 행, 법의 해석, 그리고 정책 문서)에서는 모든 시스템이 「감지하고 알리되 사람이 정한다」로 내려앉는다. 증거의 질은 얇다: MBSE 편익 주장 2,900건 중 **86%** 에 지표가 없고, DDD 는 동료평가 논문이 **36편**뿐이며, SDD 는 단일 세션 측정밖에 없고, 이 조사도 여섯 노트 전부 검색 예산이 도중에 소진돼 「없다」의 상당수는 「이번에 안 나왔다」다. 앞선 조사(『기능 지도와 정본 링크 사례』)와 합치면 함의는 분명하다. 이 사용자의 구상 — 값을 복사하지 않고 세부마다 정본을 가리키는 지도, 그 위의 소유자 판정 — 은 실패한 형태(값을 다 담는 완전한 모델)가 아니라 **살아남은 형태, 곧 선언된 링크로 이어진 연합**(virtual SUM · DDD 의 Context Map · 미 국방부의 복수형 authoritative source*s* of truth · Bézivin 의 megamodel)이고, claim 에 적힌 소유자 판정은 국방부가 2022년에 ASoT 를 "an entity such as a person, governing body, or system that applies expert judgment and rules to proclaim a digital artifact is valid" 로 다시 정의한 것과 같은 물건이다. 선례가 없는 자리는 하나다 — 산문의 한도·권한 값과 코드의 값 사이를 기계가 잇는 검사기. 양쪽이 실행 가능한 Cedar(밤마다 약 1억 건의 차등 시험)와 사람이 나란히 읽는 Catala·Rules as Code 만 그 근처에 있고, 그래서 이 층은 조정 루프가 아니라 Terraform 의 자세(감지 → 사람의 판정 → 기록)로 짓고, Puppet 처럼 변경을 intentional/corrective 로 분류하고, Nuseibeh 처럼 판정마다 재평가 시점을 적고, 아무도 측정하지 않은 지표 — 낡은 정본에서 답한 비율 — 를 스스로 측정해야 한다.

## 이름은 스무 개가 넘지만, 축에 담긴 것은 넷 중 하나다

통합 아키텍처가 처음 이름을 붙였다. Hohpe & Woolf 의 *Canonical Data Model*(2003)은 "Design a *Canonical Data Model* that is independent from any specific application. Require each application to produce and consume messages in this common format" 이라는 **메시징** 패턴이고, 그 약속은 산수다 — 애플리케이션 6개면 번역기 30개 대신 12개 ([EIP 패턴 페이지](https://www.enterpriseintegrationpatterns.com/patterns/messaging/CanonicalDataModel.html)). 저자 자신이 한 달 뒤에 단서를 달았다: "We have to find a common data representation that suits every participant equally well -- an effort that is all too rarely blessed with success" ([Hohpe, 2003-11-12](https://www.enterpriseintegrationpatterns.com/ramblings/03_hubandspoke.html)). 이 패턴이 와이어 형식에서 **조직의 개념 모델**로 승격될 때 나오는 네 가지 문제를 Poole(2008)과 Tilkov(2015)가 경험으로 적었다 — 모두가 자기 속성을 넣겠다고 해서 선택 속성투성이가 된 "a zombie interface model", 중앙 병목, 허브를 통한 결합, 버전 변경의 고통 — 그리고 둘의 처방은 같다: canonical schema 는 서비스 경계 **뒤에서만** 쓰고("we will have a *different* canonical schema for each service"), 중앙 팀이 내리누르지 말고 팀이 필요할 때 "pull" 하게 하라 ([Poole, 2008-05-31](http://bill-poole.blogspot.com/2008/05/enterprise-canonical-schemas-continued.html); [Tilkov, 2015-03-24](https://www.innoq.com/en/blog/2015/03/thoughts-on-a-canonical-data-model/)). 데이터 플랫폼 쪽은 같은 결론을 다른 이름으로 냈다. Dehghani 의 data mesh 는 옛 중앙 팀의 일을 "Responsible for global canonical data modeling" 이라 적고, 연합 거버넌스에는 도메인 경계를 넘는 **polysemes** 만 남긴다 ([Dehghani, 2020-12-03](https://martinfowler.com/articles/data-mesh-principles.html)). 이 계보의 비판은 전부 정성적이고 측정된 것이 없다는 점은 미리 적어 둔다.

산업 표준은 같은 것을 *reference model* 이라 부르고, 살아남은 것은 예외 없이 **프로파일로 구현되고 밖에서 의무화된** 것이었다. HL7 v3 의 Reference Information Model 은 "all data needed for any sort of healthcare communication is represented in the HL7 RIM" 이고 모든 메시지를 *design by constraint* 로 derive 하게 했는데, 그 결과 국제 수준에서 "10 different CMETs for the concept of 'Patient'" 가 생겼다 ([HL7 FHIR R5, Comparison – v3](https://www.hl7.org/fhir/comparison-v3.html)). 통신의 TM Forum SID(Shared Information/Data Model, 2000년 시작)는 ABE(Aggregated Business Element)마다 "adoption" 점수를 누적하는 적합성 인증으로 검사하고(tmforum.org 가 403 이라 검색 요약만 확인) ([TM Forum](https://www.tmforum.org/information-framework-conformance-about/)), 전력의 IEC CIM 은 ENTSO-E 가 **CGMES 라는 프로파일**로 잘라 해마다 상호운용성 시험(IOP)을 돌리고 Declaration/Attestation of Conformity 를 유효기간과 함께 발급하며, 프로파일에 안 들어가는 TSO–DSO 사례는 "novel extensions" 로 처리한다 ([ENTSO-E, CIM Conformity](https://www.entsoe.eu/data/cim/cim-conformity-and-interoperability/)). 미국 정부의 NIEM 은 IEPD·NDR·CTAS 로 교환 단위를 적합하게 하고 2025년 12월 OASIS 표준이 됐으며 "used across all 50 U.S. states" 라 한다 ([OASIS, 2025-12-09](https://www.oasis-open.org/2025/12/09/oasis-approves-two-niemopen-standards-to-advance-ai-ready-data-interoperability/)). 공정 산업의 ISO 15926 은 "a Lingua Franca for computer systems" 를 표방했지만 "difficult to understand and more challenging to implement" 이라는 평가를 받았고, 업계가 실제로 인수인계에 쓴 것은 Shell 의 사내 표준(2004~)에서 나온 표 모양의 CFIHOS 였다(벤더·업계 단체 페이지, 검색 요약) ([Wikipedia, ISO 15926](https://en.wikipedia.org/wiki/ISO_15926); [Revisionz](https://revisionz.com/bridging-information-gaps-in-process-industries-the-synergy-of-iso-15926-and-cfihos/)). 벤더가 소유한 축 둘은 단일 조직의 축에 가장 가깝다. Microsoft 의 Common Data Model 은 "thousands of entities such as Customer, Product, Opportunity" 를 정의하고 Dataverse·Dynamics·Power Platform 이 쓰며 ([Microsoft Learn](https://learn.microsoft.com/en-us/common-data-model/use)), SAP 의 One Domain Model 은 객체마다 OID 를 덧붙이고 API 에 `@ODM.Semantic.BusinessObject:"WorkforcePerson"` 같은 주석을 달아 ODM Catalog 와 맞추는 방식이다(벤더 슬라이드; "More than [n] objects aligned" 의 숫자는 그림이라 못 읽었다) ([SAPSA, 2023-01](https://sapsa.se/wp-content/uploads/2023/01/sap-one-domain-modelsugen.pdf)). 국내 공공은 모델이 아니라 **어휘**를 축으로 세웠다. 「공공데이터 공통표준용어」는 2020년 8월 338개에서 2024년 11월 7차 9,027개로 늘었고, 「공공기관의 데이터베이스 표준화 지침」(행정안전부고시 제2023-18호) 제8조 제5항은 운영 중인 DB 의 비표준데이터를 표준화된 데이터와 **매핑·관리**하도록 명시한다 — 어긋남을 금지하지 않고 매핑 의무로 바꾼 것이다 ([CISP, 2024-11](https://www.cisp.or.kr/archives/25017); [행정안전부 고시 공지, 2023-04-03](https://www.mois.go.kr/frt/bbs/type001/commonSelectBoardArticle.do?bbsId=BBSMSTR_000000000016&nttId=99662)).

소프트웨어 설계 쪽의 이름은 Evans 의 것이다. *domain model* 은 "A system of abstractions that describes selected aspects of a domain", *ubiquitous language* 는 "A language structured around the domain model and used by all team members within a bounded context", *bounded context* 는 "A description of a boundary … within which a particular model is defined and applicable" 이고, 축이 어디 사는지도 명시돼 있다 — "A domain model is not a particular diagram; it is the idea that the diagram is intended to convey", 코드는 "ultimately the most important product of a software project", 그리고 "The code becomes an expression of the model, so a change to the code may be a change to the model" ([DDD Reference, 2015-03](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf); [Evans, Part I](https://www.dddcommunity.org/wp-content/uploads/files/books/evans_pt01.pdf)). 문서에 허락된 자리는 둘뿐이다: 한 쪽짜리 Domain Vision Statement 와 3~7쪽의 distillation document 이고, 후자만 변경 절차(상의 → 통지 → 새 판 배포)를 갖되 "they do not actually modify the model or the code itself" 다. Vernon(2013)은 이를 운영 규칙으로 바꿨다 — 그림과 용어집은 "be quite prepared to abandon" 하라, "team speech and the model in the code" 만이 "the only guaranteed current denotation" 이다 ([Vernon, InformIT](https://www.informit.com/articles/article.aspx?p=1944876&seqNum=3)). 이웃 실천들도 같은 방향이다. Simon Brown 의 C4 는 *diagram* 이 아니라 *model then views* 를 주장하고("A model is just data!"), 그 보장은 한 모델에서 나온 뷰끼리 어긋나지 않는다는 것뿐이다 ([c4model.com/tooling](https://c4model.com/tooling)). Martraire 의 *Living Documentation*(2019)은 목차에 "Setting Up a Reconciliation Mechanism (aka Verification Mechanism)", "Living Glossaries", "Living Diagrams" 를 두고 코드에 붙은 주석에서 문서를 **생성**하자고 한다(본문은 이번에 못 열었다) ([InformIT 목차](https://www.informit.com/store/living-documentation-continuous-knowledge-sharing-by-design-9780134689326)). EventStorming 과 Domain Storytelling 은 워크숍 산출물을 축으로 두지 않는다 — 도메인 스토리는 "not intended to be a stand-alone document" 이고 "a memory aid" 이며, 저자들의 다음 단계는 "Modeling in Code" 다 ([domainstorytelling.org](https://domainstorytelling.org/quick-start-guide); [dpunkt 공개 PDF](https://www.assets.dpunkt.de/openbooks/Schwentner_Domain_Storytelling_Broschuere_2A_Web.pdf)). 국내 실무는 이 용어를 음차 그대로 쓴다 — 유비쿼터스 언어(간혹 보편 언어)·도메인 모델·바운디드 컨텍스트·에그리거트 — 그리고 카카오페이 여신코어 팀은 "정책이 명확한 도메인" 이라 DDD 를 골랐고 정렬은 "PlantUML을 이용하여 코드로 비즈니스 흐름을 가시화" 하는 사람의 실천이었으며, 남은 비용은 "JPA Entity를 중복으로 만들게 되었고 도메인 변경에서 개발자가 잊지 않고 챙겨하는 포인트가 늘어나게 되었습니다" 였다 ([카카오페이 기술 블로그, 2025-05-23](https://tech.kakaopay.com/post/backend-domain-driven-design/)).

모델 주도와 시스템 공학은 축을 **공학 모델**로, 문서를 **생성물**로 둔다. OMG 의 MDA Guide(2003)는 CIM·PIM·PSM 을 정의하고 "crank it through a machine" 을 약속했지만, 모델과 파생물을 맞추는 문장은 §3.8 한 줄 — "An MDA modeling tool that keeps a record of transformation may keep a PIM and PSM in synchronization" — 뿐이고 "round-trip" 이라는 말은 문서 전체에 없다 ([MDA Guide 1.0.1](https://www.omg.org/news/meetings/workshops/UML_2003_Manual/00-2_MDA_Guide_v1.0.1.pdf)). INCOSE 의 MBSE 정의(2007)는 산출물이 아니라 실천이고("The formalized application of modeling to support system requirements, design, analysis, verification and validation activities…"), 2025년 7월 채택된 SysML v2 는 KerML 형식 의미론·텍스트 문법·"navigate, query, and update the model" 하는 표준 API 를 더해 처음으로 표준 수준의 *repository* 를 갖췄다 ([SEBoK](https://sebokwiki.org/wiki/Model-Based_Systems_Engineering_(MBSE)_(glossary)); [OMG PR, 2025-07-21](https://www.omg.org/news/releases/pr2025/07-21-25.htm)). 미 국방부의 2018년 Digital Engineering Strategy 는 이 구상에 가장 가까운 공식 정의를 갖고 있다 — *authoritative source of truth* 는 "the current state and the history of the technical baseline" 을 담는 "the central reference point for models and data across the lifecycle" 이고 "Changes made to the authoritative source of truth will propagate throughout the digital design model" 한다 — 그런데 2022년 *Digital Engineering Fundamentals* 는 그것을 **복수형**으로 쓰고 "An entity such as a person, governing body, or system that applies expert judgment and rules to proclaim a digital artifact is valid" 로 다시 정의했으며, DoDI 5000.97(2023-12)은 *digital thread* 를 "Connects authoritative data and digital models" 로, *digital artifacts* 를 "Digital products and views that are dynamically generated from the digital ecosystem" 으로 정의했다 ([DE Strategy 2018](https://ac.cto.mil/wp-content/uploads/2019/06/USA001603-18-DSD.pdf); [DE Fundamentals 2022](https://ac.cto.mil/wp-content/uploads/2022/03/DE-Fundamentals-2022.pdf); [DoDI 5000.97 요약](https://www.cto.mil/wp-content/uploads/2024/01/info-dodi-500097-de-summary.pdf)). 학계는 이 구상을 글자 그대로 형식화했다. Orthographic Software Modeling 의 *Single Underlying Model* 은 "all information about the system under development is represented in a single underlying model" 이고, Vitruvius 의 정의는 "A SUM is a complete definition of a system and contains all known information about it. It contains no redundant or implicitly dependent information and is thus always free of contradictions" 인데, 같은 논문이 곧바로 그것을 **virtual SUM** — 기존 메타모델들을 "Consistency Preservation Rules" 로 결합한 것 — 으로 바꾼다 ([Burger, 2014](https://publikationen.bibliothek.kit.edu/1000043437); [Klare et al., JSS 2021](https://publikationen.bibliothek.kit.edu/1000124711/89982634)). 이 지도 자체의 이름도 있다: Bézivin 의 *megamodel* 은 "a model of which at least some elements represent and/or refer to models or metamodels" 다(검색 요약만 확인) ([Semantic Scholar](https://www.semanticscholar.org/paper/On-the-Need-for-Megamodels-B%C3%A9zivin-Jouault/f9461d81370e071cf8b57c240cbab55b0759b239)). 국내 MBSE 담론은 「모델 기반 시스템 엔지니어링」「디지털 스레드/쓰레드」를 쓰되, 열어 본 자료 어디에도 「단일 진실 공급원」은 없었다 — ASoT 는 한국어로 어휘화되지 않았다 ([캐드앤그래픽스, 2022-06-02](https://www.cadgraphics.co.kr/newsview.php?pages=news&sub=news01&catecode=2&num=70982)).

온톨로지 계보는 축을 **데이터 뒤의 객체와 행동**으로 둔다. Palantir 의 Ontology 는 "an operational layer for the organization" 으로 "semantic elements (objects, properties, links)" 와 "kinetic elements (actions, functions, dynamic security)" 를 갖고 "a digital twin of the organization" 을 자처하며, object type 은 데이터셋에 매달린다("you can think of each object type as analogous to a dataset") ([Palantir docs, overview](https://www.palantir.com/docs/foundry/ontology/overview); [core concepts](https://www.palantir.com/docs/foundry/ontology/core-concepts)). Gartner 의 *Digital Twin of an Organization*(2017~)은 "a dynamic software model that relies on operational and contextual data" 이고 실제 시장은 프로세스 마이닝 벤더 약 80곳이다 ([Gartner Market Guide, 2024-11-20, PDF 미러](https://www.eqv.it/doc/Market_Guide.pdf)). Dietz 의 DEMO/*Enterprise Ontology*(2006)는 actor role 과 transaction kind 의 essential model 로, 저자들 스스로 25년 뒤 "the theories are complex and not always easy to understand" 는 평가를 인용한다 ([Dietz & Mulder, 2020](https://ceur-ws.org/Vol-2825/paper6.pdf)). Bosch 의 SMT 온톨로지는 여덟 주 여섯 워크숍으로 53개 매핑을 만들었고, 그 지식이 어디 있었는지를 논문이 적었다 — "only available in internal documents and in the head of Bosch engineers" ([Kalaycı et al., ISWC 2020](https://ghxiao.org/publications/2020-iswc-bosch.pdf)). 국내에서 조직의 「온톨로지」를 표방한 것은 둘 다 2025–26년 벤더 발표다: 삼성SDS 의 Palantir 를 따라가는 녹스 포털 적용 검토와, LG CNS 가 개발 표준·보안 규정·소스 코드·산출물을 한 온톨로지 DB 에 넣는다는 「지식 파운데이션」(운영 지표 없음) ([디일렉, 2025-11-19](https://www.thelec.kr/news/articleView.html?idxno=44150); [뉴스와이어, 2026-06-08](https://www.newswire.co.kr/newsRead.php?no=1036029&sourceType=rss)).

계약·명세 계보는 축을 **좁고 기계가 검사할 수 있는 조각**으로 자른다. Zalando 의 API 가이드라인은 rule 100 "MUST follow API first principle", 101 "MUST provide API specifications using OpenAPI", 192 "MUST publish OpenAPI specification", 234 "MUST only use durable and immutable remote references" 를 두고, 8,000개 넘는 서비스와 300개 넘는 팀에서 길드 리뷰·API Portal·Zally 린터로 지킨다 ([Zalando guidelines](https://opensource.zalando.com/restful-api-guidelines/); [Zalando Engineering, 2019-04-04](https://engineering.zalando.com/posts/2019/04/developing-zalando-apis.html)). Pact 의 consumer-driven contract 는 소비자 테스트가 실제로 의존하는 요청·응답만 계약으로 굳히고 `can-i-deploy` 가 Pact Matrix 를 보고 배포를 막는다 ([docs.pact.io](https://docs.pact.io/); [can-i-deploy](https://docs.pact.io/pact_broker/can_i_deploy)). Confluent Schema Registry 는 등록 시점에 호환성(기본 BACKWARD)을 강제하고 모드마다 소비자·생산자 업그레이드 순서를 처방하며 ([Confluent docs](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html)), Buf 는 Protobuf 를 FILE·PACKAGE·WIRE_JSON·WIRE 네 엄격도로 기준선과 비교해 PR 을 깨뜨린다 ([buf.build](https://buf.build/docs/breaking/)). 2025–26년의 *spec-driven development* 는 이 조각을 제품 의도 전체로 넓혔다 — GitHub Spec Kit 은 "Specs become the shared source of truth", Amazon Kiro 는 "Kiro's specs stay synced with your evolving codebase", Tessl 은 2025년 9월 `@generate` 와 `// GENERATED FROM SPEC - DO NOT EDIT` 로 *spec-as-source* 를 겨냥했고, OpenSpec 은 `specs` 폴더를 "the authoritative requirements and scenarios describing current expected behavior" 로 두고 `changes` 의 델타를 archive 때 합친다 ([GitHub Blog, 2025-09-02](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/); [kiro.dev](https://kiro.dev/blog/introducing-kiro/); [Tessl, 2025-09-23](https://tessl.io/blog/tessl-launches-spec-driven-framework-and-registry); [OpenSpec](https://github.com/Fission-AI/OpenSpec)). Böckeler 는 이를 *spec-first*(한 번 쓰고 버림) · *spec-anchored*(기능과 함께 진화) · *spec-as-source*(사람이 스펙만 편집) 세 수준으로 갈랐다 ([martinfowler.com, 2025-10-15](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)). 국내 소개는 「스펙 주도 개발」「스펙(명세서)」「진실 공급원(source of truth)」을 쓴다 ([데이터넷, 2025-09-19](https://www.datanet.co.kr/news/articleView.html?idxno=205454)).

마지막 계보는 어긋남을 **전제**로 축을 세운다. Kubernetes 의 객체는 `spec`(desired state)과 `status`(observed state)를 갖고, "controllers are control loops that watch the state of your cluster, then make or request changes where needed" 이며 설계 원칙은 "All APIs should be declarative", "Functionality must be level-based", "Object status must be 100% reconstructable by observation", "Assume an open world" 다 ([Kubernetes docs, Controllers](https://kubernetes.io/docs/concepts/architecture/controller/); [design principles](https://raw.githubusercontent.com/kubernetes/design-proposals-archive/main/architecture/principles.md)). OpenGitOps v1.0(2021-10)은 원하는 상태를 "Declarative · Versioned and Immutable · Pulled Automatically · Continuously Reconciled" 로 정의하고 ([OpenGitOps PRINCIPLES.md](https://github.com/open-gitops/documents/blob/v1.0.0/PRINCIPLES.md)), Terraform 은 설정과 state 파일 둘을 축으로 두어 `plan` 이 "Proposes a set of change actions" 만 하며 ([Terraform CLI docs](https://developer.hashicorp.com/terraform/cli/commands/plan)), Puppet 은 수렴하는 매 변경을 *intentional*(코드가 바뀜)과 *corrective*(현실이 어긋남)로 이름 붙인다 ([Puppet 7 glossary](https://www.puppet.com/docs/puppet/7/glossary)). 이론 쪽 이름은 *lens*(GetPut/PutGet 법칙, least change), *bidirectional transformation*, *inconsistency management*(resolve / ignore / defer / circumvent / ameliorate)이고, 규칙 쪽은 *policy as code*(OPA/Rego, Sentinel, Cedar), *Rules as Code*(OECD 의 "isomorphism"), Catala 의 literate programming 이다 ([Foster et al., TOPLAS 2007](https://www.cis.upenn.edu/~bcpierce/papers/lenses-toplas-final.pdf); [Nuseibeh et al., 2000](https://www.cs.toronto.edu/~sme/papers/2000/IEEEComputer2000.pdf); [OECD, 2020-10](https://www.oecd.org/content/dam/oecd/en/publications/reports/2020/10/dechiffrer-le-code_d56cab77/3afe6ba5-en.pdf); [Catala, ICFP 2021](https://arxiv.org/abs/2103.03198)). 국내 실무 어휘는 직접 차용이다 — 기대 상태(Desired State)·현재 상태(Actual State)·인프라 드리프트·자동 동기화(Self-heal)·단일 진실 소스 ([LabHub, 2026-03-07](https://labhub.hopto.org/blog/devops/2026-03-07-devops-terraform-opentofu-drift-detection-remediation); [컴투스온, 2025-11](https://on.com2us.com/tech/kubernetes-gitops-argocd-multi-cluster-deployment/)).

이 스무 개 이름을 내용으로 다시 세면 넷이 된다 — **교환용 데이터 구조**(CDM·RIM·SID·CIM·NIEM·Microsoft CDM·ODM·EDM·공통표준용어), **제품의 공학 모델**(MDA PIM·MBSE·DoD ASoT·SUM), **도메인 개념과 이름 붙은 규칙**(DDD·Palantir·DEMO), **기계가 실행하거나 검사하는 좁은 조각**(OpenAPI·Pact·registry·Kubernetes `spec`·OPA/Cedar·Catala). 어느 것도 **정책 문서의 값**(한도·권한)을 1급 원소로 갖지 않는다 — 그 점은 다섯째 절에서 다시 본다. 표는 갈래별로 무엇을 축에 넣었고 어긋남을 어떻게 다뤘으며 무슨 일이 있었는지의 요약이고, 각 칸의 근거는 뒤 절에 있다.

## 완전한 축을 세운 곳에서는 축 자체가 드리프트했다

가장 잘 기록된 사례가 HL7 RIM 이다. 하나의 추상 모델, 의무적 derive, 맞춤 도구, 작은 전문가 풀 — 1인칭 기록 셋이 같은 세 비용을 댄다. FHIR 의 훗날 Product Director 인 Grahame Grieve 는 2011년에 "HL7 v3 has failed" 라 적고, 이유로 기술 중립 설계가 부른 비용, "a large program and highly skilled insiders" 가 필요한 점, RIM 이 "created semantic interoperability but not clinical interoperability" 한 점, design by constraint, 과도한 사전 모델링을 들었다 ([Grieve, 2011-08-20](https://www.healthintersections.com.au/2011/08/20/hl7-needs-a-fresh-look-because-v3-has-failed.html)). 온톨로지 학자 Barry Smith 는 "after 14 years of development effort" 뒤 Rik Smithies 의 목록에 "22 known software implementations based on the RIM" 뿐이라 했고, RIM 이 "a disease and its diagnosis, … an action and its documentation" 을 혼동한다고 진단했으며, 2006년 논문의 초록은 "the time has come to abandon an unworkable paradigm" 이다(초록은 검색 요약, PDF 는 못 열었다) ([HL7 Watch, 2011-04-02](http://hl7-watch.blogspot.com/2011/04/fall-of-rim.html); [Smith & Ceusters, MIE 2006](https://philarchive.org/rec/SMIHRA)). 미들웨어 벤더 Muir 는 "There is no such thing a single optimal data model to serve all purposes" 와 "The only organisations spending money on v3 are governments and some big corporations like Oracle" 을 적었고, 영국 실무자 Meredith 는 "It got expensive. Very expensive." 와 "Tooling needed to be custom built" 을 적었다 ([Muir, 2011-03](http://hl7-watch.blogspot.com/2011/03/rise-and-fall-of-hl7.html); [Meredith, 2017-09-27](https://www.archetextur.es/why-did-hl7-version-3-fail/)). v3 를 강제한 대표 프로그램인 영국 NHS NPfIT 는 2011년 해체됐고 공공회계위원회는 "likely to cost taxpayers more than £9.8 billion" 이라 했다 — 다만 v3 강제와의 인과는 Smith 의 귀속이고 위원회 보고서는 계약과 거버넌스를 주원인으로 든다 ([UK PAC](https://committees.parliament.uk/committee/127/public-accounts-committee/news/181704/npfit-report/); [IEEE Spectrum, 2011](https://spectrum.ieee.org/npfit-dismantled-uk-government-announces-end-of-its-127-billion-national-electronic-health-record-program)). FHIR 는 중앙 모델을 없앤 것이 아니라 **강등**했다: "It is possible to implement FHIR with absolutely no knowledge of the HL7 RIM", RIM 매핑은 "a guide, not an absolute", 코어의 기준은 개념적 완전성이 아니라 "if approximately 80% of systems maintaining the resource will support the element" ([HL7 FHIR R5, Comparison – v3](https://www.hl7.org/fhir/comparison-v3.html)). Grieve 가 그 규칙의 근거로 든 수는 완전한 모델이 왜 구현 가능한 모델이 못 되는지의 정량 근거다 — 자기가 만난 DICOM 원소 900개 중 이미지의 80% 넘게 나타난 것은 **30개**, 1% 미만에만 나타난 것이 약 700개 ([Grieve, 2013-01-09](https://www.healthintersections.com.au/2013/01/09/fhir-extensions-the-8020-rule-dicom-and-the-long-tail.html)). 그 대가로 어긋남은 한 층 위로 옮겨 갔다 — 겹치는 FHIR 프로파일의 증식을 다룬 2022년 프리프린트가 "profiliferation" 이라는 말까지 만들었는데 본문은 403 이라 수치는 없다 ([medRxiv, 2022](https://www.medrxiv.org/content/10.1101/2022.03.09.22272163.full.pdf)). 채택 쪽 수치는 협회 조사다: 2025 State of FHIR 에서 응답국 71% 가 최소 몇 개 사례에 FHIR 를 쓰고, 전자 건강 데이터 교환 규제를 가진 78% 의 나라 중 73% 가 FHIR 를 의무·권고한다(PDF 는 검색 요약만) ([HL7, 2025](https://www.hl7.org/documentcenter/public/white-papers/2025%20State%20of%20FHIR%20Survey%20Report.pdf)).

전사 데이터 모델 쪽은 사후 분석이 아니라 실무자 단언이 증거의 전부다. "Models that are used together in very detailed context are coupled very strongly", "The business will evolve faster than the implementation of the model", "Without context, there is no meaning for a name" ([feststelltaste, 2017-01-03](https://www.feststelltaste.de/why-enterprise-data-models-dont-work/)); "there is not a single company today that has a complete and up-to-date data model of the information contained in all its applications" ([Wessely, 2024-07-20](https://towardsdatascience.com/modern-enterprise-data-modeling-a3d61f7c0c25/)). 검색에 자주 도는 문장 "by the time the EDM is completed, it is already obsolete" 는 어느 원문에서도 확인되지 않아 무귀속으로 둔다. 분석가 수치는 EDM 이 아니라 이웃 프로그램의 것이다 — Gartner 의 「2027년까지 D&A 거버넌스 이니셔티브 80% 실패」는 측정이 아니라 예측이고, 「MDM 프로그램 75% 가 사업 목표 미달」은 2차 기사로만 확인된다 ([Gartner, 2024-02-28](https://www.gartner.com/en/newsroom/press-releases/2024-02-28-gartner-predicts-80-percent-of-data-and-analytics-governance-initiatives-will-fail-by-2027-due-to-a-lack-of-a-real-or-manufactured-crisis-); [DATAVERSITY, 2025-07-11](https://www.dataversity.net/articles/common-master-data-management-mdm-pitfalls/)). 국내 은행·보험의 전사 데이터 모델 사후 기록은 기간·비용·준수율 어느 것도 찾지 못했다(검색 예산 소진).

모델 주도 아키텍처는 비평가들이 진단을 미리 적었고 20년 뒤 조사가 확인했다. UML 2.0 태스크포스를 공동 의장한 Selic 은 2003년에 "if models end up merely as documentation, they are of limited value, because documentation all too easily diverges from reality" 라 했고, 코드 생성 뒤 모델은 "abandoned because, like all software documentation, they require scarce and expensive resources to maintain" 하며, 코드→모델 역변환은 "usually can't perform the kind of abstraction that a human can" 이라 했다 ([Selic, IEEE Software 2003](https://www.state-machine.com/doc/Selic-Pragmatics.pdf)). Fowler 는 "Night of the Living Case Tools" 편에 섰고 "I don't see that the UML provides this abstraction jump - and without it the MDA will not succeed" 라 했으며 ([Fowler, 2004-02-02](https://martinfowler.com/bliki/ModelDrivenArchitecture.html)), Dave Thomas 는 "The term executable specification is an oxymoron—if the specification were truly executable, it would actually be 'the thing'" 이라 적고 PL/I·Algol 68·AD/Cycle 과 같은 운명을 예고했다 ([Thomas, IEEE Software 2004](https://www.martinfowler.com/ieeeSoftware/mda-thomas.pdf)). Wikipedia 는 Gartner 가 2006년 MDA 를 "on the rise" 로, Forrester 가 같은 해 "D.O.A." 로 봤다고 적는다(3차 자료) ([Wikipedia, MDA](https://en.wikipedia.org/wiki/Model-driven_architecture)). 실무자 450명 조사와 심층 면접 22건의 결론은 "developers rarely use it to generate whole systems. Rather, they apply MDE to develop key parts of a system" 이었다(초록) ([Whittle et al., IEEE Software 2014](https://doi.org/10.1109/MS.2013.65)). 살아남은 것은 보편 모델을 요구하지 않는 부분 — Xtext·JetBrains MPS 같은 DSL 작업대 — 이다 ([eclipse.dev/Xtext](https://eclipse.dev/Xtext/); [jetbrains.com/mps](https://www.jetbrains.com/mps/)).

시스템 공학의 축은 「측정한 사람이 거의 없다」가 결론이다. Henderson & Salado 는 MBSE 편익 문헌을 measured/observed/perceived/referenced 로 갈라 "two thirds of claimed MBSE benefits are only supported by perceived evidence, while only two papers reported measured evidence" 라 했고(초록), 밑수는 논문 847편 중 편익 언급 360편, 측정 2·관찰 27·인식 236 이다 ([Henderson & Salado, 2021](https://incose.onlinelibrary.wiley.com/doi/abs/10.1002/sys.21566); [SERC IW2021 슬라이드](https://www.omgwiki.org/MBSE/lib/exe/fetch.php?media=mbse:incose_mbse_iw_2021:benchmarking_the_benefits_and_current_maturity_of_mbse_3-2020.pdf)). Campo 등은 60편에서 주장 2,900건을 코딩해 "47%" 가 저자 의견이고 "Most claims (86%) were not substantiated by a metric" 이라 했다(초록) ([Campo et al., 2023](https://incose.onlinelibrary.wiley.com/doi/full/10.1002/sys.21644)). SERC 성숙도 조사의 장애물 순위는 "Organizational culture, Workforce knowledge/skills, Leadership support/commitment" 이고 도구는 상위에 없다 — 축이 죽는 자리는 저장소가 아니라 누가 모델을 유지하고 그 유지를 누가 지불하느냐다. JPL 의 Europa 슬라이드는 이 구상의 어려운 부분을 가장 정직하게 적었다: 한쪽에 "Single Source of Truth … Automated generation of traditional and non-traditional documents – Gate products" 를 약속하면서, 규모는 ">40 people … 10-15 people working in the modeling tool … Needed to build infrastructure" 이고, 36번 슬라이드의 제목이 「Single source of truth」인데 내용은 질문이다 — "The same piece of underlying information will show up in multiple views. Which is the one to edit? Which one is the source of truth? Who can edit what? What happens if someone else edits it?" ([JPL, Jackson 슬라이드](https://sma.nasa.gov/docs/default-source/News-Documents/jackson_gsfc_mbse_europa.pdf?sfvrsn=4)). 국방부 전략 8년 뒤의 공식 평가는 한 방향이다: RAND 는 "the benefits of DE to date have not resulted in notable cost savings or schedule reduction" ([RAND RRA2333-2, 2024-07-25](https://www.rand.org/pubs/research_reports/RRA2333-2.html)), 국방과학위원회는 "moving from anecdotal evidence to qualitative and quantitative measurements is essential" 과 "Business case analyses should be conducted before applying digital engineering to any part of the life cycle" ([DSB, 2024-05](https://dsb.cto.mil/wp-content/uploads/2024/08/DSB_DE_Final-Report_050124_Stamped.pdf)), 그리고 DoDI 5000.97 로 의무화된 뒤에도 2026년 GAO 검토 대상 48개 프로그램 중 시스템 수준 digital twin 을 계획한 곳은 4곳이라는 수치가 있다(업계지 요약, 249쪽 PDF 는 대조 못 함) ([Mobility Engineering Technology, 2026-07-27](https://www.mobilityengineeringtech.com/component/content/article/55520-digital-twin-adoption-remains-limited-in-major-weapon-programs)).

학계의 단일 모델은 자기 손으로 물러섰다. SUM 의 후속 연구는 "the SUM gets complex for small models. This complexity does not allow a single user to understand the whole SUM" 이라 적고 ([Werner & Aßmann, MRT'18](https://ceur-ws.org/Vol-2245/mrt_paper_3.pdf)), Burger 는 투영 접근이 "the problem of providing a common formalism that is able to cover all the view points" 에 부딪힌다고 했으며 ([Burger, 2014](https://publikationen.bibliothek.kit.edu/1000043437)), Vitruvius 의 평가는 기존 오픈소스를 넣어 보니 "For most of the elements, project-specific rules had to be defined. This implies high effort" 이고 "Defining consistency between more than two metamodels can easily lead to contradictions" 이며 성능·확장성 평가는 없다 ([Klare et al., JSS 2021](https://publikationen.bibliothek.kit.edu/1000124711/89982634)). 체계적 문헌 검토 둘이 바깥을 확인한다 — 8,600건 중 40편을 고른 2019년 검토는 "multi-view approaches have not been evaluated in industrial settings" 이고 "the community does not appear to consider [semantic consistency management] as a priority" 라 했고(초록), 도구 80개를 본 2020년 검토는 "35% do not provide any consistency checking" 이라 했다 ([Cicchetti et al., SoSyM 2019](https://doi.org/10.1007/s10270-018-00713-w); [Torres et al., SoSyM 2020](https://www.springerprofessional.de/en/a-systematic-literature-review-of-cross-domain-model-consistency/18509540)). DDD 쪽도 문서 층의 수치를 처음 냈다: 검증된 DDD 저장소 2,502개 중 **25.3%** 가 "record no explicit business context" 이고 저자들은 "a persistent gap between how domain intent is designed and how it is preserved in version control" 이라 부르며 "lightweight architectural traceability standards" 를 요구한다(초록) ([Özkan et al., 2026-07](https://arxiv.org/abs/2607.06471)). 따로 유지되는 모델의 운명은 UML 문헌이 유일하게 세어 놓았다 — 전문 엔지니어 50명 중 UML 을 안 쓰는 쪽 35명, 「선택적」 사용자 11명은 "for as long as it is considered useful, after which it is discarded" 이고 ([Petre, ICSE 2013](https://www.pragmadev.com/downloads/UmlInPractice.pdf)), 오픈소스 10개 중 기존 다이어그램을 고친 프로젝트는 **2개**뿐이었다 ([Osman & Chaudron, 2013](https://ceur-ws.org/Vol-1078/paper3.pdf)).

온톨로지는 "most accurate the day it ships" 이고 유지에서 죽는다. 1990년대 미 자동차 금융사의 메타데이터 저장소·온톨로지는 새 분석 도구와 바뀐 리스크 관행에 "abandoned *within months*" 됐고 교훈은 "an incomplete ontology is not just lagging behind; it's wrong" 이다 ([Farmer, 2024-09-24](https://creativedifferences.substack.com/p/interested-in-ontologies-let-me-tell)); 시맨틱 웹 회고는 "failed on upkeep" — 설계·채우기·유지 세 문제 중 셋째 — 로 요약되고 "an ontology of your own business, affordably kept accurate by your own people" 은 끝내 오지 않았다고 한다(저자 소속 미확인) ([Reynar, 2026-08-07](https://www.thisandthat.chat/blog/semantic-web-failed-on-upkeep)). 거버넌스 위원회가 분기마다 갱신하는 FIBO 조차 수렴하지 않는다 — JPMorgan 연구자의 측정으로 2017Q3 클래스 3,921개가 분기마다 +449/−2(10.3%), +429/−472(22.0%) 식으로 바뀌어 "as much as one third of the entire ontology changing quarterly. Rather than converging toward a steady state, the pace of change seems erratic" ([Chen, 2021-08-11](https://arxiv.org/pdf/2108.05401)). Palantir 구현 파트너가 적은 2년차 실패 유형은 전부 조직적이다 — "Modeling the source system instead of the business", "Treating the ontology as a warehouse", "Shipping applications without action types", "Unresolved identity" — 그리고 처방은 "every object type has a named owner with the authority to settle definitional questions" 다(컨설팅) ([BD Emerson, 2026-07-30](https://www.bdemerson.com/article/palantir-ontology-explained)). Uber 의 2019년 강연 제목이 "Lessons from Reality" 이고 교훈은 "We are not all ontologists", "Good enough does not scale" 다 ([Shinavier, KGC 2019](https://www.slideshare.net/joshsh/building-an-enterprise-knowledge-graph-uber-lessons-from-reality)). 국내에서 유일하게 발견된 실패 기록은 2026년 개인 블로그다: "6개월짜리 온톨로지 위원회가 열리고… 그 뒤로 아무도 그것을 질의하지 않습니다", 원인은 "완결성을 위해 모델링했지 _사용_을 위해 모델링하지 않은 것" ([youngju.dev, 2026-07-15](https://labhub.hopto.org/blog/2026-07-15-domain-knowledge-ontology)).

가장 좁은 축조차 손으로 유지하면 드리프트한다. 공개 OpenAPI 를 측정한 연구를 2026년 논문이 모아 인용한다 — APIs.guru 스펙 91개 중 "40% produced errors when a correct client calls a real API", 1,000개 이상 중 "almost 99% … contained some mismatch"(둘 다 2차 인용) — 그리고 자기 실험에서 스펙이 구현보다 느슨한 `REQUEST_LOOSE` 결함은 커버리지를 0.97pp 밖에 안 움직이면서 요청·응답 품질을 47.90pp 떨어뜨렸다: "coverage metrics capture broad degradation but miss hidden degradation entirely" ([Mazhar et al., 2026-07-13](https://arxiv.org/html/2607.12101v1)). REST API 50개·엔드포인트 1,023개 표본에서는 보안 스킴 오류 14.4% 등으로 자동 래퍼가 76.5% 만 통과했다 ([Mastouri et al., 2025-07-21](https://arxiv.org/html/2507.16044v1)). 트래픽과 스펙을 대조하던 도구는 둘 다 사라졌다 — Dredd 는 2024-11-08, Optic 은 2026-01-12 에 아카이브됐고, 경쟁 벤더의 부고 기사조차 "contains no statistical data on actual API drift rates" 라 적는다 ([apiaryio/dredd](https://github.com/apiaryio/dredd); [opticdev/optic](https://github.com/opticdev/optic); [FlareCanary, 2026-04-14](https://dev.to/flarecanary/optic-is-dead-what-now-for-api-drift-detection-2kb8)). 큰 회사의 「스펙이 정본」도 실은 파이프라인이다: Stripe 의 v1 SDK 는 공개 OpenAPI 에서, v2 는 "an internal dump of the protobuf definitions" 에서 생성되다가 2025-09-08 에야 한 생성원으로 합쳐졌다 ([stripe-node PR #2398](https://github.com/stripe/stripe-node/pull/2398)). 2025–26년 SDD 의 1인 측정은 같은 그림을 Markdown 으로 반복한다: Spec Kit 으로 코드 689줄에 생성 Markdown 2,577줄, 사람 검토 3.5시간, 스펙 없는 기준선 대비 약 10배 ([Scott Logic, 2025-11-26](https://blog.scottlogic.com/2025/11/26/putting-spec-kit-through-its-paces-radical-idea-or-reinvented-waterfall.html)); 날짜 하나 표시하는 데 파일 8개·1,300줄 ([Marmelab, 2025-11-12](https://marmelab.com/blog/2025/11/12/spec-driven-development-waterfall-strikes-back.html)); 그리고 모두가 같은 실패 지점을 짚는다 — "updating a separate document is unrewarded work that no sprint board tracks", "a linter does not flag it, CI does not flag it" ([Sharda, dev.to](https://dev.to/kunalsharda/spec-driven-development-with-ai-is-real-now-the-stale-spec-is-the-part-nobody-fixed-2001)), SDD 는 요구사항 문서·Gherkin·위키 설계문서·손으로 쓴 OpenAPI 에 이은 "the fifth iteration" 이고 "Each of them drifted from the code at exactly the same rate" ([Frisinger, dev.to](https://dev.to/tmfrisinger/spec-driven-development-is-the-prose-spec-drift-trap-reborn-4p99)). Böckeler 는 모델 주도 개발의 교훈을 그대로 옮긴다 — "specs sit at an awkward abstraction level and just create too much overhead" — 그리고 유일하게 spec-as-source 를 겨냥했던 Tessl 은 2026년 문서 사이트맵에서 `@generate`·`@describe` 페이지가 사라지고 "Verifiers" 와 "Keep docs in sync"("A scheduled docs audit checks whether the docs still match the code and opens a PR when they have drifted")만 남았다 — 스펙이 원천이 아니라 **감지하고 제안하는** 모델로 후퇴한 것이다 ([Böckeler, 2025-10-15](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html); [docs.tessl.io 사이트맵](https://docs.tessl.io/sitemap.md)). Thoughtworks 안에서도 무엇이 정본인지 갈린다: Radar 는 SDD 를 Assess 에 두며 "handcrafting detailed rules for AI ultimately doesn't scale" 이라 했고, Liu 는 "executable code remains the source of truth you need to maintain" 이라 썼다 ([Thoughtworks Radar, 2025-11](https://www.thoughtworks.com/en-us/radar/techniques/spec-driven-development); [Liu, 2025-12-04](https://www.thoughtworks.com/en-us/insights/blog/agile-engineering-practices/spec-driven-development-unpacking-2025-new-engineering-practices)). 국내 GeekNews 의 댓글은 긴 세션에서 `tasks.md` 와 실제 구현이 갈라졌다고 보고했다 ([news.hada.io, 2025-09-15](https://news.hada.io/topic?id=23074)).

## 살아남은 축은 다섯 조건을 갖췄고, 넷은 기술이 아니다

여섯 갈래를 겹쳐 놓으면 생존 조건이 다섯으로 모인다. 이 다섯은 인용된 틀이 아니라 이 조사의 종합이다. **첫째, 구속하는 부분이 작고 경험으로 골라졌다.** FHIR 의 코어는 "approximately 80% of systems maintaining the resource will support the element" 로 정해지고 나머지는 extension 과 profile 로 간다 ([HL7 FHIR R5](https://www.hl7.org/fhir/comparison-v3.html)); data mesh 의 전역 층은 polysemes 와 플랫폼이 강제하는 표준뿐이고 그 경계를 정하는 것은 "an art" 다 ([Dehghani, 2020](https://martinfowler.com/articles/data-mesh-principles.html)); Tilkov 는 완전한 비즈니스 객체 대신 "formats and small fragments" 를 표준화하라 하고 ([Tilkov, 2015](https://www.innoq.com/en/blog/2015/03/thoughts-on-a-canonical-data-model/)), Evans 는 대규모 구조에 대해 "it is best not to shoot for comprehensiveness, but rather to find a minimal set that solves the problems that have emerged. Less is more" 라 했다 ([DDD Reference p. 48](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf)); 국내 공공 표준은 개념 모델이 아니라 명칭·형식만 표준화한다 ([행정안전부 카드뉴스, 2025-01-02](https://www.mois.go.kr/frt/bbs/type002/commonSelectBoardArticle.do?bbsId=BBSMSTR_000000000205&nttId=114836)). **둘째, 그 작은 부분은 교환 경계에서 기계가 검사한다 — 문서를 읽어서가 아니라.** CGMES 적합성은 "applications only on certain CGMES functionalities that are supported by the assessed Application" 을 시험하고 등록부에 유효기간을 적으며 ([ENTSO-E](https://www.entsoe.eu/data/cim/cim-conformity-and-interoperability/)), SID 는 ABE 별 점수, NIEM 은 IEPD 의 NDR 적합성, Confluent 는 등록 시점의 호환성 거부, Buf 는 PR 실패, Zalando 는 CI 의 린터다. 어느 경우에도 「내부 모델이 표준과 같은가」를 검사하지 않는다 — 적합성은 늘 「선언한 부분집합에 대해 표준 형식을 내고 받을 수 있는가」이고, 그래서 내부의 어긋남은 영구적이며 값이 매겨져 있다. **셋째, 참조 층은 명시적으로 비구속이다.** RIM 매핑은 "should be taken as a guide, not an absolute" 이고, Tilkov 의 대안은 중앙 팀이 내리누르는 대신 팀이 가치를 볼 때 "pull" 하도록 검색 가능한 저장소를 두는 것이며 ([Tilkov, 2015](https://www.innoq.com/en/blog/2015/03/thoughts-on-a-canonical-data-model/)), Palantir 의 설계 지침조차 "A slightly imperfect Ontology that is in use and generating value is better than a theoretically perfect one" 이라 적는다 ([Palantir, best practices](https://www.palantir.com/docs/foundry/ontology/ontology-best-practices-and-anti-patterns)). **넷째, 밖의 누군가가 비준수를 비싸게 만든다.** MISMO 는 "required by most regulators, housing agencies and the GSEs"(협회 FAQ, 검색 요약) ([MISMO FAQs](https://www.mismo.org/about-MISMO/mission-and-vision/mismo-faqs)), CGMES 는 EU 네트워크 코드, NIEM 은 연방·주 정부, 공통표준용어는 고시다; 이 조건이 없던 ISO 15926-2 는 한 회사의 사내 표준에서 나온 표 모양의 CFIHOS 로 대체됐다. **다섯째, 공개 변경 절차로 버전이 관리되고 상호운용성 시험의 결함이 표준으로 되먹인다** — ENTSO-E 의 IOP 보고서에 "Issues recorded during this testing and proposed resolutions are included" 되는 식이다 ([ENTSO-E](https://www.entsoe.eu/data/cim/cim-conformity-and-interoperability/)). RIM 은 (1)~(3)을 어기고 영국에서 (4)만 가졌으며, ISO 15926-2 는 (1)(2)(4)가 없었고, 그것을 대체한 CFIHOS 는 다섯을 다 가졌다.

조직 안에서 살아남은 축도 같은 모양이다 — 작고, 게이트가 있고, 리뷰하는 이름 붙은 몸이 있다. Zalando 는 "8,000+ active service applications", "300+ delivery teams" 에서 스펙을 코드 전에 PR 로 올려 동료 리뷰를 받고 "the API Guild" 가 중요한 API 를 보며 "Zally - our API Linter" 가 파이프라인에서 형식·이름·오류 처리·보안을 검사한다 — 그리고 비용도 적었다: "compliant creates some efforts" ([Zalando Engineering, 2019-04-04](https://engineering.zalando.com/posts/2019/04/developing-zalando-apis.html)). Google 의 AIP-100 은 proto 표면을 API 리뷰어가 보되 "Run the API linter beforehand" 이고 ([google.aip.dev/100](https://google.aip.dev/100)), Pact 를 은행에 심은 컨설팅 사례는 6개 엔드포인트에 수동 E2E 66% 절감·프로덕션 결함 2건을 보고하되(자기 보고) 성공 요인을 "Contract Testing Champions are essential" 과 "Group of Practice" 로 적는다 ([Sngular, 2024-10-14](https://www.sngular.com/insights/321/pactflow-contract-testing-a-business-case-study)). 셋의 공통점은 (a) 이름 붙은 리뷰 몸, (b) 산출물이 반드시 게시되는 자리, (c) 기계 게이트이고, 셋 중 하나를 빼면 기록은 드리프트 이야기가 된다. 반대로 SDD 도구들은 리뷰 몸도 게시 자리도 없이 게이트를 에이전트의 판단에 맡긴다 — Kiro 의 정렬은 "ask Kiro to update specs" 와 `tasks.md` 의 "Sync Files" 버튼이고 ([kiro.dev best practices](https://kiro.dev/docs/specs/best-practices/)), 그래서 같은 불평이 1인칭 기록마다 되풀이된다. 축이 「무엇이 정본인가」를 선언만 하고 무엇도 깨뜨리지 않으면 드리프트한다는 것은 이 조사에서 가장 일관된 발견이다.

「모델에서 파생한다」는 성질이 실제로 성립한 곳은 셋뿐이고 전부 데이터 모델이다. Zalando 의 MDM 은 System·Table·Column·Concept·Attribute·Relationship 여섯 노드로 시스템 데이터 모델을 그래프에 넣고, 손으로 하는 일은 "recording column-to-concept mappings" 뿐이며, Python 스크립트가 "the logical data model and transformation specifications" 를 생성해 "automatic generation of all deliverables directly from the graph, creating a single source of truth with maintained data lineage" 를 냈다 — 범위는 수십 개 테이블·수백 개 컬럼이다 ([Zalando Engineering, 2021-07-29](https://engineering.zalando.com/posts/2021/07/knowledge-graph-master-data-mdm.html)). Uber 의 Config Knowledge Graph 는 7개 도메인·3,000개 이상 마이크로서비스·3,500개 이상 feature-flag 네임스페이스의 교차 설정을 REQUIRES/EVALUATES/CAN_LAUNCH_IN 관계로 검증하고 ACID 트랜잭션으로 실패 시 되돌리며, "Two engineers built production infrastructure in under 12 weeks", 도메인 팀이 넣은 안전장치 27개 — 다만 벤더 고객 사례다 ([Neo4j, 2026-07-27](https://neo4j.com/customer-stories/uber/)). 셋째는 앞 절의 Stripe·GitHub·Twilio 로, 공개 OpenAPI 에서 SDK·문서를 생성하되 그 스펙 자체는 내부 원천(JSON 스키마와 계약 테스트, 비공개 생성기, protobuf)의 **투영**이다 ([GitHub Blog, 2020-07-27](https://github.blog/news-insights/product-news/introducing-githubs-openapi-description/); [stripe/openapi](https://github.com/stripe/openapi)). 세 경우 모두 파생의 원천은 기계가 이미 갖고 있는 것(컬럼, 플래그, 스키마)이지 사람이 쓴 정책이 아니다.

국내에서 확인되는 생존 형태도 같다. 공공 표준은 다섯 조건 중 넷(작음·고시·매핑 의무·연 1회 제·개정)을 갖췄고 기계 검사만 확인이 안 된다 — 학술 논문 한 편이 공통표준용어를 변환 대상으로 삼아 Seq2seq 로 비표준 컬럼명을 바꾸되 "데이터를 모델에 적용하기 위해서는 데이터를 전환하는 작업 등 사람의 개입이 필요하다" 고 적을 뿐 준수율 통계는 없다 ([신대원 외, 2023, KCI](https://www.kci.go.kr/kciportal/ci/sereArticleSearch/ciSereArtiView.kci?sereArticleSearchBean.artiId=ART002970114)). 카카오페이의 DDD 는 조건 (1)과 리뷰 몸(여신전문가·기획자·개발자가 함께 모델을 정함)을 갖췄고 게이트는 사람이다. 국내 금융의 전사 데이터 모델은 벤더 거버넌스 도구 사례(KB국민은행 6개월 포털 구축, 메타데이터·lineage·용어 정리)로만 보이고 결과 수치는 없다 ([컴퓨터월드, 2019-11-29](https://www.comworld.co.kr/news/articleView.html?idxno=49753)).

## 어긋남을 다룬 다섯 방식은 결국 한 선으로 갈린다 — 기계가 관찰하는 쪽만 루프가 돈다

**모델에서 생성**은 가장 오래된 답이고 조건이 붙어 있다. Selic 은 완전한 생성일 때만 성립한다고 못 박았다 — "With complete code generation, there is rarely, if ever, a need to examine or modify the generated program directly" 그리고 "Model accuracy is guaranteed because the model eventually becomes the system that it was modeling" ([Selic, 2003](https://www.state-machine.com/doc/Selic-Pragmatics.pdf)) — 그런데 실무는 부분 생성만 한다(Whittle). 국방부의 답도 생성이다: digital artifacts 는 "dynamically generated" 되고 JPL 은 gate product 를 모델에서 뽑는다. 문서 쪽에서 성립한 생성은 Living Documentation 의 living glossary, C4 의 뷰, Zalando MDM 의 산출물, 그리고 2026년 프리프린트가 제안한 "Generated from the store... on every build so that the description cannot drift from the content" 다 ([Zappa, 2026-09, 프리프린트](https://arxiv.org/pdf/2609.14121)). 생성은 원천이 기계 안에 있을 때만 드리프트를 없앤다 — 원천이 사람의 문장이면 생성물이 아니라 원천이 드리프트한다.

**모델이 곧 코드**는 DDD 의 답이다. 규칙은 이름 붙은 모델 원소가 된다 — Evans 의 1장에서 "Allow 10% overbooking." 이라는 요구는 처음엔 `voyage.capacity() * 1.1` 이라는 guard 안에 숨어 있다가 `OverbookingPolicy` 클래스로 끌려 나온다 ([Evans, Ch.1, InformIT](https://www.informit.com/articles/article.aspx?p=102604&seqNum=4)) — 그리고 정렬은 코드를 전문가가 읽을 수 있게 만드는 것이지 문서의 숫자와 코드의 숫자를 비교하는 검사기가 아니다. 이 답의 한계도 이 계보가 스스로 적었다: Declarative Design 은 "Many declarative approaches can be corrupted if the developers bypass them intentionally or unintentionally" 이고 ([DDD Reference p. 25](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf)), 코드를 모델에 대조하는 도구(jMolecules/ArchUnit, Context Mapper)는 **구조**만 본다 — Context Mapper 는 "We currently only validate in one direction. We ensure that objects in the code also exist in the model. But we do not validate whether objects in the model also exist in the code" 라 명시한다 ([contextmapper.org](https://contextmapper.org/docs/architecture-validation-with-archunit/); [jMolecules 백서, 2022-02](https://xmolecules.org/aea-paper.pdf)). 규칙을 코드로 옮긴 policy as code(OPA·Sentinel·Cedar)는 축을 코드 쪽으로 **이전**한 것이지 산문과 코드를 맞춘 것이 아니다 — 산문은 주석이 된다 ([OPA docs](https://www.openpolicyagent.org/docs/latest/)).

**조정 루프**는 Kubernetes 가 완성했고, 그 문서가 조건 셋을 적어 놓았다: 원하는 상태가 `spec` 에 완전하고 선언적일 것, 모든 행위자가 뒤집힐 수 있음을 전제할 것("Don't assume a component's decisions will not be overridden or rejected"), 그리고 객체마다 관리 방식이 하나일 것 — "Mixing and matching techniques for the same object results in undefined behavior" ([design principles](https://raw.githubusercontent.com/kubernetes/design-proposals-archive/main/architecture/principles.md); [Object Management](https://kubernetes.io/docs/concepts/overview/working-with-objects/object-management/)). Borg→Omega→Kubernetes 논문은 루프가 왜 튼튼한지("when a controller fails or restarts it simply picks up where it left off")와 무엇을 못 푸는지("multiple controllers might think they have jurisdiction over a single pod. It is important to prevent such conflicts through appropriate configuration choices")를 같이 적는다 ([Burns et al., ACM Queue 2016](https://john.e-wilkes.com/papers/2016-Queue-Kubernetes.pdf)). 공유 모델 안의 소유권은 server-side apply 가 필드 단위로 객체 **안에** 적는다 — `.metadata.managedFields` 에 관리자별 소유 필드를 저장하고, 남이 소유한 필드를 바꾸려는 apply 는 **409** 로 거부하며, 세 갈래(강제로 덮어써 단독 소유 · 필드를 내 매니페스트에서 빼서 소유 포기 · 적용 안 함)만 허용한다; 다만 소유권은 역할이 아니라 **마지막으로 쓴 쪽**이 얻고, KEP 은 "Controllers should force" 라 권한다 ([Kubernetes, Server-Side Apply](https://kubernetes.io/docs/reference/using-api/server-side-apply/); [KEP-555](https://raw.githubusercontent.com/kubernetes/enhancements/master/keps/sig-api-machinery/555-server-side-apply/README.md)). GitOps 두 주류 도구의 기본값은 **감지만** 한다 — Argo CD 는 self-heal 이 "disabled by default", prune 도 기본 꺼짐, 3분마다 폴링 ([Argo CD, Automated Sync](https://argo-cd.readthedocs.io/en/stable/user-guide/auto_sync/)); Flux 의 Helm drift detection 은 v2.2.0(2023-12)부터 있되 기본 `disabled` ([Flux docs](https://fluxcd.io/flux/installation/configuration/helm-drift-detection/)). 그리고 둘 다 「런타임이 정본인 필드」를 손으로 적는 예외 목록을 갖는다 — HPA 가 고치는 `/spec/replicas`, 웹훅이 바꾸는 필드, Helm 이 매번 새로 만드는 난수 ([Argo CD, Diffing Customization](https://argo-cd.readthedocs.io/en/stable/user-guide/diffing/)). Terraform 은 루프를 사람 앞에서 세우도록 설계됐다: `plan` 은 제안이고, HCP 의 drift detection 은 "non-actionable" 알림이며, 벤더 튜토리얼은 두 해법(인프라를 되돌린다 · 설정을 현실에 맞춘다)을 둘 다 정당한 것으로 적고 `-refresh-only` 는 "while responding to an incident" 에 밖에서 고친 것을 기록에 맞추는 명령이다 ([HashiCorp tutorial](https://developer.hashicorp.com/terraform/tutorials/state/resource-drift); [HCP health assessments](https://developer.hashicorp.com/terraform/cloud-docs/workspaces/health)). 스키마 도구도 전부 알림에서 멈춘다 — Atlas 는 Slack/webhook 으로 diff 를 보내고 "does not auto-fix" ([Atlas docs](https://atlasgo.io/monitoring/drift-detection)). 유병률은 벤더 수치뿐이고(Firefly 의 "90%"·"13%" 는 보고서를 못 열어 미검증), 학술 수치 하나는 AWS 워크스페이스 150개 이상에서 심각도 필터가 알림을 73% 줄인다는 것 — 드리프트 신호가 분류가 필요할 만큼 잦다는 간접 증거다 ([tfdrift, arXiv 2608.18173](https://arxiv.org/abs/2608.18173)). 루프의 부재가 비싼 예는 규제 문서에 있다: Knight Capital 은 새 코드를 서버 8대 중 7대에만 배포했고 "Knight did not have a second technician review this deployment", 45분에 $460M 손실, 사전 경고 메일 97통은 "not design[ed] … to be system alerts" 였다 ([SEC 34-70694, 2013-10-16](https://www.sec.gov/litigation/admin/2013/34-70694.pdf)). 루프 위에 **측정**을 얹은 것은 Puppet 이 유일하고 2016년에야 생겼다 — 매 변경을 intentional(코드가 바뀜)과 corrective("unauthorized or unintentional changes on a node" 를 되돌림)로 나눠 보고한다 ([Puppet glossary](https://www.puppet.com/docs/puppet/7/glossary)).

**검증**은 축이 좁을수록 세다. Cedar 는 Dafny(뒤에 Lean) 모델을 "a reference" 로 두고 프로덕션 Rust 와 밤마다 "approximately 100 million total tests" 의 differential random testing 을 돌려 증명으로 4건, DRT/PBT 로 21건의 결함을 잡았다 — 이 조사에서 「스펙이 축이고 적합성 시험이 있다」에 가장 가까운 사례이며, 전제는 **양쪽이 실행 가능**하다는 것이다 ([Amazon Science, 2023-05-10](https://www.amazon.science/blog/how-we-built-cedar-with-automated-reasoning-and-differential-testing); [Disselkoen et al., 2024](https://arxiv.org/abs/2407.01688)). Schemathesis 는 스키마에서 속성 기반 테스트를 생성해 14가지 검사를 돌리고 ([Schemathesis checks](https://schemathesis.readthedocs.io/en/stable/reference/checks/)), oasdiff 는 스펙 대 스펙의 breaking change 를 PR 에 단다 ([oasdiff](https://github.com/oasdiff/oasdiff)); PactFlow 의 로드맵은 왜 스펙 검증이 불충분한지를 적었다 — "Schemas are abstract, and introduce ambiguity which can lead to misinterpretations" ([pactflow/roadmap#31](https://github.com/pactflow/roadmap/issues/31)). 세 기제가 못 보는 것은 같다: 스펙에 적히지 않은 업무 규칙, 그리고 스펙이 현실보다 느슨한 쪽의 「숨은 열화」(Mazhar 2026).

**기록하고 수용**은 이론과 실무가 따로 발명한 답이다. DDD 의 Context Map 은 어긋남을 관계 유형의 어휘로 적는다 — Partnership · Shared Kernel · Customer/Supplier · Conformist · Anticorruption Layer · Open-host Service · Published Language · Separate Ways · Big Ball of Mud — 그리고 지시는 "Map the existing terrain. Take up transformations later." 다 ([DDD Reference pp. 29–38](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf)). Domain Storytelling 은 as-is 와 to-be 를 갱신해야 할 한 산출물이 아니라 **별개** 스토리로 둔다 ([domainstorytelling.org](https://domainstorytelling.org/quick-start-guide)). 요구공학의 inconsistency management 는 목표를 「일관되게 유지」에서 「불일치를 관리」로 바꿨다: "Maintaining consistency at all times is counterproductive", 전역 일관성 검사는 "truly intractable", "You will never obtain a complete set of rules", 그래서 감지 → 진단 → 처리(resolve / ignore / defer / circumvent / ameliorate) → 위험 재평가의 루프를 돌리고 "The decision to tolerate an inconsistency is a risk-based decision … you have to reevaluate risk periodically" 한다. 문서 사례도 그 논문에 있다 — 순서도와 본문이 갈라지자 개발자들은 "the text should be regarded as definitive whenever it failed to match the diagram" 이라는 면책 문구를 넣어 ameliorate 했고, 재평가를 빼먹은 값은 Ariane-5 였다("The decision to tolerate the inconsistency was not wrong for Ariane-4, but the lack of available tools to indicate that the risk needed to be reevaluated for Ariane-5 proved disastrous") ([Nuseibeh, Easterbrook, Russo, IEEE Computer 2000](https://www.cs.toronto.edu/~sme/papers/2000/IEEEComputer2000.pdf)). Palantir 는 같은 것을 기계로 만들었다 — Experimental/Active/Deprecated/Promoted 상태, 폐기에는 사유와 삭제 기한 필수, 깨는 변경은 마이그레이션을 정의해야 저장되고, 정리 도구가 "Stale datasources" 와 "Past deprecation dates" 를 뽑는다 ([Palantir, Statuses](https://www.palantir.com/docs/foundry/object-link-types/metadata-statuses); [Schema migrations](https://www.palantir.com/docs/foundry/object-edits/schema-migrations); [Cleanup](https://www.palantir.com/docs/foundry/ontology-manager/cleanup)). 이론은 왜 자동 조정이 끝까지 못 가는지를 증명해 놓았다. 렌즈의 두 법칙(GetPut·PutGet)은 고른 역변환이 정보를 잃지 않는다는 것만 보장하고, "there are many ways to equip a given get function with a putback function … we need some means of specifying which putback is intended" 이며, 목차와 절 제목을 서로 만들어 주는 직관적 동작은 "not injective and cannot participate in a lens in our sense" 다 ([Foster et al., TOPLAS 2007](https://www.cis.upenn.edu/~bcpierce/papers/lenses-toplas-final.pdf)); 뷰 갱신은 "unambiguous, i.e., there can be exactly one way to do it" 이어야 하고 ([GRACE 보고서, 2009](https://gsd.uwaterloo.ca/sites/default/files/GRACE-report-ICMT09.pdf)), least change 는 "much less well understood" 다 ([Oxford TLCBX](https://www.cs.ox.ac.uk/projects/tlcbx/)). 그래서 Vitruvius 는 언어 안에 「사용자에게 묻기」를 넣었다 — "either restrict the possible solutions by implementing a certain strategy, or ask the user for a clarification of intent" ([Klare et al., 2021](https://publikationen.bibliothek.kit.edu/1000124711/89982634)). 법과 정책 쪽은 처음부터 사람을 남긴다: OECD 의 Rules as Code 는 사람용과 기계용을 **동시에** 초안해 "isomorphism … an effective 1-to-1 mapping" 을 겨냥하되 "there is no technology solution that can accurately and effectively convert human-readable rules into machine-consumable form without human involvement" 이고 재량·해석이 드는 규칙은 범위 밖이며 ([OECD, 2020](https://www.oecd.org/content/dam/oecd/en/publications/reports/2020/10/dechiffrer-le-code_d56cab77/3afe6ba5-en.pdf)), Catala 는 법조문 문단 바로 뒤에 코드를 두는 literate programming 으로 대응하되 변호사는 "observers and reviewers" 이고, 두 시간 교육 뒤 코드를 읽을 수 있다고 한 변호사 7명 중 일부러 심은 ⩽/⩾ 결함을 찾은 사람은 **2명**이었다 ([Merigoux et al., ICFP 2021](https://arxiv.org/pdf/2103.03198)).

다섯 방식을 한 표에 놓으면 선이 보인다. 자동으로 수렴하는 행은 예외 없이 「현실이 기계에 관찰되고 기계가 되돌릴 수 있는」 곳이고, 한쪽이 모델에 없는 상태를 쥐는 순간(오토스케일러의 replicas, DB 의 행, 법의 해석) 모든 프로젝트가 예외 목록이나 알림 전용으로 내려간다. 정책 문서의 값은 전부 둘째 쪽에 있다.

| 방식 | 축 | 조정 기제 | 모델과 현실이 충돌하면 | 사람이 남는 자리 |
|---|---|---|---|---|
| 생성(MDA · DoD · JPL · Zalando MDM) | 모델·저장소 | 정방향 변환 | 생성물은 덮어쓴다; 손댄 생성물은 다음 생성에 사라짐 | 원천 편집; 부분 생성 범위 결정 |

## 값(한도·권한)은 어느 축에도 1급이 아니었고, 그래서 이 구상의 새 부분은 검사기가 아니라 판정이다

이 사용자가 정본을 매달려는 세부는 개념이 아니라 **값**이다 — 검증 상한, 등급별 권한, 기본값. 여섯 갈래 중 어느 축도 이것을 검사 가능한 1급 원소로 갖지 않았다. 산업 reference model 은 데이터 구조이고("semantic interoperability but not clinical interoperability"), MDA 의 PIM 은 애플리케이션의 계산 구조, MBSE 는 요구·구조·행위·검증, SUM 은 메타모델이 있는 소프트웨어 모델이며, 어느 국방부 문서도 정책 값이나 기획 결정을 모델 안에 두지 않는다. DDD 는 값을 **이름 붙은 클래스**에 넣지만(`OverbookingPolicy`) 그 안의 상수가 정책 문서의 숫자와 같은지 보는 검사기는 없고, 문서 층의 유일한 변경 절차인 distillation document 는 "which concepts are core" 를 다루지 값을 다루지 않는다. API 계약은 구조 제약(`minimum`·`maximum`·`pattern`·enum)을 검증기와 Bean Validation 주석으로 강제하지만, 실무자가 적었듯 "The provided minimum value has to be equal or smaller than the maximum … can neither expressed by an OpenAPI specification nor considered by any generator" 이고 "This basically applies to all validations taking multiple fields of a class into account" ([Rotsch, 2020-04-19](https://guntherrotsch.github.io/blog_2020/openapi-bean-validation.html)); 보안 쪽은 더 직설적이다 — OpenAPI 는 "cannot catch requests that are structurally correct but semantically wrong" 이고 `minimum: 0` 은 거래 한도도 계정 등급도 강제하지 않는다(벤더 블로그) ([Axeploit, 2026-08-05](https://axeploit.com/blog/business-logic-flaws-won-t-show-up-in-your-openapi-spec-here-s-where-they-hide)). 값이 1급이고 기계가 검사하는 자리는 계약 밖에 있다: Kubernetes 는 CRD 스키마 안에 `x-kubernetes-validations` 의 CEL 규칙(`self.minReplicas <= self.replicas`)을 두어 API 서버가 거부하고 ([Kubernetes docs, CRD](https://kubernetes.io/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/)), OPA 는 `opa test` 와 커버리지로 정책을 시험하며 ([OPA policy testing](https://www.openpolicyagent.org/docs/policy-testing)), Cedar 는 앞 절의 차등 시험이고, Palantir 는 규칙을 action type 의 검증과 function 의 코드로만 표현한다("functions provide a way to author and evolve business logic with arbitrary complexity") ([Palantir docs, overview](https://www.palantir.com/docs/foundry/ontology/overview)). 이 셋의 공통점은 규칙이 **곧 강제 지점**이라는 것이고, 그래서 정렬된다 — 산문 정책과의 연결은 없다. 규칙을 통제 자연어로 적는 표준(OMG SBVR 1.4)은 존재하되 채택 근거가 없고 ([OMG SBVR](https://www.omg.org/spec/SBVR/1.4/About-SBVR)), 정책 **문서**를 평가에 배선한 예는 하나뿐이다 — OpenAI Model Spec 의 각 조항이 ID(`sy73` 같은)를 갖고 "challenging prompts" 파일에 링크돼 성공 기준이 된다는 Grove 의 설명(2차 전사) ([Tessl 의 정리, 2025-07-04](https://tessl.io/blog/the-most-valuable-developer-skill-in-2025-writing-code-specifications/)). 국내도 같다 — 카카오페이는 한도·회수일 기본값을 `Account.create()` 팩토리 안에 두고, 정렬은 사람이다.

앞선 조사와 합치면 이 구상의 자리가 정확해진다. 앞선 보고서([『기능 지도와 정본 링크 사례』](2026-09-25-canonical-link-feature-map-prior-art.md))의 결론은 「값을 복사하지 않고 정본을 가리킨다」「소유자와 시점」「기계가 확인하는 포인터」는 각각 선례가 있고, **세부 단위의 사람 판정 + 형식 있는 포인터 + 명시적 「정본 아직 없음」** 의 결합을 검색 층 위에 얹은 것이 없다는 것이었다. 이번 조사가 더하는 것은 그 결합이 어느 **형태**에 속하느냐다. 완전한 중심 모델 — 값을 다 담고 모두가 거기서 derive 하는 것 — 은 RIM·EDM·SUM 이 밟은 실패한 형태이고, 이 구상은 그것이 아니다. 지도가 값을 담지 않고 **가리키며**, 세부마다 다른 산출물(정책 문서 절·코드 상수·스키마 제약)을 정본으로 둘 수 있다는 점에서 이 구상은 살아남은 형태다: 기존 산출물을 그대로 두고 선언된 대응 규칙으로 잇는 Vitruvius 의 *virtual SUM*, 모델을 하나로 합치지 않고 접점마다 관계 유형을 적는 DDD 의 *Context Map*, 2022년에 **복수형**이 된 국방부의 authoritative source*s* of truth, 그리고 이름 그대로 「원소가 다른 모델을 가리키는 모델」인 Bézivin 의 *megamodel*(정의는 검색 요약만 확인). 이 계보들이 왜 그 형태로 물러섰는지가 곧 이 구상의 근거다 — 하나의 형식으로 모든 관점을 덮을 수 없고(Burger), 완전한 모델은 작은 시스템에서도 한 사람이 이해 못 하며(Werner & Aßmann), 총체적 통일은 "not … feasible or cost-effective"(Evans via Fowler)다 ([Fowler, BoundedContext, 2014](https://martinfowler.com/bliki/BoundedContext.html)). 그리고 claim 에 적힌 **소유자 판정** 은 이 조사에서 이름을 얻는다: 국방부 2022년 Fundamentals 의 ASoT — "An entity such as a person, governing body, or system that applies expert judgment and rules to proclaim a digital artifact is valid" — 는 권위를 저장소의 성질이 아니라 **거버넌스의 지정**으로 다시 정의한 것이고, 그 지침의 Fundamental 3 이 요구하는 것(access control, traceability, quality, acceptance criteria) 중 traceability 와 acceptance 가 이 구상의 결정자·시점·근거 칸이다 ([DE Fundamentals 2022](https://ac.cto.mil/wp-content/uploads/2022/03/DE-Fundamentals-2022.pdf)). 실무 쪽 대응물은 Alation 의 필수 사유가 붙는 Trust Flag 와 Wikidata 의 rank + "reason for rank" 였고(앞선 보고서), 「정본이 없다」를 결정의 한 갈래로 적은 곳은 Uber uMetric 의 위원회 질문("In the case where none of the data sources is qualified, what actions should be taken and who are the owners?")뿐이었다 ([Uber, 2021-01-12](https://www.uber.com/blog/umetric/)).

새로 남는 자리는 하나이고, 이번 조사는 그것을 어떻게 지어야 하는지도 말해 준다. 산문의 값과 코드의 값 사이에는 어느 갈래에도 기계 검사기가 없다 — 양쪽이 실행 가능한 Cedar 와, 사람이 나란히 읽는 Catala·Rules as Code 만 근처에 있다. 그러니 이 층은 **조정 루프가 아니라 Terraform·Atlas 의 자세**로 지어야 한다: 감지는 늘, 정정은 사람. 정책 문서의 「관찰된 상태」는 기계가 재구성할 수 없으므로(Kubernetes 의 "Object status must be 100% reconstructable by observation" 을 만족 못 한다) 루프의 자동 정정 조건이 처음부터 안 선다. 대신 빌려 올 것은 루프가 아니라 그 **장부**다. (1) 앞선 보고서가 이미 짚은 Doorstop 의 방식 — 포인터에 대상의 fingerprint 를 저장하고, 대상이 바뀌면 판정을 suspect 로 떨어뜨리며, 사람이 다시 판정해야 돌아온다 — 는 이번 조사의 언어로 「defer 된 불일치에 재평가 시점을 붙이는 것」이고, Ariane-5 가 그 시점을 빼먹은 값이다 ([Doorstop item](https://raw.githubusercontent.com/doorstop-dev/doorstop/develop/docs/reference/item.md)). (2) Puppet 의 intentional/corrective 분류를 판정 변경에 그대로 옮기면 — 정본을 **바꾼** 것(결정이 바뀜)과 정본에 **맞춘** 것(어긋남을 되돌림)을 가르면 — 아무도 낸 적 없는 수, 곧 corrective 의 비율과 그 소요 시간이 나온다. (3) server-side apply 의 필드 매니저처럼 소유권은 지도 객체 **안에** 필드 단위로 적고, 다른 소유자의 세부를 건드리는 변경은 자동 병합이 아니라 거부·명시적 강제로 남긴다; 다만 SSA 의 교훈대로 「마지막으로 쓴 쪽이 소유」가 되지 않게 역할로 묶는다. (4) 정당한 어긋남은 Context Map 의 어휘(Conformist·Anticorruption Layer·Separate Ways·Published Language)로 **이름 붙여** 적는다 — 프론트의 리터럴이 백엔드 상수를 따르는 관계와, 정책 문서가 낡았음을 알고 코드를 정본으로 둔 관계는 다른 관계다. (5) Nuseibeh 의 다섯 처리(resolve / ignore / defer / circumvent / ameliorate)를 판정 칸의 어휘로 삼으면 「정본 아직 없음」은 defer 이고, 「문서 절이 낡았지만 지금은 코드가 맞다」는 ameliorate(면책 문구)이며, 「이 규칙은 이 세부엔 안 맞는다」는 circumvent 다. (6) 구속 범위는 FHIR 처럼 **사용 빈도**로 고른다 — 질문이 실제로 닿는 세부만 지도에 넣고, 나머지는 "a guide, not an absolute" 로 둔다; 이는 이 사용자의 기존 실측(정답에 닿는 것은 적재·읽기 범위가 결정한다)과 같은 방향이다.

무엇이 이것을 죽이는지도 갈래마다 같은 답이다 — 저장소가 아니라 유지와 소유다. SERC 의 장애물 1~3위(문화·기량·리더십), Selic 의 「문서로 남은 모델은 유지 자원이 없어 버려진다」, 온톨로지의 "finite patience", SDD 의 "unrewarded work that no sprint board tracks", 그리고 앞선 보고서의 Backstage 소유자 필드가 퇴사자를 가리키는 사례 ([Backstage FAQ](https://backstage.io/docs/features/software-catalog/faq/))와 GAO 가 지적한 「권위 페이지가 변경 절차 없이 바뀐 일」 ([GAO-19-284](https://www.gao.gov/products/gao-19-284)). 1인 조직에서는 이 비용의 이름이 자기 시간이고, 가장 가까운 함정은 국내 블로그의 「6개월짜리 온톨로지 위원회」와 Palantir 의 anti-pattern "The Kitchen Sink" 다. 갈래마다 처방도 같다: JPL 의 "Keep it Super Simple… Refactoring can always be done later", Thoughtworks 의 "minimum viable ontology" 와 competency questions 먼저, Fraunhofer 의 "scope limited to prioritized CQs", 파트너의 "model one operational workflow end to end… before adding a second", 그리고 국내 블로그의 "개념이 아니라 질문에서 시작하십시오" ([Thoughtworks, 2026-06-17](https://www.thoughtworks.com/en-us/insights/blog/data-strategy/why-ontologies-matter-fail-build-anyway); [Fraunhofer, 2024-09-20](https://arxiv.org/html/2409.13425v1); [BD Emerson, 2026-07-30](https://www.bdemerson.com/article/palantir-ontology-explained)). 지도의 첫 항목은 개념 목록이 아니라 **이미 판정이 붙은 값**들이어야 하고, 지도가 커지는 속도는 질문이 닿는 속도를 넘지 않아야 한다.

「여러 출처를 임베딩하는 것에 더해」 축을 두는 방향은 기존 지식 그래프와 **반대 방향**이라는 점도 적어 둔다. Uber·LinkedIn·Airbnb·Siemens·Bosch 의 그래프는 데이터가 **먹이고** 문서는 뒤에 **붙는다** — NASA 의 lessons-learned 는 LDA 토픽으로 묶인 노드가 됐고, Uber 지원 조직의 그래프는 500만 개 자산 위의 graph-RAG 다(둘 다 벤더 기사) ([Neo4j/NASA, 2017-05-17](https://neo4j.com/blog/nasa-critical-data-knowledge-graph/); [Writer/Uber, 2024](https://writer.com/blog/uber-customer-story/)); 신선도는 사용자가 이미 편집하는 것(프로필·재고·설정)이라 파이프라인 성질이고, 정책과 설계 결정처럼 아무도 제품 화면에서 편집하지 않는 것에는 그 기제가 옮겨지지 않는다. Palantir 가 LLM 을 온톨로지로 접지한다는 "RAG / OAG" 는 블로그가 403 이라 검색 요약만 있고 평가 수치가 없다 ([Palantir blog](https://blog.palantir.com/reducing-hallucinations-with-the-ontology-in-palantir-aip-288552477383)). 그러니 앞선 보고서의 결론은 그대로 선다 — 이 구상은 「검증된 방법」이 아니라 「측정되지 않은 결합」이고, 유리한 두 근거(에이전트가 따르는 것은 개요가 아니라 지시·결정이라는 실험, 신선도 판정을 모델 밖 규칙으로 빼기만 해도 10~21pp 가 났다는 논문)에 이번 조사가 더하는 것은, 그 결합이 역사가 살려 둔 형태와 같은 모양이라는 사실이다 ([Gloaguen et al., 2026](https://arxiv.org/abs/2602.11988); [arXiv 2606.01435](https://arxiv.org/abs/2606.01435)).

용어는 이렇게 쓰면 지어내지 않아도 된다. 한국어로 굳은 것은 유비쿼터스 언어·도메인 모델·바운디드 컨텍스트·모델 기반 시스템 엔지니어링·디지털 스레드·스펙 주도 개발·기대 상태/현재 상태·드리프트·자동 동기화·공통표준용어·기준정보이고, 원어로 둘 것은 Canonical Data Model·reference model·profile·authoritative source of truth(국내 MBSE 자료에 「단일 진실 공급원」이 없다)·Context Map·Single Underlying Model·megamodel·reconciliation(루프는 「조정 루프」로 이미 이 사용자가 쓴다)·server-side apply 의 field manager·intentional/corrective change·suspect link·inconsistency management 의 다섯 처리·Rules as Code·isomorphism 이다. 「정본」은 국내 법률·기록관리에서 다른 뜻을 이미 갖고 있으므로(앞선 보고서) 첫 등장에서 「세부마다 사람이 지정한 권위 출처」라고 못 박는다.

## 결론

이 조사가 뒤집는 직관은 「축이 완전할수록 어긋남이 준다」는 것이다. 기록은 반대다 — 축이 완전할수록 축 자체가 드리프트했고, 살아남은 것은 완전성을 포기한 축들이었다: 사용 빈도 80% 선에서 잘린 코어, 도메인 경계를 넘는 polysemes 만 남긴 전역 층, 기존 모델을 규칙으로 잇는 virtual SUM, 이름 붙은 어긋남을 적는 Context Map, 복수형이 된 authoritative sources. 그 다섯 조건 중 넷은 기술이 아니라 거버넌스(누가 검사하고, 누가 비준수를 비싸게 만들고, 누가 변경을 승인하는가)였고, 죽인 것도 저장소가 아니라 유지할 사람의 부재였다. 이 사용자의 구상은 이미 그 살아남은 모양이다 — 값을 담지 않는 지도, 세부마다 다른 정본, 사람의 판정 — 그리고 그 판정에는 이제 이름이 있다(ASoT 를 "an entity … that applies expert judgment and rules to proclaim a digital artifact is valid" 로 다시 정의한 2022년 문장). 그래서 설계의 단위는 모델도 포인터도 아니고 **판정과 그 생애주기**다: 판정마다 처리 유형(resolve / ignore / defer / circumvent / ameliorate)과 재평가 시점을 적고, 대상이 바뀌면 suspect 로 떨어뜨리며, 판정의 변경을 intentional 과 corrective 로 갈라 세고, 소유권을 세부 단위로 객체 안에 두되 마지막 편집자가 아니라 역할이 갖게 한다. 이 장부에서 나오는 세 수 — corrective 의 비율, suspect 에 머문 시간, 낡은 정본에서 답한 비율 — 는 어느 갈래도 낸 적이 없고, 이 구상이 「측정되지 않은 결합」에서 벗어나는 길은 그 수를 스스로 내는 것뿐이다.

두 가지는 조사의 한계로 남긴다. 어느 갈래도 축을 **유지하는** 비용을 팀 규모 대비로 적지 않았다(JPL 의 모델러 10~15명이 유일한 인력 수치이고, Bosch 의 8주와 Uber 의 12주는 구축 비용이다); 그리고 국내는 여섯 노트 모두 검색 예산이 도중에 소진돼 네이버·토스·당근·국내 은행의 사례는 「없다」가 아니라 「이번에 안 나왔다」다. 그 빈자리와 별개로, 가장 가까운 함정은 기록이 분명히 가리킨다 — 완결성을 위해 6개월을 모델링하고 아무도 질의하지 않는 것. 지도는 질문이 닿은 값에서 시작하고, 질문보다 빨리 자라지 않는다.
