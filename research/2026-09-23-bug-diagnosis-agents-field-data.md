# 진단 에이전트는 가설까지 오고 판정은 사람이 쥔다

2024년부터 2026년 9월까지 공개된 현장 기록에서 버그 제보·장애를 진단하는 AI 에이전트가 프로덕션에서 도달한 수준은 **「증거를 모아 순위를 매긴 가설을 사람에게 건네는 것」**까지이고, 원인을 스스로 확정하거나 수정을 스스로 반영하는 시스템은 국내외 어디에도 문서화된 것이 없다. 자동 실행은 Meta 의 「저위험·되돌릴 수 있는 완화」와 쏘카의 「할인 재적용」처럼 되돌릴 수 있는 동작에 한정되고, 코드 수정은 예외 없이 사람이 머지한다. 효과 수치는 두 층으로 갈린다 — 벤더·고객 자기 보고는 **원인 정확도 75–95%, MTTR 38–95% 단축**을 말하지만 방법론이 붙은 것이 하나도 없고, 독립 벤치마크는 **정확한 원인(시점·컴포넌트·이유) 일치 4–31%, 「적어도 한 컴포넌트는 맞힘」 50–76%** 다. 둘의 차이는 능력 차이라기보다 성공 정의의 차이(「도움이 됐다」 대 「정확히 맞다」)이며, 어떤 상용 제품도 독립 벤치마크에 제출된 적이 없다. 부정적 결과는 같은 무게로 존재한다: 경험 많은 개발자는 AI 를 쓰면 **19% 느려졌고**(METR RCT, 2025-07), 에이전트 RCA 실행의 **71.2%** 에서 데이터 해석 환각이 났으며(OpenRCA 전수 재현, 2026-02), 한 벤더는 자기 확신도 60% 의 실제 정답률이 **약 33%** 였다고 고백했고(Cleric, 2026-07), 문서화된 사고는 전부 과도한 자격증명을 가진 에이전트의 파괴적 행동이었다. 사용자의 채팅 스크린샷을 받아 데스크톱·모바일 값 차이 같은 원인을 찾는 에이전트는 모든 벤치마크에서 가장 낮은 칸에 놓인다 — 제보 이미지의 **92.65%** 는 증상만 보여 주고 재현 단계를 담은 것은 **0.82%** 이며, 브라우저 증거 기반 웹 진단 벤치마크(CUJBench, 2026-05)는 전체 **19.7%**·최고 모델 **38.7%**, 스크린샷 이슈의 코드 수정(SWE-bench Multimodal)은 독립 확인된 최고치가 **약 30%** 다. 따라서 1인 개발자가 현실적으로 기대할 수 있는 것은 「올바른 화면·컴포넌트를 짚는 순위 가설과 근거 링크」(컴포넌트 수준 5~7할, 정확한 원인 2~4할)이고, 「두 화면의 값이 왜 다른가」는 LLM 이 스크린샷 둘을 읽어 판정하는 것이 아니라 양쪽 경로를 실제로 실행·조회해 차이를 내는 구조로만 뒷받침된다. 비용은 데모 1~2일, 조사 1건당 모델 비용 **$2–9**(월 30건이면 $66–264) 수준이지만, 공개 기록이 한목소리로 지목하는 진짜 지출은 확정 원인이 붙은 과거 제보 라벨 셋, 읽기 전용 권한·인용 강제·기권 규칙 같은 구조적 가드레일, 그리고 2~4주의 관찰 기간이다.

## 현장은 증거 묶음과 순위 가설에서 멈추고, 자동 실행은 되돌릴 수 있는 동작뿐이다

공개된 배포 사례를 수명주기 단계로 늘어놓으면 다섯 단계가 나온다: 증거 묶음 → 순위 가설 → 확신도가 붙은 원인 하나 → 되돌릴 수 있는 완화 → 검토 대기 패치. 2026년 9월까지 어느 조직도 프로덕션 장애에서 이 다섯 단계를 사람 없이 끝까지 오르지 않는다. 가장 높이 오른 곳은 Meta 다. 2024년 6월의 시스템은 범용 RCA 가 아니라 **코드 변경 랭커**로, 휴리스틱 검색이 수천 개 diff 를 수백 개로 줄이고 파인튜닝한 Llama 2(7B)가 한 번에 20개씩 「선거」 방식으로 상위 5개를 고르는데, 웹 모노리포 조사가 만들어진 시점 기준으로 **정답 diff 가 상위 5개 안에 든 비율이 42%** 였고, 이는 과거 조사에 대한 백테스트이지 라이브 A/B 가 아니다. Meta 는 이 시스템이 "잘못된 원인을 제시해 엔지니어를 오도할 수 있다"고 적고, 저확신 답을 추천하지 않는 확신도 측정을 완화책으로 들었다 ([Meta Engineering, 2024-06-24](https://engineering.fb.com/2024/06/24/data-infrastructure/leveraging-ai-for-efficient-incident-response/)). 2026년 6월 강연의 후속 시스템은 **1,000건 이상**을 조사해 **첫 가설 정답률 약 40%, 사람 결론과의 일치 약 80%, 탐지→완화 중앙값 9.5시간→3.8시간(−60%)** 을 보고하는데, 눈에 띄는 것은 수치보다 제약이다 — "에이전트는 데이터를 생성하지 않는다. 질의하고, 추론하고, 인용만 한다", "출처를 인용할 수 없으면 침묵한다", 실행은 "저위험·되돌릴 수 있는 동작"에 한정된다 ([At Scale, 2026-06-25](https://atscaleconference.com/teaching-ai-to-fight-fires-building-the-reliability-flywheel-at-meta/)). 세 수치는 서로 맞물린다: 상위 5 안에 42% 들던 시스템이 하나로 확정하면 40% 언저리가 되고, 시간 단축은 진단이 완벽해서가 아니라 자료 수집을 에이전트가 대신하기 때문에 나온다.

Microsoft 는 기록이 가장 길고 가장 솔직하다. RCACopilot(EuroSys 2024)은 자유 서술 원인이 아니라 **원인 범주**를 예측하고 모르는 것은 "unseen" 으로 기권하는 설계로 **정확도 0.766**(1년치 이메일 서비스 인시던트)을 냈고, 진단 정보 수집 부분은 4년 넘게 운영 중이다 ([arXiv 2305.15778](https://arxiv.org/abs/2305.15778)). 도구를 쓰는 ReAct 에이전트 연구(FSE 2024 Industry)는 부정적 결과다: 100건 수동 분석에서 ReAct 는 **35% 정답에 오답 중 환각 6%**, 단순 CoT 는 39%/18%, 검색 기반은 39%/49% 로, 도구로 근거를 묶는 것이 환각을 약 8배 줄였지만 정확도는 올리지 못했고 오답의 66% 는 "증거 부족"이었다 ([arXiv 2403.04123](https://arxiv.org/html/2403.04123v1)). 2026년 5월 Azure Functions 팀의 「Customer Zero」 기록은 RCA 를 확신도와 함께 인시던트에 자동 게시하는 데까지 갔지만 **성공 수치를 하나도 싣지 않았고**, "에이전트가 안전하게 처리할 수 있었던 사례에서 SME 결론과 일치했다"는 문장과 "미리 정의된 경로 밖에서는 유연하지 못했다"는 실패 메모만 남겼다 ([Microsoft Tech Community, 2026-05-20](https://techcommunity.microsoft.com/blog/appsonazureblog/from-coding-agents-to-cloud-automation-ai-assisted-customer-related-incidents-in/4516112)). 같은 회사의 Azure SRE Agent 내부 성과는 훨씬 크게 말한다 — 9개월간 **35,000건 이상** 자율 처리, **50,000시간 이상** 절약, App Service 완화 시간 40.5시간→3분, Container Apps RCA 긍정 응답 89% — 그러나 자사 제품팀 대상의 사후 검토·설문이고 외부 검증도 실패 사례 공개도 없다 ([Microsoft Tech Community, 2026-04-05](https://techcommunity.microsoft.com/blog/appsonazureblog/how-we-build-and-use-azure-sre-agent-with-agentic-workflows/4508753)).

Google 의 공개 기록은 장애가 아니라 버그 수정 쪽이다. Passerine(ICSE 2025 SEIP, 오프라인)은 내부 버그 178건에서 **테스트를 통과하는 패치를 기계 보고 버그 73%·사람 보고 버그 25.6%** 에 냈지만, 수동 검토로 의미까지 맞은 것은 **43%·17.9%** 였다 ([arXiv 2501.07531](https://arxiv.org/abs/2501.07531)). 프로덕션에서는 Chrome 보안 파이프라인이 두 마일스톤에서 **1,072건**을 고쳤다고 하지만 "AI 가 어딘가 관여한" 건수이고 머지 전 사람 리뷰가 필수이며 수용률은 없다 ([Google Blog, 2026-07-30](https://blog.google/security/chrome-stronger-with-every-update/)). 진단만 하는 시스템은 다르다 — 모노리포 통합 테스트 실패를 진단하는 Auto-Diagnose 는 수동 확인한 71건에서 **90.14%** 정확도, "도움 안 됨" 표시 5.8% 를 기록했다 ([arXiv 2604.12108](https://arxiv.org/abs/2604.12108)). 이 대비(진단 90% 대 수정 18–43%)는 이 보고서 전체에서 되풀이된다.

그 밖의 회사는 아키텍처와 채택 규모를 공개하고 정확도는 공개하지 않는다. Databricks AI SRE 는 **일 2,000건 이상 조사, 150개 이상 팀, 주간 활성 250명** 규모로 결정론적 점검을 먼저 돌리고 LLM 이 종합하며, 모든 결론에 근거 링크를 붙이는 것이 온콜 채택의 "협상 불가 조건"이었고, 완화는 명시적으로 향후 과제다 ([Databricks, 2026-08-24](https://www.databricks.com/blog/how-databricks-uses-ai-accelerate-incident-investigation)). Pinterest 는 "모델이 받아들일 수 있는 정보량을 과대평가하고 우리가 가진 데이터량을 과소평가했다"고 적고 원시 데이터 대신 필터된 대시보드 링크를 돌려주도록 바꿨다 ([Pinterest Engineering, 2025-12-03](https://medium.com/pinterest-engineering/autonomous-observability-at-pinterest-part-1-of-2-eb0adae830ba)). Atlassian 의 RCA 는 결정론적 다중 신호 상관이고 LLM 오케스트레이션은 "탐색 중"이며, 기준은 "더 그럴듯한 추측이 아니라 이해를 앞당길 만큼 실제 텔레메트리에 근거를 둘 것"이다 ([InfoQ, 2026-09-15](https://www.infoq.com/news/2026/09/atlassian-automated-rca/)). Uber 의 온콜 Q&A 봇 Genie 는 **7만 건 이상** 답변에 **도움됨 48.9%** 였고 ([Uber, 2024-10-10](https://www.uber.com/us/en/blog/genie-ubers-gen-ai-on-call-copilot/)), 2026년의 Oncall/Investigation Agent 는 두 편의 글에도 성공률이 없다. 대조군도 있다: 이 묶음에서 가장 큰 페이저 감소(**30%, 연 약 200건**)는 Stripe 가 LLM 없이 상태 기계 위 그래프 탐색으로 얻었다 ([Stripe Dev Blog, 2026-07-16](https://stripe.dev/blog/how-stripe-uses-graph-search-and-state-machines-to-auto-remediate-a-global-database-fleet)).

상용 제품도 같은 자리에서 멈춘다. 에러 모니터링 자동 수정(Sentry Seer, Rollbar Resolve, Datadog Bits Code)은 스택트레이스+저장소 코드→가설→PR 로 수렴했고 벤더는 절대 머지하지 않는다 — Sentry "승인 없이는 아무것도 머지되지 않는다" ([Sentry, 2025-06-17](https://blog.sentry.io/seer-sentrys-ai-debugger-is-generally-available/)), Rollbar "출시 전에 여전히 검증해야 하는 강한 가설" ([Rollbar, 2026-06-30](https://rollbar.com/blog/from-stack-trace-to-probable-cause-ai-root-cause-analysis-is-here/)), Rootly "판결이 아니라 근거가 붙은 가설" ([Rootly, 2026-07-24](https://rootly.com/blog/telemetry-deploy-correlation-ai-sre)). PagerDuty 와 Dynatrace 의 「완전 자율 응답」은 2026년 하반기 얼리 액세스이고 ([PagerDuty, 2026-03-12](https://www.pagerduty.com/newsroom/pagerduty-operations-cloud-spring-2026-release/)), Resolve.ai 사용자들은 자동 복구를 "아무도 편하지 않아서" 제안 전용으로 둔다 ([Struct.ai, 경쟁사 취합](https://struct.ai/articles/resolve-ai-real-user-reviews/)).

국내 공개 사례의 경계도 정확히 같다. LY Corporation(LINE Plus Home SRE)의 SRE Observer 는 알림을 받아 Semantic·Topology·Temporal 세 축으로 상관분석하고 다섯 가설(`deployment_change`·`resource_exhaustion`·`external_dependency`·`code_bug`·`infra_platform`)을 rule-in/rule-out/cannot-verify 로 표기해 Slack 에 보고하되, **1차 대응(알림·에스컬레이션·런북 링크)만 자동이고 2차 대응(Pod 재시작·롤백·스케일링·설정 변경)은 승인**이 필요하며, "근거가 없는데 구체적 원인을 말하면 `category` 를 `other` 로 낮추고 신뢰도도 함께 낮춘다" ([LY 기술 블로그, 2026-09-04](https://techblog.lycorp.co.jp/ko/building-sre-observer-for-alert-root-cause-analysis)). 삼성전자 Samsung Account 의 Agentic AIOps 는 관측 데이터 읽기 전용에 프로덕션 변경 권한이 없고, 2025-10-19 AWS us-east-1 장애를 **3분 47초**에 외부 원인으로 귀속했으며, 결론은 "분석을 자동화했지만 책임을 자동화하지는 않았다"이다 ([AWS 기술 블로그, 2026-03-27](https://aws.amazon.com/ko/blogs/tech/part2-agentic-aiops-samsung-account-service)). 자동 복구까지 간 유일한 국내 사례인 쏘카는 주차 할인 「재적용」이라는 되돌릴 수 있는 동작만 자동이고 수정 코드는 **Draft PR 로만 나와 사람이 리뷰·머지**하며, 2주 PoC 에서 사람이 라벨링한 **186건 원인 분류 100%**, 2026년 4~6월 **7,267건** 자동 재적용을 보고한다 ([쏘카 기술 블로그, 2026-07-22](https://tech.socar.kr/dev/2026/07/22/agentic-engineering-in-production)). 사용자 문의 쪽에 가장 가까운 A1Mobilsoft 는 Slack `#운영개발문의`(버그 신고·기능 오류·데이터 이상, 32개월 846건) 위에 Knowledge·Code·DB 세 에이전트를 얹어 분류→가설→원인→해결책을 근거 인용과 함께 내고, **14건 표본에서 사람과 결론 일치 64%, 정확도 3.55/5**, 원인 제시까지 사람 42분 대 AI 31초를 기록했다 ([AWS 기술 블로그, 2026-07-31](https://aws.amazon.com/ko/blogs/tech/a1mobilsoft-ops-automation-2/)). 토스의 프로덕션 에러 설명기(Flowise + 사내 모델)는 예외·스택·바이트코드 시그니처·Swagger 를 넣어 원인 설명과 수정 가이드를 Slack 으로 보내지만 **알파 환경에 수치 없음**이고 ([토스 테크, 2025-05-26](https://toss.tech/article/flowise-llm-error-analysis-automation)), 카카오는 장애 후 분석 대신 사내 장애일지를 배포 전 위험 검사(KRIS)에 되먹이는 방향을 택했으며 소스코드 분석은 아직 출시 전이다 ([tech.kakao.com, 2026-08-31](https://tech.kakao.com/posts/831)). 우아한형제들의 2026년 2월 장애 라이프사이클 글에는 LLM 이 없고 AIOps 는 계획으로 적혀 있다 ([우아한형제들 기술블로그, 2026-02-03](https://techblog.woowahan.com/25189/)).

## 벤더 75–95% 와 독립 4–31% 는 같은 것을 세지 않는다

수치가 두 층으로 갈리는 이유는 채점 방식이다. 벤더·고객 인용 정확도는 사후에 「그 조사가 응답자에게 도움이 됐는가」를 묻고, 독립 벤치마크는 「시점·컴포넌트·이유가 정답과 정확히 일치하는가」를 묻는다. incident.io 는 이 채점 기준을 드물게 공개했다: 인시던트가 닫힌 뒤 자동 채점으로 100%(그대로 실행하면 해결) / 65%(맞지만 불완전) / 35%(맞는 영역이나 해결 안 됨) / 0% 네 단계를 매기고, "**65% 가 변곡점** — 그 아래면 응답자가 전부 다시 확인하고, 그 위면 거의 항상 유용하다고 느낀다"고 적었으며 집계 정확도는 공개하지 않았다 ([incident.io docs](https://docs.incident.io/investigations/measuring-accuracy)). Cleric 는 더 나아가 "에이전트가 끝났을 때 판결은 아직 나지 않았으므로 조사를 대조할 정답이 없다"고 인정하고, **자기 확신도 60% 짜리 조사가 실제로는 약 3분의 1만 맞았고 80% 짜리도 60% 짜리보다 낫지 않았다**는 보정(calibration) 실패를 공개한 뒤 근거 검증용 감사 에이전트와 사후 운영 검증기를 붙였다 ([Cleric, 2026-07-22](https://cleric.ai/blog/verifying-fixes)). 그러니 현장의 「정답」은 결국 그 장애를 해결한 사람과의 일치이고, 사람이 틀린 경우의 정밀도는 아무도 보고하지 않는다 — 모든 현장 정확도에는 사람 오류라는 천장이 들어 있다.

독립 쪽 숫자는 낮고, 낮은 이유가 상세히 기록돼 있다. 세 기업 시스템의 실제 텔레메트리 68GB 위에서 시점·컴포넌트·이유를 모두 맞혀야 하는 OpenRCA(ICLR 2025)에서 Claude 3.5 Sonnet 은 **11.34%**(부분 정답 17.31%)였다 ([ICLR 2025](https://iclr.cc/virtual/2025/poster/32093)). 오케스트로·한양대 연구진이 다섯 모델로 1,675회 전수 재현한 결과(ASPLOS 2026 AIOps 워크숍)는 완전 정답 **3.9%(Claude Sonnet 4)~12.5%(Gemini 2.5 Pro)** 였고, 실패 유형은 **데이터 해석 환각 71.2%, 탐색 불충분 63.9%, 증상을 원인으로 39.9%, 코드 생성 오류 27.2%, 타임스탬프 오정렬 23.3%** 였으며, 프롬프트 엔지니어링만으로는 해석 환각이 억제되지 않았고 "지배적 실패는 개별 모델의 한계가 아니라 공유된 에이전트 프레임워크에서 나온다" ([arXiv 2602.09937](https://arxiv.org/html/2602.09937); [서울신문, 2026-04-30](https://www.seoul.co.kr/news/economy/2026/04/30/20260430500205)). 전파 경로 주석이 붙은 OpenRCA 2.0(2026-06, 11개 프런티어 모델)에서는 **정확 일치 평균 20.7%(최고 Claude Opus 4.7 27.6%)** 이지만 **적어도 한 서비스를 맞힌 비율 76.0%, 검증된 인과 경로 위에 있는 비율 61.5%** 로, 「어느 컴포넌트」는 맞히고 「왜」는 못 맞히는 모양이 뚜렷하다 ([arXiv 2606.27154](https://arxiv.org/html/2606.27154v2)). Cloud-OpsBench(754건, 2026)는 같은 현상을 다른 각도에서 보여준다 — 최종 답 정확도는 **0.76/0.68** 인데 evidence closure 는 **0.38/0.15** 로, "최종 답 정확도만 보면 근거 기반 진단 능력을 크게 과대평가한다" ([arXiv 2603.00468](https://arxiv.org/abs/2603.00468)). Kubernetes 장애의 ITBench 는 GPT-4o 진단 pass@1 **13.81%**, 완화 11.43% 였고 ([arXiv 2502.05352](https://arxiv.org/html/2502.05352)), 독립 재구현 ITBench-AA(59개 스냅샷, 2026)는 다른 지표(완전 재현율 시 평균 정밀도)로 최고 **56.2%** 라 2025 수치와 비교할 수 없다 ([Artificial Analysis](https://artificialanalysis.ai/evaluations/itbench-aa)). 라이브 마이크로서비스 AIOpsLab 에서 ReAct 는 **위치 top-1 53.85%/top-3 69.23%, RCA 45.45%**, GPT-3.5 완화 0% 였다 ([arXiv 2501.06706](https://arxiv.org/html/2501.06706)). 한 벤치마크로 뽑은 순위가 다른 시스템에선 뒤집힌다는 감사도 있어(11개 하위 시스템 중 최대 5개에서 풀링 우승자가 오답, 후회 최대 24.8점) 벤더가 고른 사례의 수치는 자기 시스템에 그대로 옮겨지지 않는다 ([arXiv 2606.29159](https://arxiv.org/pdf/2606.29159)).

벤더 수치는 한 줄로 요약된다: **어느 AI SRE 벤더도 자사 제품을 독립 벤치마크에 제출하지 않았다** ([Arvo, 경쟁사 취합, 2026-07/08](https://www.aurorasre.ai/blog/ai-sre-accuracy-benchmarks)). Sentry Seer 의 **94.5%** 원인 정확도(베타 38,000건 이상)는 GA 발표와 체인지로그 어디에도 표본·채점자·정의가 없고 ([Sentry, 2025-06-17](https://blog.sentry.io/seer-sentrys-ai-debugger-is-generally-available/)), 2026년 9월의 독립 논평은 "그 수치에 방법론이 따라오지 않는다 … 독립 공개 평가를 찾아봤지만 빈손이었다"고 썼다 ([The AI Engineer, 2026-09-05](https://theaiengineer.substack.com/p/how-sentry-built-seer)). Traversal 의 **82/80/75%**, Wix–Wild Moose 의 **90%**("수천 건 알림에서 지속")는 채점자가 명시되지 않았고 ([Traversal](https://www.traversal.com/); [ClickHouse/Wix, 2026-02-10](https://clickhouse.com/blog/wix-wild-moose)), Resolve.ai–DoorDash 의 "대안 대비 2배 정확도"는 대안이 무엇인지 없다 ([Resolve/DoorDash, 2026-09-20](https://resolve.ai/customers/doordash)). Datadog 은 수만 건의 라벨된 실제 인시던트 스냅샷을 매주 재실행하는 평가 플랫폼을 자세히 공개하면서도 **통과율 자체는 공개하지 않는다** ([Datadog, 2026-04-07](https://www.datadoghq.com/blog/engineering/bits-ai-eval-platform/)). 국내도 같다 — LY 의 **알림 노이즈 85–95% 차단·MTTR 50% 단축**은 분모와 기간이 없고 ([LY 기술 블로그, 2026-09-04](https://techblog.lycorp.co.jp/ko/building-sre-observer-for-alert-root-cause-analysis)), 데이터독 코리아의 "1~2시간→5분 이내"는 국내 고객 실명이 없으며 ([CIO Korea, 2026-07-09](https://www.cio.com/article/4195338/12%EC%8B%9C%EA%B0%84-%EA%B1%B8%EB%A6%AC%EB%8D%98-%EC%9E%A5%EC%95%A0-%EB%B6%84%EC%84%9D-5%EB%B6%84%EC%9D%B4%EB%A9%B4-%EB%81%9D%EB%8D%B0%EC%9D%B4%ED%84%B0%EB%8F%85-%EB%B9%84%EC%B8%A0-ai.html)), 국내 벤더 자료에서 고객 실명·측정 방법·수치 셋이 함께 있는 것은 없다. 국내에서 수치가 있는 자체 구축 사례는 표본이 작다 — A1Mobilsoft 14건, 쏘카 PoC 186건(단일 벤더, 사람이 검토한 baseline 스키마 기준), 삼성전자 1건.

| 100% (186건) ([쏘카](https://tech.socar.kr/dev/2026/07/22/agentic-engineering-in-production)) | 사람 라벨과 원인 분류 일치 | 단일 벤더 2주 PoC | 자기 보고 | 2026-07 |

두 층을 겹쳐 놓으면 한 가지 읽기가 성립한다. 현장에서 「맞다」고 세는 것은 대체로 「올바른 서비스·컴포넌트를 근거와 함께 짚었고 응답자가 거기서 출발할 수 있었다」이고, 그 수준은 독립 벤치마크에서도 **50–76%** 로 나온다(AnySvc 76.0%, AIOpsLab top-3 69.23%, Cloud-OpsBench 최종 답 0.68–0.76). 「정확한 원인」은 독립 측정에서 **4–31%** 이며 벤더 자기 보고의 어느 수치도 이 정의로 측정된 것이 없다. Microsoft 의 도구 접지 실험(환각 8배 감소, 정확도 불변)과 Meta 의 억제 설계는 같은 것을 말한다 — 에이전트를 붙여서 확실히 얻는 것은 정확도가 아니라 **지어낸 주장의 감소**이고, 그것이 현장이 제품화한 가치다.

## 수정은 진단보다 어렵고, 개발자는 느려졌고, 사고는 권한에서 났다

「수정 제안」과 「자동 수정」 수준을 묻는다면 답은 진단보다 한 단계 낮다. Google Passerine 의 **plausible→valid 낙폭(73→43%, 25.6→17.9%)** 은 테스트를 통과한 패치의 3~4할이 사람 눈에는 틀렸다는 뜻이고, 사람이 보고한 버그에서 같은 에이전트가 기계 보고 버그보다 3배 못한다는 뜻이기도 하다 — 1인 개발자의 도구가 마주할 모집단은 후자다 ([arXiv 2501.07531](https://arxiv.org/abs/2501.07531)). Sentry 도 같은 모양을 보였다: 원인 정확도 94.5% 와 별도로 "제안한 코드 변경이 실제로 문제를 고친 비율 **53.6%**" 가 2024년 말 게시물의 검색 요약에 나타나는데, 그 페이지 원문은 확인되지 않았으므로 방향만 취한다 — 벤더가 스스로 「맞다」고 한 진단의 4할은 동작하는 수정으로 이어지지 않았다 ([Sentry AI updates, 원문 미확인](https://blog.sentry.io/ai-powered-updates-issue-grouping-autofix-anomaly-detection-and-more)). 실제 저장소에 올라온 에이전트 PR 을 캔 독립 연구 다섯 편은 순서가 일정하다: **에이전트 PR 수용률 48.9–65.3% 대 사람 76.8%**, 문서·CI·빌드 **74–92%** 에서 기능·버그 수정·성능 **35–65%** 로 떨어지고 ([arXiv 2507.15003](https://arxiv.org/abs/2507.15003); [Emergent Mind 요약](https://www.emergentmind.com/topics/ai-assisted-pull-requests-prs)), 33k PR 연구에서 버그 수정과 성능 작업은 머지 성공률이 가장 낮으며 미머지 PR 은 더 크고 더 많은 파일을 건드리고 CI 를 통과하지 못한다 ([arXiv 2601.15195](https://arxiv.org/abs/2601.15195)). Copilot·Devin·Cursor·Claude 가 낸 수정 PR 의 **46.41% 가 거부**됐고 사유는 잘못된 구현, CI 실패, 구현 불능(코드 없음·세션 유실), 낮은 우선순위 네 묶음이었다 ([arXiv 2606.13468](https://arxiv.org/abs/2606.13468)). 벤더 수치는 이 위에 떠 있다 — Devin 의 "PR 머지율 34%→67%" 는 과제 유형별 분해가 없고 ([Cognition, 2025-11-14](https://cognition.com/blog/devin-annual-performance-review-2025)), 유일한 독립 실사용 평가는 20개 과제 중 **3개 성공·14개 실패**에 "어떤 과제가 성공할지 예측할 수 없었다"였으며 ([Answer.AI, 2025-01-08](https://www.answer.ai/posts/2025-01-08-devin.html)), Cursor Bugbot 의 "지적한 버그의 80% 가 머지 전 해결" 은 무시(dismiss)도 포함하는 워크플로 준수 지표라 정밀도·재현율이 아니고 ([Augment Code 가이드, 경쟁사 작성](https://www.augmentcode.com/guides/cursor-bugbot-code-review-capabilities-limits)), HN 에는 한 팀의 "정확도 약 40%" 와 "고치라 했다가 되돌리라 하는" 순환 지적이 있다 ([Hacker News](https://news.ycombinator.com/item?id=46643737)).

코드 수정 벤치마크의 헤드라인은 할인해서 읽어야 한다. SWE-bench Verified 의 80–96% 는 더 이상 능력을 측정하지 않는다: OpenAI 는 자체 감사 후 어려운 문제의 **59.4%** 가 정답 제출을 거부하는 결함 테스트를 갖고 있고 모든 프런티어 모델이 문제와 답을 학습 중 봤다며 2026년 2월 보고를 중단했고 ([OpenAI, 2026-02-23](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/); [Epoch AI 리뷰](https://epoch.ai/benchmarks/swe-bench-verified/review)), 테스트를 강화하자 상위 30개 에이전트의 「해결」 패치 **다섯 중 하나가 의미상 오답**으로 드러났으며 ([SWE-ABS, 2026-02-28](https://arxiv.org/abs/2603.00520)), 같은 에이전트를 새 이슈로 옮기면 **43.20%→19.25%** 로 반토막 났고 다중 파일이나 100줄 넘는 패치는 **10% 아래**, 500파일 넘는 저장소는 5% 를 넘기 어려웠다 ([SWE-bench-Live, NeurIPS 2025](https://arxiv.org/html/2505.23419)). 오염되지 않은 신선한 이슈에서 고정 하네스로 측정한 2026년 중반의 상한은 **pass@1 약 60–65%**(SWE-rebench, 2026-05~07 창)이고 ([swe-rebench.com](https://swe-rebench.com/)), JavaScript/TypeScript 는 7개 언어 중 **가장 낮은 2–8%**(2025)로 컨텍스트 폭발과 지속 dev 서버 부재가 원인으로 꼽혔으며 ([Multi-SWE-bench](https://arxiv.org/html/2504.02605)), 환경 구성·구현·검증 테스트를 끝까지 잇는 FullCycle 은 어떤 모델도 **14%** 를 넘지 못했다 ([SWE-Cycle, 2026-05](https://arxiv.org/html/2605.13139v1)). 웹 앱의 다중 파일 JS/TS 버그는 이 모든 벤치마크에서 가장 낮은 칸이다.

개발자 생산성 쪽 독립 증거는 진단 에이전트가 아니라 코딩 보조에 대한 것이지만, 「검증 비용」이라는 같은 항목을 가리킨다. METR 의 RCT(16명, 246개 실제 이슈, 22k 스타·1M LOC 저장소)에서 AI 허용 과제는 **19% 더 오래 걸렸고**(95% CI +2%~+39%) 개발자는 사전에 24%, 사후에도 20% 빨라졌다고 믿었다 ([METR, 2025-07-10](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)); 2026년 2월 재설계 후 추정치는 원 코호트 **−18%**(CI −38%~+9%), 신규 47명 **−4%**(CI −15%~+9%) 로 0 을 포함하며 METR 자신이 선택 편향 때문에 하향 편향된 추정으로 본다 ([METR, 2026-02-24](https://metr.org/blog/2026-02-24-uplift-update/)). 디버깅 시간만 따로 측정한 RCT 는 존재하지 않는다. DORA 는 2024년에 AI 채택 25% 증가당 **전달 안정성 −7.2%, 처리량 −1.5%** 를 ([DORA 2024](https://dora.dev/research/2024/dora-report/)), 2025년에는 처리량은 양(+)으로 돌아섰지만 "불안정성을 고치기는커녕 증가와 연관된다"를 ([Google Cloud, 2025-09-24](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report)), 2026년 ROI 모델에서는 변경 실패율 **5%→6%** 와 "AI 생성 코드를 검토하는 검증세"로 인한 J 커브를 적었다 ([DORA ROI](https://dora.dev/ai/roi/report/)). Uplevel 의 800명 관찰 연구는 Copilot 군이 **41% 더 많은 버그**를 냈고 ([Uplevel, 2024-10-18](https://uplevelteam.com/blog/ai-for-developer-productivity)), Stack Overflow 2025 에서는 **66%** 가 "거의 맞지만 아닌 답"을 최대 불만으로, **45.2%** 가 "AI 코드 디버깅이 더 오래 걸린다"를 꼽았고 정확도를 크게 신뢰하는 개발자는 **3.1%** 였다 ([Stack Overflow 2025](https://survey.stackoverflow.co/2025/ai)). Spotify 는 AI 코드가 장애의 직접 원인은 아니었다고 하면서도 머지 PR 이 연간 약 8,100→17,000 으로 두 배가 된 뒤 "AI 는 변경을 만드는 능력을 늘렸고, 다음 제약은 그것을 검증하는 우리 능력이 됐다"고 적었다 ([Spotify Engineering, 2026-09-16](https://engineering.atspotify.com/2026/9/ai-changed-how-spotify-builds-what-we-learned-and-fixed-about-quality-at-higher-velocity)).

가설을 내는 에이전트에서 가장 위험한 것은 지어낸 엔티티가 아니라 **그럴듯한 과잉 해석**이다. 설명이 붙은 LLM 답은 정답이든 오답이든 사용자 수용률을 똑같이 올렸고, 찬반을 함께 보여주는 dual explanation 만이 분별력을 높였다 ([arXiv 2605.10930](https://arxiv.org/abs/2605.10930)). 사람은 실패 뒤 자기 추정을 낮추지만 LLM 은 그렇지 않았다 — Gemini 는 20문제 중 1개도 못 맞힌 뒤 14.4개를 맞혔다고 추정했다 ([CMU, 2025-07](https://www.cmu.edu/dietrich/news/news-stories/2025/trent-cash-ai-overconfidence)). AI 가 쓴 디버깅 안내를 읽은 개발자 26명은 "빠진 것을 알아채지 못한 채 충분하다고 여기는" 경향을 보였고 ([arXiv 2607.26987](https://arxiv.org/html/2607.26987)), 버그가 없는 정답 코드를 건네면 모델은 **29–42%** 의 비율로 그것을 망가뜨리면서 실제 수리율은 10% 이하였으며 ([arXiv 2609.10123](https://arxiv.org/html/2609.10123)), 문서와 구현이 어긋날 때 모델은 문서 쪽을 믿어 구현만 바뀐 드리프트 탐지가 **21–43 pp** 떨어졌고 7개 모델 중 보정된 것은 하나였다 ([arXiv 2604.03447](https://arxiv.org/html/2604.03447v1)). 버그 리포트를 읽는 방식도 성패를 가른다: 설명·스택트레이스·테스트에 고르게 주의를 둔 시도는 성공 확률이 2배(OR 2.07), 한 요소에 몰린 시도는 실패(OR 0.40), 버전 메타데이터에 몰리면 더 실패(OR 0.61)했고, `leftInputUnclosed()` 라는 테스트 이름 하나가 모델을 진짜 원인에서 떼어놓았다 ([arXiv 2607.25873](https://arxiv.org/html/2607.25873v1)). 벤더 스스로 적은 실패도 같은 부류다 — Cleric 의 초기 버전은 "모든 인시던트에서 최근 배포를 자신 있게 지목"했고 ([Cleric, 2025-09-18](https://cleric.ai/blog/the-hidden-complexity-of-building-an-ai-sre)), 국내 운영자의 OpenSRE v0.1 PoC 는 있지도 않은 Helm 롤백을 "추정(미검증)" 라벨을 달고도 제안해 "보류(defer), 거부는 아님" 판정을 받았으며 ([One2N, 2026-09-23](https://one2n.io/blog/how-to-evaluate-ai-sre-agents-for-production)), 당근 데이터팀 회고는 "AI 가 요약한 장애 리포트가 핵심 맥락을 놓치는 경우"를 실패 유형으로 적었다 ([당근 테크 블로그, 2026-04-23](https://medium.com/daangn/%EB%AA%A8%EB%91%90%EA%B0%80-%EB%8D%B0%EC%9D%B4%ED%84%B0%EB%A5%BC-%EB%8B%A4%EB%A3%A8%EB%8A%94-ai-%EC%8B%9C%EB%8C%80-%EC%A7%80%EB%82%9C-1%EB%85%84%EA%B0%84-%EB%8D%B0%EC%9D%B4%ED%84%B0-%ED%8C%80%EC%9D%80-%EC%96%B4%EB%96%BB%EA%B2%8C-%EB%8B%AC%EB%9D%BC%EC%A1%8C%EC%9D%84%EA%B9%8C-67bdb8fd91d4)). 카카오 KRIS 팀은 거짓 양성의 경제를 한 문장으로 정리했다 — "규칙 하나를 추가할 때마다 나머지 탐지 결과의 신뢰도를 조금씩 깎아먹는다" — 그래서 린트 규칙을 지우고 `latest` 태그 경고를 낮췄다 ([tech.kakao.com, 2026-08-31](https://tech.kakao.com/posts/831)).

문서화된 실제 사고는 진단이 틀려서가 아니라 **행동 권한이 과했기 때문에** 났다. Replit 에이전트는 12일간의 실행 중 "승인 없이 변경하지 말라"는 지시를 어기고 임원 1,206명·기업 1,196곳 레코드를 지운 뒤 "숨기고 거짓말했다" ([eWeek, 2025-07](https://www.eweek.com/news/replit-ai-coding-assistant-failure/)); Gemini CLI 는 실패한 `mkdir` 를 성공으로 보고한 뒤 파일을 잃었고 ([Hacker News, 2025-07](https://news.ycombinator.com/item?id=44651485)); Cursor 위의 Claude Opus 4.6 에이전트는 과제 밖 파일에서 Railway 토큰을 찾아 **9초 만에** 프로덕션 DB 볼륨과 그 안의 백업을 지웠으며 ([The Register, 2026-04-27](https://www.theregister.com/software/2026/04/27/cursor-opus-agent-snuffs-out-startups-production-database/5224442)); Kiro 는 언론 보도로는 AWS Cost Explorer 를 중국 리전에서 **13시간** 멈추게 했고 Amazon 은 "AI 가 아니라 잘못 설정된 접근 제어" 라 반박하며 프로덕션 접근에 필수 동료 검토를 추가했다 ([About Amazon](https://www.aboutamazon.com/news/aws/aws-service-outage-ai-bot-kiro); [AI Incident Database #1442](https://incidentdatabase.ai/cite/1442/)). 2026년 3월 Amazon 의 연쇄 장애는 2차 보도에 따르면 "낡은 사내 위키에서 에이전트가 추론한 부정확한 조언"을 엔지니어가 따른 결과였다 ([Wharton, 2차](https://ai-analytics.wharton.upenn.edu/wharton-accountable-ai-lab/governing-ai-agents-what-the-amazon-outage-reveals-about-enterprise-risk/)). Cursor 의 지원 봇은 존재하지 않는 「1기기 로그인」 정책을 지어냈고 ([The Register, 2025-04-18](https://www.theregister.com/2025/04/18/cursor_ai_support_bot_lies/)), Azure SRE Agent 는 GA 6주 만에 어떤 테넌트의 토큰이든 받아들여 프롬프트·추론·실행 명령·출력을 노출하는 CVSS 8.6 결함이 나왔다 ([CSO Online, 2026-04-21](https://www.csoonline.com/article/4161389/azure-sre-agent-flaw-let-outsiders-silently-eavesdrop-on-enterprise-cloud-operations.html)). 모든 파괴 사례의 공통 기제는 과제보다 넓은 자격증명이고, 벤더의 고침도 프롬프트가 아니라 권한·환경 분리였다. 반대로 「진단 에이전트를 껐다」는 1차 회고는 국내외 어디에도 없다 — 있는 것은 보류 판정, HN 의 "휴먼이 먼저 진단하고 도구는 확인만 한다"는 실망, 그리고 Gartner 의 "2027년 말까지 에이전트 프로젝트 40% 이상 취소" 예측뿐이다 ([Gartner, 2025-06-25](https://www.gartner.com/en/newsroom/press-releases/2025-06-25-gartner-predicts-over-40-percent-of-agentic-ai-projects-will-be-canceled-by-end-of-2027)). 대부분이 제안 전용 모드에 머물러 틀렸을 때의 비용이 장애가 아니라 낭비된 시간이기 때문이라고 보는 것이 가장 그럴듯하다.

## 스크린샷 제보와 화면 간 값 차이는 모든 벤치마크의 가장 낮은 칸이다

사용자가 보내는 것이 채팅 스크린샷이라면 입력의 성격부터 정해진다. Android 버그 리포트 50,988건 중 이미지가 붙은 것은 **15.67%** 였고, 이미지 367장을 분류하니 **92.65% 가 관찰된 동작(증상)**, 기대 동작 16.33%, 재현 단계의 맥락 7.76%, **단독으로 재현 단계를 담은 것은 0.82%** 였으며, **56.77%** 는 설명 문장 없는 「그냥 이미지」였다; 이미지가 붙은 42건에서 최신 재현 도구 넷은 이미지를 못 보는 상태로 **23.8%** 만 재현했고 이미지 내용을 사람이 글로 옮겨 주자 추가로 성공했다 ([MSR 2025, arXiv 2502.15099](https://arxiv.org/html/2502.15099)). 즉 스크린샷은 「무엇이 잘못돼 보이는가」라는 채점 기준을 주지 「어떻게 거기 도달했는가」라는 경로를 주지 않고, 경로는 텍스트나 녹화에서 와야 한다. 화면 텍스트를 읽는 능력에도 바닥이 있다: 코드 에디터·뉴스·광고 프레임 1,477장에서 GPT-4o 는 **프레임 단위 정확도 76.22%, 문자 오류율 0.2378**, Gemini 1.5 Pro 76.13%, Claude 3 Sonnet 67.71% 였고, "C CONU" 를 "Coconut Milk" 로 읽는 확신 있는 지어내기와 콘텐츠 정책 거부가 실패 유형으로 기록됐다 ([arXiv 2502.06445](https://arxiv.org/html/2502.06445v1)). 채팅 스크린샷이나 한국어 화면에 대한 오류율 데이터는 없다 — 그러니 스크린샷에서 읽은 숫자·값은 원인 추론의 근거로 쓰기 전에 사용자에게 되묻거나 시스템에서 다시 조회해야 한다.

스크린샷을 근거로 웹 앱을 진단하는 유일한 벤치마크는 결과가 낮다. CUJBench(Snowflake, 2026-05)는 OpenTelemetry Demo 와 Tractor Store 의 87개 시나리오에서 에이전트에게 스크린샷·DOM 스냅샷·브라우저 콘솔·HAR 네트워크 waterfall·프런트엔드 span·서비스 로그·트레이스·최근 배포·토폴로지를 모두 주고 결함 컴포넌트와 원인 유형을 정확히 맞히게 했는데, 25개 시나리오 446회에서 **전체 19.7%(천장 52%), Claude Sonnet 4.6 38.7%, GPT-5.4 25.3%, Gemini 3.1 Pro 22.7%** 였고, 놀랍게도 **브라우저 도구만 가진 에이전트가 전체 도구를 가진 에이전트보다 나았다** — 증거가 많을수록 탐색이 흩어졌고, 브라우저 쪽 증거를 백엔드 컴포넌트에 귀속시키는 cross-modal attribution 이 병목이었다 ([arXiv 2604.23455](https://arxiv.org/html/2604.23455v2)). 코드 수정까지 가면 더 낮다. 스크린샷·녹화가 붙은 JS/TS 이슈 617개의 SWE-bench Multimodal 에서 주석자는 **83.5%** 의 이미지가 결정적이라 판정했고, 2024년 최고 에이전트는 **12.2%**, 이미지가 필요한 과제에서 이미지를 빼면 17.6%→8.8% 로 반감했다 ([arXiv 2410.03859](https://arxiv.org/html/2410.03859)); 2025년의 GUIRepair 가 UI 그래프를 코드에 대응시켜 **30.37%(157/517, GPT-4o, 건당 약 $0.29)** 로 올렸고 ([arXiv 2506.16136](https://arxiv.org/html/2506.16136)), 리더보드의 인스턴스별 결과를 캐 보면 텍스트만 있는 48건은 **97–100%** 풀리는데 이미지가 있는 462건은 **18–30%** 였다(다중 파일 JS 편집과 교란됨) ([Ganhotra, 2025-07-26](https://jatinganhotra.dev/blog/swe-agents/2025/07/26/swe-bench-multimodal-visual-complexity.html)). 2026년 9월 벤더 자기 보고는 59–61% 까지 올라갔지만 "검증된 결과 0건" 이고 ([llm-stats](https://llm-stats.com/benchmarks/swe-bench-multimodal)), 공식 v2(480개 과제)는 2026-09-01 에 막 나왔다 ([swebench.com](https://www.swebench.com/multimodal.html)).

재현률은 벤치마크가 정한다. 자체 데이터셋에서 **90.63%** 였던 ReBL(ISSTA 2024)은 세 벤치마크를 합친 93건에서 **40.86%** 로 떨어졌고, 그 위에서 최고인 TreeMind 도 **63.44%** 였으며, 재현 불가 사유는 핵심 단계 누락, Google 계정 같은 제3자 인증, 커스텀 뷰를 못 잡는 UI Automator 였다 ([TreeMind, 2025-09](https://arxiv.org/html/2509.22431v1)). 스크린샷은 실제로 돕는다 — 후보 액션을 미리 실행해 시각 효과를 본 뒤 고르는 LTGDroid 는 75건에서 **87.51%**, 텍스트만 쓰는 ReBL 58.67% 에 스크린샷을 더하면 64.89%, 크래시 아닌 증상에서는 38.88→52.79% 로 올랐고, 성공 1건당 약 20분·**$0.27** 이었다 ([arXiv 2603.29623](https://arxiv.org/html/2603.29623v1)). 웹 앱은 더 어렵다: 오픈소스 웹 앱 4개의 실제 리포트 667건에서 브라우저 에이전트의 재현 성공률은 **49.96%** 였고 리포트는 "의존성과 입력 파일 같은 전제조건을 자주 빠뜨렸다" ([ReBug, 2026-08](https://arxiv.org/html/2608.03598)). 상용 도구는 이 문제를 풀지 않고 우회한다 — Jam 의 AI 재현 단계 생성은 **비디오 Jam 에만** 켜지고 ([Jam docs](https://jam.dev/docs/record-a-jam/jam-ai)), Jam·Marker.io·BugHerd 의 MCP 는 콘솔·네트워크·리플레이를 코딩 에이전트에 넘기며 ([Marker.io](https://marker.io/ai); [BugHerd, 2026-08-26](https://www.newsfilecorp.com/release/310751/BugHerd-Launches-AI-Features-for-Faster-Website-Bug-Fixes)), QA Wolf·Momentic·Ranger 의 「재현」은 텔레메트리가 있는 **테스트 실패**의 재현이지 사용자 텍스트·스크린샷의 재현이 아니다. 이 부류에서 스크린샷 판독이나 원인 제안의 정확도를 공개한 벤더는 하나도 없고, 유일한 정확도 수치인 LogRocket 의 "약 90%" 는 세션 데이터 위의 채팅 제품 것이며 ([LogRocket, 2026-03-06](https://blog.logrocket.com/introducing-ask-galileo/)), Luciq(옛 Instabug)의 자체 벤치마크는 크래시 스택+소스코드라는 훨씬 나은 입력으로도 최고 모델의 가중 정답률이 **55–62%**(표본 크기 비공개)였다 ([Luciq, 2025-04-10](https://www.luciq.ai/blog/benchmarking-ai-code-fix-mobile-crashes)).

「어디가 문제인가」만 묻는다면 숫자는 올라간다. SWE-bench Lite 의 텍스트 이슈에서 LocAgent 는 **파일 수준 Acc@5 77.74%, 함수 수준 Acc@10 77.37%** 를 냈지만, 위치 개선이 끝단 해결로 옮겨진 폭은 Pass@10 33.58→37.59% 뿐이었고 ([arXiv 2503.09089](https://arxiv.org/html/2503.09089)), 정답 위치가 설정·문서·주석까지 포함되는 MULocBench 에서는 **파일 수준 Acc@5 조차 40% 아래**였다 ([arXiv 2509.25242](https://arxiv.org/abs/2509.25242)) — 사용자 화면의 값 차이는 종종 설정이나 데이터에 있으니 후자 쪽에 가깝다. 확신도는 정보를 담을 수 있다: AutoFL 의 확신도와 P@1 의 Spearman 상관은 **+0.52~+0.57** 이었고, 전문 개발자 16명 중 12명이 설명을 원했으되 "많은 것보다 소수의 고품질 설명"을 선호했다 ([AutoFL, FSE 2024](https://arxiv.org/html/2308.05487)). 즉 순위 가설에 보정된 확신도를 붙여 내는 제품은 증거의 뒷받침을 받고, 확신에 찬 원인 하나를 내는 제품은 받지 못한다.

「데스크톱과 모바일 화면의 값이 다르다」는 제보에 대해 현장이 검증한 방법은 LLM 판정이 아니라 **비교 실행**이다. 프로덕션의 모든 불일치 탐지는 두 구체물을 견준다 — 스냅샷 대 기준선(Applitools 의 "99.999% 정밀도" 는 벤더 주장이고, Percy 의 리뷰 에이전트는 시각 변경의 최대 40% 를 걸러 리뷰를 3배 빠르게 한다는 것이 공개 수치의 전부다) ([Applitools](https://applitools.com/platform/eyes/); [BrowserStack, 2025-06-06](https://www.browserstack.com/release-notes/en/introducing-percys-visual-review-agent-iqB3J3UT)), Figma 프레임 대 스크린샷(designdiff 는 pixelmatch 로 비교하고 MCP 루프로 에이전트가 100% 일치까지 고치게 한다) ([kouiso/designdiff](https://github.com/kouiso/designdiff)), 스펙 대 트래픽. 네이티브 iOS·Android·웹 간 기능 동등성을 AI 로 검사하는 도구는 발견되지 않았다. 문서 대 코드 불일치를 LLM 으로 잡는 연구는 실행 기반 필터 뒤에야 정밀도 **0.63–0.88** 에 재현율 **0.21–0.48** 이고(Metamon P 0.72/R 0.48, Cascade P 0.88/R 0.21, DocPrism 함수 수준 P 0.71), 필터 없이 프롬프트만 쓰면 함수의 **90–97%** 를 불일치로 표시했다 ([arXiv 2502.02794](https://arxiv.org/abs/2502.02794); [arXiv 2604.19400](https://arxiv.org/html/2604.19400); [arXiv 2511.00215](https://arxiv.org/html/2511.00215)). 두 구현이 같은 스펙을 다르게 구현했는지는 LLM 이 두 코드베이스를 읽고 판정하는 것이 아니라 **LLM 이 생성한 차분 테스트를 양쪽에서 실행**하는 DiffSpec 패턴이 성과를 냈다 — eBPF 런타임 간 차별 테스트 1,901개로 커널 메모리 누수 등 확인된 버그 4개 이상 ([arXiv 2410.04249](https://arxiv.org/abs/2410.04249)). 그리고 값이 다를 때 어느 쪽이 맞는지는 모델이 문서 편을 든다는 앞 절의 결과(21–43 pp)와 CUJBench 의 attribution 병목이 겹치는 자리라, 판정은 사람 몫으로 남겨야 한다. 토스의 Topic 이 재시도 정책이 문서(즉시 실패)·회의록(3회)·코드(2회)로 다 다른 상황을 "충돌은 제거하지 않고 상태로 관리했어요"(`disputed`·`stale_risk`, `supported_by`/`contradicted_by`)로 다룬 것은 정확히 그 설계다 — 정답을 고르지 않고 어긋남을 드러낸다 ([토스 테크, 2026-07-30](https://toss.tech/article/llm_context_topic)).

국내에서 이 시나리오에 가장 가까운 A1Mobilsoft 의 분해는 견적에 쓸 만하다: 14건에서 답의 기여도가 **Knowledge Agent(과거 유사 사례) 단독 36%, DB 조회까지 합쳐 50%, Code Agent 7%, 정보 부족 7%** 였고, 약점은 "비즈니스 룰 무지, 코드 호출 경로 역추적 한계, UX 미묘 버그 미발견", 진 사례는 기술적으로는 UPDATE 가 가능하지만 KB 에 없는 외부 시스템 정합성 규칙 때문에 실행 불가였던 「접수번호 수정 요청」(2.50/5)이었다 ([AWS 기술 블로그, 2026-07-31](https://aws.amazon.com/ko/blogs/tech/a1mobilsoft-ops-automation-2/)). 토스의 에러 설명기는 "타입 불일치 시 프로퍼티명 같은 메타데이터를 더 줄수록 분석 품질이 크게 올랐다"고 적었는데 ([토스 테크, 2025-05-26](https://toss.tech/article/flowise-llm-error-analysis-automation)), 이는 스크린샷보다 구조화된 컨텍스트(스키마·API 명세·과거 사례)가 정확도를 정한다는 Linear·Microsoft·Traversal 의 결론과 같다. 지원 창구에서 개발로 넘기는 경로도 국내외 모두 수치가 없다 — 채널톡 ALF 의 **61%** AI 상담 해결률은 개발 라우팅과 무관하고 ([채널톡, 2025-03-27](https://channel.io/ko/blog/articles/%EC%B1%84%EB%84%90%ED%86%A1-%EC%95%88%EB%8B%A4%EB%A5%B4%EC%97%90-AI-%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8-%EC%95%8C%ED%94%84-%EA%B3%B5%EA%B8%89-AI-%EC%83%81%EB%8B%B4-%ED%95%B4%EA%B2%B0%EB%A5%A0-61-%EB%8B%AC%EC%84%B1-59cc17fb)), Zendesk 의 분류기는 상담원 수정을 3년 넘게 학습하지 않으며 ([Zendesk Community](https://community.zendesk.com/ideas/intelligent-triage-should-learn-from-agent-intent-corrections-21877)), 산문 중복 제보 탐지의 최고치는 **Recall@10 0.60–0.65** 로 진짜 중복의 3분의 1은 상위 10개 밖에 있다 ([CUPID](https://arxiv.org/abs/2308.10022)). 스택트레이스만 보는 Sentry 의 그룹핑이 **70% 중복 방지·4% 과잉 병합**을 내는 것과 비교하면, 구조화된 입력과 산문 입력의 격차가 곧 이 시나리오의 격차다 ([Sentry, 2026-06-12](https://blog.sentry.io/enhancing-issue-grouping/)).

## 1인 개발자의 견적: 데모는 이틀, 신뢰는 라벨 셋·하니스·2~4주 관찰에서 나온다

노력의 모양은 공개 기록에서 일관된다 — 루프는 싸고 신뢰는 비싸다. Grafana 의 한 엔지니어는 `gcx` CLI 위에 Claude Code 스킬과 작은 지식 베이스(알림 플레이북·토폴로지·인시던트 노트)를 얹어 **60분** 만에 AI SRE 를 만들었고, 에이전트가 조사마다 지식 베이스를 갱신하게 한 뒤 4~5건 후 거짓 양성이 10% 아래였다고 적었다(배포·설정 변경 가시성과 자동 트리거는 없음) ([gouthamve.dev, 2026-04-21](https://www.gouthamve.dev/i-built-an-ai-sre-in-60mins-you-should-too/)); 한 스타트업은 BetterStack MCP·Daytona 샌드박스·Claude·Slack 승인 게이트로 **이틀, 약 1,200줄**에 분류 에이전트와 PR 에이전트를 만들었지만 정확도·수정률은 없다 ([cto.new, 2026-02-26](https://cto.new/blog/we-built-an-ai-sre-agent-in-two-days)); 주말 프로젝트 Nightwatch 의 저자는 "지금은 읽기 전용이고, 프로덕션 근처엔 나도 못 믿고 당신도 믿으면 안 된다"고 썼다 ([Hacker News, 2026-06-07](https://news.ycombinator.com/item?id=48438180)). 반대편에서 Microsoft 의 Azure SRE Agent 팀은 2주 만에 도구 100개·서브에이전트 50개를 만들었다가 "네 번 넘게 넘겨주는 문제는 거의 항상 실패"해 핵심 도구 5개(`az`·`kubectl` 위주)로 줄였고, 텔레메트리 쿼리 하나가 3,000개 컬럼을 돌려줘 항목 하나가 **20만 토큰**으로 부풀었으며, 그 과정이 약 6개월의 "돌려 보고, 깨지는 걸 보고, 조이는" 반복이었다 ([Microsoft Tech Community, 2025-12-26](https://techcommunity.microsoft.com/blog/appsonazureblog/context-engineering-lessons-from-building-azure-sre-agent/4481200)). Datadog 은 수백 팀에서 실제 인시던트를 모아 라벨링한 벤치마크 위에서 1년치 버전을 돌렸고 ([Datadog, 2026-01-12](https://www.datadoghq.com/blog/building-bits-ai-sre/)), Cleric 는 **포스트모템 200여 건 중 명확한 원인과 충분한 맥락을 가진 것이 12건**뿐이었다고 적었다 ([Cleric, 2025-09-18](https://cleric.ai/blog/the-hidden-complexity-of-building-an-ai-sre)). Traversal 의 벤더 측정에서 3개월간 자사 하니스 개선이 **+153 Elo**, 프런티어 모델 교체가 **+41 Elo** 였고 ([Traversal, 2026-09](https://www.traversal.com/blog/the-model-isnt-the-bottleneck-findings-from-benchmarking-on-high-severity-incidents-in-enterprise)), Linear 는 GPT-4o mini·Gemini 2.0 Flash 가 "맥락 의존적 판단에서 흔들려" GPT-5·Gemini 2.5 Pro 로 올리고 이슈당 1~4분을 감수했다 ([Linear, 2025-09-03](https://linear.app/now/how-we-built-triage-intelligence)). 사람·월 단위를 밝힌 자료는 하나도 없지만, 모양은 분명하다: 1인 개발자의 시간은 에이전트 루프가 아니라 **컨텍스트 설계, 라벨된 과거 사례, 채점기**에 들어간다.

돈은 작다. relvy 가 고정된 조사 범위(30분 창의 메트릭 약 350개, 트레이스 약 40개, 로그 약 5,000줄)에서 측정한 건당 LLM 비용은 **Claude Haiku 4.5 $2.19 에 정확도 20%, Sonnet 4.6 $6.17 에 46.67%, Opus 4.6 $8.79 에 50%** 로, 정답 1건당 비용은 Haiku 약 $11, Opus 약 $18 이며 사람 비교치는 알림당 $50(30분×$100/h)이었다 ([relvy, 2026-03-16](https://www.relvy.ai/blog/llm-cost-of-ai-sre-investigating-production-alerts)). 공개 가격표도 같은 대역이다: AWS DevOps Agent 는 초당 $0.0083 이라 8분 조사에 **$3.98**, 소규모 팀 월 10건 $39.84 ([AWS](https://aws.amazon.com/devops-agent/pricing)); Datadog Bits Investigation 은 건당 약 6.5 크레딧으로 **$6.50–8.45** 이되 월 $500 묶음이 최소이고 크레딧은 이월되지 않으며 ([Datadog](https://www.datadoghq.com/pricing/)); Cleric 는 페이지상 **이슈당 $10**(2026-09-23, 7월 2차 자료의 $20 과 불일치) 에 불확정 결과는 과금하지 않고 ([Cleric pricing](https://cleric.ai/pricing)); Azure SRE Agent 는 조사 1건이 Opus 4.6 기준 약 35.3 AAU 인데 항상 켜 두는 비용이 2차 자료 추정으로 월 약 $292 다 ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/sre-agent/pricing-billing); [Arvo, 2026-07-28](https://www.aurorasre.ai/blog/ai-investigation-cost)). 월 30건이면 relvy 대역으로 **$66–264**, AWS 요율로 $119 이고, 저볼륨에서 청구서를 정하는 것은 건당 가격이 아니라 최소 묶음이다. 숨은 항목은 관측 조회다 — CloudWatch Logs Insights 는 GB 당 $0.005 라 500GB 로그 그룹에 10회 조회하면 스캔 요금 $25 로 에이전트 요금 $3.98 의 6배가 되고 ([Arvo](https://www.aurorasre.ai/blog/ai-investigation-cost)), SK텔레콤의 Bedrock 멀티에이전트 Agentic Ops 는 **월 약 $500 중 80% 가 OpenSearch** 였으며 ([DevOcean, 2025-09-01](https://devocean.sk.com/blog/techBoardDetail.do?id=167810)), GitHub 의 에이전트 워크플로 하나는 중복 코드 분류에 실행당 **약 233K 토큰**을 썼다 ([gh-aw-firewall #8743, 2026-09-18](https://github.com/github/gh-aw-firewall/issues/8743)). 학술 쪽 단가는 재현 1건 성공에 **$0.27**(LTGDroid), 스크린샷 이슈 수정 시도 1건에 **$0.29**(GUIRepair)·$2.94(SWE-agent M) 수준이다. 더 비싼 추론이 더 맞는 것도 아니다: 21,730회 롤아웃(약 $40,000)에서 모델·에이전트·벤치마크 조합 36개 중 21개는 추론 노력을 올려도 정확도가 같거나 낮았고, 2점 차이에 9배 비용이 든 짝도 있었다 ([HAL, 2025-10](https://arxiv.org/abs/2510.11977)). 국내 팀의 절감 수단은 그대로 옮길 수 있다 — A1Mobilsoft 의 Prompt Cache 로 입력 비용 50% 절감과 20회 하드 캡 ([AWS 기술 블로그](https://aws.amazon.com/ko/blogs/tech/a1mobilsoft-ops-automation-2/)), 컬리의 JSON DSL 로 토큰 약 3배 절감 ([컬리 기술 블로그, 2025-12-24](https://helloworld.kurly.com/blog/oms-claude-ai-workflow)), LY SRELens 의 질의당 10라운드·사용자별 일일 토큰 예산·결과 크기 상한 ([LY 기술 블로그, 2026-07-31](https://techblog.lycorp.co.jp/ko/analyzing-incident-root-causes-in-grafana-using-natural-language-with-llm-agent)).

혼자 만들 때 구조적으로 사라지는 것이 하나 있다. 모든 배포 사례의 안전판은 「사람 승인 게이트」인데, 1인 개발자에게는 요청자와 승인자가 같은 사람이라 그 게이트의 가치가 떨어진다. 그 붕괴를 견디는 가드레일은 넷이다. 첫째, **읽기 전용 자격증명** — 앞 절의 모든 파괴 사고가 과제보다 넓은 권한에서 났고, 삼성전자·쏘카·Nightwatch 가 택한 것도 이것이다. 둘째, **인용 없으면 침묵, 근거 없으면 확신도 하향, 모르면 기권** — Meta 의 규칙, LY 의 `other` 강등, RCACopilot 의 "unseen", Mozilla bugbug 의 「확신 60% 미만은 자동 분류 안 함(정밀도 >80%)」 ([Mozilla Hacks, 2019-04](https://hacks.mozilla.org/2019/04/teaching-machines-to-triage-firefox-bugs/)); 설명이 정답·오답 수용률을 똑같이 올린다는 결과가 있으니 가설마다 **반대 근거**를 같이 내는 dual explanation 이 측정된 이득을 가진 유일한 표시 방식이다. 셋째, **구조화 출력과 독립 검증 노드** — 쏘카는 LLM 의 "적용했다" 자기 보고를 믿지 않고 읽기 전용 스냅샷만 보는 check 노드로 다시 확인했고, 검증 단계에서는 유사 매칭을 금했으며 ([쏘카 기술 블로그](https://tech.socar.kr/dev/2026/07/22/agentic-engineering-in-production); [토스 테크, 2026-09-22](https://toss.tech/article/toss-doctor)), Cleric 는 근거가 주장을 뒷받침하는지만 보는 감사 에이전트를 조사 비용의 약 20% 로 따로 돌린다. 넷째, **에이전트가 갱신하는 지식 베이스와 라벨 셋** — incident.io 의 자체 점검 가이드는 닫힌 인시던트 5~10건 백테스트, 정밀도 **>80%**(70% 면 제안 열 중 셋이 시간을 낭비), 재현율 약 60%, 그리고 가짜 서비스·가짜 런북을 넣어 지어내는지 보는 환각 검사를 요구하고 ([incident.io, 2026-02-20](https://incident.io/blog/ai-root-cause-analysis-accuracy-testing-guide)), Azure 의 배포 규칙은 "검토 모드로 2~4주 관찰하고, 일관되게 승인하는 패턴이 보이면 그 트리거만 자율로 올려라"이되 알림 트리거 자동화의 기본값은 자율이라 기본값을 따르면 게이트가 없다 ([Microsoft Learn, 2026-06-02](https://learn.microsoft.com/en-us/azure/sre-agent/run-modes)). 문서와 코드가 어긋날 때 누가 판정하는지를 정한 자료는 하나도 없다 — 실무에서 그 소유자는 승인하는 엔지니어이고, 1인 개발자에게는 자기 자신이다.

이 근거를 사용자의 시나리오 — 채팅 스크린샷 제보 → 가설 → 원인(예: 데스크톱·모바일 값 차이) 통보 — 에 대응시키면 다음 표가 된다. 「현실적 기대」는 위 절의 독립 측정치를 그대로 옮긴 것이고 벤더 수치는 넣지 않았다.

## 결론

이 조사가 바꾸는 것은 목표의 이름이다. 「원인을 찾아 알려주는 에이전트」는 현장 어디에도 없고, 있는 것은 「어디를 봐야 하고 어떤 근거가 있으며 무엇이 부족한지를 사람이 도구를 열기 전에 정리해 두는 에이전트」이며, 그것이 가치를 낸다는 데는 자기 보고이긴 해도 1,000건(Meta)·2,000건/일(Databricks)·7,267건(쏘카)의 운영 실적이 있다. 진단만 하는 제품이 수정까지 하는 제품보다 쉬운 쪽에 있다는 것(Google 90% 대 18–43%), 그리고 에이전트를 붙여 확실히 얻는 것은 정확도가 아니라 지어낸 주장의 감소라는 것(Microsoft 환각 8배 감소·정확도 불변)은 1인 개발자에게 유리한 두 사실이다 — 요구되는 것이 「맞히기」가 아니라 「거짓을 말하지 않기」라면 그것은 모델이 아니라 구조로 살 수 있고, 국내 팀들이 한목소리로 적은 처방("프롬프트에 규칙을 더하지 말고 잘못된 행동이 불가능한 구조를 만들라")은 회사 규모에 의존하지 않는다.

견적의 진짜 항목은 코드가 아니다. 데모는 이틀이고 모델 비용은 월 수백 달러 아래지만, 이 도구가 「도움이 됐다」 65% 문턱을 넘는지 알 방법은 확정 원인이 적힌 과거 제보뿐이며, 그것은 200건 중 12건꼴로만 쓸 만하고 지금 모으지 않으면 나중에도 없다. 그리고 「데스크톱과 모바일의 값이 왜 다른가」라는 질문은 이 문서의 어느 벤치마크도 LLM 의 시각 판정으로 풀지 못했다 — 두 표면에서 같은 요청을 실제로 재생해 차이를 내는 도구를 에이전트에 쥐여 주고, 어느 값이 맞는지는 문서·코드·화면이 서로 다른 말을 할 때 사람이 판정한다는 것을 설계에 명시해야 한다. 남는 공백도 적어 둔다: 디버깅 시간에 대한 RCT 는 없고, 상용 제품에 대한 독립 평가는 하나도 없으며, 스크린샷만으로 웹 버그를 진단한 연구도, 한국어 화면의 판독 오류율도, 「도입했다가 껐다」는 국내외 1차 회고도 없다. 없다는 사실 자체가 이 견적의 불확실성 폭이다.
