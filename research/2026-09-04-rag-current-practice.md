## 0. 이 문서가 무엇이고 무엇이 아닌가

**무엇인가.** 2026-09-04 대화에서 오간 질문과 그 답을, **질문을 그대로 절 제목으로 삼아** 정리한
것이다. 다음 단위에서 **khala 현행과 대조**할 기준선으로 쓴다.

**무엇이 아닌가.** khala 의 설계 문서가 아니다. 여기 적힌 것은 **밖의 관행과 문헌**이고, 우리
구현에 대한 판정은 이 문서에 없다(대조 보고서가 따로 나온다).

**한계.**

- 공개 자료만 봤다. **성공한 것만 글이 되므로 생존 편향이 있다.**

- 수치는 원 출처의 보고값이고 **독립 검증하지 않았다.** 정의가 달라 출처끼리 비교할 수 없다.
- ⛔ 절 안의 **⚠ 판단** 표시는 조사가 아니라 이 대화에서 끌어낸 것이다.

## 1. 「검색·커넥터 층과 에이전트·거버넌스 층이 각각 무엇이며, 왜 그 형태로 정착했나」

### 1.1 두 층

두 층을 가르는 **질문이 다르다.** 아래층은 *무엇을 꺼내 줄까*, 위층은 *꺼낸 것으로 무엇을 하고
누가 책임지나.*

| | **검색·커넥터 층** | **에이전트·거버넌스 층** |
|---|---|---|
| 구성 | 커넥터 · 전수/증분 동기화 · 정규화·청킹·임베딩 · 하이브리드 색인 · **ACL 미러링** · 신원 결속(IdP↔SaaS) · 랭킹·융합 | 도구·skill 레지스트리 · 실행 환경 · 프롬프트/정책 계약 · 워크플로 · **소유권·수명주기·폐기 판정** · 출처 등급 · 감사 신호 |
| 정답 기준 | 맞았나 틀렸나 (재현율·정밀도) | **회사 정책에 맞나** — 회사마다 다르다 |
| 실패의 성질 | 틀리면 **유출** (상방 없음) | 잘 맞추면 **조직 고유 자산** (상방 있음) |
| 변경 주기 | 분기 | 주 |

### 1.2 왜 그 선인가 — 네 가지

1. **상각이 되느냐.** 커넥터 유지보수는 벤더의 고객 수로 나뉜다. *"우리 회사에서 무엇이
   정본인가"* 는 나눌 대상이 없다. **나눌 수 있는 것은 사고, 없는 것은 만든다.**
2. **실패의 성질.** 권한 미러링은 *잘 만들면 이득* 이 아니라 **틀리면 사고**다. 상방 없는 것을
   자체 구축하면 그 하방을 혼자 진다.
3. **변경 속도.** 속도가 다른 둘을 한 계약에 묶으면 느린 쪽이 빠른 쪽을 막는다. **경계는 변경
   속도가 꺾이는 자리에 생긴다.**
4. **벤더가 대신 정할 수 없는 것.** 조직도·승인 권한·문서 소유자·폐기 규칙은 회사의 구조 그
   자체다. 제품이 이걸 정해 주면 **그 제품의 조직 모델을 이식하는 것**이 된다.

⭐ 이유 1의 가장 좋은 근거가 **벤더 자신의 진술**이다 — Glean 은 각 조직의 데이터 수집 난이도를
과소평가했고 **각 SaaS 의 권한을 자사 검색 시스템 안에 복제해야 했으며 그것이 상당한 작업**
이었다고 적는다. 파는 쪽이 어렵다고 말한 것이라 자기 이해에 반한다.

### 1.3 이 선은 고정이 아니다

**위에서** 하이퍼스케일러(M365 Copilot · Gemini Enterprise · Amazon Q)와 Glean 이 거버넌스 층까지
올라와 통째로 팔려 한다. **아래에서** 에이전트가 사람보다 훨씬 많은 질의를 던지는데 지금의
검색층은 사람 규모를 전제로 설계됐다는 지적이 있다[벤더]. ⇒ **현재의 균형이지 구조적 필연이
아니다.**

## 2. 「검색 성능이 불만족스러울 때 원인이 어느 층인지 어떻게 판단하나」

### 2.1 표준 분류 — Barnett et al., *Seven Failure Points* (CAIN 2024)

현업은 두 층으로 안 가른다. **파이프라인 단계**로 가른다.

| | 실패 지점 | 무엇 | 층 |
|---|---|---|---|
| **FP1** | Missing Content | 필요한 내용이 애초에 저장소에 없다 | 적재·커넥터 |
| **FP2** | Missed the Top-Ranked | 문서는 있는데 top-k 안에 못 올린다 | 검색(랭킹) |
| **FP3** | Not in Context | 검색은 됐는데 통합에서 빠진다 | 조립 |
| **FP4** | Not Extracted | 컨텍스트에 있는데 LLM 이 못 집는다 | 생성 |
| **FP5** | Wrong Format | 형식 지시를 안 따른다 | 생성 |
| **FP6** | Incorrect Specificity | 너무 일반적이거나 너무 복잡하다 | 생성 |
| **FP7** | Incomplete | 컨텍스트에 있던 것을 빠뜨린다 | 생성 |

*(FP 정의는 논문을 요약한 2차 자료에서 가져왔다 — 원문 표를 직접 뽑지 못했다.)*

논문의 결론 둘이 질문에 직접 답한다: **① RAG 검증은 운영 중에만 가능하다. ② 견고함은 설계되는
것이 아니라 진화한다.** ⇒ *사전에 어느 층인지 알 수 없다* 는 것이 그 분야의 합의다.

### 2.2 실제 판별 — 지표 **두 쌍의 조합**

| `context recall` | `faithfulness` | 판정 |
|---|---|---|
| 낮음 | — | **검색 층** (FP1/FP2) |
| 높음 | 낮음 | **생성 층** (FP4/FP7) |
| 높음 | **높음**인데 답이 틀림 | ⚠ **어느 지표도 안 잡는다** → §5.2 |

### 2.3 지표보다 **추적(trace)** 이 먼저다

AI 네이티브 관측 플랫폼(Langfuse · LangSmith · Arize Phoenix · Braintrust)은 **트레이스를 1급
객체**로 두고 에이전트·리트리버·도구를 중첩 span 으로 남긴 뒤 프로덕션 트래픽에 점수를 붙인다.
Phoenix 는 **청크 단위까지** 내려가 문제가 검색된 청크에 있는지 엉뚱한 청크에 있는지 가른다.

⭐ 가장 실무적인 한 줄: **"리트리버가 틀린 문서를 냈는데 HTTP 상태는 전부 200이다."** 인프라
모니터링이 원리적으로 못 보는 층이고, **span 기록이 없으면 사후에 층을 가를 방법 자체가 없다.**

## 3. 「오프라인·온라인 평가가 무엇이고, 처음에는 골든셋 없이 시작하나」

### 3.1 오프라인 vs 온라인

| | **오프라인** | **온라인** |
|---|---|---|
| 대상 | 고정된 **골든셋** | **실제 사용자 트래픽** |
| 시점 | 배포 **전** | 배포 **후**, 상시 |
| 정답 | 있다 | 없다 |
| 재현성 | 같은 입력을 다시 돌린다 → **비교 성립** | 같은 질의가 두 번 안 온다 → 비교 불가 |
| 목적 | **결정** — 배포할 것인가 | **감시** — 지금 나빠지고 있는가 |

**고리**: 프로덕션 트래픽 → trace → 온라인 채점·👎로 낮은 점수 질의 선별 → 사람이 기대값 부착
→ 오프라인 골든셋 편입 → 이후 모든 변경이 그 질의를 통과해야 배포(= 회귀 검사).

⇒ *"골든셋은 프로덕션 트레이스에서 큐레이션한다"* 의 뜻: **머리로 지어내지 말고 실제로 들어온
질의에서 뽑아라.** 지어낸 질문은 저자가 코퍼스를 보고 짓게 되어, *코퍼스가 답을 가졌을 때 답을
내는가* 는 측정해도 *사람들이 실제로 묻는 것에 답하는가* 는 측정하지 못한다.

### 3.2 t=0 — 골든셋 없이 시작하는 게 아니라 **틀린 줄 알면서 씨앗으로** 시작한다

가능한 것 셋: **①라벨이 필요 없는 채점**(결정론 검사기 + reference-free — 0건으로 오늘 돈다)
· **②합성 셋**(RAGAS testset generator 는 evolutionary 방식으로 reasoning·conditioning·
multi-context 유형 분포를 지정할 수 있다) · **③사람이 지은 씨앗 10~30건**.

⭐ **②③ 은 품질을 측정하지 못한다. 깨지는 것만 탐지한다** — 둘 다 코퍼스에서 나왔기 때문이다.

**합성 셋의 분포 어긋남은 측정돼 있다.**

- 실제 질의는 합성 질의보다 **짧다** (사람은 타이핑을 아낀다)
- 실제 질의는 **"무엇"으로 시작하는 비율이 유의하게 높다**
- ⭐ **서로 다른 질의의 70%가 딱 한 번만 나온다** — 롱테일이라 **LLM 이 대표적 질의를 상상하는
  것 자체가 구조적으로 불가능하다**
- ⇒ **합성 셋은 실데이터로 가는 경유지이지 영구 대체물이 아니다.**

### 3.3 실제 질문은 트래픽보다 먼저 존재한다

t=0 에도 조직 안에 **사람이 실제로 물은 기록**이 있다 — 기존 사내 검색 기록 · 지원 티켓 ·
**사람이 사람에게 물은 채팅 질문** · FAQ · 도메인 전문가 인터뷰. 코퍼스가 아니라 **필요에서
나왔기 때문에** 합성 셋보다 분포가 맞는다.

| Phase | 채점 | 그 수로 말할 수 있는 것 |
|---|---|---|
| **0** (골든셋 0) | 결정론 + reference-free, 씨앗 10~30은 **회귀 검사 전용** | *"안 깨졌다"* 만. **품질을 말하지 않는다** |
| **1** (채굴) | 기존 기록·티켓·채팅에서 실제 질의를 뽑아 기대값 부착 | 여기부터 **골든셋** |
| **2** (트래픽) | trace 에서 큐레이션, 👎·낮은 점수 승격 | 대표성 상승 |
| **3** (정착) | 골든셋이 회귀 검사가 된다 | 변경이 이걸 통과해야 나간다 |

⚠ **흔한 실패**: t=0 에 큰 합성 골든셋을 만들고 몇 달 최적화한다. 이미 천장이라 깨지는 것만
탐지하는데 올라가는 숫자를 개선으로 읽는다.

## 4. 「reference-free 채점이 무엇이고, 사람 개입 빈도는」

### 4.1 정의 — **정답 라벨 없이**이지 **사람 없이**가 아니다

기제: 정답과 비교하는 대신 **답을 원자적 주장으로 분해하고, 각 주장이 근거에 함의(entail)되는지**
본다(NLI). `faithfulness` = 지지된 주장 ÷ 전체 주장.

### 4.2 ⚠ 전부 reference-free 가 아니다 — 중요한 구분

| 지표 | 참조 필요 | 비고 |
|---|---|---|
| `faithfulness` · `answer relevancy` | **불필요** | 생성 층 |
| `LLMContextPrecisionWithoutReference` | **불필요** | 기준이 **생성된 답변** → §5.3 함정 |
| `LLMContextPrecisionWithReference` | 정답 답변 | |
| `NonLLMContextPrecisionWithReference` | 정답 컨텍스트 | 문자열 유사도, LLM 불필요 |
| **`context recall` (세 변형 전부)** | **필수** | 문서가 명시: *"context recall 계산은 항상 비교할 참조를 요구한다"* |

**왜 recall 만 구조적으로 불가능한가**: precision 의 분모는 **가져온 것**(시스템 안)이고 recall 의
분모는 **필요한 전부**(시스템 밖)다. ⭐ **precision 은 있는 것에 대한 진술, recall 은 없는 것에
대한 진술이다.** 시스템이 못 가져온 것을 열거할 수 있었다면 애초에 안 놓쳤다.

⇒ 라벨이 없으면 **FP1(코퍼스에 없다)과 FP2(있는데 못 찾았다)를 원리적으로 구별할 수 없다.**

### 4.3 recall 라벨의 세 형태 — 비용이 다르다

| 변형 | 참조 | 계산 | LLM |
|---|---|---|---|
| `LLMContextRecall` | **정답 답변** | 정답을 주장으로 분해 → 각 주장이 근거에 귀속되는가 | 필요 |
| `NonLLMContextRecall` | **정답 청크 본문** | 문자열 유사도 | 불필요 |
| **`IDBasedContextRecall`** | **정답 청크 id** | 집합 연산 | **불필요** |

⭐ 세 번째가 **완전 결정론**이다. 라벨은 *"이 질의의 정답 청크 id"* 하나, 채점은 집합 연산.
**비용이 드는 곳은 채점이 아니라 라벨을 만드는 한 번이다.**

### 4.4 라벨 비용을 줄이는 표준 — pooling

여러 시스템·설정의 **상위 k 합집합**만 사람이 판정하고 그것을 정답으로 쓴다.
⚠ **대가**: 어떤 시스템도 안 가져온 문서는 영원히 판정되지 않는다 ⇒ 그 재현율은 *코퍼스 대비*
가 아니라 **pool 대비**다. 인용할 때 그렇게 밝혀야 한다.

### 4.5 사람은 얼마나 필요한가 — 갈래에 따라 완전히 다르다

**갈래 A — LLM 심판**: 초기 정렬에 **사람 라벨 50~200건**, 심판과의 일치도 **Cohen 카파 0.6 이
합격선, 0.8 이상이면 프로덕션 급**. 이후 **5~10% 표본 사람 확인**, 감사는 프로덕션 트레이스
100~300건을 2~3명이 라벨.

⚠ 심판의 체계적 편향: **position bias 10~15%p** · **verbosity bias**(사람보다 훨씬 심하게 긴 답을
과대평가) · **self-preference** · 프롬프트 취약성. ⛔ 앙상블·순서 뒤집기는 **심판 사이의 분산**은
줄여도 **공유된 체계적 편향**은 못 줄인다.

**갈래 B — 작은 전용 함의 모델**: §5 참조. 재정렬 빈도가 훨씬 낮다.

## 5. 「함의 판정에 다른(큰) 모델을 쓰면 낫지 않나 / 자기참조 순환을 어떻게 깨나」

### 5.1 큰 모델이 더 낫지 않다 — 측정치

`LLM-AggreFact` 리더보드 기준.

| 판정기 | balanced accuracy |
|---|---|
| **Bespoke-MiniCheck-7B** | **77.4%** (공개 리더보드 최상위) |
| GPT-4 | 75.3% |
| MiniCheck-Flan-T5 (훨씬 작다) | 74.7% |
| Claude 3 Opus | 74.1% |

설명이 이렇게 붙는다 — *"기존 전용 fact-checker 와 off-the-shelf LLM 을 **크기와 무관하게** 전부
앞선다."* 그리고 MiniCheck 계열은 **비용이 400배 낮고**, **단일 GPU 에서 종단 200ms(최적화 시
100ms 미만)**, 맥북에서도 도는 drop-in HuggingFace 모델이며 출력은 `support score` 확률 하나다.

⇒ **주장 하나하나에 라이브로 걸 수 있다.** 큰 모델은 (주장 수 × 질의 수)라 그게 안 된다.

### 5.2 ⚠ 진짜 중요한 것은 이 숫자의 다른 쪽 — **천장이 77%다**

⛔ **어느 함의 판정기도 게이트가 될 수 없다.** 넷 중 하나는 틀린 이유로 막거나 통과시킨다.

그리고 오류가 무작위가 아니다. *Verify with Caution* 이 측정한 것: 지표들이 **서로 불일치**하고
시스템 수준 성능을 **오추정**하며, 체계적으로 **강하게 의역된 출력**과 **원문의 먼 부분들을 끌어다
쓴 출력**에 불리하다. 권고: *"자기 도메인에서 신뢰성을 직접 검증한 뒤에 쓰라."*

⭐ **둘째 편향이 멀티홉이다** — 그 판정기를 그대로 채점에 걸면 **개선하려는 종류의 답을 체계적으로
깎는다.**

### 5.3 자기참조 순환 — 기준을 **답변에서 질의로** 바꾼다

문제의 정체는 **짝**이다. `LLMContextPrecisionWithoutReference` 는 `답변 ↔ 청크` 를 보므로 답이
틀리면 기준이 틀린다. **틀린 답을 뒷받침한 청크가 "관련 있음" 으로 채점된다.**

TruLens 의 **RAG triad** 가 이 순환을 피하려고 세 관계를 각각 다른 짝으로 본다.

| 지표 | 짝 | 답변을 보나 |
|---|---|---|
| **`context relevance`** | **질의 ↔ 청크** | ⭐ **안 본다** |
| `groundedness` | 청크 ↔ 답변 | 본다 |
| `answer relevance` | 질의 ↔ 답변 | 본다 |

⇒ 참조 없는 정밀도를 *개선* 하는 게 아니라 **`context relevance` 로 갈아타는 것**이 해법이다.
⚠ 다만 이것도 정밀도다 — **재현율의 구조적 한계(§4.2)는 그대로다.**

### 5.4 더 강한 방법 — 관련성 대신 **인과** (ContextCite)

*"이 청크가 관련 있나"* 가 아니라 **"이 청크가 이 문장을 실제로 만들어 냈나"** 를 묻는다. 컨텍스트를
**빼 보고**(ablation) 응답 확률이 얼마나 떨어지는지로 귀속 점수를 낸다. 논문이 든 쓸모 셋: 생성
문장 검증 · 컨텍스트 가지치기 · **오염(poisoning) 탐지**.

⭐ 자기참조를 **원리적으로** 깬다 — 답변의 *내용* 이 아니라 **생성 의존성**을 측정하기 때문이다.
그리고 *인용이 검증되는데 그 문서가 답에 아무 기여도 안 한 경우* 를 잡는다.

### 5.5 층은 경쟁이 아니라 적층 — cascade

| | 정밀도 | 커버리지 |
|---|---|---|
| 결정론 검사기(인용 존재·숫자 대조) | 사실상 **100%** | **좁다** |
| 함의 모델 | **~77%** | **넓다** |

**항상 맞는 검사기를 4분의 3만 맞는 것으로 바꾸는 게 아니다. 겹쳐 쌓는 것이다.**

권고 순서: ①**결정론 검사기**(전부에 건다, 사람 0·잡음 0·비용 0) → ②**함의 모델**(결정론이
침묵한 주장, 100~200ms) → ③**큰 모델**(`support score` 가 불확실 구간인 것만).

보고된 절감(항상 큰 모델 대비): **비용 −76%(Claude) · −49%(GPT) · −81%(Gemini)**, 지연 −61~82%.

⛔ **에스컬레이션 트리거를 생성기의 confidence 로 잡지 마라** — LLM 의 자기 보고 confidence 는
**교정이 안 돼 있다.** 사실이 틀렸는데도 높은 토큰 확률로 유창하고 단정적인 답을 낸다.

### 5.6 라벨 없는 불일치 신호

**자기일관성**(같은 질문 k회 → 합의) · **교차 모델**(다른 모델이 같은 컨텍스트로 답) — 둘 다
*정답을 모른 채* **"여기 문제가 있다"만** 낸다. 판정이 아니라 **사람 감사 대상 선별**에 쓴다.

## 6. 「골든셋이 항상 최신이라 가정하나 / 사람 재서명이 현업 전략인가」

### 6.1 라벨도 썩는다 — 측정돼 있다

*Pervasive Label Errors in Test Sets Destabilize ML Benchmarks* (arXiv 2103.14749):

- 주요 벤치마크 **10개에서 평균 최소 3.3%** 라벨 오류. **ImageNet 검증셋은 최소 6%**
- 알고리즘이 지목한 후보의 **51%가 사람 검증에서 진짜 오류로 확인**
- ⭐ **그 정도로 순위가 뒤집힌다** — 오류 6%면 ResNet-18 이 ResNet-50 을, CIFAR-10 은 5%에서
  VGG-11 이 VGG-19 를 앞선다

### 6.2 "자동 갱신 금지 + 사람 재서명" 은 표준 관행이다

**① 데이터셋을 코드와 같은 거버넌스로.** 관행 쪽 진술: *"데이터셋을 1급 산출물로 다룬다 —
**버전이 붙고, ground truth 변경은 코드 리뷰를 거치며, 라벨된 사례를 지우거나 고치는 것은
프로덕션 위험으로 취급된다.**"*

**② 사람 승인 절차는 제품화돼 있다.**

- **LangSmith `annotation queue`** — 실행을 리뷰로 표시해 **도메인 전문가에게 배정**한다. 리뷰어는
  점수만 매기지 않고 **출력을 수정하고, 트레이스를 데이터셋에 직접 넣고, 쌍 비교를 돌리고, 추가
  리뷰어에게 에스컬레이션**한다.
- **Braintrust `calibration queue`** — 여러 리뷰어가 **같은 항목을 주기적으로** 채점해 rubric
  정렬을 유지한다.

**③ 왜 자동 갱신이 금지인가.** 홀드아웃 규율과 사전 등록이다. **자동 라벨 갱신은 채점기가
시스템에 맞춰지는 경로를 연다** — 점수가 나쁠 때마다 라벨이 움직이면 채점기는 아무것도
판정하지 않는다.

### 6.3 `eval set decay` — 부패의 형태

벤치마크 예시가 프롬프트에 재사용된다 · 주석이 canonical 표현을 베낀다 · **검색 색인이 그 답을
유난히 쉽게 만든다** · 골든 예시가 널리 돈다 ⇒ **점수는 오르는데 라이브 성능은 안 오른다.**

관행이 더 갖고 있는 것 둘: **rubric 에도 버전을 붙인다**(*"기대가 바뀌면 주석 가이드를 고치고
대표 부분집합을 다시 라벨한다"*) · **living benchmark**(예시 추가 · 과제 추가 · **오래된 데이터
폐기** · 라벨 오류 수정을 상시 절차로 둔다).

## 7. 「부패 관리는 거버넌스인가 / 개선의 천장이 인프라 한계 아닌가 / 사면 제약 아닌가」

### 7.1 낡음은 표준 지표의 사각지대다

낡은 문서는 **정확히 검색되고**(`context recall`·`context precision` 통과) 생성기가 **충실히
옮긴다**(`faithfulness` 통과). 그런데 답은 틀렸다. **표준 지표는 색인이 믿을 만하다는 것을
가정으로 깔고, 그 가정 자체는 측정 대상 밖에 있다** — `faithfulness` 0.95 를 받고도 틀린 답이
나온다. 그리고 의미 유사도에는 시간 축이 없어서 **낡은 임베딩이 최신 것과 같은 점수를 받는다**
(경고 신호 없이 검색 정확도를 최대 20% 떨어뜨린다는 보고).

**HoH 벤치마크**(ACL 2025)가 이걸 정면으로 다룬다 — 낡은 정보는 ①정확도를 떨어뜨리고
②**최신 정보가 함께 있어도** 모델을 오도한다.

⚠ 그리고 이것이 채택을 죽인다: 낡은 것과 최신이 공존하면 신뢰가 무너지고 **출시 3~6개월 뒤
채택이 빠지는 것이 널리 기록된 형태**다. PoC 통과 뒤 실패한 프로젝트의 **60%가 검색 품질이
아니라 신선도 유지 실패** 때문이라는 보고도 있다[벤더].

### 7.2 그래서 낡음은 지표가 아니라 **운영 규율**로 다룬다

- **부패 속도별 검토 주기** — 고부패(API 문서·가격·정책) **2~4주** · 중(아키텍처 가이드·런북)
  **분기** · 저(기초 문서) **연 1회**
- **마감이 다가온 문서를 소유자에게 자동 통지**, 무응답 시 에스컬레이션
- **낡음에 버그 트래커 항목·소유자·해소 SLA 를 붙인다**
- ⭐ *"신선도가 누군가의 명시적 업무가 되기 전까지는 아무의 업무도 아니다."*

### 7.3 ⭐ 천장은 실재한다 — 후처리는 **지울 수 있고 올릴 수 없다**

2단 검색에서 **2단의 재현율 상한은 1단이 정한다.** 리랭커는 후보 집합 안에서 정밀도를 올릴 뿐
1단이 놓친 것을 복구하지 못한다 — *"리트리버 재현율이 나쁘면 어떤 리랭커도 구해 주지 못한다."*

부패 관리를 검색 **뒤에** 붙이면 그것은 정의상 후처리다. 실제로 현업의 temporal 계층 구현이
스스로를 *"post-retrieval temporal layer"* 라 부르고, 만료된 사실을 hard-remove 하고 시간 감쇠로
최신을 올린다 — **벡터 검색 하류에서 도는 순수 후처리**다.

⇒ 낡은 문서를 지워도, **최신 문서가 1단에서 안 왔으면 결과는 최신 답이 아니라 빈손이다.**

### 7.4 산 층에서 부딪히는 벽은 구체적이다

M365 Copilot 커넥터 문서에 명시된 것:

- 크롤 주기: 일·주·격주·4주, 또는 하루 안에서 **15분~12시간 간격**
- **증분 크롤은 권한 갱신을 처리하지 않는다** → 전수 크롤을 주기적으로 돌려야 한다
- 증분 크롤은 삭제를 자동 처리하지 않는다 — 커넥터가 삭제 항목을 명시적으로 보내야 하고,
  **안 보내면 원본에서 지운 항목이 색인에 남는다**

| 거버넌스 약속 | 실제 상한 |
|---|---|
| "고부패 콘텐츠 2~4주 검토" | **크롤 주기보다 촘촘할 수 없다** |
| "권한 변경 즉시 반영" | **전수 크롤 주기보다 촘촘할 수 없다** |
| "폐기 문서는 검색에서 빠진다" | 커넥터가 삭제를 전파하느냐에 달렸다 |

### 7.5 그런데 천장의 높이는 **벤더 속성 하나**로 갈린다

Glean 은 Indexing(Push) API 로 **문서·사용자·권한·메타데이터를 직접 밀어 넣게** 한다. custom
property 는 **facet/operator 로 필터** · 렌더링 · **searchability 와 랭킹 신호**로 쓰이고 타입에
`DATE` 가 있다(에폭 초면 facet 도 된다). ⇒ **거버넌스 메타데이터를 1단 색인에 심을 수 있으면
부패 관리가 후처리가 아니라 1단의 일부가 되고, 천장이 올라간다.**

⚠ 열려 있지 않은 것: **랭킹 가중치 직접 제어 방법은 문서에 없다**(*"자동으로 색인을 풍부하게 해
검색성과 랭킹을 개선한다"* 까지만). 행동 신호가 섞이고 커넥터마다 타임스탬프가 달라 **신선도
취급이 커넥터별로 갈린다.** 그리고 과한 recency boost 는 **정본 정책 문서 위로 새 무관 문서를
올린다** — 조절 값을 잘못 돌리면 거버넌스를 역행시킨다.

⭐ **가장 큰 제약은 평가일 수 있다.** 벤더 쪽 글 자체가 적는다 — **엔터프라이즈 검색에는 쓸 만한
공개 벤치마크가 없고**, 라벨된 질의 집합과 기준선 없이 하는 relevancy 작업은 추측이다(*하나
고치고 열을 모르게 깨뜨린다*). ⇒ **산 층에서는 자기 천장의 높이조차 측정하기 어렵다.**

### 7.6 구매 검토에서 물을 다섯

1. 문서·권한·**날짜형 커스텀 속성**을 우리가 직접 밀어 넣을 수 있나
2. 그 속성이 **필터**로만 쓰이나, **랭킹 신호**로도 쓰이나, 가중치를 우리가 정하나
3. 증분 동기가 **삭제**와 **권한 변경**을 전파하나. 아니면 전수 크롤을 얼마나 짧게 잡나
4. 최소 크롤 간격
5. **우리 질의 집합으로 오프라인 평가를 돌릴 수 있나** — 후보 풀과 순위를 볼 수 있나

⭐ 5번이 가장 중요하다. 없으면 **앞의 넷에 대한 답이 참인지 확인할 방법이 없다.**

## 8. 「코퍼스에 무엇이 들어 있고 인덱스와 무엇이 다른가 / 가르는 기준은 / 다른 프로젝트가 섞이면」

### 8.1 코퍼스 vs 인덱스

| | 코퍼스 | 인덱스 |
|---|---|---|
| 무엇 | **내용 그 자체** — 사실이 여기 있다 | 그 내용을 **찾을 수 있게 만든 파생 구조** |
| 지우면 | **사실이 사라진다** | 못 찾을 뿐, 다시 만들면 된다 |

⭐ **"코퍼스에 있다"와 "찾을 수 있다"는 다른 사실이고, 후자만 사용자에게 보인다.**

### 8.2 코퍼스에 실제로 들어가는 것

문서 한 건이 **두 층**으로 앉는다.

**문서 층** — 신원(제목·출처 URI·버전·내용 해시) · **가르는 열**(테넌트·기밀등급·소유자) ·
**거버넌스 열**(상태 active/superseded/soft_deleted · 격리 여부 · 문서 종류 · 라벨 · 품질 플래그 ·
상위 거버넌스 도구의 검토 도장) · **시간 둘** · 계보(출처 종류 · 파이프라인 · 입력 · 변환).

⭐ **시간이 둘이어야 하는 이유**: *적재 시각* 으로는 **재적재하면 모든 문서가 새것이 되므로
"낡았나"를 구조상 못 묻는다.** 원본이 말하는 마지막 수정 시각을 따로 받고, **비었으면 "모른다"**
로 둔다(≠ 새것).

**청크 층** — 부모 문서 · 문서 안 위치(절 경로) · 순번 · 원문 조각 · **검색용 텍스트**(절 경로나
문맥 접두어 + 원문 조각. **검색과 임베딩이 실제로 보는 것은 이것이다**) · 벡터 · 어휘 색인 벡터.
그리고 **권한 관련 열을 문서에서 복제해 다시 갖는다**(필터를 청크 단계에서 걸어야 하므로).

⇒ **코퍼스 = 사실 + 그 사실을 누가 볼 수 있고, 언제 것이며, 어디서 왔는가.** 텍스트 더미가 아니다.

### 8.3 코퍼스를 가르는 기준 — 둘뿐

1. **볼 수 있는 사람이 다른가** (하드 요건)
2. **측정을 격리해야 하는가** (평가 팩)

**나머지는 전부 열(column)로 둔다** — 문서 종류 · 포맷 · 소유자 · TTL · 출처 시스템 · 등급.

⭐ **왜: 분리는 되돌릴 수 없고 메타데이터는 되돌릴 수 있다.** 코퍼스를 가르면 후보 풀이 갈려
**경계마다 §7.3 의 재현율 천장이 하나씩 생긴다.** 그리고 가르는 순간 **라우터가 필요**해지는데,
라우터가 틀리면 정답 문서가 **구조적으로 도달 불가**다.

⚠ 그리고 등급으로 되는 것을 테넌트로 가르지 마라 — **등급은 같은 코퍼스 안의 필터라 경계를 넘는
질문이 안 죽는다. 테넌트는 죽인다.**

### 8.4 포맷이 다르면 가르나 — 아니다

포맷이 정하는 것은 **적재 경로와 출처 등급**이지 코퍼스가 아니다. 문서 종류는 **거버넌스를
움직인다** — 종류별 TTL 이 §7.2 의 검토 주기를 코퍼스 분리 없이 구현하는 방법이다.

### 8.5 다른 프로젝트가 섞이면 — **위험이지 결함이 아니다**

진짜 해악은 후보 풀이 아니라 **어휘 충돌**이다. 두 프로젝트가 같은 낱말을 쓰면 어휘·의미 양쪽에서
오탐이 나고, 최악은 **두 프로젝트의 사실을 유창하게 합친 답**이다.

⭐ **그리고 이 실패는 지금까지의 검사기 어느 것도 못 잡는다** — `faithfulness` 통과(각 주장이 각자
출처에 근거) · 인용 검증 통과(제목이 실재) · 신선도 통과(둘 다 최신). **틀린 것은 문서 *사이의*
관계이고, 그건 어느 문서 안에도 안 적혀 있다.**

⚠ **판단**: 그래도 **가르기 전에 크기를 측정하라.** 가르는 것은 되돌리기 비싸고(경계를 넘는 질문이
영구히 죽는다) 측정은 싸다. 그리고 **세는 단위를 조심하라** — 문서 수로 세는 것과 청크·글자로
세는 것이 정반대 결론을 낼 수 있다. **검색은 문서가 아니라 청크를 매긴다.**

### 8.6 코퍼스↔인덱스 드리프트도 부패다 — 그런데 종류가 다르다

| | 문서 부패 | 인덱스 드리프트 |
|---|---|---|
| 무엇이 틀렸나 | **내용**이 낡았다 | 내용은 맞는데 **못 찾거나 옛 내용으로 찾힌다** |
| 고치는 주체 | 문서 소유자(**사람**) | 파이프라인(**기계**) |
| 자동 판정 | 안 된다 | **전부 된다 — 결정론** |
| 관리 수단 | 검토 주기 · 소유자 · SLA | **회귀 검사** |

**네 형태와 각각의 모집단**(이게 핵심이다 — 모집단이 다르므로 한 지표로 못 센다):

| 형태 | 모집단 | 왜 다른 지표에 안 보이나 |
|---|---|---|
| **청크가 아예 없다 (유령 문서)** | 문서 | 커버리지 모집단이 *청크* 라 **청크 0인 문서는 분모에도 분자에도 안 들어간다 → 100%로 건강하게 보인다** |
| 벡터가 비었다 | 청크 | — |
| 세대가 섞였다 | 컬럼 | 행당 한 칸짜리 라벨은 벡터 컬럼 둘을 설명하지 못한다 |
| **벡터가 있는데 틀렸다** | 값 | NULL 이 아니면 "채워짐"으로 센다. **재계산 말고는 볼 방법이 없다** |

⭐ **처방**: 값싼 셋은 상시, 비싼 넷째는 표본+주기. 그리고 **대조군을 먼저 읽어라** — 방금 다시
임베딩한 청크는 정의상 현재 텍스트의 벡터이므로, 그게 1.0 이 안 나오면 **평가 하니스가 고장난
것**이고 나머지 수치는 못 쓴다.

⚠ **사용자에게 구별해서 보여라.** 드리프트가 나면 검색은 0행을 내고 답변자는 *"문서에서 답을 찾지
못했습니다"* 라고 한다. 사용자는 **코퍼스에 없는 것**과 **인덱스가 끊긴 것**을 구별할 수 없다.
원인 셋은 고칠 사람이 다르다 — 코퍼스가 빈 것(적재 담당) · 질의가 안 맞은 것(사용자) ·
등급/테넌트가 가린 것(운영자).

## 9. 「어떤 문서 타입까지 관리하나 / 그림·디자인은 / 포맷 변환은」

### 9.1 실제로 색인되는 것

| 층 | 타입 |
|---|---|
| 거의 모든 사례 | 런북 · 정책/컴플라이언스 · 온보딩 가이드 · 제품 스펙 |
| 엔지니어가 실제로 치는 것 | 코드베이스 · API 레퍼런스 · **ADR** · 인시던트 포스트모템 |
| 그다음 | 티켓 · 릴리스 노트 · 사내 논의 · 회의록 |

측정치 하나: B2B SaaS 지원 RAG 를 **티켓 + 릴리스 노트 + 런북** 셋에만 걸어 L2 에스컬레이션
**38% 감소**. 그리고 관행은 문서 타입을 **`source_type` 메타데이터**로 단다 — §8.3 과 같다.

### 9.2 마크다운 정규화가 기본인가 — 맞다

> LLM 친화적이지 않은 포맷을 다루는 표준 접근은 **마크다운으로 변환하는 것**이다.

| 도구 | 강점 | 주의 |
|---|---|---|
| **MarkItDown** (MS) | 깨끗한 디지털 문서 · Office · GPU 불필요 | **표·구조에 약하다** |
| **Docling** (IBM) | 복잡한 표·다단·재무 문서. `TableFormer` 가 병합셀·중첩표를 잘 다룬다 | 무겁다 |
| **LlamaParse** | 복잡한 레이아웃 최고 정확도(**92% F1**) | 상용 |
| **Unstructured** | 30종+ 파일(이메일·이미지·틈새 포맷) | **배포가 가장 무겁다** |

관행 패턴: **MarkItDown 먼저 → 품질이 부족한 문서만 Docling 으로 낙하.**

### 9.3 그림이 본문인 문서 — 여기서 갈린다

⭐ **기업 PDF 의 약 80%가 표·차트·복잡 레이아웃을 최소 하나 포함한다.** 그 문서에서 OCR 기반
RAG 는 **애초에 깨진 입력**으로 시작한다.

| 방식 | 무엇 | 언제 |
|---|---|---|
| **caption-and-index** | 그림을 설명문으로 바꿔 텍스트로 색인 | 가장 단순. ⚠ 자동 캡션은 *이 자리에서 무엇이 중요한지* 를 놓쳐 **사람 검토가 필요** |
| **통합 비전 임베딩** | Cohere Embed 4 · voyage-multimodal-3.5 | 중간 |
| **page-as-image + late interaction** | **ColPali · ColQwen2.5 · ColNomic** — OCR 없이 페이지를 시각 객체로 색인 | 레이아웃이 의미인 문서 |

기록된 권고: **배선도·CAD 스크린샷이 있는 엔지니어링 문서에는 ColPali + 강한 VLM 이 맞다 —
텍스트 절차와 그림이 *둘 다* 검색 가능해야 하므로 하이브리드가 이긴다.**

⇒ **화면 설계서가 그 부류다.** 텍스트로 접으면 값이 사라지고(좌표·상태·분기), 그림만 두면 텍스트
절차가 안 걸린다.

⚠ **기계가 읽은 텍스트에는 등급을 붙여야 한다.** 판독 재현성의 잡음 폭을 먼저 측정하지 않으면
그 텍스트를 근거로 쓸 수 없다.

### 9.4 디자인 파일 — ⭐ 색인이 아니라 **도구**로 붙인다

Figma 파일을 문서로 색인하는 사례는 안 보이고 **MCP 실시간 접근**이 표준이 됐다. 공식 Dev Mode
MCP 서버(2025년 말 출시, 2026-02 기준 도구 14개)가 넘기는 것은 이미지가 아니라 **디자인 트리** —
계층 · auto-layout 규칙 · 변수 참조 · **Code Connect 매핑**. 그래서 모델이 **픽셀 근사가 아니라
실제 제약**에 대고 코드를 만든다.

**왜 색인이 아닌가**: 디자인 파일은 **매일 바뀐다.** 색인하면 그 순간 부패가 시작되고 §7.4 의
크롤 주기 하한에 걸린다. **질의 시점에 가져오면 그 부패가 존재하지 않는다.**

## 10. 「문서 외 도구를 언제 부르나 / 어떤 도구를 몇 개나」

### 10.1 판단 기제 — 층이 둘이다

- 앞단에 **분류기**를 둬서 *에이전트 검색이 필요한가 / 빠른 하이브리드 RAG 로 충분한가* 를 가른다.
  목적은 정확도가 아니라 **지연** — *"이터레이션이 이득 없는 70% 질의"* 를 빠른 길로 보낸다.
- 그 뒤의 실제 도구 선택은 **LLM 호출 그 자체**다. 판단 근거는 **명시적 도구 정의와 지시**.

⭐ 관행이 명시하는 설계 규칙: **라벨 집합을 작게 유지하고 구체적 커넥터에 묶어라.** 라우터가
*비슷한* 소스들 사이에서 고르게 두면 검색 개선이 아니라 **모호성 디버깅**에 시간을 쓴다.

⇒ **트리거는 규칙이 아니라 도구 설명이다.** 개선 방법도 라우터 튜닝이 아니라 **도구 설명 다시
쓰기**다.

### 10.2 도구 수 — 실전 데이터

| 측정 | 값 |
|---|---|
| Berkeley Function Calling Leaderboard, 일정 잡기 | 도구 **4 → 51**: 정확도 **43% → 2%** |
| 고객지원, gpt-4o | 1도메인·9도구 **58%** → 7도메인·51도구 **26%** |
| 프로덕션 관측 | **10~15를 넘으면** 정확도가 측정 가능하게 떨어진다 |
| 컨텍스트 비용 | 도구 58개 ≈ **55K 토큰**. 일부 구성은 **134K 초과** |
| 점유율 | 수십 개면 JSON 스키마가 컨텍스트의 **40~50%** |

⇒ **한 자리 수, 많아야 10~15.** 그 이상이 필요하면 해법은 **동적 발견**이다 — RAG-MCP 는 검색 기반
도구 선택으로 정확도 **13.62% → 43.13%**, 프롬프트 토큰 **절반 이하**. Anthropic 은 2026-03 에
`Tool Search Tool` 로 이 문제를 Claude 계열에서 해결로 선언했다.

### 10.3 실제로 붙는 도구

1차 사례: **Uber Context Graph** — 소스코드 · 문서 · Jira · Slack. **Anthropic 팀** — Slack ·
Linear · GitHub · 사내 DB · 사내 API. **Stripe Kai** — 1,000+ skill 이지만 그건 *가용* 수이지
한 세션이 보는 수가 아니다.

시장 반복 등장: GitHub · Jira · Slack · Notion · Filesystem · Sentry · Postgres · Playwright.
상위 50 중 **42개가 엔지니어 대상**.

**최소 집합**: 문서 검색 + ①코드 ②이슈 ③대화 ④관측(로그·메트릭·에러) ⑤디자인.

### 10.4 ⭐ 색인할 것과 도구로 부를 것을 가르는 기준

| | **색인한다** | **도구로 부른다** |
|---|---|---|
| 변화 속도 | 느리다 | **빠르다** — 로그·메트릭·티켓 상태·디자인 파일 |
| 값의 성질 | 서술·근거·결정 | **현재값** |
| 부패 | 크롤 주기가 하한 | **부패가 없다** |
| 비용 | 적재 1회 | 질의마다 |

**부패 관리의 가장 싼 해법은 부패하지 않게 만드는 것이다.**

⚠ 대가: 도구는 실패하고, 느리고, 권한 모델이 다르며, **인용을 붙이기 어렵다**(그 시점의 값이라
재현이 안 된다). ⇒ 도구 결과에는 **가져온 시각을 같이 남기고 문서 인용과 다른 등급으로 표시**한다.

## 11. 한 장 요약

| 축 | 현행 관행의 결 |
|---|---|
| **구조** | 검색·커넥터는 사고, 에이전트·거버넌스는 만든다. 경계는 **변경 속도가 꺾이는 자리** |
| **실패 귀속** | 두 층이 아니라 **FP1~FP7 파이프라인 단계**. 그리고 **span 이 없으면 못 가른다** |
| **평가** | 오프라인(결정) + 온라인(감시)의 **고리**. 골든셋은 지어내지 말고 **채굴한다** |
| **채점** | 결정론 → 작은 함의 모델 → 큰 모델의 **cascade**. **77% 천장이라 게이트 금지** |
| **라벨** | 라벨도 썩는다. **버전 · 코드 리뷰 · 사람 재서명**, 자동 갱신 금지 |
| **부패** | 문서 부패는 **소유자·주기·SLA**, 인덱스 드리프트는 **회귀 검사**. 층마다 모집단이 다르다 |
| **천장** | 후처리는 **지울 수 있고 올릴 수 없다.** 높이는 *거버넌스 메타데이터를 1단에 쓸 수 있는가* 가 정한다 |
| **코퍼스** | 가르는 기준은 **"누가 볼 수 있나"** 하나. 나머지는 전부 열 |
| **문서 타입** | 마크다운으로 접되 **그림이 의미인 것만 page-as-image**. 자주 바뀌는 것은 색인하지 않는다 |
| **도구** | **10개를 넘기지 마라.** 트리거는 라우터가 아니라 도구 설명 |
