# Khala 생태계 정체성 + docs 사이트 — 설계 문서 (하위 프로젝트 A)

- 작성일: 2026-06-07
- 상태: 설계 승인 대기 → spec 리뷰
- 범위: 상위 비전("5개 도구를 하나의 생태계로 + docs 사이트 게시")을 분해한 **첫 조각 A**
- 형: 정적 docs 사이트 + 생태계 정체성(네이밍·내러티브). **기존 도구 코드 변경 없음.**

## 0. 맥락과 분해

상위 요청: Khala·Archon·Probe·specledger·mutqa 5개를 하나의 도구 생태계로 묶고, 목적·철학·사용법을 게시하는 전문적 온보딩 docs 사이트를 만든다. 사용자는 "실제 기술 통합"(Khala 버스 배선·통합 설치·모노레포·공통 규약 전부)을 원함 → **단일 스펙 불가, 분해 합의됨:**

| | 하위 프로젝트 | 비용·위험 | 순서 |
|---|---|---|---|
| **A** | **생태계 정체성 + docs 사이트** (본 문서) | 낮음 / 낮음 | **1 (지금)** |
| B | 모노레포 + 공통 규약 (네이밍·버전·로고·config, 코드 개명 Khala→Nexus 포함) | 중상 / 중 | 2 |
| C | 통합 설치/분배 (Docker compose + 스크립트) | 중 / 중 | 3 |
| D | Khala 버스 배선 (런타임 통합, 일부 설계됨) | 상 / 상 | 4 |

B/C/D는 각자 spec→plan→구현 사이클을 별도로 받는다. 본 문서는 **A만** 다룬다.

**YAGNI 플래그(C·D에서 검증할 것, A에서 답이 나옴):** Nexus(인프라 서비스)·mutqa(개발시점 스킬)·specledger(의사결정 게이트)는 청중·실행맥락이 다르다. "5개를 한 번에 설치하는 단일 사용자"가 실재하지 않으면 생태계는 **배포 단위가 아니라 내러티브 단위**이고, 그 경우 C·D는 축소/연기 대상이다.

## 1. 목표와 비목표

### 목표
- 5개 도구를 하나의 **Khala 생태계**로 framing하는 단일 통합 docs 사이트.
- 1차 청중 = **도구를 쓰는 개발자**(사용법 중심). 2차 = 미래 협업자/팀 + OSS 커뮤니티.
- 게시 대상 3종: **목적 · 철학 · 사용법**. 체계적·전문적 온보딩.
- 이중언어 KR+EN.

### 비목표 (A의 범위 컷)
- 도구 코드/아키텍처 변경(B·C·D 영역).
- 블로그, 버전드 docs, 검색 애널리틱스, 풀 API 레퍼런스 중복, 커스텀 테마 심화.
- 깊은 기여 가이드(협업자는 2차 청중 → 경량 placeholder 1p).

## 2. 정체성 결정 (확정)

- **Khala** = 생태계/철학의 이름. 모든 프로토스의 정신을 잇는 "링크/공유의식" → 도구들을 묶는 우산.
- **Nexus** = 지식 베이스 본체 컴포넌트(구 "Khala" 컴포넌트). 프로토스 본진·중앙 허브, "모든 게 이걸 통해 연결"되는 구조. 영어 nexus=연결점이라 이중 의미.
- **Archon**(집정관) · **Probe**(정찰병) · **specledger** · **mutqa** = 그대로.

**개명 처리(A 범위):** docs는 진실원천으로 **Nexus**를 쓴다. 단 **코드/repo 개명은 B에서** 수행. A에서는:
- Nexus 페이지 상단 콜아웃: "구 Khala 컴포넌트, repo 개명은 B에서 진행 중."
- 설치 지시는 현재 실재 경로(`khala` repo/패키지)를 쓰되 주석으로 명시.
이로써 docs의 개념적 진실(Nexus)과 코드 현실(khala) 불일치를 명시적으로 관리한다.

## 3. 기술 아키텍처

- **플랫폼: Astro Starlight** (정적, MD/MDX). 선정 이유: 이중언어 i18n 1급·무료·폴리시·풀 컨트롤·기존 README 이식 용이·Probe가 이미 TS/Node라 툴체인 친숙.
  - 대안 검토: Docusaurus(무거움), Mintlify(SaaS·i18n/컨트롤 제약) → 탈락.
- **검색**: Starlight 내장 Pagefind(오프라인·다국어).
- **i18n**: 기본 로케일 **EN(루트)**, 보조 **/ko**. (국제/OSS/포트폴리오 도달력 우선.)
- **호스팅**: Cloudflare Pages(또는 GitHub Pages). push 시 CI 자동 빌드·배포. 도메인은 후속 선택.
- **repo**: 새 우산 repo `khala-docs` (`[projects] khala-ecosystem/khala-docs/`). 이름은 B에서 모노레포 흡수 시 조정 가능(이 폴더가 임시 home). 본 spec이 그 repo의 첫 산출물.

## 5. 콘텐츠 모델

각 **도구 페이지**는 동일 템플릿(Diátaxis 경량) — 일관성이 "체계적 온보딩"의 핵심:

1. **개요** — 무엇/왜(해결하는 문제, 한 줄 정체성, 캘리브레이션 대상).
2. **핵심 개념** — 그 도구를 이해하는 데 필요한 도메인 어휘.
3. **Quickstart** — 설치 + 첫 성공 국면. (깊이 = **중간**)
4. **How-to 2~3개** — 대표 작업(도구별 핵심 사용 시나리오).
5. **레퍼런스** — 각 도구 repo README/docs로 링크.

**진실원천 규칙:** 깊은 레퍼런스의 진실원천 = 각 도구 repo. 사이트는 큐레이션·링크(중복=드리프트 회피). Quickstart/How-to만 사이트가 정규 보유하며 **"마지막 검증일"** 표기.

**도구별 콘텐츠 소스(이식 재료):**
- Nexus: `khala/README.md`, `khala/docs/`
- Archon: khala repo 브랜치 `spec/domain-invariant-governance`, `khala/docs/superpowers/{specs,plans}/2026-06-06-*`
- Probe: `probe/README.md`, `probe/docs/`
- specledger: `[claude] mcp-tools/specledger/README.md`, BACKLOG.md, spec/plan
- mutqa: `[claude] skills/mutqa/SKILL.md`, dogfood docs

## 6. 철학 내러티브 (사이트의 척추)

`/philosophy`가 핵심 페이지. 구성:

- **Khala(링크)** 가 AI시대 *오(誤)캘리브레이션*에 맞서 도구들을 하나로 묶는다.
- 실패 모드 ① **기계가 거짓말한다**(낡거나 틀린 걸 확신처럼) → **Archon**(+Nexus 그라운딩)이 방어.
- 실패 모드 ② **사람이 판단을 포기한다**(AI 산출물 거수기 승인) → **specledger**가 방어.
- 사각지대 **AI 생성 테스트가 그럴듯하나 행위검증이 0** → **mutqa**가 결정론적으로 강제.
- 통합 명제 **캘리브레이션**: 정답을 보장하는 게 아니라 *soft/낡은 답을 단정하지 않는다*. 어드바이저리(LLM 권고)가 포화된 곳에 **결정론적 그라운딩/강제**를 둔다.
- **캘리브레이션 맵 표**(roadmap 기반): 도구 / 정체 / 캘리브레이션 대상 / 청중 / Khala 관계 / 타이밍.
- 핵심 관계: 세 생산 도구는 서로 직접 호출하지 않고 **오직 Khala를 통해** 연결. Probe = Khala 창구의 소비자. Archon = 사람·에이전트가 도메인 진실을 물어보러 오는 단일 권위 창구.

## 7. 온보딩 흐름 (1차 청중=개발자)

`/start`가 **의도별 라우팅**(역할/목표 → 도구):

| "나는 ~하고 싶다" | → 도구 |
|---|---|
| 내 코드/도메인에 근거한 답이 필요 | Nexus / Archon |
| 내 PR·트러블슈팅을 조직 컨텍스트에 그라운딩 | Probe |
| 스펙을 거수기로 승인하는 걸 멈추고 싶다 | specledger |
| AI가 생성한 테스트가 진짜 행위를 검증하게 | mutqa |

- 각 라우트 → 해당 도구 Quickstart로 딥링크.
- 별도 "**5분 투어**" 경로: 랜딩 → 철학 → 생태계(개념만 빠르게).
- 전제조건 섹션: 공통(git, 적절한 런타임) + 도구별(Nexus=Docker/Postgres, Probe=Node≥20, mutqa=Python/cosmic-ray 등).

## 8. i18n 구조

- Starlight i18n: 기본 EN + `ko` 로케일. 페이지 미러링, 네비 라벨 번역, Pagefind 다국어 검색.
- **초기 이중언어 범위 = 랜딩 · 철학 · 도구별 개요**(가장 높은 가치). 깊은 How-to/Quickstart는 한쪽 선행·다른쪽 지연 허용(유지비 통제, YAGNI).
- 번역 지연 페이지는 Starlight fallback(미번역 시 기본 로케일 표시) 활용.

## 9. 엣지/에러 처리 (docs 특화)

- **개명 불일치(Nexus vs `khala` repo):** Nexus 페이지 콜아웃 + 설치 지시 주석. (§2)
- **콘텐츠 드리프트:** 레퍼런스는 repo 링크가 진실원천, Quickstart/How-to는 최소 유지 + "마지막 검증일" 표기.
- **배포 실패:** CI 빌드 실패 시 배포 차단(깨진 사이트 게시 방지).
- **깨진 링크:** 빌드 파이프라인에 링크체커 포함(내부·외부).

## 10. 검증 / 테스트

A는 코드 로직이 아닌 docs 사이트이므로 검증은 다음으로 구성:

1. **빌드 통과** — `astro build` 무에러.
2. **양 로케일 렌더** — EN/ko 둘 다 핵심 페이지 렌더 확인.
3. **링크체커** — 내부·외부 깨진 링크 0.
4. **Quickstart 실행 검증** — 각 도구 Quickstart를 최소 1회 실제 실행해 동작 확인(드리프트 방지), "마지막 검증일" 기록.
5. (선택) a11y/Lighthouse 기본 점검.

## 11. 구현 단위 (B/C/D로의 핸드오프 경계)

A 완료 = 빌드·배포되는 이중언어 통합 docs 사이트로, 5도구의 목적·철학·사용법이 일관 템플릿으로 게시되고 의도별 온보딩이 동작. **이후:**
- B: 코드 개명(Khala→Nexus) 반영 → docs 콜아웃 제거, 설치 경로 갱신.
- C/D: 통합 설치·버스 배선 실재화 시 `/ecosystem`·`/start` 갱신, 통합 Quickstart 추가.
- A에서 검증된 "내러티브 단위 vs 배포 단위" 신호로 C·D 범위 재조정.
