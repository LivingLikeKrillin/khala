## Preconditions

- `pip install -e ken -e ken-web/api` and `cd ken-web/web && npm install` (see
  `ken-web/README.md`).
- A server-side key:

  ```bash
  export ANTHROPIC_API_KEY=sk-ant-...
  echo "$ANTHROPIC_API_KEY"   # must be non-empty before proceeding
  ```

  > **Secret hygiene (how the 2026-06-24 run did it):** rather than pasting the key into a
  > prompt or a shell command (where it lands in transcripts/history), drop it into a
  > gitignored file (`.e2e-data/anthropic_key.txt`, ignored via `.e2e-data/` in root
  > `.gitignore`) and inject it only into the server process at launch:
  > `export ANTHROPIC_API_KEY="$(tr -d ' \t\r\n' < .e2e-data/anthropic_key.txt)"`. The value
  > is never echoed; only its presence/prefix is asserted.

## Steps

Run from the monorepo root. Use an isolated data dir so the walkthrough does not
touch any real stores.

```bash
export KEN_DATA_DIR="$(pwd)/.e2e-data"
mkdir -p "$KEN_DATA_DIR"
```

> **⚠ Windows / Git Bash gotcha (hit on 2026-06-24):** `$(pwd)` under Git Bash yields an
> MSYS path (`/c/Users/.../.e2e-data`). The server is native-Windows Python, whose
> `pathlib.Path("/c/Users/...")` re-roots that to `C:\c\Users\...` — so the "isolated" data
> dir silently lands in a **mangled sibling tree**, not `./.e2e-data`. Isolation *intent*
> still held (the real root `ken.manifest.yaml` was untouched, `git status` stayed clean),
> but the files were elsewhere. On Windows pass a **native** path instead, e.g.
> `export KEN_DATA_DIR="C:/Users/.../[projects] khala/.e2e-data"`. (POSIX hosts are unaffected.)

1. **Start the API** (terminal 1):

   ```bash
   uvicorn ken_web_api.app:app --reload     # http://localhost:8000
   ```

2. **Start the web dev server** (terminal 2):

   ```bash
   cd ken-web/web && npm run dev            # http://localhost:5173 (proxies /api)
   ```

3. **Register one khala artifact.** Pick a real doc, e.g. a spec:

   ```
   docs/superpowers/specs/2026-06-23-ken-v1-repayment-loop-design.md
   ```

   In the browser at http://localhost:5173, register it (or POST it):

   ```bash
   curl -s localhost:8000/api/artifacts \
     -H 'content-type: application/json' \
     -d '{"path":"docs/superpowers/specs/2026-06-23-ken-v1-repayment-loop-design.md"}'
   ```

4. **Start a review** from Home → the SPA loads grounded questions
   (`GET /api/artifacts/{id}/due`, which generates on first use).

5. **Answer one question well** → expect a **pass** ("Vouched"), auto-advance to the
   next question.

6. **Answer one question wrong** → expect a **fail** with a **RemediationPanel**
   showing artifact-grounded guidance; acknowledge to continue.

7. **Finish the session** → session summary (vouched / queued-for-next counts).

8. **Observe coverage move** on Home (`GET /api/coverage`).

## Live run results (2026-06-24)

Driven against the live API with `curl` (the React SPA is a thin client over these same
endpoints; vitest already covers the SPA on `FakeLLM`, so the browser pass was not separately
performed). Model: `claude-sonnet-4-6`. Isolated store under `KEN_DATA_DIR`.

**3. Register** — `POST /api/artifacts` → `201`:

```json
{"artifact_id":"16ca6c1a693d",
 "path":"docs/superpowers/specs/2026-06-23-ken-v1-repayment-loop-design.md",
 "status":"orphan","weak_count":0}
```

**4. Generate due (real LLM)** — `GET /api/artifacts/16ca6c1a693d/due` → `200`, 5 grounded
questions. They are demonstrably grounded in the actual spec, e.g.:

- *"What computed formula does the spec define for a question's `id`, and what is the
  consequence of an artifact's content changing on that id?"*
- *"What specific condition involving zero attempts does the spec identify as 'easiest to get
  wrong' in the `is_vouched` truth table…?"*
- *"What is the architectural reason the agent-driven review loop requires no
  `ANTHROPIC_API_KEY`…?"*

**5. Pass path** — `POST /api/attempts` with a strong, grounded answer to the "no API key"
architecture question (`8d73df9564d4`) → `200`:

```json
{"passed":true,"score":0.82,"remediation":null}
```

**6. Fail path** — `POST /api/attempts` with a deliberately wrong answer to the zero-attempts
question (`3e59f1379524`, answering "zero attempts ⇒ auto-vouched/passes by default") → `200`:

```json
{"passed":false,"score":0.05,"remediation":"<grounded correction>"}
```

The remediation is **grounded in the artifact** — it states the spec says the *opposite*
("a question with zero attempts **blocks vouching** → the artifact is **not vouched**") and
cites Section 10 (`is_vouched` truth table), Section 3 (`vouch` unit), and Section 7 (Initial
state). Exactly the "withheld until all pass" case the spec flags as easiest to get wrong.

**8. Coverage moved** — `GET /api/coverage`:

| | total | covered | ratio | orphans | weakness |
|---|---|---|---|---|---|
| before | 0 | 0 | 0.0 | [] | [] |
| after | 1 | 0 | 0.0 | ["16ca6c1a693d"] | [{q:`3e59f1379524`, fail_count:2}] |

Artifact after: `status:"orphan"`, `weak_count:2`.

> **Reading the result:** coverage is **artifact-granular** under the v2 slice-C vouch model
> (`is_vouched` = *no due questions*). One passing answer among five does **not** make the
> artifact covered — the other four questions are still due/unanswered, so the artifact stays
> `orphan` and `covered` stays 0. This is correct, not a regression: the original step-8 note
> ("covered ratio should reflect the passing answers") predates the all-questions-fresh model.
> What *did* move is the **weakness map** — the failed question now surfaces with
> `fail_count:2` (it was failed twice: once for the walkthrough, once for the encoding check
> below), and the artifact's `weak_count` went 0 → 2.

**Data integrity / no 5xx.** Every happy-path call returned `200`/`201`; no `4xx`/`5xx`.
The HTTP response body and the on-disk attempts ledger both **strict-decode as UTF-8**; the
em-dashes/arrows in the remediation are real Unicode characters (`—` `→`), not corruption.
(An earlier `\udce2…` mojibake seen while inspecting was purely a Windows console cp949 /
`json.tool` display artifact — the console itself raised `cp949 codec can't encode '—'`,
proving the lossy layer was the terminal, not ken-web.) The ledger persists
`person/artifact_id/question_id/content_hash/passed/score/ts` only — remediation is computed
and returned per-request, not stored.
